## 7. Удаление ученика — необратимое действие

- **Приоритет:** Critical
- **Статус:** uncovered
- **Тег:** `@students`

### Шаги journey

1. Учитель открывает контекстное меню или кнопку «Удалить» в `StudentViewDialog`.
2. Открывается `StudentDeleteDialog` с предупреждением о необратимости.
3. Подтверждает → `DELETE /api/students/:id`.

### Задействованные модули

### Наблюдаемый результат

Ученик и все связанные данные удалены без следов в БД.

### Почему критичен

Единственный способ полностью очистить ошибочные данные. Каскадное удаление через `onDelete: Cascade` — если правило ошибочно отвалится (например, при миграции), удаление сломается тихо и оставит сиротские записи.

## 8. Удаление урока — разового vs всей серии recurring (deleteAllFuture=true)

- **Приоритет:** Critical
- **Статус:** uncovered
- **Тег:** `@lessons`

### Шаги journey

1. Учитель в `LessonViewDialog` нажимает «Удалить».
2. Открывается `LessonDeleteDialog`; если урок recurring — показан чекбокс «Удалить все запланированные повторы».
3. Случай A (разовый): `DELETE /api/lessons/:id` с `deleteAllFuture=false` → удаляется только текущий урок.
4. Случай B (серия): чекбокс включён → `deleteAllFuture=true` → бэкенд через `getRecurringLessonKey` находит ВСЕ будущие уроки той же серии, вызывает `cancelRemindersForLesson` для каждого, `prisma.lesson.deleteMany`, отправляет WS `broadcastStudentLessonDeleted`.
5. Прошедшие/оплаченные уроки серии не затронуты.

### Задействованные модули

- Frontend: `shared/ui/LessonDeleteDialog/LessonDeleteDialog.tsx`, `shared/ui/LessonDeleteDialog/lesson-delete-dialog.model.ts`, `features/lessons/models/lesson-actions.model.ts`
- Backend: `controllers/lessons/deleteLesson.ts` (`DELETE /api/lessons/:id`), `services/recurringHelpers.ts` (`getRecurringLessonKey`)

### Наблюдаемый результат

Для разового — урок исчезает; для серии — пропадают все будущие повторы, история сохранена.

### Почему критичен

Необратимое каскадное действие. Ошибка в группировке `getRecurringLessonKey` (например, при изменении ключа группировки) удалит чужие уроки или пропустит часть серии — потеря данных без обнаружения.

### Что покрыто сейчас

Покрытия нет. Создание recurring-серии покрыто `recurring-lessons.spec.ts`, но удаление — нет.

## 9. Каскадный сдвиг серии recurring при изменении времени (preview + apply)

- **Приоритет:** Critical
- **Статус:** uncovered
- **Тег:** `@lessons`

### Шаги journey

1. Учитель открывает `LessonForm` для recurring-урока (статус SCHEDULED), меняет время начала/окончания, нажимает «Сохранить».
2. `shouldConfirmTimeChange` возвращает `true` (recurring + SCHEDULED + время изменилось) → показывается `ConfirmDialog` с предупреждением о каскадном сдвиге.
3. Учитель подтверждает → `PUT /api/lessons/:id`.
4. Бэкенд внутри Serializable-транзакции: `previewShiftFutureRecurringLessons` вычисляет deltaStart/deltaEnd, проверяет конфликты — при наличии возвращает 409 `RecurringShiftConflictError`.
5. При успехе: `applyShiftFutureRecurringLessons` обновляет все уроки серии, пересчитывает reminders, отправляет WS-уведомления.
6. Frontend получает обновлённый `$lessons`, все карточки серии показывают новое время.

### Задействованные модули

- Frontend: `features/lessons/ui/LessonForm/LessonForm.tsx`, `features/lessons/models/lesson-form.model.ts`, `features/lessons/models/lesson-form.helpers.ts` (`shouldConfirmTimeChange`)
- Backend: `controllers/lessons/updateLesson.ts`, `services/recurringHelpers.ts` (`previewShiftFutureRecurringLessons`, `applyShiftFutureRecurringLessons`)

### Наблюдаемый результат

Все запланированные уроки серии смещаются на одинаковую дельту; при конфликте — 409, ни один урок не изменяется (атомарность).

### Почему критичен

Самая сложная транзакционная логика в системе. Частичный сдвиг (часть уроков обновлена, часть нет) необнаружимо ломает расписание и приводит к потере денег за «невидимые» уроки.

### Что покрыто сейчас

Покрытия нет. `reschedule-lesson.spec.ts` покрывает только `RESCHEDULED`-статус для одного урока с отключённым каскадом.

## 11. Ручное создание бэкапа БД

- **Тег:** `@admin`

### Шаги journey

### Шаги journey

1. Ученик открывает `/student-invite/:token` с истёкшим / USED / REVOKED токеном.
2. Фронт: `GET /api/student-invitations/validate/:token` → `{ valid: false }`.
3. `StudentInviteGate.open` проставляет `$validationState = { valid: false }`.
4. На экране — сообщение «Ссылка недействительна — она могла быть уже использована или отозвана. Обратитесь к преподавателю за новой».
5. Кнопка «Зарегистрироваться» не отображается; регистрационный эндпоинт не вызывается.

### Задействованные модули

- Frontend: `pages/studentInvite/StudentInvitePage.tsx`, `features/studentAuth/models/student-invite.model.ts` (`validateInvitationTokenFx`, `$validationState`)
- Backend: `services/studentInvitation/studentInvitation.ts` (`validateRawToken`), `controllers/studentInvitations.ts` (`GET /api/student-invitations/validate/:token`)

### Наблюдаемый результат

Error-state без формы; 410 не возвращается, потому что регистрация даже не пытается стартовать.

### Почему важен

Если error-state сломается и покажет форму с невалидным токеном, ученик попытается зарегистрироваться и получит 410 без внятного UX-объяснения. Draft есть.

## Замечания по архитектуре тестов

1. **Draft-файлы.** 8 файлов с суффиксом `.draft.spec.ts` существуют как наброски (преимущественно по фиче 029-student-cabinet) и **не запускаются в CI**. Их перевод в `*.spec.ts` — самая быстрая первоочередная задача: уже есть steps и assertions, нужно дописать fixtures (особенно для двух-контекстного сценария учитель+студент в #5).

2. **Эндпоинты без UI.** Reports-эксплорер обнаружил, что `lastMonthEarnings` и `by-student` API возвращают данные, которые UI не рендерит. Это потенциальный dead-code или скрытый баг — но e2e тут не применим. Стоит вынести в bug-hunt отдельно.

3. **WebSocket двойные контексты.** Journeys #5 (realtime student) и потенциально #15 (push) требуют двух браузерных контекстов одновременно — это уже есть в `websocket-status-update.spec.ts`, можно переиспользовать паттерн.

4. **Cron mocking.** Journey #14, #15, #11 требуют ручного триггера cron-задач или time-mocking. Существующие `create-lesson-and-auto-status.spec.ts` и `websocket-status-update.spec.ts` уже решают эту задачу — переиспользовать.
