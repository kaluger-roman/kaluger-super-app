# Bug Hunt Report — 2026-05-09 (третья итерация)

**Всего багов:** 10 (Critical: 1, High: 7, Medium: 2, Low: 0)
**Покрытые области:** Backend services / Real-time, Backend Auth/Security, Frontend Effector, Frontend WebSocket, Backend Data integrity, Backend Auth Information Leak

## Резюме

Главный риск этой итерации — **необработанный `RangeError` в формировании текста push-уведомлений**: один пользователь, отправивший невалидный заголовок `x-timezone`, навсегда теряет своё напоминание (статус уже `SENT`) и одновременно ломает обработку всех последующих ремайндеров текущего батча. Семь High-багов задействуют финансовую и реляционную целостность (`delete dataToUpdate.paymentDate` Prisma не интерпретирует как `null`; `shiftFutureRecurringLessons` после commit транзакции; `archiveStudent` теряет CANCELLED-уроки и не отменяет напоминания), а также фронтовые сценарии с WS-реконнектом после логаута и автозакрытием view-диалога при тапе на «Оплачено» внутри него.

## 1. `x-timezone` без валидации → необработанный `RangeError` теряет батч напоминаний

- **Severity:** Critical
- **Файлы:**
  - `backend/src/middleware/auth.ts:32-39`
  - `backend/src/services/reminderProcessor.ts:99-117`
  - `backend/src/services/pushNotification.ts:99-109`
- **Категория:** Backend Auth/Security / Real-time / Data loss

### Описание

В `authenticateToken` любой авторизованный пользователь может отправить заголовок `x-timezone` с произвольной строкой — middleware безусловно сохраняет её в `users.timezone` без валидации. Позже cron `processScheduledReminders` каждую минуту делает атомарный «claim» — в одной транзакции помечает все PENDING-напоминания как `SENT` (строки 13–45), затем ВНЕ транзакции и ВНЕ try/catch вокруг отправки (try/catch начинается на строке 119, охватывает только `sendPushToUser`) формирует payload через `formatReminderBody(..., user?.timezone)` (строка 102). `formatReminderBody` вызывает `Date.toLocaleTimeString("ru-RU", { timeZone: timezone })`, который при невалидном таймзоне бросает `RangeError: Invalid time zone specified`.

Исключение пробрасывается из `for`-цикла наверх в `processScheduledReminders` (которая не имеет внешнего try/catch) → пойман только cron-обёрткой в `index.ts:120`, текущий тик прерывается. Все остальные ремайндеры из этого батча (до 100 шт.) остаются с `status: "SENT"` в БД, но **никогда не отправлены** — и не будут перепосланы (фильтр в claim-транзакции — `status: "PENDING"`).

### Воспроизведение

1. Авторизованный пользователь делает `GET /api/lessons` (или любой авторизованный эндпойнт) с заголовком `x-timezone: INVALID/TZ`.
2. Middleware безусловно пишет `INVALID/TZ` в `users.timezone`.
3. У пользователя есть несколько `scheduledReminders` (ему скоро уроки).
4. На следующем тике `processScheduledReminders` (каждую минуту) транзакция помечает 100 пендингов (включая его) как SENT.
5. Цикл по ремайндерам встречает запись с его `userId`, читает `user.timezone = "INVALID/TZ"`, формирует payload → `RangeError` → крах текущего тика.
6. Оставшиеся ремайндеры в батче навсегда лежат с `status: "SENT"`, физически не доставленные.

### Последствия

1. **Потеря данных**: уроки нескольких пользователей не получают push-напоминаний, бесшумно — фронтенд показывает "включены", БД говорит SENT, фактически нет доставки.
2. **DoS сервиса напоминаний**: пока запись `INVALID/TZ` в БД, каждый минутный тик может крашиться повторно (если этот пользователь имеет ремайндеры на каждой минуте).
3. **Эскалация**: атакующий может намеренно поставить себе плохой таймзон и стабильно ломать чужие ремайндеры (если повезёт попасть в один батч).

### Предлагаемое исправление

Валидировать timezone в middleware и обернуть формирование payload:

```ts
// backend/src/middleware/auth.ts
const isValidTimezone = (tz: string): boolean => {
  try {
    new Intl.DateTimeFormat(undefined, { timeZone: tz });
    return true;
  } catch {
    return false;
  }
};

const timezone = req.headers["x-timezone"] as string | undefined;
if (timezone && payload.userId && isValidTimezone(timezone)) {
  prisma.user
    .update({ where: { id: payload.userId }, data: { timezone } })
    .catch(() => {});
}
```

И страховка в `reminderProcessor.ts`:

```ts
// before
body: formatReminderBody(
  lesson.subject, lesson.lessonType, lesson.student.name,
  lesson.startTime, lesson.endTime, user?.timezone
),

// after
body: (() => {
  try {
    return formatReminderBody(..., user?.timezone);
  } catch {
    return formatReminderBody(..., undefined);
  }
})(),
```

Дополнительно — внешний try/catch в `for`-цикле, чтобы один сломавшийся ремайндер не валил весь батч; на ошибке откатывать его статус в FAILED, а не оставлять SENT.

### Почему это не false positive

Прочитаны:
- `middleware/auth.ts:32-39` — нет валидации, безусловный update.
- `reminderProcessor.ts:99-117` — `formatReminderBody` вызывается **до** try-блока строки 119.
- `reminderProcessor.ts:13-45` — claim-транзакция уже пометила пакет как SENT.
- `pushNotification.ts:99-103` — `Date.toLocaleTimeString("ru-RU", { timeZone: timezone })` поднимает `RangeError` при невалидном TZ (стандартное поведение V8/ICU).

В тестах `reminderProcessor.test.ts` сценарий с невалидным timezone не моделируется. Регрессии нет.

## 2. `delete dataToUpdate.paymentDate` не очищает поле в БД (Prisma `undefined` = "не менять")

- **Severity:** High
- **Файл:** `backend/src/controllers/lessons/updateLesson.ts:147-148`
- **Категория:** Data integrity / Финансы

### Описание

При отмене ранее оплаченного урока с включённым переносом оплаты на следующий неоплаченный:

```ts
nextLessonForTransfer = await findNextUnpaidLesson(userId!, existingLesson);
dataToUpdate.isPaid = false;
delete dataToUpdate.paymentDate;
```

Дальше `dataToUpdate` уходит в `prisma.lesson.update({ where: { id }, data: dataToUpdate })`. **Prisma трактует `undefined` (или отсутствующее поле) как «не изменять»** ([prisma docs: null and undefined](https://www.prisma.io/docs/orm/prisma-client/special-fields-and-types/null-and-undefined)). Значит после операции в БД остаётся `isPaid: false`, но `paymentDate` сохраняется как старая дата оплаты.

Запись внутренне противоречива: «не оплачен», но «оплачен такого-то числа».

### Воспроизведение

1. Урок A: `isPaid: true`, `paymentDate: "2026-04-15"`.
2. Существует следующий неоплаченный урок B того же ученика.
3. `PUT /api/lessons/A` с `{ status: "CANCELLED" }`.
4. После запроса: A — `isPaid: false`, `paymentDate: "2026-04-15"` (не null, не undefined). B — `isPaid: true`, `paymentDate: "2026-04-15"`.
5. Один платёж теперь привязан к двум урокам по `paymentDate`.

### Последствия

- В отчёт `getStatistics.paymentsInRange` (фильтр по `paymentDate` И `isPaid: true`) урок A не попадёт корректно.
- Однако любая будущая логика, опирающаяся на `paymentDate IS NOT NULL` как индикатор оплаты, будет считать A оплаченным.
- При экспорте/восстановлении/аналитике данные расходятся между разными представлениями.

### Предлагаемое исправление

```ts
// before
dataToUpdate.isPaid = false;
delete dataToUpdate.paymentDate;

// after
dataToUpdate.isPaid = false;
dataToUpdate.paymentDate = null;
```

Добавить регрессионный тест: после отмены проверить, что `paidAfter.paymentDate === null`.

### Почему это не false positive

`delete` оператор удаляет ключ из объекта — Prisma получает `data` без `paymentDate`. По официальной документации Prisma это означает «оставить поле как есть». Тест `updateLesson.test.ts` (строки ~464-516) проверяет `isPaid: false` и `nextAfter.paymentDate`, но не проверяет `paymentDate === null` у отменённого урока — баг тестом не покрыт.

## 3. `updateLesson`: транзакция фиксируется до проверки `shiftFutureRecurringLessons`

- **Severity:** High
- **Файл:** `backend/src/controllers/lessons/updateLesson.ts:151-194`
- **Категория:** Backend services / Data integrity

### Описание

```ts
const lesson = await prisma.$transaction(async (tx) => {
  if (nextLessonForTransfer && existingLesson.paymentDate) {
    await tx.lesson.update({ where: { id: nextLessonForTransfer.id }, data: { ... } });
  }
  return tx.lesson.update({ where: { id }, data: dataToUpdate, include: ... });
});

// ↓ ПОСЛЕ commit транзакции:
if (existingLesson.isRecurring && (updateData.startTime || updateData.endTime) && ...) {
  result = await shiftFutureRecurringLessons(existingLesson, newStart, newEnd);
  if (result.conflicts && result.conflicts.length > 0) {
    throw new Error("Перенесенная серия конфликтует с другими уроками");
  }
}
```

`shiftFutureRecurringLessons` запускается **уже после** того, как основной урок зафиксирован в БД. Если функция возвращает конфликты — выбрасывается `Error`, попадает в `catch (error)` строка 235-238 → клиент получает HTTP 500. Но изменения времени основного урока уже сохранены и видимы.

### Воспроизведение

1. Регулярный урок A в серии каждый понедельник в 12:00.
2. На вторник 13:00 уже есть несвязанный одноразовый урок B.
3. `PUT /api/lessons/A` с `{ startTime: "...вторник 13:00..." }`.
4. Транзакция переставляет A на вторник 13:00 (commit).
5. `shiftFutureRecurringLessons` пытается перенести следующие в серии — обнаруживает конфликт с B.
6. `throw new Error(...)` → 500 в ответе клиенту.
7. Клиент видит «ошибка», обновляет страницу — расписание сдвинулось у первого урока, но не у серии. Состояние неконсистентно.

### Последствия

- Частичный сдвиг серии: первый урок перенесён, остальные на старом времени.
- Клиент получает 500 без понимания причины и думает, что обновление откатилось.
- Невозможно пере-выполнить запрос — он либо вызовет ту же ошибку, либо просто вернёт «нет изменений».

### Предлагаемое исправление

Pre-check конфликтов **до** транзакции, чтобы при их наличии вернуть 409 без изменений в БД:

```ts
// before
const lesson = await prisma.$transaction(async (tx) => { ... });
if (existingLesson.isRecurring && ...) {
  result = await shiftFutureRecurringLessons(existingLesson, newStart, newEnd);
  if (result.conflicts?.length) throw new Error("...");
}

// after
let plannedShift: ShiftResult | undefined;
if (existingLesson.isRecurring && (updateData.startTime || updateData.endTime) && ...) {
  plannedShift = await previewShiftFutureRecurringLessons(existingLesson, newStart, newEnd);
  if (plannedShift.conflicts?.length) {
    return res.status(409).json({ error: "Перенесенная серия конфликтует с другими уроками" });
  }
}
const lesson = await prisma.$transaction(async (tx) => {
  if (plannedShift) await applyShiftFutureRecurringLessons(tx, existingLesson, newStart, newEnd);
  if (nextLessonForTransfer && existingLesson.paymentDate) { ... }
  return tx.lesson.update({ where: { id }, data: dataToUpdate, include: ... });
});
```

Долгосрочно — выполнять и сдвиг серии, и обновление главного урока в одной транзакции.

### Почему это не false positive

Прочитан `updateLesson.ts:151-194`: `prisma.$transaction` явно завершается на строке 163, `shiftFutureRecurringLessons` вызывается строкой 176 — вне транзакции. Тест `updateLesson.test.ts:168-205` проверяет HTTP 500 при конфликтах сдвига, но не проверяет состояние БД у основного урока — частичная фиксация не покрыта тестом.

## 4. WebSocket reconnect: ignores logout-state и допускает параллельные таймауты

- **Severity:** High
- **Файл:** `frontend/src/app/model/web-socket.model.ts:131-141`
- **Категория:** Frontend Effector / Real-time

### Описание

Два связанных дефекта в reconnect-логике:

**A — reconnect после logout.** `reconnectTimeoutFx.doneData` безусловно триггерит `connectWebSocket` (строки 138-141). Если за время 5-секундной задержки пользователь разлогинился (`disconnectWebSocket()` поставил `$isWebSocketEnabled = false`), всё равно создастся новое соединение. Хуже — `connectWebSocket` сначала ставит `$isWebSocketEnabled = true` (строки 89-93), фактически «переоткрывая» WebSocket-режим вопреки воле пользователя.

**B — нет защиты от множественных таймаутов.** В `sample` на строках 131-136 нет проверки `!reconnectTimeoutFx.pending`. Если `webSocketClosed` срабатывает несколько раз подряд (нестабильный канал, бэкенд флапает), каждый запуск стартует свой 5-секундный таймаут. Через 5 секунд все они выпустят `connectWebSocket` → создадут N параллельных WebSocket'ов. `$webSocketConnection` хранит только последний, но прежние остаются открытыми и будут продолжать триггерить `webSocketClosed` при их закрытии — самовоспроизводящийся цикл утечки.

### Воспроизведение (B)

1. Сетевая нестабильность: WS закрывается 3 раза за 1 секунду.
2. Каждое `webSocketClosed` стартует новый `reconnectTimeoutFx` (3 параллельных).
3. Через ~5 сек все три выпускают `connectWebSocket` → 3 новых соединения.
4. Сервер шлёт каждое уведомление каждому из них — пользователь видит дубликаты.

### Последствия

- A: соединение от лица разлогиненного пользователя (с истекающим/невалидным токеном) — лишняя нагрузка, лишние логи на сервере.
- B: дублирующиеся WebSocket-уведомления (3-кратные сообщения о статусе уроков, screen_updated и т.п.); утечка ресурсов; самораскрутка цикла.

### Предлагаемое исправление

```ts
// before
sample({
  clock: webSocketClosed,
  source: $isWebSocketEnabled,
  filter: (isEnabled) => isEnabled,
  target: reconnectTimeoutFx,
});

sample({
  clock: reconnectTimeoutFx.doneData,
  target: connectWebSocket,
});

// after
sample({
  clock: webSocketClosed,
  source: { isEnabled: $isWebSocketEnabled, pending: reconnectTimeoutFx.pending },
  filter: ({ isEnabled, pending }) => isEnabled && !pending,
  fn: () => undefined,
  target: reconnectTimeoutFx,
});

sample({
  clock: reconnectTimeoutFx.doneData,
  source: $isWebSocketEnabled,
  filter: (isEnabled) => isEnabled,
  fn: () => undefined,
  target: connectWebSocket,
});
```

### Почему это не false positive

- Тестов `web-socket.model.test.ts` нет (нашёл только `app-init.model.test.ts` рядом).
- Effector `createEffect` без `concurrency` ограничения — параллельные запуски подтверждаются документацией.
- `connectWebSocket` (строки 89-93) действительно ставит `$isWebSocketEnabled = true` без проверок.

## 5. `lessons-view-dialog`: любой `updateLessonFx.doneData` для текущего урока закрывает диалог

- **Severity:** High
- **Файл:** `frontend/src/features/lessons/models/lessons-view-dialog.model.ts:223-229`
- **Категория:** Frontend Effector / UX

### Описание

```ts
sample({
  clock: lessonModel.updateLessonFx.doneData,
  source: $viewingLesson,
  filter: (viewing, updated): viewing is Lesson =>
    Boolean(viewing && viewing.id === updated.id),
  fn: () => false,
  target: $isViewDialogOpen,
});
```

Это правило закрывает view-диалог при ЛЮБОМ успехе `updateLessonFx` для просматриваемого урока. Но внутри самого диалога есть тогглы `PaymentStatus` и `HomeworkSentStatus`, которые при подтверждении вызывают `lessonModel.updateLesson`. Каждое нажатие тоггла → `updateLessonFx.doneData` → диалог закрывается. Также при стороннем триггере (cron сменил статус, WebSocket обновил состояние) — диалог пользователя захлопывается без действия пользователя.

### Воспроизведение

1. Открыть view-диалог любого SCHEDULED-урока.
2. Нажать тоггл «Оплачено» → подтвердить.
3. Сразу после подтверждения диалог закрывается; пользователь не видит обновлённое состояние и не может, например, тут же отметить «Домашнее задание отправлено».

Дополнительный сценарий: пользователь открыл view-диалог, в это время сработал cron (`lessonStatusUpdater`), сменил статус, прислал WebSocket → фронт вызвал `updateLesson` для того же урока → диалог закрылся без действий пользователя.

### Последствия

UX-баг: пользователь воспринимает каждый тогл как «закрыл диалог сам собой». Особенно неприятно при последовательной разметке нескольких полей из view-диалога (оплата → ДЗ).

### Предлагаемое исправление

Удалить sample, закрывающий диалог. Закрытие из view-диалога уже обрабатывается явными событиями `cancelFromViewRequested`, `restoreFromViewRequested`, `editFromViewRequested`, `deleteFromViewRequested`, `rescheduleFromViewRequested` (строки 86-134). Для синхронизации содержимого диалога с обновлением остаётся sample на строках 215-221 (`target: $viewingLesson`) — этого достаточно.

```ts
// удалить блок 223-229:
sample({
  clock: lessonModel.updateLessonFx.doneData,
  source: $viewingLesson,
  filter: ...,
  fn: () => false,
  target: $isViewDialogOpen,
});
```

### Почему это не false positive

- Прочитан `lessons-view-dialog.model.ts` целиком: альтернативного пути закрытия диалога после `updateLessonFx.doneData` нет; sample на строках 215-221 уже обновляет содержимое диалога без закрытия.
- `LessonDetails.tsx` (включает `PaymentStatus` и `HomeworkSentStatus` с `needConfirm`), которые используют `lessonModel.updateLesson` через `lesson-actions.model.ts`, что обязательно триггерит `updateLessonFx.doneData`.
- Тестов на `lessons-view-dialog.model.ts` нет.

## 6. `subscribe`: `findUnique + create` race условие при первой подписке

- **Severity:** High
- **Файл:** `backend/src/controllers/push/subscribe.ts:38-70`
- **Категория:** Backend services / Race condition

### Описание

```ts
const existing = await prisma.pushSubscription.findUnique({
  where: { endpoint: data.subscription.endpoint },
});
// ...
if (existing) { /* update */ }
const subscription = await prisma.pushSubscription.create({ data: subscriptionData });
```

Между `findUnique` и `create` нет ни транзакции, ни блокировки. Поле `PushSubscription.endpoint` объявлено `@unique` (`schema.prisma:159`). Если две вкладки/устройства одновременно регистрируют подписку с одинаковым endpoint (Service Worker может повторно зарегистрироваться при reload, или браузер делает retry), оба запроса увидят `existing = null`, оба попытаются `create` — второй упадёт с `Prisma P2002 (Unique constraint failed)`, попадёт в `catch` строка 78-81 и вернёт 500 «Внутренняя ошибка сервера».

### Воспроизведение

1. Service Worker инициализируется, шлёт `POST /api/push/subscribe`.
2. Параллельно тот же SW шлёт второй такой же запрос (например, при гонке `pushManager.getSubscription()` и `subscribe()`, или при двойном запуске SW).
3. Оба `findUnique` возвращают `null`.
4. Оба идут в `create` — один успешен, второй ловит P2002 → 500.

### Последствия

- Пользователь при первом включении уведомлений может получить 500. На фронте вероятно отобразится «не удалось подписаться» — он отключит тогл, потеряв напоминания.
- Логи сервера засоряются стектрейсами `PrismaClientKnownRequestError`.

### Предлагаемое исправление

Заменить пару `findUnique + create` на `upsert`, добавить guard на чужой `userId` отдельным условием:

```ts
// before
const existing = await prisma.pushSubscription.findUnique({ where: { endpoint } });
if (existing) {
  if (existing.userId !== userId) return res.status(403).json({ error: "..." });
  const updated = await prisma.pushSubscription.update({ where: { endpoint }, data: subscriptionData });
  return res.status(200).json(updated);
}
const subscription = await prisma.pushSubscription.create({ data: subscriptionData });
return res.status(201).json(subscription);

// after
const existing = await prisma.pushSubscription.findUnique({ where: { endpoint } });
if (existing && existing.userId !== userId) {
  return res.status(403).json({ error: "Подписка принадлежит другому пользователю" });
}

const subscription = await prisma.pushSubscription.upsert({
  where: { endpoint: data.subscription.endpoint },
  update: subscriptionData,
  create: subscriptionData,
});
return res.status(existing ? 200 : 201).json({ ... });
```

### Почему это не false positive

- `schema.prisma:159` — `endpoint String @unique`, то есть P2002 гарантирован при гонке.
- Прочитан `subscribe.ts` целиком — паттерн именно `findUnique + create` без транзакции.
- Тесты не моделируют параллельные регистрации с одним endpoint.

## 7. `archiveStudent`: удаляет CANCELLED-уроки и оставляет «осиротевшие» PENDING-напоминания

- **Severity:** High
- **Файл:** `backend/src/controllers/students/archiveStudent.ts:19-25`
- **Категория:** Backend services / Data integrity / Real-time

### Описание

Два связанных дефекта в одной транзакции:

**A — `deleteMany` без `status`-фильтра.** `where: { studentId: id, startTime: { gte: new Date() } }` физически удаляет ВСЕ будущие уроки студента, включая `CANCELLED` (отменённые ранее). История отмен теряется. Сравните с `deleteLesson.ts`, где удаление одного урока намеренно бережнее.

**B — `cancelRemindersForLesson` не вызывается.** Поскольку `ScheduledReminder.lesson` имеет `onDelete: Cascade`, FK-каскад в БД удалит ремайндеры при удалении уроков — это покрывает «уже не запущенные». Но если cron `processScheduledReminders` ровно сейчас claim-нул их в свою транзакцию (`status: "PENDING" → "SENT"`), ремайндеры в его выборке уже выпали из выборки cascade-delete (они не PENDING). Cron продолжает обработку: пытается прочитать `lesson.status`, но lesson может уже быть удалён в этот момент. В лучшем случае — Prisma вернёт `null` и `lesson.status` вылезет с TypeError. В худшем — ремайндер успеет отправиться юзеру об уроке, который только что архивирован.

Также в `archiveStudent.ts` нет вызова `cancelRemindersForLesson` перед `deleteMany` — паттерн, явно используемый в `deleteLesson.ts`.

### Воспроизведение

A:
1. Создан урок A, отменён (`status: CANCELLED`), но запланирован в будущем.
2. Архивация студента → A удаляется без следа.

B:
1. У студента 3 ремайндера с `status: "PENDING"` на ближайший урок.
2. Cron `processScheduledReminders` в момент tick T0 захватывает их все, помечает SENT.
3. В тот же момент tutor нажал «архивировать студента» — `deleteMany` удаляет уроки → cascade пытается удалить ремайндеры → они уже `SENT`, не подпадают под FK-cascade условие? Нет, FK-cascade удаляет всё связанное независимо от status. Но cron в этот момент держит lesson в `include`, обрабатывает его как объект в JS-памяти, формирует payload → `sendPushToUser` → push доставлен. Запись в БД к этому моменту удалена.
4. Пользователь получает push об уроке только что архивированного студента.

### Последствия

A: безвозвратная потеря истории отменённых уроков; статистика и аудит за прошедшие периоды искажаются (хотя фильтр по `startTime: { gte: new Date() }` ограничивает только будущим — но это всё равно потеря).

B: пользователю приходят push-уведомления об «исчезнувшем» студенте; стрес на UI (попытка перейти на урок → 404).

### Предлагаемое исправление

```ts
// before
const result = await prisma.$transaction(async (tx) => {
  await tx.lesson.deleteMany({
    where: { studentId: id, startTime: { gte: new Date() } },
  });
  // ...
});

// after
const result = await prisma.$transaction(async (tx) => {
  // отменяем ремайндеры до удаления уроков
  const futureLessons = await tx.lesson.findMany({
    where: {
      studentId: id,
      startTime: { gte: new Date() },
      status: { notIn: ["COMPLETED", "CANCELLED"] },
    },
    select: { id: true },
  });
  for (const { id: lid } of futureLessons) {
    await tx.scheduledReminder.updateMany({
      where: { lessonId: lid, status: "PENDING" },
      data: { status: "CANCELLED" },
    });
  }
  await tx.lesson.deleteMany({
    where: {
      studentId: id,
      startTime: { gte: new Date() },
      status: { notIn: ["COMPLETED", "CANCELLED"] },  // не трогаем CANCELLED
    },
  });
  // ...
});
```

### Почему это не false positive

- `archiveStudent.ts:20-25` — действительно нет `status`-фильтра и нет `cancelRemindersForLesson`.
- Сравнение с `deleteLesson.ts` — там паттерн с `cancelRemindersForLesson` явно используется (см. инфраструктуру в `services/`).
- `schema.prisma:195` — `lesson Lesson @relation(... onDelete: Cascade)` для `scheduledReminders`.
- Тест `archiveStudent.test.ts` (если есть) не моделирует CANCELLED-ситуации.

## 8. `getBackupSettings`: race + `runBackupJob` без overlap-guard → двойной `pg_dump`

- **Severity:** High
- **Файлы:**
  - `backend/src/services/backup.ts:20-31` (race условие создания singleton)
  - `backend/src/services/backup.ts:183-219` (отсутствие overlap-guard)
- **Категория:** Backend services / Data integrity / Operations

### Описание

**A — `findFirst + create` без guard.** `getBackupSettings` делает `findFirst()`, и при `null` создаёт запись. Модель `BackupSettings` (`schema.prisma:206-216`) **не имеет уникальных полей кроме `@id`**. При двух параллельных запросах (admin-panel параллельно с cron-стартом, или две вкладки админки) оба видят `null`, оба создают запись — в БД оказываются 2 строки `BackupSettings`. `findFirst()` без `orderBy` возвращает произвольную, поэтому `updateBackupSettings` обновляет одну, а `runBackupJob` читает другую — настройки из UI не применяются к крону.

**B — `runBackupJob` без overlap-guard.** Cron каждый час (`index.ts:127-137`). Внутри `performBackup` использует `execAsync(... timeout: 300000)` (5 минут). Если `pg_dump` зависает или просто долгий (большая БД), процесс execAsync убивается через 5 минут, бросая `ETIMEDOUT` — в этом случае `lastBackupAt` НЕ обновляется (строки 209-212 не выполнены, исключение пробрасывается). Следующий cron-tick через час снова видит `lastBackupAt` старым, снова стартует `pg_dump`. Если БД действительно большая — каждый tick стартует pg_dump поверх предыдущего, ресурсы VPS уходят на конкурирующие dump'ы.

### Воспроизведение (B)

1. БД ≥ 1 ГБ, `pg_dump | gzip` занимает >5 мин.
2. В 00:00 cron стартует backup → `pg_dump` убивается по таймауту.
3. `lastBackupAt` не обновлено.
4. В 01:00 cron снова стартует — в БД ничего не изменилось — снова `pg_dump`.
5. Каждый час: новый таймаут-killed dump → нагрузка на VPS, незавершённые `.sql.gz`-файлы (хотя `performBackup` чистит их строкой 134-137).

### Последствия

A: настройки бэкапов меняются в UI, но бэкап-крон не учитывает их — бэкапы продолжают идти по старому интервалу (или, наоборот, выключение `enabled: false` через UI не доходит до крона).

B: продолжающаяся 100% CPU нагрузка от пер-часовых `pg_dump`, зависание VPS, незавершённые файлы. Если БД действительно большая — бэкапов нет вовсе при таймауте, проблема не диагностируется.

### Предлагаемое исправление

A — добавить `id String @id @default("singleton")` для singleton-таблицы и использовать `upsert`:

```prisma
// schema.prisma
model BackupSettings {
  id            String    @id @default("singleton")
  // ...
}
```

```ts
// services/backup.ts
export const getBackupSettings = async () =>
  prisma.backupSettings.upsert({
    where: { id: "singleton" },
    update: {},
    create: { id: "singleton", enabled: true, intervalHours: 6, maxStorageMb: 300 },
  });
```

B — добавить module-level lock:

```ts
let backupRunning = false;

export const runBackupJob = async (): Promise<void> => {
  if (backupRunning) {
    console.warn("runBackupJob: предыдущий бэкап ещё выполняется, пропускаем");
    return;
  }
  backupRunning = true;
  try { /* ... existing ... */ } finally { backupRunning = false; }
};
```

Кроме того — поднять timeout для большого pg_dump или сменить стратегию (стрим в S3) при росте БД.

### Почему это не false positive

- `schema.prisma:206-216` — `BackupSettings` не имеет ни одного `@unique` поля (кроме `@id`); ни `@@unique`.
- `backup.ts:20-31` — `findFirst + create` явно, без транзакции.
- `backup.ts:183-219` — `runBackupJob` без try/finally вокруг `lastBackupAt`-обновления; не обновляет `lastBackupAt` при исключении (см. строки 202-211).
- `index.ts:127-137` — `cron.schedule("0 * * * *", ...)` каждый час, без `overlap` опции (`node-cron` не поддерживает её нативно).
- Тестов на race и overlap нет.

## 9. `handleMessage`: `ws.send` без проверки `readyState` + параметр `data: any`

- **Severity:** Medium
- **Файл:** `backend/src/lib/websocket/messageHandler.ts:3,8`
- **Категория:** Real-time / Convention violation

### Описание

```ts
export const handleMessage = (ws: AuthenticatedWebSocket, data: any) => {
  console.log(`Received message from ${ws.userId}:`, data);
  ws.send(JSON.stringify({ type: "message_received", originalMessage: data }));
};
```

Два дефекта:
1. **`data: any`** напрямую запрещён конвенцией проекта (`docs/conventions/backend.md`: «no `any` — use `unknown`»).
2. **`ws.send` без `readyState`-проверки** — если клиент отправил сообщение и сразу закрыл соединение (race CLOSING/CLOSED), `ws.send` синхронно бросает `Error: WebSocket is not open`. Исключение проглатывает обработчик в `WebSocketManager.handleMessage`, но в логи попадает мисслидинговая запись «Error parsing WebSocket message» — это ломает диагностику в продакшне. Сравните с `sendWelcomeMessage` (там `readyState`-guard уже есть в `WebSocketManager.ts:75`) и `sendToUser` (тоже guard'ится).

### Воспроизведение

1. Клиент шлёт сообщение и сразу теряет связь (mobile network drop).
2. На сервере `ws.on("message")` срабатывает; `handleMessage` вызывает `ws.send` на закрытом сокете.
3. В логах: «Error parsing WebSocket message» (хотя парсинг прошёл успешно).

### Последствия

- Невозможно диагностировать реальную проблему по логам — сообщение «parsing» вводит в заблуждение.
- При расширении `handleMessage` (сейчас echo, но планируется handlers) — частично выполненный код, незавершённые side-эффекты.
- `any` нарушает конвенцию.

### Предлагаемое исправление

```ts
// before
export const handleMessage = (ws: AuthenticatedWebSocket, data: any) => {
  console.log(`Received message from ${ws.userId}:`, data);
  ws.send(JSON.stringify({ type: "message_received", originalMessage: data }));
};

// after
import { WebSocket } from "ws";

export const handleMessage = (ws: AuthenticatedWebSocket, data: unknown): void => {
  console.log(`Received message from ${ws.userId}:`, data);
  if (ws.readyState !== WebSocket.OPEN) return;
  ws.send(JSON.stringify({ type: "message_received", originalMessage: data }));
};
```

### Почему это не false positive

- `messageHandler.ts:3` — действительно `data: any`.
- `messageHandler.ts:8` — действительно нет `readyState` guard.
- В `WebSocketManager.ts:75` (sendWelcomeMessage) и `WebSocketManager.ts:121` (sendToUser) guard есть — паттерн в проекте есть, тут он пропущен.
- В тесте `messageHandler.test.ts` сценарий с `readyState !== OPEN` не моделируется.

## 10. Email enumeration через `/api/auth/resend-verification` и `/api/auth/verify-email`

- **Severity:** Medium
- **Файлы:**
  - `backend/src/controllers/emailVerification.ts:33-35`
  - `backend/src/controllers/emailVerification.ts:125-127`
- **Категория:** Auth / Information disclosure

### Описание

Оба эндпойнта возвращают **`404 "Пользователь не найден"`** для несуществующего email. Это даёт нулевую неоднозначность: ответ 404 → email не зарегистрирован, любой другой код (`400 "Email уже подтвержден"`, `400 "Срок действия кода истёк"`, `200`) → email есть в системе.

Оба роута публичны (нет `authenticateToken` middleware в `routes/auth.ts:22-23`). Rate-limit (`authRateLimiter`) присутствует, но энумерация не требует высокой скорости — медленный перебор пройдёт под лимитами.

### Воспроизведение

1. `POST /api/auth/resend-verification { "email": "victim@gmail.com" }` → если 404, email не в системе; если 400/200 — email есть.
2. Через серию запросов составляется список зарегистрированных email-ов.

### Последствия

- Список зарегистрированных пользователей для целевого фишинга или credential stuffing.
- Утечка факта пользования сервисом (privacy concern).

### Предлагаемое исправление

Возвращать одинаковый успех независимо от существования аккаунта (если уже подтверждён, тоже маскировать):

```ts
// resendVerification — before
if (!user) {
  return res.status(404).json({ error: "Пользователь не найден" });
}
if (user.isEmailVerified) {
  return res.status(400).json({ error: "Email уже подтвержден" });
}

// after
if (!user || user.isEmailVerified) {
  return res.json({ message: "Если email зарегистрирован и не подтверждён, код отправлен" });
}
```

В `verifyEmail` оставлять 404 при несовпадении email/code сложнее (нужна возможность диагностировать ошибку), но как минимум вернуть универсальный 400 «Неверный код подтверждения» вместо 404 «Пользователь не найден».

### Почему это не false positive

- `emailVerification.ts:34`, `emailVerification.ts:126` — действительно `res.status(404).json({ error: "Пользователь не найден" })`.
- `routes/auth.ts:22-23` — оба роута публичны без `authenticateToken`.
- Тестов на enumeration-resistant ответы нет.
