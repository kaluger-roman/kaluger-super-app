# Bug Hunt Report — 2026-05-24

**Всего багов:** 8 (Critical: 0, High: 3, Medium: 5, Low: 0)
**Покрытые области:** Frontend Effector, Backend Services, Backend Auth, Real-time WebSocket, Data Integrity / Cron, Push-уведомления

## Резюме

Главные риски этого прохода — несколько race condition-ов и проблем с атомарностью на бэкенде. Самый
критичный — read-modify-write счётчика попыток ввода кода в `changeEmail.ts`, открывающий путь к
обходу лимита параллельными запросами (и потенциальному brute-force 6-значного кода). На фронте —
повторяющийся системный диалог запроса push-разрешений при каждом resume PWA и лишний reload при
удалении урока. На бэкенде — несколько мест, где связанные операции (отмена напоминаний + удаление
уроков) выполняются вне транзакций, и асимметрия в инициализации tutor- vs student-WebSocket
handlers, где tutor-ветка не получила исправление, явно сделанное в student-ветке.

## 1. Race condition в счётчике попыток ввода кода смены email — обход лимита

- **Severity:** High
- **Файл:** `backend/src/services/changeEmail.ts:106-128`
- **Категория:** Backend Service / Security / Race condition

### Описание

В `verifyEmailChange` при неверном коде логика такая: читаем `user.verificationAttempts` из БД
(строка 83 в `findUnique`), прибавляем 1 в JavaScript (строка 107), затем пишем обратно через
`prisma.user.update` (строки 125–128). Два параллельных запроса с одинаковым неверным кодом прочитают
один и тот же снапшот (`attempts = 0`), оба посчитают `newAttempts = 1`, и оба запишут `1` — вместо
ожидаемого `2`. В итоге лимит `MAX_VERIFICATION_ATTEMPTS` достигается медленно или вовсе никогда при
достаточной степени параллелизма.

Для контраста — в `backend/src/services/studentEmailVerification/studentEmailVerification.ts:74-78`
точно та же логика решена правильно через атомарный инкремент на уровне БД, с явным комментарием
почему:

```ts
// Атомарный инкремент — иначе параллельные запросы с неверным кодом
// читают одинаковый снапшот и перезаписывают друг друга, обходя лимит.
const updated = await prisma.studentUser.update({
  where: { id: studentUser.id },
  data: { verificationAttempts: { increment: 1 } },
  select: { verificationAttempts: true },
});
```

То есть в кодовой базе уже есть знание о проблеме, и есть готовое корректное решение, но
`changeEmail.ts` его не применяет.

### Воспроизведение

1. Пользователь инициировал смену email — в БД `verificationCode` есть, `verificationAttempts = 0`.
2. Злоумышленник (с валидным JWT владельца аккаунта) отправляет 10 параллельных `POST
   /api/user/change-email/verify` с неверным кодом.
3. Все 10 запросов одновременно делают `findUnique` — все видят `attempts = 0`.
4. Все 10 запросов вычисляют `attempts = 0 + 1 = 1` и выполняют `update({ data: {
   verificationAttempts: 1 } })`.
5. После завершения всех запросов в БД `verificationAttempts = 1`, а не `10`.

### Последствия

Обход rate-limit на код подтверждения смены email на уровне приложения. Учитывая, что код —
6-значное число (~1 000 000 вариантов) и живёт ~15 минут, при достаточном параллелизме и отсутствии
внешнего слой rate-limiting на эндпоинте brute-force становится практически осуществимым. Это
приводит к компрометации аккаунта через смену email (далее — сброс пароля на новый email).

### Предлагаемое исправление

Заменить read-modify-write атомарным инкрементом, точно как в `studentEmailVerification.ts:74-78`:

```ts
// before — backend/src/services/changeEmail.ts:106-128
if (user.verificationCode !== code) {
  const attempts = user.verificationAttempts + 1;

  if (attempts >= MAX_VERIFICATION_ATTEMPTS) {
    await prisma.user.update({
      where: { id: userId },
      data: {
        verificationCode: null,
        verificationCodeExpiry: null,
        verificationCodeSentAt: null,
        verificationAttempts: 0,
      },
    });
    throw Object.assign(
      new Error("Превышено количество попыток. Запросите новый код"),
      { statusCode: 400 },
    );
  }

  await prisma.user.update({
    where: { id: userId },
    data: { verificationAttempts: attempts },
  });
  throw Object.assign(new Error("Неверный код верификации"), { statusCode: 400 });
}

// after
if (user.verificationCode !== code) {
  const updated = await prisma.user.update({
    where: { id: userId },
    data: { verificationAttempts: { increment: 1 } },
    select: { verificationAttempts: true },
  });

  if (updated.verificationAttempts >= MAX_VERIFICATION_ATTEMPTS) {
    await prisma.user.update({
      where: { id: userId },
      data: {
        verificationCode: null,
        verificationCodeExpiry: null,
        verificationCodeSentAt: null,
        verificationAttempts: 0,
      },
    });
    throw Object.assign(
      new Error("Превышено количество попыток. Запросите новый код"),
      { statusCode: 400 },
    );
  }

  throw Object.assign(new Error("Неверный код верификации"), { statusCode: 400 });
}
```

### Почему это не false positive

- В `studentEmailVerification.ts:72-78` тот же сценарий уже описан в комментарии и решён через
  атомарный инкремент.
- Тесты `backend/src/services/__tests__/changeEmail.test.ts` проверяют только последовательный
  сценарий и не покрывают параллельную гонку.
- В `backend/src/utils/auth.ts` нет промежуточной нормализации, дополнительной защиты на уровне
  middleware от параллельных одинаковых запросов нет.

## 2. Push: автоматическая повторная подписка срабатывает при каждом возобновлении PWA

- **Severity:** High
- **Файл:** `frontend/src/entities/notifications/notifications-toggle.model.ts:26-33`
- **Категория:** Frontend Effector / PWA UX

### Описание

Sample слушает `clock: [loadSettingsFx.doneData, loadVapidKeyFx.doneData,
checkPushSubscriptionFx.doneData]` и при `settings.enabled && !subscribed && vapidKey !== null && reg
!== null` вызывает `subscribePushFx`, которая внутри делает `Notification.requestPermission()`.

В `frontend/src/app/model/app-init.model.ts` событие `appResumed` (срабатывает при
`visibilitychange → visible`) вызывает `notificationsModel.loadSettings`, что приводит к
`loadSettingsFx.doneData` и повторному срабатыванию sample. Никакой дедупликации (вроде store
`$autoSubscribeAttempted`) нет.

В результате каждый раз, когда PWA выходит из фона и `settings.enabled === true && !subscribed`
(например, браузер сам отозвал push-подписку после обновления Service Worker), пользователь получит
системный диалог запроса разрешений — без какого-либо явного действия с его стороны.

### Воспроизведение

1. Пользователь включил push-уведомления — на сервере `settings.enabled = true`, в браузере есть
   активная push-подписка.
2. Браузер/OS сам сбросил push-подписку (типичный сценарий после очистки Service Worker или смены
   браузерных профилей). `$isPushSubscribed` после следующего `checkPushSubscriptionFx` — `false`.
3. Пользователь сворачивает PWA, разворачивает.
4. `visibilitychange → visible` → `appResumed` → `notificationsModel.loadSettings` →
   `loadSettingsFx.doneData` → sample срабатывает → `subscribePushFx` →
   `Notification.requestPermission()` → системный диалог разрешений всплывает прямо в момент
   возвращения пользователя в приложение.
5. Цикл повторяется при каждом следующем resume, пока пользователь не примет/отклонит диалог.

### Последствия

UX-регрессия: системный диалог `Notification.requestPermission()` появляется без явного действия
пользователя. Если пользователь явно отклоняет диалог, разрешение блокируется навсегда (`denied`) —
включить уведомления потом будет невозможно без ручного восстановления настроек в браузере.

### Предлагаемое исправление

Ввести явный флаг `$autoSubscribeAttempted` и добавить его в `filter` — авто-подписка должна
срабатывать максимум один раз за сессию:

```ts
// after — добавить
export const $autoSubscribeAttempted = createStore(false);

sample({
  clock: [loadSettingsFx.doneData, loadVapidKeyFx.doneData, checkPushSubscriptionFx.doneData],
  source: {
    settings: $reminderSettings,
    subscribed: $isPushSubscribed,
    vapidKey: $vapidKey,
    reg: $serviceWorkerRegistration,
    attempted: $autoSubscribeAttempted,
  },
  filter: ({ settings, subscribed, vapidKey, reg, attempted }) =>
    !attempted && settings.enabled && !subscribed && vapidKey !== null && reg !== null,
  fn: ({ vapidKey, reg }) => ({ vapidKey: vapidKey!, registration: reg! }),
  target: subscribePushFx,
});

// помечаем флаг и при success, и при fail — чтобы цикл точно прервался
sample({
  clock: [subscribePushFx.done, subscribePushFx.fail],
  fn: () => true,
  target: $autoSubscribeAttempted,
});

// и при выходе из аккаунта сбрасываем
sample({
  clock: userModel.logoutUser,
  fn: () => false,
  target: $autoSubscribeAttempted,
});
```

### Почему это не false positive

- В `frontend/src/app/model/app-init.model.ts:145-150` `appResumed` действительно вызывает
  `notificationsModel.loadSettings` — `loadSettingsFx.doneData` будет эмититься на каждый возврат
  PWA в видимое состояние.
- Тесты `frontend/src/entities/notifications/__tests__/notifications.model.test.ts` не покрывают
  сценарий "потеря push-подписки на стороне браузера + resume PWA".
- В коде уже есть `$isManualToggle` (строка 52) — то есть концепция "когда подписка инициирована
  пользователем" известна. Но именно для авто-подписки на initial-загрузке dedup-флага нет.

## 3. Лишний reload `loadUpcomingLessons` после удаления урока — несогласованный фильтр

- **Severity:** High
- **Файл:** `frontend/src/features/lessons/models/lessons-reload.model.ts:156-174`
- **Категория:** Frontend Effector / Performance / UX

### Описание

Sample на `removeLessonFx.doneData` (строки 156–174) безусловно вызывает `loadUpcomingLessonsFx` без
фильтрации по `lessonsViewMode` или `currentTab`. Все аналогичные sample на `updateLessonFx.doneData`
в этом же файле (строки 61–83, 85–107, 109–131) корректно фильтруют по
`lessonsViewMode === "paged" && currentTab === <соответствующий таб>`. Несогласованность в
single-source-of-truth (этот же файл) — явный сигнал, что `filter` был пропущен.

В результате удаление урока с любого таба ("Прошедшие", "Отменённые") в weekly/schedule-режимах
приводит к лишнему HTTP-запросу `GET /api/lessons?status=upcoming&...` и перезаписывает
`$upcomingLessons` в фоне.

### Воспроизведение

1. Пользователь на табе "Прошедшие" в `paged`-режиме, фильтр оплат отключён.
2. Удаляет прошедший урок (или любой урок).
3. В Network уходит `GET /api/lessons?...` с параметрами для **upcoming**, а не для текущего таба.
4. `$upcomingLessons` перезаписывается, пагинация upcoming-таба может сброситься на 1-ю страницу.
5. При возврате на "Запланированные" пользователь видит первую страницу, а не ту, на которой был.

### Последствия

Лишний сетевой запрос при каждом удалении. Возможная "потеря места" в пагинации запланированных
уроков. На больших списках — заметный лаг.

### Предлагаемое исправление

Добавить `source` с `lessonsViewMode`/`currentTab` и `filter`, как в соседних sample:

```ts
// before — frontend/src/features/lessons/models/lessons-reload.model.ts:156-174
sample({
  clock: lessonModel.removeLessonFx.doneData,
  source: {
    pagination: lessonModel.$upcomingPagination,
    onlyUnpaid: filtersModel.$onlyUnpaid,
    onlyWithoutHomework: filtersModel.$onlyWithoutHomework,
    paymentDateFrom: filtersModel.$paymentDateFrom,
    paymentDateTo: filtersModel.$paymentDateTo,
  },
  fn: ({ pagination, ... }) => ({ ... }),
  target: lessonModel.loadUpcomingLessonsFx,
});

// after
sample({
  clock: lessonModel.removeLessonFx.doneData,
  source: {
    lessonsViewMode: viewModeModel.$lessonsViewMode,
    currentTab: tabsModel.$currentTab,
    pagination: lessonModel.$upcomingPagination,
    onlyUnpaid: filtersModel.$onlyUnpaid,
    onlyWithoutHomework: filtersModel.$onlyWithoutHomework,
    paymentDateFrom: filtersModel.$paymentDateFrom,
    paymentDateTo: filtersModel.$paymentDateTo,
  },
  filter: ({ lessonsViewMode, currentTab }) =>
    lessonsViewMode === "paged" && currentTab === UPCOMING_TAB_INDEX,
  fn: ({ pagination, ... }) => ({ ... }),
  target: lessonModel.loadUpcomingLessonsFx,
});
```

Аналогичный sample для weekly/schedule-режимов отсутствует — это отдельный пробел, но не
обязательно баг (зависит от того, нужен ли вообще reload weekly после удаления — `updateLessonFx`
для weekly есть на строках 32-51, для `removeLessonFx` отсутствует).

### Почему это не false positive

- Соседние sample на `updateLessonFx.doneData` в том же файле имеют точно такие же `source` +
  `filter` — паттерн установлен.
- Тестов для именно этого sample (`removeLessonFx.doneData → loadUpcomingLessonsFx`) с разными
  табами/режимами в `__tests__` нет.
- При прочтении файла видно, что 6 sample-ов идут "семейством" — с filter, а 2 (на
  `removeLessonFx`) — без полного фильтра. Это инкомплитная имплементация.

## 4. WebSocket: tutor-handlers регистрируются после `clients.set` — race с синхронным close

- **Severity:** Medium
- **Файл:** `backend/src/lib/websocket/WebSocketManager.ts:83-104`
- **Категория:** Real-time / Race condition

### Описание

В `handleConnection` (tutor-ветка) порядок такой:

1. Строка 83: `this.clients.set(decoded.userId, ws)` — запись добавляется в Map.
2. Строки 90–104: регистрируются `ws.on("close", ...)` и `ws.on("error", ...)`, которые удаляют
   запись из Map.

Если socket по какой-либо причине синхронно закрылся между шагом 1 и шагом 2 (например, peer
оборвал соединение сразу после handshake), close-event может быть эмиттирован/потерян до того, как
handler навешен — запись в `clients` останется навсегда, превратившись в утечку (мёртвый сокет
никогда не удалится из Map).

В student-ветке (строки 148–176) этот же класс **явно исправлен**:

```ts
// Регистрируем close/error handlers ДО `set`, иначе синхронный close
// между set и регистрацией оставит запись-сироту в studentClients.
ws.on("close", () => { ... });
ws.on("error", (error) => { ... });
ws.on("message", () => {});

if (ws.readyState !== WebSocket.OPEN) {
  return;
}

this.studentClients.set(decoded.studentUserId, ws);
```

Tutor-ветка не получила это исправление — асимметрия чётко видна между двумя методами одного и того
же класса.

### Воспроизведение

Воспроизвести стабильно сложно из-за тайминга, но сценарий:

1. Клиент устанавливает WebSocket-соединение, проходит async `authenticateWebSocket`.
2. До того, как `handleConnection` доходит до строки 90, peer уже закрыл соединение (RST или
   `client.close()` сразу после получения OPEN).
3. ws-библиотека эмитит close-event синхронно — но `ws.on("close")` ещё не вызван → handler не
   сработал.
4. Запись `userId → ws` остаётся в `this.clients` навсегда.

### Последствия

- Утечка памяти: запись в Map с мёртвым сокетом не удаляется.
- `getConnectedUsersCount()` некорректен.
- `broadcastLessonStatusUpdate` при отсутствии `tutorId` итерируется по `this.clients.forEach` и
  пытается `send` на мёртвом сокете (защищено `readyState === OPEN`, но всё равно лишняя работа).
- `sendToUser(userId, ...)` возвращает `true` или `false` в зависимости от `readyState` — на
  мёртвом сокете будет возвращать `false` и сообщения теряются (особенно после reconnect-логики
  фронта: новый сокет создан, но в `clients` всё ещё мёртвый).

### Предлагаемое исправление

Переписать tutor-ветку симметрично student-ветке: handlers ДО `set`, проверка `readyState` перед
`set`:

```ts
// before — backend/src/lib/websocket/WebSocketManager.ts:82-124
this.clients.set(decoded.userId, ws);

console.log(`WebSocket connected: ${decoded.email} (${decoded.userId})`);

ws.on("close", () => {
  if (this.clients.get(decoded.userId) === ws) {
    this.clients.delete(decoded.userId);
  }
});
ws.on("error", (error) => { /* ... */ });
ws.on("message", (message) => { /* ... */ });

if (ws.readyState === WebSocket.OPEN) {
  sendWelcomeMessage(ws, decoded.userId);
}

// after — handlers и readyState-guard перед set
ws.on("close", () => {
  if (this.clients.get(decoded.userId) === ws) {
    this.clients.delete(decoded.userId);
  }
});
ws.on("error", (error) => { /* ... */ });
ws.on("message", (message) => { /* ... */ });

if (ws.readyState !== WebSocket.OPEN) {
  return;
}

this.clients.set(decoded.userId, ws);

console.log(`WebSocket connected: ${decoded.email} (${decoded.userId})`);

try {
  sendWelcomeMessage(ws, decoded.userId);
} catch (error) {
  console.error("Failed to send welcome message:", error);
}
```

### Почему это не false positive

- Прямая асимметрия между tutor- и student-ветками одного класса с явным комментарием в
  student-ветке "Регистрируем close/error handlers ДО `set`, иначе синхронный close между set и
  регистрацией оставит запись-сироту в studentClients" — то есть автор уже осознал проблему, но
  применил фикс только в одной ветке.
- Тесты `backend/src/lib/websocket/__tests__/WebSocketManager.test.ts` не симулируют синхронный
  close между set и регистрацией handler.
- Существующий previous-close на строках 70–80 (закрытие предыдущего соединения для того же
  userId) не покрывает этот сценарий — это другой механизм.

## 5. Студенческий JWT не поддерживает отзыв — нет `tokenVersion` ни в payload, ни в схеме

- **Severity:** Medium
- **Файл:** `backend/src/middleware/studentAuth.ts:5-26`, `backend/prisma/schema.prisma` (model
  StudentUser, строки 108+)
- **Категория:** Backend Auth / Security

### Описание

В отличие от `authenticateToken` для репетиторов (`backend/src/middleware/auth.ts:34-66`), который
проверяет `tokenVersion` против БД (с кэшем) и отвергает токен, если версия не совпадает,
`authenticateStudent` (`studentAuth.ts:5-26`) только проверяет подпись JWT и завершает — никаких
обращений к БД или кэшу.

В модели `StudentUser` поле `tokenVersion` тоже отсутствует. `generateStudentToken`
(`backend/src/utils/studentAuth.ts`) не включает `tokenVersion` в payload, а `loginStudent`
(`backend/src/services/studentAuth/studentAuth.ts`) — тем более.

Это означает, что **отзыв студенческого токена невозможен** при любом из сценариев:

- Принудительный logout студента со стороны репетитора.
- Удаление аккаунта `StudentUser` (токен продолжит "работать" с подписью, упасть может только в
  момент конкретного запроса при попытке прочитать student-данные).
- Будущий "сменить пароль студента" / "сменить email студента".

7-дневный TTL JWT (`STUDENT_JWT_EXPIRES_IN`) — единственная защита. Архитектурный инвариант,
заложенный в tutor-ветке, в student-ветке нарушен.

### Воспроизведение

1. Студент зарегистрировался по инвайту, получил JWT.
2. Репетитор вызывает `DELETE /api/student-cabinet/...` (или вручную удаляет `StudentUser` через
   будущий endpoint).
3. JWT студента продолжает проходить `authenticateStudent` (он подписан валидно).
4. Внутри контроллера запросы вида `prisma.studentUser.findUnique({ where: { id: studentUserId } })`
   вернут `null`, контроллер вернёт 404 — но это уже после прохождения middleware. Endpoints,
   которые не делают такой lookup, могут вернуть данные другого формата.

### Последствия

Удалённый/деактивированный студенческий аккаунт может в течение до 7 дней показывать 401 с задержкой
или вообще проходить middleware и падать в каком-то контроллере с 5xx. Архитектурно нет способа
отозвать токен — что блокирует любые будущие фичи "выход со всех устройств / смена пароля у
студента".

### Предлагаемое исправление

Добавить `tokenVersion` в `StudentUser` и сделать middleware симметричным tutor-варианту:

```prisma
// backend/prisma/schema.prisma — model StudentUser
model StudentUser {
  // ...
  tokenVersion Int @default(0)
}
```

```ts
// backend/src/utils/studentAuth.ts — generateStudentToken
export const generateStudentToken = (payload: {
  studentUserId: string;
  studentId: string;
  email: string;
  tokenVersion: number;          // ← добавить
}) => { ... };

// backend/src/middleware/studentAuth.ts — добавить проверку версии
const payload = verifyStudentToken(token);
if (!payload) { /* 401 */ }

const dbUser = await prisma.studentUser.findUnique({
  where: { id: payload.studentUserId },
  select: { tokenVersion: true },
});

if (!dbUser || (payload.tokenVersion ?? 0) !== dbUser.tokenVersion) {
  return res.status(401).json({ error: "Токен отозван" });
}

req.studentUser = payload;
next();
```

И инкрементировать `tokenVersion` во всех будущих "изменить пароль / выгнать студента" операциях.
Для оптимизации — кеш на короткое время, аналогично `tokenVersionCache` для tutor-ветки.

### Почему это не false positive

- Прямой паттерн в `backend/src/middleware/auth.ts:34-66` с комментарием "Verify tokenVersion so
  password/email changes immediately revoke previously issued tokens" — это явное архитектурное
  решение, не применённое к студентам.
- Поиск `grep -rn "tokenVersion" backend/src` не находит ни одного упоминания в коде студенческого
  кабинета.
- Тест `backend/src/__tests__/cross-role-security.test.ts` не проверяет отзыв токена студента.
- В feature spec `029-student-cabinet` не было явного требования "не реализовывать отзыв", но
  имеющаяся реализация tutor-аналога делает текущее состояние асимметричным.

## 6. `deleteStudent`: TOCTOU между `findFirst` и `delete` — 500 при двойном клике

- **Severity:** Medium
- **Файл:** `backend/src/controllers/students/deleteStudent.ts:11-24`
- **Категория:** Backend Controller / UX

### Описание

Контроллер сначала проверяет владение через `findFirst({ where: { id, tutorId: userId } })`, а затем
отдельным запросом `delete({ where: { id } })`. Между двумя запросами окно для гонки: если параллельный
DELETE с тем же id уже завершился, первый запрос пройдёт `findFirst` (студент ещё видим), а `delete`
выбросит `P2025 RecordNotFound`, который не обрабатывается отдельно — попадает в `catch` и возвращает
500 вместо 404.

Реалистичный кейс: пользователь дважды быстро нажимает "Удалить" (или два открытых таба с
одинаковым студентом). Первый запрос успешно удаляет, второй — 500.

Для контраста — в `revokeInvitation` (`studentInvitation.ts:97-100`) уже используется правильный
паттерн с `updateMany` + проверкой `count`.

### Воспроизведение

1. Открыть студента в двух вкладках.
2. В первой вкладке нажать "Удалить" — `DELETE /api/students/:id` → 200.
3. Во второй вкладке быстро нажать "Удалить" — `DELETE /api/students/:id` →
   `findFirst` сначала находит студента из кэша/реплики (либо вообще проходит до коммита первой
   транзакции), потом `delete` выбрасывает `P2025` → catch → 500.

### Последствия

UX: пользователь видит "Внутренняя ошибка сервера" вместо корректного "Ученик не найден".
Срабатывает Sentry/log-алерт на ошибку 500. Сами данные не повреждаются — оба запроса хотят одного
и того же.

### Предлагаемое исправление

Использовать атомарный `deleteMany` с ownership-фильтром и проверять `count`:

```ts
// before — backend/src/controllers/students/deleteStudent.ts:11-30
const existingStudent = await prisma.student.findFirst({
  where: { id, tutorId: userId },
});

if (!existingStudent) {
  return res.status(404).json({ error: "Ученик не найден" });
}

await prisma.student.delete({
  where: { id },
});

res.json({ message: "Ученик успешно удален" });

// after
const result = await prisma.student.deleteMany({
  where: { id, tutorId: userId },
});

if (result.count === 0) {
  return res.status(404).json({ error: "Ученик не найден" });
}

res.json({ message: "Ученик успешно удален" });
```

`deleteMany` не выбрасывает `P2025` при нулевом совпадении — он просто возвращает `{ count: 0 }`,
поэтому никаких гонок между check и mutate уже не остаётся.

### Почему это не false positive

- В `services/passwordReset.ts:136` и `services/studentAuth/studentAuth.ts:89` используется
  аналогичный паттерн с `updateMany` для атомарной проверки и изменения — то есть в проекте знают
  правильный путь.
- Generic `catch (error) { res.status(500) }` действительно не различает `P2025` — это видно прямо
  по коду строки 27-30.
- Тесты в `backend/src/controllers/__tests__/students.test.ts` (если есть) не проверяют двойной
  параллельный DELETE.

## 7. `deleteLesson` (deleteAllFuture): отмена напоминаний и удаление уроков вне транзакции

- **Severity:** Medium
- **Файл:** `backend/src/controllers/lessons/deleteLesson.ts:50-54, 67-68`
- **Категория:** Data integrity / Atomicity

### Описание

В ветке `deleteAllFuture` цикл `for (const lessonId of toDeleteIds) { await
cancelRemindersForLesson(lessonId); }` (строки 51–53) и `prisma.lesson.deleteMany` (строка 54)
выполняются последовательно вне транзакции. Тот же паттерн в одиночной ветке (строки 67–68).

Если `deleteMany` (или `delete` в одиночной ветке) упадёт после того, как часть напоминаний уже
переведена в статус `CANCELLED`, мы получим несогласованное состояние: уроки остаются в БД, но
будущих push-напоминаний для них не будет — `reminderProcessor` пропустит CANCELLED-записи.

Cascade на `Lesson → ScheduledReminder` (`schema.prisma:268`) частично спасает: при успешном
`deleteMany` reminders каскадно удаляются. Но именно при сбое самого `deleteMany` (transient DB
error, deadlock) reminders уже CANCELLED, а lesson — на месте.

Для контраста — `archiveStudent` (хоть и с другим багом, см. ниже) хотя бы выполняет всё в
`prisma.$transaction`.

### Воспроизведение

1. У репетитора серия recurring-уроков на 10 будущих дат.
2. Запрос `DELETE /api/lessons/:id { deleteAllFuture: true }`.
3. Цикл `cancelRemindersForLesson` успешно проходит для всех 10 уроков (`scheduledReminder.updateMany
   → status: "CANCELLED"`).
4. `prisma.lesson.deleteMany({ where: { id: { in: toDeleteIds } } })` падает с deadlock /
   connection drop.
5. В БД: 10 уроков существуют со статусом `SCHEDULED`, их reminders в `CANCELLED`. Cron больше не
   будет посылать пуши, но уроки видны в расписании репетитора и студента.

### Последствия

- Тихая потеря push-уведомлений для существующих уроков. Пользователь увидит урок в расписании,
  но не получит напоминание перед ним.
- `lesson.status` остаётся `SCHEDULED`, а `reminderProcessor.ts:123` проверяет именно статус урока —
  но reminder уже CANCELLED, поэтому даже после восстановления БД ничего не починится автоматически.
- Необходимо ручное вмешательство (запустить `recalculateRemindersForUser` для пострадавшего
  репетитора).

### Предлагаемое исправление

Обернуть в `prisma.$transaction` обе ветки `deleteLesson`:

```ts
// before — deleteAllFuture ветка
if (toDeleteIds.length > 0) {
  for (const lessonId of toDeleteIds) {
    await cancelRemindersForLesson(lessonId);
  }
  await prisma.lesson.deleteMany({ where: { id: { in: toDeleteIds } } });
}

// after — обе ветки в транзакции
await prisma.$transaction(async (tx) => {
  await tx.scheduledReminder.updateMany({
    where: {
      lessonId: { in: toDeleteIds },
      status: { in: ["PENDING", "PROCESSING"] },  // см. ACTIVE_REMINDER_STATUSES
    },
    data: { status: "CANCELLED", claimedAt: null },
  });
  await tx.lesson.deleteMany({ where: { id: { in: toDeleteIds } } });
});
```

Это устраняет окно несогласованности и заодно соответствует контракту
`ACTIVE_REMINDER_STATUSES` (`reminderScheduler.ts:60`) — нужно отменять и `PROCESSING`, а не только
`PENDING`.

### Почему это не false positive

- В коде проекта `recalculateRemindersForUser` (`reminderScheduler.ts:79`) и `archiveStudent`
  (`archiveStudent.ts:21`) обе используют `$transaction` для аналогичных связанных операций.
- Cascade на `Lesson → ScheduledReminder` помогает только при успешном `deleteMany`, не при
  partial failure.
- Тесты `backend/src/controllers/lessons/__tests__/deleteLesson.test.ts` не проверяют состояние
  `ScheduledReminder` после симулированного сбоя.

## 8. `archiveStudent`: cancel reminders фильтрует только `PENDING`, упуская `PROCESSING`

- **Severity:** Medium
- **Файл:** `backend/src/controllers/students/archiveStudent.ts:27-37`
- **Категория:** Real-time / Cron / Race condition

### Описание

В `archiveStudent` транзакция отменяет напоминания с `status: "PENDING"`:

```ts
await tx.scheduledReminder.updateMany({
  where: {
    lesson: { studentId: id, startTime: { gte: now }, status: { notIn: ["COMPLETED", "CANCELLED"] } },
    status: "PENDING",
  },
  data: { status: "CANCELLED" },
});
```

Но `ACTIVE_REMINDER_STATUSES` из `reminderScheduler.ts:60` включает и `PENDING`, и `PROCESSING`:

```ts
const ACTIVE_REMINDER_STATUSES = ["PENDING", "PROCESSING"] as const;
```

Если в момент архивации `reminderProcessor` уже сделал claim (PENDING → PROCESSING) на одно из
напоминаний к будущему уроку студента, цикл обработки этого напоминания продолжится в фоне:
- `deleteMany` через cascade удалит запись `scheduledReminder` (FK `onDelete: Cascade` на
  `Lesson → ScheduledReminder`).
- Но в памяти процессора reminder уже взят в работу — он попытается отправить push на основании
  snapshot.lesson (поле в include на момент `findMany` в claim).
- Studio удалит запись, поэтому `finalize` сделает `updateMany` на несуществующую запись →
  0 строк затронуто (silent no-op).
- Пользователь получит push для урока, который уже удалён.

### Воспроизведение

1. Репетитор имеет студента с уроком через 10 минут, на который запланирован push-reminder.
2. В 13:59:59 cron `reminderProcessor` срабатывает, claim'ит reminder (PENDING → PROCESSING).
3. В 14:00:00 репетитор архивирует студента — `archiveStudent` запускает транзакцию.
4. `updateMany` фильтрует только `PENDING` — claim'нутый reminder (статус PROCESSING) не
   затрагивается.
5. `deleteMany` удаляет урок → cascade удаляет ScheduledReminder.
6. Параллельный процессор уже подгрузил данные в память и через долю секунды отправит push.
7. Пользователь получает push-уведомление "Урок через 10 минут" для урока, которого больше нет.

### Последствия

Минорный UX-баг: push-уведомление для архивированного/удалённого урока. Не critical, но раздражает
пользователя — он откроет PWA и не найдёт урока, о котором сообщили.

### Предлагаемое исправление

Включить `PROCESSING` в фильтр, как это сделано в `recalculateRemindersForUser` и
`cancelRemindersForLesson`:

```ts
// before — backend/src/controllers/students/archiveStudent.ts:34
status: "PENDING",

// after
status: { in: ["PENDING", "PROCESSING"] },
```

Это согласуется с константой `ACTIVE_REMINDER_STATUSES` из `reminderScheduler.ts:60` (которую,
возможно, имеет смысл экспортировать и переиспользовать).

### Почему это не false positive

- В `reminderScheduler.ts:60` константа `ACTIVE_REMINDER_STATUSES` явно определена для именно этого
  кейса с комментарием "Если PROCESSING-запись (claim в процессе доставки) пропустить, watchdog в
  `processScheduledReminders` через 10 минут вернёт её в PENDING".
- В `cancelRemindersForLesson` (`reminderScheduler.ts:62-73`) фильтр `{ in:
  [...ACTIVE_REMINDER_STATUSES] }` уже применён.
- В `archiveStudent.ts:34` константа не используется и захардкожен только `"PENDING"`.
- Тесты `backend/src/controllers/students/__tests__/archiveStudent.test.ts` не симулируют
  параллельный claim в процессоре во время архивации.
