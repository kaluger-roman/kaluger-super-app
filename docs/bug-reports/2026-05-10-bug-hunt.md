# Bug Hunt Report — 2026-05-10

**Всего багов:** 10 (Critical: 3, High: 7, Medium: 0, Low: 0)
**Покрытые области:** Auth/Security, Backend Services, Real-time/Cron, Data Integrity (Prisma), Frontend Effector

## Резюме

Главные риски прохода — серьёзная компрометация безопасности модуля экранного мониторинга (хардкод-секрет + timing-attack + отсутствие rate-limit на reset-password) и кластер race-condition'ов в бизнес-критичных операциях: обновлении уроков, обработке recurring-серий, постановке/доставке push-напоминаний и сбросе пароля. Отдельно — системный финансовый баг: цены и налоговая ставка хранятся как `Float`, что приводит к накопительной погрешности в отчётах и расчёте налога.

## 1. SCREEN_SECRET имеет hardcoded fallback — токены экранного мониторинга подделываются с известным секретом

- **Severity:** Critical
- **Файл:** `backend/src/controllers/screen/helpers.ts:3`
- **Категория:** Backend Auth / Security

### Описание

Константа определена как `process.env.SCREEN_SECRET || "screen-monitoring-secret-key"`. Если переменная не задана в окружении (dev без `.env`, ошибка при деплое, забытый секрет в `.env.production`), приложение продолжает работать с публично известным секретом. Все `generateScreenToken` / `verifyScreenToken` используют его. В отличие от `JWT_SECRET` (`utils/auth.ts` бросает `Error` при отсутствии), здесь silently используется небезопасный дефолт.

### Воспроизведение

1. `SCREEN_SECRET` не выставлен в production (или попал в репозиторий из публичного кода).
2. Атакующий вычисляет `signature = HMAC_SHA256("screen-monitoring-secret-key", userId).slice(0, 16)`.
3. Шлёт POST `/api/screen/upload` с заголовком `x-screen-token: ${userId}.${signature}` и произвольным payload — успех.

### Последствия

Полная компрометация модуля экранного мониторинга: подделка токена для любого `userId`, перезапись скриншотов чужого пользователя, неограниченная запись произвольных файлов на диск.

### Предлагаемое исправление

```ts
// before
const SCREEN_SECRET = process.env.SCREEN_SECRET || "screen-monitoring-secret-key";

// after — паттерн как в getJwtSecret() в utils/auth.ts
const getScreenSecret = (): string => {
  const secret = process.env.SCREEN_SECRET;
  if (!secret) throw new Error("SCREEN_SECRET is not set");
  return secret;
};
```

И заменить все ссылки на `SCREEN_SECRET` вызовом `getScreenSecret()` внутри `generateScreenToken` / `verifyScreenToken`.

### Почему это не false positive

Прочитал `helpers.ts` целиком — это единственный файл, где используется секрет. Сравнил с паттерном `getJwtSecret()` в `utils/auth.ts:19` — там при отсутствии env-переменной выбрасывается ошибка, что является эталоном безопасности проекта. Здесь паттерн нарушен.

## 2. `Float` для денег и налоговой ставки — накопительная потеря точности в финансовой отчётности

- **Severity:** Critical
- **Файл:** `backend/prisma/schema.prisma:63,85,110`
- **Категория:** Data Integrity / Prisma

### Описание

Поля `Lesson.price` (`Float?`), `Student.hourlyRate` (`Float?`) и `TaxRatePeriod.rate` (`Float`) объявлены как IEEE-754 double. PostgreSQL хранит их как `DOUBLE PRECISION`. Для денег это неприемлемо: 1234.56 может храниться как 1234.5599999999999... При агрегации через Prisma `_sum` (используется в `getStatistics.ts` и `getLessons.ts`) погрешность накапливается, а ставка налога 7.5% хранится как 7.499999999... — `calcLessonTax` даёт неверный результат после нескольких операций.

### Воспроизведение

Репетитор проводит 100 уроков по 1500.50 ₽. `prisma.lesson.aggregate({ _sum: { price: true } })` возвращает `150049.99999999997` вместо `150050.00`. Налог по нерегулярной ставке (например, 7.5%) — после нескольких операций даёт ошибки округления в копейках.

### Последствия

Финансовая отчётность содержит ошибки округления; расчёт налога (модуль рассчитан на отчётность для ФНС) неточен. Для приложения, у которого основная пользовательская ценность — учёт денег, это прямой бизнес-ущерб.

### Предлагаемое исправление

```prisma
// before
price       Float?
hourlyRate  Float?
rate        Float

// after
price       Decimal? @db.Decimal(10, 2)
hourlyRate  Decimal? @db.Decimal(10, 2)
rate        Decimal  @db.Decimal(5, 2)
```

В коде заменить числовую арифметику на `Prisma.Decimal` (`taxRate.ts:47,103`, `getStatistics.ts:48-56,110-129`, `getLessons.ts:148`).

### Почему это не false positive

Прочитал схему: `Lesson.price` и `Student.hourlyRate` помечены как `Float?`, `TaxRatePeriod.rate` — `Float`. Тестов на точность арифметики нет. Это известное анти-правило для денежных значений в PostgreSQL.

## 3. `processScheduledReminders` — молчаливая потеря push-напоминаний при падении процесса

- **Severity:** Critical
- **Файл:** `backend/src/services/reminderProcessor.ts:30-33`
- **Категория:** Real-time / Cron

### Описание

Транзакция (строки 14–46) атомарно переводит до 100 `PENDING`-напоминаний в статус `SENT` **до** начала цикла доставки push-уведомлений (строка 54). Если Node.js-процесс упадёт (OOM, SIGKILL, деплой через `systemctl restart`) после коммита транзакции, но до завершения цикла — все уже помеченные `SENT` записи останутся в этом статусе навсегда. `processScheduledReminders` выбирает только `PENDING`-строки (`status: "PENDING"` в `findMany`, строка 17), повторной попытки не будет.

### Воспроизведение

Накопилось 80 overdue-напоминаний (например, сервер простаивал 20 минут). Тик забирает все 80 атомарным апдейтом в `SENT`, начинает цикл push-доставки. На 40-й итерации systemd перезапускает процесс при деплое или OOM-killer убивает процесс. Оставшиеся 40 напоминаний навсегда застревают в `SENT`, push не отправлен.

### Последствия

Пользователь не получает push-напоминания о занятиях — тихая потеря без любой ошибки в логах или UI. Так как в проекте есть PWA-напоминания (008-pwa-lesson-reminders) — это прямой удар по основному use case.

### Предлагаемое исправление

Вводим промежуточный статус `PROCESSING` (или поле `claimedAt`), финализируем в `SENT` только после успешной доставки внутри тела цикла.

```ts
// before — массовый перевод в SENT до доставки
await tx.scheduledReminder.updateMany({
  where: { id: { in: ids }, status: "PENDING" },
  data: { status: "SENT", sentAt: now },
});

// after — резервируем как PROCESSING, переводим в SENT после успеха
await tx.scheduledReminder.updateMany({
  where: { id: { in: ids }, status: "PENDING" },
  data: { status: "PROCESSING", claimedAt: now },
});
// ...затем в цикле, после успешного sendPushToUser:
await prisma.scheduledReminder.update({
  where: { id: reminder.id },
  data: { status: "SENT", sentAt: now },
});
```

И добавить watchdog: записи в `PROCESSING` с `claimedAt` старше 10 минут считать «застрявшими» и возвращать в `PENDING`.

### Почему это не false positive

Прочитал файл целиком: `findMany` на строке 15 фильтрует только `PENDING`. Записи в `SENT` не перебираются повторно ни в одном другом месте кода (grep по `status:`). Существующий `try/catch` (строка 142) ловит JS-ошибки, но не падение процесса. Тесты `reminderProcessor.test.ts` покрывают happy-path и `sendNotification`-fail, но не симулируют kill.

## 4. Timing attack при верификации screen-токена через `!==`

- **Severity:** High
- **Файл:** `backend/src/controllers/screen/helpers.ts:25`
- **Категория:** Backend Auth / Security

### Описание

Сравнение HMAC-подписи выполняется через обычный оператор строкового сравнения `signature !== expected`, а не через `crypto.timingSafeEqual`. Это позволяет атакующему измерять время ответа и побайтово восстанавливать ожидаемую подпись (timing oracle). Сигнатура усечена до 16 hex-символов — пространство перебора компактное.

### Воспроизведение

Атакующий знает свой `userId`. Многократно делает POST `/api/screen/upload` с разными последними символами `signature`, измеряет статистику latency ответов, восстанавливает правильную сигнатуру для **чужого** `userId` за ~256 × 16 ≈ 4096 запросов.

### Последствия

Форжинг screen-токена для произвольного пользователя без знания `SCREEN_SECRET`. Усугубляется отсутствием rate-limiting на `/upload` (см. также баг #1).

### Предлагаемое исправление

```ts
// before
if (signature !== expected) return null;

// after
import { timingSafeEqual } from "crypto";

const sigBuf = Buffer.from(signature, "utf8");
const expBuf = Buffer.from(expected, "utf8");
if (sigBuf.length !== expBuf.length || !timingSafeEqual(sigBuf, expBuf)) return null;
```

### Почему это не false positive

Прочитал `helpers.ts` полностью — других сравнений секретов нет. `timingSafeEqual` требует одинаковой длины буферов, поэтому проверка `length` обязательна перед вызовом.

## 5. `/reset-password/verify` и `/reset-password` без rate-limiting

- **Severity:** High
- **Файл:** `backend/src/routes/auth.ts:34-35`
- **Категория:** Backend Auth / Security

### Описание

Маршруты не имеют rate limiting:

```ts
router.post("/reset-password/verify", verifyResetToken);
router.post("/reset-password", resetPassword);
```

При этом `/forgot-password` (выдача токена) защищён `passwordResetRateLimiter` (5 req / 15 min). Использование токена — нет. Хотя сам токен 32-байтный (256 бит энтропии), отсутствие лимита открывает несколько векторов: оракул валидности токена через `/verify`, автоматизированный перебор `newPassword` при компрометации токена, информационная разведка.

### Воспроизведение

Скрипт делает тысячи запросов к `/reset-password/verify` (200 vs 400 раскрывает валидность токена) или к `/reset-password` с разными `newPassword` при известном токене.

### Последствия

Информационная утечка по валидности токена; отсутствие защиты при компрометации одной ссылки сброса. Также упрощает эксплуатацию race-condition из бага #7.

### Предлагаемое исправление

```ts
// before
router.post("/reset-password/verify", verifyResetToken);
router.post("/reset-password", resetPassword);

// after
router.post("/reset-password/verify", passwordResetRateLimiter, verifyResetToken);
router.post("/reset-password", passwordResetRateLimiter, resetPassword);
```

Лимитер уже определён в `middleware/rateLimit.ts` — нужно только применить.

### Почему это не false positive

Прочитал `routes/auth.ts` построчно: `passwordResetRateLimiter` применяется только к строке 33. Строки 34-35 — без middleware. `middleware/rateLimit.ts` содержит готовый лимитер.

## 6. TOCTOU при `updateLesson` — проверка конфликтов расписания вне транзакции

- **Severity:** High
- **Файл:** `backend/src/controllers/lessons/updateLesson.ts:47-67`
- **Категория:** Backend Services

### Описание

В `validateUpdateData` конфликт расписания проверяется через `prisma.lesson.findFirst` **вне** транзакции. Главная `prisma.$transaction` (строка 183) стартует только после проверки — между чтением «нет конфликтов» и записью обновлённого урока есть окно, когда другой запрос может успешно создать/обновить урок в этом же слоте. В соседнем `createLesson.ts` та же проверка корректно вынесена внутрь транзакции через `checkSchedulingConflicts(userId, start, end, tx)`.

### Воспроизведение

Два конкурентных запроса `PATCH /api/lessons/:id` (или один `update` + один `create`) меняют время уроков на перекрывающееся. Оба проходят `findFirst` (не видят конкурента), затем оба коммитят — в БД два урока с пересекающимися `startTime/endTime`.

### Последствия

Нарушение бизнес-инварианта «без конфликтов в расписании». В UI у репетитора появляются накладки в расписании, которые он сам не сможет исправить из приложения (валидация запрещает создание нового конфликта).

### Предлагаемое исправление

```ts
// before — проверка вне транзакции
const conflictingLesson = await prisma.lesson.findFirst({ ... });
if (conflictingLesson) throwHttp(...);
const { lesson } = await prisma.$transaction(async (tx) => {
  const updated = await tx.lesson.update({ ... });
});

// after — проверка внутри транзакции, как в createLesson.ts
const { lesson } = await prisma.$transaction(async (tx) => {
  const conflictingLesson = await tx.lesson.findFirst({ ... });
  if (conflictingLesson) throwHttp(...);
  const updated = await tx.lesson.update({ ... });
});
```

### Почему это не false positive

`createLesson.ts` использует тот же сценарий, но проверку делает в `tx`. Тест `updateLesson.test.ts` не покрывает конкурентный сценарий. Это асимметрия между двумя контроллерами одного домена.

## 7. Race condition в `applyPasswordReset` — два параллельных запроса с одним токеном оба применяют смену пароля

- **Severity:** High
- **Файл:** `backend/src/services/passwordReset.ts:105-134`
- **Категория:** Backend Services / Security

### Описание

`applyPasswordReset` вызывает `findValidResetToken(token)` вне транзакции (строка 105), затем выполняет batch-`prisma.$transaction([update token, update user])` (строка 125). Между этими шагами другой параллельный запрос с тем же токеном может пройти `findValidResetToken` (`usedAt` ещё `null`), и оба запроса последовательно завершат свои batch-транзакции — второй установит свой пароль поверх первого. Batch-транзакция (`$transaction([...])`) не делает условную проверку «не использован» атомарно с чтением.

### Воспроизведение

Атакующий получил доступ к ссылке сброса пароля (через перехват e-mail, утечку, MITM). Шлёт два конкурентных POST `/api/auth/reset-password` с разными `newPassword`. Оба проходят `findValidResetToken` до того, как первый помечает `usedAt`. Второй устанавливает пароль атакующего поверх пароля владельца.

### Последствия

Завладение чужой учётной записью даже после того, как владелец уже использовал ссылку. Усугубляется багом #5 (отсутствие rate-limit).

### Предлагаемое исправление

Перевести на интерактивную транзакцию с атомарным conditional-update токена — Prisma выбросит `P2025`, если токен уже помечен:

```ts
// before
const record = await findValidResetToken(token);
// ...
await prisma.$transaction([
  prisma.passwordResetToken.update({ where: { id: record.id }, data: { usedAt: now } }),
  prisma.user.update({ where: { id: record.userId }, data: { password: hashedPassword } }),
]);

// after
await prisma.$transaction(async (tx) => {
  const now = new Date();
  // Атомарное conditional-update: бросит P2025, если токен уже использован
  const record = await tx.passwordResetToken.update({
    where: { tokenHash, usedAt: null },
    data: { usedAt: now },
  });
  await tx.user.update({
    where: { id: record.userId },
    data: { password: hashedPassword },
  });
});
```

### Почему это не false positive

Тест `passwordReset.test.ts:232-253` проверяет последовательное повторное использование (отклоняется), но не конкурентный сценарий. Prisma `$transaction([...])` (batch) не атомарен с чтением вне транзакции.

## 8. `processRecurringLessons` — отсутствие overlap-guard и транзакции при создании recurring-серий

- **Severity:** High
- **Файл:** `backend/src/services/recurringLessons.ts:44-92`
- **Категория:** Real-time / Cron

### Описание

Cron `processRecurringLessons` для каждого слота делает `prisma.lesson.findMany` (проверка конфликтов, строка 46), затем после цикла — `prisma.lesson.createMany` (строка 89). Эти операции **не** обёрнуты в транзакцию, и в файле нет module-level флага вида `recurringRunning` (в `backup.ts:191-199` такой флаг есть). При параллельном запуске двух экземпляров (рестарт при тике, ручной trigger) оба пройдут `findMany`, оба выполнят `createMany` — дубликаты.

В схеме `Lesson` нет `@@unique` по `(tutorId, startTime)`, дубли проходят и на уровне БД.

### Воспроизведение

Сервер перезапускается в 02:00 MSK (тик cron). Старый процесс уже выполнил `findMany`, новый стартует и тоже выполняет `findMany`. Оба вставляют одни и те же слоты.

### Последствия

В UI репетитора появляются дублирующиеся уроки в расписании на 3 месяца вперёд. Удаление вручную трудоёмко. Финансовая статистика (выручка, кол-во занятий) задваивается.

### Предлагаемое исправление

```ts
// before
export const processRecurringLessons = async () => {
  // ...findMany + createMany без guard
};

// after — module-level флаг как в backup.ts
let recurringRunning = false;

export const processRecurringLessons = async () => {
  if (recurringRunning) return;
  recurringRunning = true;
  try {
    await prisma.$transaction(async (tx) => {
      // findMany + createMany через tx
    });
  } finally {
    recurringRunning = false;
  }
};
```

И второй уровень защиты — `@@unique([tutorId, startTime])` в схеме + `createMany({ skipDuplicates: true })`.

### Почему это не false positive

Сравнил с `backup.ts:191-199` (там `backupRunning` есть). Тест `recurringLessons.test.ts` запускает функцию последовательно, параллельный сценарий не покрыт. Cron-расписание + рестарты делают сценарий вполне реальным.

## 9. `scheduleRemindersForLesson` — TOCTOU при создании напоминаний приводит к дубликатам push

- **Severity:** High
- **Файл:** `backend/src/services/reminderScheduler.ts:38-53`
- **Категория:** Real-time / Data Integrity

### Описание

Идемпотентная защита читает существующие `PENDING`-записи через `findMany`, формирует `Set` интервалов, фильтрует новые, затем выполняет `createMany`. Эти две операции **не** обёрнуты в транзакцию. При параллельном вызове (быстрый повторный submit `updateLesson`, одновременный cron-тик recurring + ручной update) оба прочитают пустой `Set` и оба выполнят `createMany` — в БД появятся дубли `(lessonId, intervalMinutes, status=PENDING)`.

В схеме `ScheduledReminder` нет `@@unique([lessonId, intervalMinutes, status])`, а `processScheduledReminders` не дедуплицирует — оба дубля будут отправлены пользователю.

### Воспроизведение

Пользователь дважды нажимает «Сохранить» при редактировании урока. Оба запроса проходят `cancelRemindersForLesson` + `scheduleRemindersForLesson`. Второй читает `existingIntervals` до того, как первый вставил строки → оба создают записи. Пользователь получает два идентичных push о том же уроке.

### Последствия

Дублирующиеся push-уведомления — UX-дефект. При большом числе пользователей — лишняя нагрузка на web-push провайдера и негативное влияние на пользовательский опыт PWA.

### Предлагаемое исправление

```ts
// before — два отдельных запроса
const existing = await prisma.scheduledReminder.findMany({ ... });
const existingIntervals = new Set(existing.map((r) => r.intervalMinutes));
const newReminders = reminders.filter((r) => !existingIntervals.has(r.intervalMinutes));
await prisma.scheduledReminder.createMany({ data: newReminders });

// after — атомарно + skipDuplicates с unique-индексом
await prisma.$transaction(async (tx) => {
  const existing = await tx.scheduledReminder.findMany({ ... });
  const existingIntervals = new Set(existing.map((r) => r.intervalMinutes));
  const newReminders = reminders.filter((r) => !existingIntervals.has(r.intervalMinutes));
  if (newReminders.length > 0) {
    await tx.scheduledReminder.createMany({ data: newReminders, skipDuplicates: true });
  }
});
```

И добавить в схему `@@unique([lessonId, intervalMinutes, status])`.

## 10. Гонка в `lesson-cancellation.model.ts` — диалог отмены показывает финансовые данные чужого урока

- **Severity:** High
- **Файл:** `frontend/src/features/lessons/models/lesson-cancellation.model.ts:37-74`
- **Категория:** Frontend Effector

### Описание

`lessonCancelRequested` одновременно пишет урок в `$cancellingLesson` и запускает `getCancellationInfoFx`. Нет защиты от конкурентных вызовов эффекта (ни `filter` по `pending`, ни сопоставление ответа с параметром через `params`). Второй sample на `getCancellationInfoFx.done` читает `$cancellationInfo` через `source` корректно для одного запроса, но при двух параллельных к моменту прихода первого (медленного) ответа `$cancellingLesson` уже содержит второй урок — диалог открывается с rasmismatched данными.

### Воспроизведение

Пользователь нажимает «Отменить» на уроке A (медленный API-ответ), затем быстро — на уроке B. Ответ для A приходит после B. `$cancellingLesson = B`, `$cancellationInfo = info_A` (с суммой переноса оплаты урока A). Диалог открывается с данными о переводе оплаты урока A для урока B. После подтверждения отменяется урок B с информацией о платеже урока A.

### Последствия

Пользователь принимает финансовое решение об отмене на основе **неверной** информации (сумма перевода, дата перевода оплаты). В tutor-приложении это прямой риск денежной ошибки.

### Предлагаемое исправление

Предпочтительный вариант — связать ответ с параметром через `params`:

```ts
// before
sample({
  clock: lessonCancelRequested,
  fn: (lesson) => lesson.id,
  target: getCancellationInfoFx,
});

// after — игнорировать ответ, не соответствующий текущему урока
sample({
  clock: getCancellationInfoFx.done,
  source: $cancellingLesson,
  filter: (cancellingLesson, { params }) => cancellingLesson?.id === params,
  fn: (_, { result }) => result,
  target: $cancellationInfo,
});
```

Альтернатива — не запускать новый запрос пока идёт предыдущий:

```ts
sample({
  clock: lessonCancelRequested,
  source: getCancellationInfoFx.pending,
  filter: (pending) => !pending,
  fn: (_, lesson) => lesson.id,
  target: getCancellationInfoFx,
});
```

### Почему это не false positive

Тесты `lesson-cancellation.model.test.ts` не покрывают сценарий двойного параллельного вызова. Тест «ID-aware cleanup» проверяет `updateLessonFx`, не `getCancellationInfoFx`. Сценарий двойного клика на медленном соединении вполне реален.
