## Резюме

Найдено три критических бага: хардкоженный дефолт `SCREEN_SECRET` позволяет любому пользователю генерировать валидные screen-токены и перезаписывать чужие скриншоты; create-recurring-lessons имеет TOCTOU между проверкой конфликтов и `createMany` без транзакции и без уникального индекса (двойной клик/ретрай создаёт дубли всей серии уроков); и `reminderSettings` использует паттерн `findUnique → create` вместо `upsert`, из-за чего параллельные первые запросы (две вкладки) роняют сервер с 500 на P2002. ## 1. Хардкоженный дефолтный `SCREEN_SECRET` — любой пользователь может перезаписать чужой скриншот

- **Severity:** Critical
- **Файл:** `backend/src/controllers/screen/helpers.ts:3`
- **Категория:** Backend Auth/Security

### Описание

`SCREEN_SECRET` объявлен с дефолтным значением `"screen-monitoring-secret-key"` через `||`-fallback. Эта переменная отсутствует в `.env.example`, и при отсутствии переменной окружения на проде токены подписываются публично известным ключом. В отличие от `JWT_SECRET` и `ADMIN_JWT_SECRET` в `utils/auth.ts`, где при отсутствии env бросается ошибка на старте, здесь молча используется слабый дефолт.

Формат токена детерминирован: `${userId}.${HMAC_SHA256(userId, SCREEN_SECRET).slice(0,16)}`. Атакующий, знающий формат, легко вычисляет валидный токен для любого `userId`.

### Воспроизведение

1. Знать любой `userId` (UUID) пользователя в системе.
2. Локально выполнить `crypto.createHmac("sha256", "screen-monitoring-secret-key").update(userId).digest("hex").slice(0, 16)`.
3. Выполнить `POST /api/screen/upload` с заголовком `x-screen-token: ${userId}.${signature}` и любым изображением.

### Последствия

Атакующий перезаписывает файл `uploads/screens/{userId}.jpg` любого пользователя. Через WebSocket-broadcast `screen_updated` жертва (и её супервизор) получают подставное изображение. Полный обход authn для этого эндпоинта.

### Предлагаемое исправление

```ts
// before
const SCREEN_SECRET = process.env.SCREEN_SECRET || "screen-monitoring-secret-key";

// after
const SCREEN_SECRET = process.env.SCREEN_SECRET;
if (!SCREEN_SECRET) {
  throw new Error("SCREEN_SECRET is not set");
}
```

И добавить `SCREEN_SECRET=` в `backend/.env.example`. Дополнительно — заменить `signature !== expected` в `verifyScreenToken` на `crypto.timingSafeEqual` (HMAC-сравнения должны быть constant-time).

### Почему это не false positive

Подтверждено `grep` по `helpers.ts:3` — fallback на хардкод. Подтверждено отсутствие `SCREEN_SECRET` в `backend/.env.example`. Подтверждено сравнением с `utils/auth.ts`, где `JWT_SECRET` бросает ошибку при отсутствии — это намерение авторов проекта, а в `helpers.ts` оно нарушено.

## 2. `createRecurringLessons` — TOCTOU между проверкой конфликтов и `createManyAndReturn` создаёт дубли уроков

- **Severity:** Critical
- **Файл:** `backend/src/controllers/lessons/createLesson.ts:112-153`
- **Категория:** Backend services / Data integrity

### Описание

В `createRecurringLessons` для каждой недели последовательно выполняется `checkSchedulingConflicts` (отдельный `SELECT` без блокировки), затем после цикла — `prisma.lesson.createManyAndReturn`. Вся последовательность не обёрнута в `prisma.$transaction`, и в БД нет уникального составного индекса на `(tutorId, startTime)` (см. `backend/prisma/schema.prisma`). Два параллельных HTTP-запроса (двойной клик на фронте, ретрай по таймауту, повторный запрос пользователя) оба пройдут все `checkSchedulingConflicts` и оба вызовут `createManyAndReturn` — в БД окажутся две идентичные серии уроков на одни и те же временные слоты.

### Воспроизведение

1. Тьютор нажимает "Создать регулярный урок" (≈13 уроков на 3 месяца).
2. Запрос медленно обрабатывается, пользователь нажимает кнопку второй раз (или фронт делает retry при таймауте).
3. Оба запроса проходят проверки конфликтов одновременно (никаких ещё нет в БД).
4. Оба `createManyAndReturn` создают по 13 уроков → в БД 26 уроков, по два на каждую неделю на один и тот же слот.

### Последствия

Дублирующие уроки на одно и то же время в расписании репетитора. Пользователь видит задвоенные уроки, статистика занятий и платежей дублируется, рекуррентные напоминания планируются дважды. Удалить дубли вручную сложно — они идентичны по полям и неотличимы визуально.

### Предлагаемое исправление

```ts
// before — checkSchedulingConflicts внутри for-цикла, затем createManyAndReturn вне транзакции
for (const week of weeks) {
  await checkSchedulingConflicts(...);
  lessons.push(...);
}
const createdLessons = await prisma.lesson.createManyAndReturn({ data: lessons });

// after — атомарно: пере-проверка + вставка в одной транзакции
const createdLessons = await prisma.$transaction(async (tx) => {
  for (const l of lessons) {
    const conflict = await tx.lesson.findFirst({
      where: {
        tutorId: userId,
        status: { not: "CANCELLED" },
        startTime: { lt: l.endTime },
        endTime: { gt: l.startTime },
      },
    });
    if (conflict) {
      const err = new Error("Конфликт расписания");
      (err as Error & { statusCode: number }).statusCode = 409;
      throw err;
    }
  }
  return tx.lesson.createManyAndReturn({ data: lessons });
});
```

Долгосрочно — добавить `@@unique([tutorId, startTime])` в `schema.prisma` (если бизнес-логика это допускает) и `skipDuplicates: true` в `createMany` для абсолютной идемпотентности.

### Почему это не false positive

В `backend/prisma/schema.prisma` нет уникального индекса на `(tutorId, startTime)`. В `backend/src/controllers/lessons/__tests__/createLesson.test.ts` нет теста с двумя параллельными запросами. Параллельный сценарий легко воспроизводится при ретрае фронта или двойном клике; без транзакции и индекса гонка реальна.

## 3. `reminderSettings`: `findUnique + create` вместо `upsert` — 500 при двух параллельных первых запросах

- **Severity:** Critical
- **Файл:** `backend/src/controllers/reminderSettings/getReminderSettings.ts:9-23` и `backend/src/controllers/reminderSettings/updateReminderSettings.ts:44-57`
- **Категория:** Backend services / Race condition

### Описание

Оба эндпоинта используют паттерн "если `findUnique` вернул `null` — `create`". Поле `ReminderSettings.userId` имеет `@unique` ограничение (`schema.prisma:164`). При двух одновременных первых запросах (две открытые вкладки приложения, мобильный + десктоп, refresh во время загрузки) оба читают `null`, оба вызывают `create` — второй получает Prisma `P2002` (unique constraint violation), которая не обработана в `catch` и выливается в 500 `"Внутренняя ошибка сервера"`.

### Воспроизведение

1. Пользователь, у которого ещё нет записи в `reminder_settings`, открывает приложение.
2. Открывает вторую вкладку до того, как первая успела отрисоваться.
3. Обе вкладки при инициализации параллельно вызывают `GET /api/reminder-settings`.
4. Один из запросов получает 500.

### Последствия

Пользователь, открывший приложение в нескольких вкладках при первом входе, получает ошибку сервера на одной из них. Запросов от уже существующих пользователей это не затрагивает, но новый пользователь может встретить ошибку на старте.

### Предлагаемое исправление

```ts
// before
let settings = await prisma.reminderSettings.findUnique({ where: { userId: userId! } });
if (!settings) {
  settings = await prisma.reminderSettings.create({
    data: { userId: userId!, enabled: false, intervals: [], muteWhenInLesson: false },
  });
}

// after
const settings = await prisma.reminderSettings.upsert({
  where: { userId: userId! },
  update: {},
  create: { userId: userId!, enabled: false, intervals: [], muteWhenInLesson: false },
});
```

Аналогично заменить в `updateReminderSettings.ts` (но там `update` уже идёт после, поэтому достаточно `upsert` сразу с финальными полями).

### Почему это не false positive

Подтверждено чтением обоих файлов: `prisma.reminderSettings.create` без обработки P2002. `userId` объявлен `@unique` в `schema.prisma:164`. Тесты `backend/src/__tests__/reminderSettings.test.ts` сбрасывают данные через `deleteMany`, но не симулируют параллельные запросы.

## 4. `price: price || student.hourlyRate` — `0` молча подменяется на `hourlyRate`

- **Severity:** High
- **Файл:** `backend/src/controllers/lessons/createLesson.ts:58` и `:127` (для рекуррентных)
- **Категория:** Data integrity / Финансы

### Описание

Логический оператор `||` считает `0` falsy, поэтому `price: price || student.hourlyRate` при намеренной цене `0` (пробный урок, благотворительное занятие) сохраняет `hourlyRate` студента вместо нуля. Валидаторы (`controllers/lessons/validators.ts`) не запрещают `price: 0`, то есть `0` рассматривается как валидный ввод. Та же ошибка повторяется в `createRecurringLessons`.

### Воспроизведение

1. Тьютор создаёт урок и явно указывает `price: 0` (бесплатный пробный).
2. У студента задан `hourlyRate: 1500`.
3. В БД сохраняется `price: 1500`.
4. В статистике этот урок учитывается как платный 1500 ₽.

### Последствия

Бесплатные/пробные уроки молча учитываются как платные по полной ставке. Доходная статистика, расчёты задолженности (`unpaidDebt`) и налогов (`taxAmount` в `getStatistics.ts`) завышены.

### Предлагаемое исправление

```ts
// before
price: price || student.hourlyRate,

// after
price: price !== undefined && price !== null ? price : student.hourlyRate ?? null,
```

Применить и в `createSingleLesson` (строка 58), и в `createRecurringLessons` (строка 127). Также добавить регрессионный тест: `price: 0 → DB.price === 0`.

### Почему это не false positive

Существующий тест в `createLesson.test.ts:190` ожидает значение `500` (hourlyRate) при входе `price: 0` — то есть тест зафиксировал баг как ожидаемое поведение. Валидатор не запрещает `0`. Сценарий "пробный бесплатный урок" реален для рынка частных репетиторов.

## 5. WebSocketManager: `sendWelcomeMessage` вызывается до регистрации `on("close")`/`on("error")` — мёртвый сокет остаётся в `clients`

- **Severity:** High
- **Файл:** `backend/src/lib/websocket/WebSocketManager.ts:41-75`
- **Категория:** Real-time / Resource leak

### Описание

В `handleConnection` порядок операций таков: (1) `this.clients.set(decoded.userId, ws)`, (2) `sendWelcomeMessage(ws, decoded.userId)` — вызывает `ws.send(...)` синхронно, (3) только после этого регистрируются обработчики `ws.on("close")` и `ws.on("error")`. Если между шагом (1) и (2) сокет уже закрылся (клиент с нестабильной сетью разорвал TCP сразу после WS handshake), `ws.send()` в библиотеке `ws@8.x` бросает синхронное исключение `Error: The socket is not open`. Исключение уходит из `handleConnection` — обработчики `close`/`error` так и не регистрируются, запись в `this.clients` остаётся навсегда.

### Воспроизведение

1. Клиент устанавливает WebSocket-соединение с валидным JWT.
2. Сразу после успешного handshake (до получения welcome-сообщения) теряет сеть/закрывает приложение → сокет переходит в `CLOSING`/`CLOSED`.
3. Сервер вызывает `sendWelcomeMessage` → `ws.send` бросает → handlers не зарегистрированы.
4. `this.clients.get(userId)` указывает на закрытый сокет; `getConnectedUsersCount()` показывает +1.

### Последствия

Постепенная утечка памяти при высокой частоте reconnect (нестабильный мобильный интернет). Метрика количества подключённых пользователей завышена. Частично спасает identity-check при следующем подключении того же пользователя (`previous.close()` вызывается на мёртвом сокете и провоцирует cleanup), но при отсутствии повторного входа запись висит вечно.

### Предлагаемое исправление

```ts
// before
this.clients.set(decoded.userId, ws);
sendWelcomeMessage(ws, decoded.userId);   // может бросить — handlers ниже не зарегистрируются
ws.on("close", () => { ... });
ws.on("error", () => { ... });
ws.on("message", () => { ... });

// after
this.clients.set(decoded.userId, ws);
ws.on("close", () => { ... });
ws.on("error", () => { ... });
ws.on("message", () => { ... });
if (ws.readyState === WebSocket.OPEN) {
  try {
    sendWelcomeMessage(ws, decoded.userId);
  } catch (error) {
    console.error("Failed to send welcome message:", error);
  }
}
```

### Почему это не false positive

Прочитал `WebSocketManager.ts:41-75` — порядок действительно: `set → sendWelcomeMessage → on("close")`. Документация `ws@8.x` подтверждает, что `socket.send()` без callback бросает синхронно при закрытом сокете. Тесты `WebSocketManager.test.ts` мокают `ws.send` без поведения throw — сценарий не покрыт. Этот баг отличен от уже исправленного "stale close-handler" (#2 в первом отчёте от 2026-05-09).

## 6. Cron-задачи без опции `timezone` — срабатывают по UTC, не по московскому времени

- **Severity:** High
- **Файл:** `backend/src/index.ts:86, 95, 103, 111`
- **Категория:** Real-time / Cron / Operations

### Описание

`node-cron@4.x` без явной опции `timezone` использует системный TZ процесса. На VPS под Linux по умолчанию настроен UTC (в `.env.example` нет `TZ=`, в скриптах деплоя нет принудительной установки). Задача `cron.schedule("0 2 * * *", ...)` (рекуррентные уроки, daily 2 AM) ожидаемо должна выполняться в 02:00 по Москве — но фактически срабатывает в 02:00 UTC = 05:00 MSK. То же для остальных трёх cron-выражений.

### Воспроизведение

1. Деплой на VPS с системным `TZ=UTC` (стандартная конфигурация).
2. Проверить: `ssh root@31.207.74.174 'date && timedatectl'` → покажет UTC.
3. Cron `"0 2 * * *"` запускается, когда в Москве 05:00.

### Последствия

Генерация рекуррентных уроков и другие "ночные" задачи происходят в раннее утро по Москве, во время потенциального пользовательского трафика. Не критично для данных, но нарушает заявленное поведение и может приводить к видимым "перестроениям" расписания у первых утренних пользователей.

### Предлагаемое исправление

```ts
// before
cron.schedule("0 2 * * *", async () => { ... });

// after — для всех 4 cron-задач
cron.schedule("0 2 * * *", async () => { ... }, { timezone: "Europe/Moscow" });
```

Альтернативно — задавать `TZ` через env при деплое (`TZ=Europe/Moscow node dist/index.js`), но явная опция в коде надёжнее.

### Почему это не false positive

`node-cron@4.x` поддерживает опцию `timezone` (документация). В `backend/src/index.ts` нет ни одного `timezone:`, ни одной TZ-настройки. В `.env.example` `TZ` отсутствует. Системный timezone VPS не зафиксирован в репозитории.

## 7. `unsubscribePushFx.finally` безусловно отключает push на сервере, даже если отписка в браузере провалилась

- **Severity:** High
- **Файл:** `frontend/src/entities/notifications/notifications-toggle.model.ts:103-107`
- **Категория:** Frontend Effector / State desync

### Описание

Sample подписан на `unsubscribePushFx.finally` (а не `.done`) и безусловно эмитит `settingsUpdated({ enabled: false })`, что через `updateSettingsFx` записывает `enabled: false` в БД сервера. `.finally` срабатывает и при `.done`, и при `.fail`. Если `unsubscribePushFx` упал (Service Worker недоступен, `pushManager.getSubscription()` бросил), сервер всё равно отметит уведомления выключенными, а браузерная push-подписка останется активной — но беспозвучной (сервер не пошлёт пуши).

### Воспроизведение

1. Пользователь авторизован, push-уведомления включены и подписаны (есть запись в `push_subscriptions`).
2. Пользователь выключает тоггл "Уведомления".
3. `unsubscribePushFx` падает (например, SW deregistered, browser quirk).
4. `unsubscribePushFx.finally` → `settingsUpdated({ enabled: false })` → `updateSettingsFx` → в БД `enabled = false`.
5. Push-подписка в браузере жива, но сервер пуши больше не шлёт.

### Последствия

Необратимая рассинхронизация: пользователь больше не получает напоминания об уроках, в UI тоггл выключен, но "включить заново" может не сработать корректно (подписка в браузере уже есть, новые попытки `subscribe` могут не пересоздать запись на сервере). Бесшумная потеря функциональности напоминаний.

### Предлагаемое исправление

```ts
// before
sample({
  clock: unsubscribePushFx.finally,
  fn: () => ({ enabled: false } as Partial<ReminderSettings>),
  target: settingsUpdated,
});

// after
sample({
  clock: unsubscribePushFx.done,
  fn: () => ({ enabled: false } as Partial<ReminderSettings>),
  target: settingsUpdated,
});

sample({
  clock: unsubscribePushFx.fail,
  fn: () => ({ message: "Не удалось отписаться от уведомлений", type: "error" as const }),
  target: showNotification,
});
```

### Почему это не false positive

Подтверждено чтением `notifications-toggle.model.ts:103-107` — действительно `.finally`. В Effector `.finally` срабатывает и при `done`, и при `fail`. Тест `notifications.model.test.ts` покрывает только success-сценарий (line ~117). Сценарий с `.fail` не тестируется.

## 8. WeeklyView: `dayKey` без года — уроки разных лет на одну дату объединяются в одну группу

- **Severity:** High
- **Файл:** `frontend/src/features/lessons/ui/LessonsList/components/WeeklyView/WeeklyView.tsx:21-24`
- **Категория:** Frontend React/UI / Data presentation

### Описание

`dayKey` формируется через `date.toLocaleDateString("ru-RU", { weekday: "long", day: "numeric", month: "long" })` — без `year`. Полученные строки вида `"понедельник, 5 мая"` используются как ключ объекта в `groupLessonsByDay`. Если в выборке `filteredLessons` присутствуют уроки из разных лет с одинаковым числом и месяцем (например, 5 мая 2025 и 5 мая 2026), они попадают в одну группу. `key={day}` в JSX становится неуникальным, React может неправильно переиспользовать DOM-узлы.

### Воспроизведение

1. Открыть вкладку "Прошедшие" с недельным режимом.
2. Иметь регулярные уроки на протяжении 1+ года (например, по понедельникам).
3. Без жёсткого date-фильтра выборка содержит уроки 5 мая 2025 и 5 мая 2026.
4. Оба урока показаны под одним заголовком "понедельник, 5 мая".

### Последствия

Уроки разных лет смешиваются в одной "дневной" группе с одним заголовком, без указания года. Пользователь видит некорректное расписание; неуникальный React `key` может приводить к stale-DOM при изменениях.

```ts
// before
const dayKey = date.toLocaleDateString("ru-RU", {
  weekday: "long",
  day: "numeric",
  month: "long",
});

// after
const dayKey = date.toLocaleDateString("ru-RU", {
  weekday: "long",
  day: "numeric",
  month: "long",
  year: "numeric",
});
```

### Почему это не false positive

Прочитал `WeeklyView.tsx:15-30` — действительно нет `year` в `toLocaleDateString`. Тест `WeeklyView.test.tsx` (если есть) не покрывает межгодовой кейс. Для тьютора с многолетней историей сценарий легко воспроизводится на вкладке "Прошедшие".

## 9. `$isAuthenticated` как `clock` в login/register form моделях — неконтекстная навигация и двойной `navigate("/")`

- **Severity:** High
- **Файл:** `frontend/src/features/auth/models/login-form.model.ts:130-134` и `frontend/src/features/auth/models/register-form.model.ts` (аналогичный sample)
- **Категория:** Frontend Effector / Routing

### Описание

В обоих фичах подписка:
```ts
sample({
  clock: userModel.$isAuthenticated,
  filter: (isAuth) => isAuth,
  target: navigateToHomeFx,
});
```
не ограничена ни gate'ом формы, ни проверкой текущего роута. `$isAuthenticated` — это `$user.map(u => u !== null)` — обновляется при любом изменении `$user` (логин, верификация email, обновление профиля). Так как оба модуля подключены глобально и оба содержат идентичную подписку, при переходе `false → true` срабатывают оба `navigateToHomeFx` → `navigate("/", { replace: true })` вызывается дважды независимо.

Дополнительно: после `verifyEmailFx.doneData` на странице `/verify-email` `$user` обновляется → `$isAuthenticated` становится `true` → пользователь перебрасывается на `/`, даже если ожидается другой флоу.

### Воспроизведение

1. Пользователь логинится через форму. `loginFx.doneData` → обновление `$user` → `$isAuthenticated` `false → true`.
2. Оба sample (из `login-form.model.ts` и из `register-form.model.ts`) срабатывают синхронно.
3. `navigate("/")` вызывается дважды.

### Последствия

Двойная навигация при логине (React Router съедает повторный `replace`, но это неправильный дизайн). Если в будущем добавится третья форма с такой же подпиской — будет тройной вызов. Помимо этого — навигация на `/` при верификации email со страницы `/verify-email` срабатывает побочно через тот же триггер, хотя верификация и логин — разные потоки.

### Предлагаемое исправление

Убрать sample по `$isAuthenticated` из обоих feature-моделей. Навигацию вызывать только из эффектов конкретного флоу:

```ts
// in login-form.model.ts — заменить
sample({
  clock: userModel.$isAuthenticated,
  filter: (isAuth) => isAuth,
  target: navigateToHomeFx,
});

// на
sample({
  clock: loginFx.doneData,
  filter: ({ response }) => response.user.isEmailVerified,
  fn: () => undefined,
  target: navigateToHomeFx,
});
```

Аналогично для `register-form.model.ts` — навигацию вызывать только из `registerFx.doneData` с проверкой `isEmailVerified`.

### Почему это не false positive

Прочитал `login-form.model.ts:130-134` — sample подтверждён. Подписки определены на module-level в feature-моделях, которые подключены глобально (импортируются в pages-уровне). `$isAuthenticated` обновляется при любом изменении `$user` (`getProfileFx.doneData`, `loginFx.doneData`, `verifyEmailFx.doneData`, `updateUser`). Тест `login-form.model.test.ts:221` явно пропускает проверку навигации (комментарий `// Navigation happens in the model via userModel.$isAuthenticated / We just verify the user state was updated`) — баг не покрыт.

## 10. `processScheduledReminders`: `findMany` без `take` — атомарно захватывает весь backlog после простоя

- **Severity:** High
- **Файл:** `backend/src/services/reminderProcessor.ts:10-30` (транзакционный `findMany` + `updateMany`)
- **Категория:** Real-time / Cron / Reliability

### Описание

Cron-задача запускается каждую минуту и в одной транзакции делает `findMany({ where: { status: "PENDING", scheduledAt: { lte: now } } })` без `take`, помечает все найденные через `updateMany` как `SENT`, затем обрабатывает по одному (web-push, settings-чек, user-fetch) — 2-3 SQL-запроса на каждый напоминатель. После простоя (deploy, инцидент) накапливается backlog — например, 1000+ просроченных напоминаний за несколько часов. Следующий cron-tick пытается обработать их все разом.

### Воспроизведение

1. Backend недоступен 6 часов (рестарт, миграция, инцидент).
2. За это время в `scheduled_reminders` накопилось 500+ записей со `scheduledAt < now` и `status = "PENDING"`.
3. Сервер поднимается, cron срабатывает в начале минуты.
4. Транзакция атомарно помечает все 500 как `SENT`, затем процесс пытается отправить 500 web-push (с rate-limited провайдером) и сделать 1500+ SQL-запросов в одном tick.

### Последствия

1. Длительный lock в транзакции PostgreSQL.
2. Перегрузка web-push провайдера и сетевого стека.
3. Все 500 напоминаний помечены `SENT` ещё до фактической отправки — если процесс упадёт в середине, часть `SENT` записей не были отправлены, и retry невозможен (статус не вернётся в `PENDING`).
4. Возможный таймаут запроса/health-check, что может привести к рестарту контейнера (PM2/systemd) и зацикливанию проблемы.

### Предлагаемое исправление

```ts
// before
const pending = await tx.scheduledReminder.findMany({
  where: { status: "PENDING", scheduledAt: { lte: now } },
  select: { id: true },
});

// after
const BATCH_SIZE = 100;
const pending = await tx.scheduledReminder.findMany({
  where: { status: "PENDING", scheduledAt: { lte: now } },
  select: { id: true },
  take: BATCH_SIZE,
  orderBy: { scheduledAt: "asc" }, // oldest first
});
```

Так каждый минутный tick обрабатывает не более 100 ремайндеров — backlog рассасывается за несколько минут без перегрузки. Дополнительно стоит подумать о статусе `IN_PROGRESS` (вместо немедленного `SENT`), чтобы при сбое сервера в середине обработки batch вернуть его в `PENDING` через TTL.

### Почему это не false positive

Прочитал `reminderProcessor.ts:10-30` — `findMany` без `take`. Cron interval — каждую минуту (по `index.ts`). Транзакционный `updateMany` помечает все как `SENT` до фактической отправки — подтверждено в строках 22-25. Индекс `@@index([status, scheduledAt])` в `schema.prisma` ускоряет SELECT, но не ограничивает размер. Теста на backlog-сценарий нет.
