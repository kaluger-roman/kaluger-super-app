# Bug Hunt Report — 2026-05-09

**Всего багов:** 10 (Critical: 2, High: 8, Medium: 0, Low: 0)
**Покрытые области:** Auth/Security, Real-time, Backend services/controllers, Data integrity, Frontend Effector, Frontend React/UI

## Резюме

Главные риски — два Critical-уровня в безопасности и инфраструктуре real-time:
сравнение пароля админа в открытом виде и race-condition при WebSocket reconnect, который тихо
выводит активного пользователя из списка получателей live-обновлений. Среди High особенно
выделяются TOCTOU-гонка в кроне обновления статусов уроков (запускается каждую минуту),
финансовая транзакция переноса оплаты вне `prisma.$transaction` и отсутствие any-кейс нормализации
email при регистрации/логине.

## 1. Пароль администратора сравнивается через `===` (открытым текстом)

- **Severity:** Critical
- **Файл:** `backend/src/controllers/admin/login.ts:26`
- **Категория:** Auth/Security

### Описание

Админский пароль читается из переменной окружения `ADMIN_PASSWORD` и сравнивается с
пользовательским вводом через прямое строковое равенство:

```ts
const isPasswordValid = password === adminPassword;
```

Bcrypt не используется (хотя для обычных пользователей `comparePassword` через bcrypt применяется,
см. `backend/src/controllers/auth.ts:114`). Пароль хранится в env как plain-text. Сравнение через `===` также подвержено timing-атаке.

### Воспроизведение

1. Получить `.env`-файл (или CI/CD secrets snapshot, или backup сервера).
2. Прочитать значение `ADMIN_PASSWORD` напрямую — мгновенный логин в `/api/admin/login`.
3. Альтернативно: при отсутствии rate-limit'а (см. баг 4) — bruteforce пароля по таймингу `===`.

### Последствия

Полный admin-доступ: `/api/admin/overview` возвращает агрегированные данные по всей БД (все пользователи,
ученики, уроки, выручка). При компрометации env-файла — мгновенный доступ к данным всех репетиторов.

### Предлагаемое исправление

Хранить хеш пароля и сравнивать через bcrypt:

```ts
// before
const adminPassword = process.env.ADMIN_PASSWORD;
const isPasswordValid = password === adminPassword;

// after
const adminPasswordHash = process.env.ADMIN_PASSWORD_HASH;
if (!adminPasswordHash) return res.status(500).json({ error: "Админ не настроен" });
const isPasswordValid = await comparePassword(password, adminPasswordHash);
```

При генерации хеша использовать `bcrypt.hash(rawPassword, 12)` единоразово и сохранить в env.

### Почему это не false positive

Прочитан `admin/login.ts` целиком (39 строк) — нет обхода или альтернативной ветки. `validators.ts`
проверяет только формат, не выполняет хеширование. `comparePassword` импортируется в файле, но
используется только для regular `auth.ts`, не для admin. Тестов на timing-safe нет.

## 2. WebSocket reconnect: stale close-handler удаляет нового клиента

- **Severity:** Critical
- **Файл:** `backend/src/lib/websocket/WebSocketManager.ts:37-42`
- **Категория:** Real-time

### Описание

При повторном подключении того же `userId` строка 29 перезаписывает `this.clients.set(userId, ws)` новой
ссылкой. Однако close-handler старого WS, зарегистрированный на строке 37, замкнут на `decoded.userId`
через closure и при срабатывании выполняет `this.clients.delete(decoded.userId)` без проверки,
что в Map всё ещё лежит именно тот сокет, к которому он принадлежит. Когда старый сокет наконец
закроется (TCP keepalive timeout, GC браузера, Nginx `proxy_read_timeout`), он удалит из Map
**уже активное новое соединение**.

### Воспроизведение

1. Открыть приложение, авторизоваться. WebSocket подключён к `userId=U`.
2. Имитировать кратковременную потерю сети (мобильный, переключение Wi-Fi). TCP не закрывается мгновенно.
3. Браузер автореконнектится — сервер регистрирует новый ws под тем же `userId=U`, перезаписывая map.
4. Через 30–60 сек старая TCP-сессия закрывается, срабатывает close-handler старого ws → `clients.delete(U)`.
5. Новое соединение остаётся живым, но сервер больше не находит его в `clients` Map.

### Последствия

Тутор подключён к WS, клиент считает соединение живым, но сервер не отправляет ему
`broadcastLessonStatusUpdate` (строки 81–86 не находят его в Map). Live-обновления статусов уроков
(IN_PROGRESS, COMPLETED от cron) **молча теряются** до полной перезагрузки страницы.

### Предлагаемое исправление

Проверять в close- и error-handler, что текущий элемент Map ещё совпадает с этим WS:

```ts
// before
ws.on("close", () => {
  this.clients.delete(decoded.userId);
});

// after
ws.on("close", () => {
  if (this.clients.get(decoded.userId) === ws) {
    this.clients.delete(decoded.userId);
  }
});
// аналогично для ws.on("error", ...)
```

Дополнительно — при reconnect закрывать старое соединение явно перед `set`:

```ts
const old = this.clients.get(decoded.userId);
if (old && old !== ws) old.close(4000, "reconnect");
this.clients.set(decoded.userId, ws);
```

### Почему это не false positive

Прочитан `WebSocketManager.ts` целиком. `handleConnection` — единственное место, где регистрируется
close-handler, и он действительно безусловно удаляет ключ. В `__tests__/WebSocketManager.test.ts`
сценария "reconnect одного и того же userId" нет — баг не покрыт регрессией.

## 3. Жёстко прописанные fallback-секреты для JWT в исходниках; разные fallback в REST и WS

- **Severity:** High
- **Файлы:**
  - `backend/src/utils/auth.ts:18,21`
  - `backend/src/lib/websocket/auth.ts:23`
- **Категория:** Auth/Security

### Описание

Три места используют fallback-секреты, **прописанные прямо в исходном коде** (попадает в git/sourcemaps/CI-логи):

```ts
// utils/auth.ts:18
process.env.JWT_SECRET || "fallback-secret-key-jdjdjjdjdjdjdiiiipq";
// utils/auth.ts:21
process.env.ADMIN_JWT_SECRET || "fallback-admin-secret-key-aabbccdd";
// lib/websocket/auth.ts:23
process.env.JWT_SECRET || "fallback-secret";   // <-- ДРУГОЕ значение
```

Если `JWT_SECRET` забыли выставить в env (новый разработчик, кривой деплой) — REST API подписывает
токен одним секретом, а WebSocket-авторизация проверяет тем же секретом, но другим fallback'ом.
Соединения не аутентифицируются. Главное же: значения известны из исходника, любой обладатель кода
может подделать любой JWT и получить доступ к любому `userId`.

### Воспроизведение

1. На стенде без `JWT_SECRET` атакующий подписывает `{ userId: "<любой-id>", email: "x@x" }` ключом
   `"fallback-secret-key-jdjdjjdjdjdjdiiiipq"` через `jwt.sign`.
2. Передаёт токен в `Authorization: Bearer ...` к любому эндпойнту → middleware пропускает.
3. Полный доступ к чужому аккаунту.

### Последствия

Полный обход аутентификации; компрометация всех данных всех пользователей. Дополнительно — REST/WS
рассинхронизация при отсутствующем env.

### Предлагаемое исправление

Запретить fallback и падать при старте, если секрет не задан:

```ts
// utils/auth.ts
const getJwtSecret = (): string => {
  const secret = process.env.JWT_SECRET;
  if (!secret) throw new Error("JWT_SECRET is not set");
  return secret;
};
```

И заменить дублирование в `websocket/auth.ts` на `verifyToken` из `utils/auth.ts`:

```ts
// lib/websocket/auth.ts
import { verifyToken } from "../../utils/auth";
const decoded = verifyToken(token);
if (!decoded) { ws.close(1008, "Authentication failed"); return null; }
```

### Почему это не false positive

Прочитаны оба файла. Действительно три **разных** fallback-значения для двух разных секретов. В тестах не симулируется
отсутствие env, поэтому регрессия скрыта.

## 4. Отсутствие rate limiting на auth-эндпойнтах

- **Severity:** High
- **Файл:** `backend/src/index.ts:24-47`, `backend/src/routes/auth.ts:19-22`, `backend/src/routes/admin.ts`
- **Категория:** Auth/Security

### Описание

Поиск `grep -rn "rateLimit\|express-rate-limit"` по `backend/src/` и `package.json` — **0 совпадений**.
Эндпойнты `/api/auth/login`, `/api/auth/register`, `/api/auth/verify-email`, `/api/auth/resend-verification`,
`/api/admin/login` (строки 19–22 в `routes/auth.ts`, без middleware) принимают неограниченное число запросов в минуту.

### Воспроизведение

- `POST /api/auth/login` — bruteforce пароля любого пользователя.
- `POST /api/admin/login` — особо опасно из-за бага 1 (plain-text сравнение).
- `POST /api/auth/resend-verification` — спам письмами на любой адрес (cooldown реализован только
  для `resendEmailChangeCode`, см. `services/changeEmail.ts`, но не для первичной верификации).

### Последствия

Bruteforce паролей; massive email spam через `resendVerification` (репутация SMTP-домена); DoS на
admin-логин с timing-атакой.

### Предлагаемое исправление

Добавить `express-rate-limit`:

```ts
// index.ts
import rateLimit from "express-rate-limit";
const authLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 20 });
const adminLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 5 });

app.use("/api/auth/login", authLimiter);
app.use("/api/auth/register", authLimiter);
app.use("/api/auth/resend-verification", authLimiter);
app.use("/api/admin/login", adminLimiter);
```

### Почему это не false positive

Подтверждено grep'ом: ни импорта, ни middleware. `routes/auth.ts` показывает прямое навешивание
контроллеров без обёртки. Cooldown в `resendEmailChangeCode` — единственное похожее по смыслу место.

## 5. Login и Register принимают email без `.toLowerCase()` — дубликаты аккаунтов

- **Severity:** High
- **Файл:** `backend/src/controllers/auth.ts:42-44, 55-57, 105-107`
- **Категория:** Auth/Security / Data integrity

### Описание

В `register` и `login` email читается из `req.body` и используется как есть для `findUnique` и
`create`. PostgreSQL колонка `User.email` объявлена как `String @unique` (`schema.prisma:18`) —
без `@db.Citext` — то есть **case-sensitive**. `validateEmail` в `utils/auth.ts:56-59` проверяет
только формат, не нормализует.

### Воспроизведение

1. Пользователь регистрируется с `User@Example.com` → создаётся аккаунт A.
2. Другой посетитель регистрируется с `user@example.com` → `findUnique` не находит совпадения
   (разный регистр) → создаётся аккаунт B (дубль того же email-адреса).
3. Первый пользователь пытается войти, вводит `user@example.com` → 401, потому что хранится
   `User@Example.com`.

### Последствия

Дубликаты пользователей; невозможность войти после изменения регистра адреса; данные репетитора
могут оказаться разделены между двумя аккаунтами.

### Предлагаемое исправление

Нормализовать email при входе/регистрации (и в верификации/смене email):

```ts
// before
const { email, password, name } = req.body;
const existingUser = await prisma.user.findUnique({ where: { email } });

// after
const email = (req.body.email ?? "").trim().toLowerCase();
const existingUser = await prisma.user.findUnique({ where: { email } });
```

Аналогично в `login`, `verifyEmail`, `resendVerification`, `changeEmail`. Для существующих записей —
миграция, приводящая `email` к нижнему регистру (с разрешением конфликтов вручную).

### Почему это не false positive

Прочитан `controllers/auth.ts` (строки 21–144) — нет нормализации. `grep -rn toLowerCase backend/src/controllers`
не находит ни одного применения к email. В `schema.prisma:18` нет `@db.Citext`. В `utils/auth.ts:56-59` — только формат.

## 6. updateLesson: перенос оплаты на следующий урок выполняется вне транзакции

- **Severity:** High
- **Файл:** `backend/src/controllers/lessons/updateLesson.ts:140-158`
- **Категория:** Backend services/controllers / Data integrity

### Описание

При отмене оплаченного урока выполняются две независимые операции **вне** `prisma.$transaction`:

1. `prisma.lesson.update(nextLesson, { isPaid: true, paymentDate })` (строки 148–151) — пометить
   следующий урок как оплаченный.
2. `prisma.lesson.update(currentLesson, dataToUpdate)` (строка 158) — пометить текущий как
   `isPaid: false` и обновить статус `CANCELLED`.

Если процесс упадёт между этими двумя update (OOM, deploy, потеря соединения с БД), `nextLesson`
останется оплаченным, а `existingLesson.isPaid` тоже останется `true`. Один платёж попадёт в два урока.

### Воспроизведение

1. Урок A в статусе SCHEDULED, `isPaid: true`, `paymentDate: 2026-05-01`.
2. Урок B (следующий неоплаченный) того же ученика.
3. `PUT /api/lessons/A` с `status: "CANCELLED"`.
4. Сервер выполняет update B (`isPaid: true`), затем падает до update A.
5. Перезапуск. Оба урока имеют `isPaid: true` для одного платежа.

### Последствия

Финансовые данные искажены: статистика и `paymentsSummary` (см. `getLessons.ts:144-148`) считают
сумму дважды, либо репетитор недополучает уведомление о долге.

### Предлагаемое исправление

Обернуть оба update в одну транзакцию:

```ts
// before
if (nextLesson) {
  await prisma.lesson.update({
    where: { id: nextLesson.id },
    data: { isPaid: true, paymentDate: existingLesson.paymentDate },
  });
}
dataToUpdate.isPaid = false;
delete dataToUpdate.paymentDate;
const lesson = await prisma.lesson.update({ where: { id }, data: dataToUpdate, include: ... });

// after
const lesson = await prisma.$transaction(async (tx) => {
  if (nextLesson) {
    await tx.lesson.update({
      where: { id: nextLesson.id },
      data: { isPaid: true, paymentDate: existingLesson.paymentDate },
    });
  }
  dataToUpdate.isPaid = false;
  delete dataToUpdate.paymentDate;
  return tx.lesson.update({ where: { id }, data: dataToUpdate, include: ... });
});
```

### Почему это не false positive

Прочитан `updateLesson.ts:140-162`. Оба `prisma.lesson.update` — на верхнем `prisma`, не на `tx`.
В `recurringHelpers.ts` (например `shiftFutureRecurringLessons`) транзакции применяются — то есть в
проекте уже есть привычный паттерн, и его пропуск тут — настоящий пропуск, а не намеренный выбор.
Тест `updateLesson.test.ts` не покрывает сценарий crash-between-updates.

## 7. lessonStatusUpdater: TOCTOU-гонка между findMany и update без проверки текущего статуса

- **Severity:** High
- **Файл:** `backend/src/services/lessonStatusUpdater.ts:11-62`
- **Категория:** Real-time / Data integrity

### Описание

Cron каждую минуту (`index.ts:95`) делает `findMany` для уроков, статус которых нужно обновить, а
затем в цикле `for (const lesson of lessonsToStart) ... await prisma.lesson.update({ where: { id }, ... })`
обновляет каждую запись **без проверки текущего статуса в `where`**. Между моментом `findMany`
(время T0) и `update` (время T1, до 60 сек на больших выборках) пользователь может через API
вручную изменить статус урока (например, в `CANCELLED`), и cron перетрёт это значение.

Дополнительно: cron не блокирует параллельные запуски. Если предыдущий тик не успел завершиться за
минуту, следующий стартует поверх — две одновременные итерации обновляют одни и те же записи.

### Воспроизведение

1. Урок A, статус `SCHEDULED`, `startTime` ровно сейчас.
2. Cron-тик стартует в 12:00:00, делает `findMany`, получает A в `lessonsToStart`.
3. В 12:00:30 пользователь через `PUT /api/lessons/A { status: "CANCELLED" }` отменяет урок.
4. В 12:00:45 cron в цикле выполняет `update({ where: { id: A.id }, data: { status: "IN_PROGRESS" } })`
   — перезаписывает только что выставленный `CANCELLED`.

### Последствия

Отменённые уроки переходят в `IN_PROGRESS` или `COMPLETED`, WebSocket рассылает фронту неверный
статус, статистика искажена. Пользователь видит "восстановившийся" урок без видимой причины.

### Предлагаемое исправление

Добавить условие на текущий статус прямо в `update`:

```ts
// before
await prisma.lesson.update({
  where: { id: lesson.id },
  data: { status: "IN_PROGRESS" },
});

// after
const result = await prisma.lesson.updateMany({
  where: { id: lesson.id, status: { in: ["SCHEDULED", "RESCHEDULED"] } },
  data: { status: "IN_PROGRESS" },
});
if (result.count === 0) continue; // статус успели изменить — broadcast не делаем
```

Аналогично для `lessonsToComplete` — `where: { id, status: { in: [...] } }`. Дополнительно — рассмотреть
advisory-lock на старте cron, чтобы избежать параллельных тиков.

### Почему это не false positive

Прочитан `lessonStatusUpdater.ts` целиком. На строках 35-37 и 50-52 в `where` только `id`, без
ограничения по статусу. Cron стартует каждую минуту (`index.ts:95-101`) без флага `noOverlap`.

## 8. getLessons: parseInt без radix и без NaN-fallback → возврат всех записей

- **Severity:** High
- **Файл:** `backend/src/controllers/lessons/getLessons.ts:28-30`
- **Категория:** Backend services/controllers / Data integrity

### Описание

```ts
const pageNum = parseInt(page as string);
const limitNum = parseInt(limit as string);
const skip = (pageNum - 1) * limitNum;
```

Если query-параметры `page=abc` или `limit=xyz` (любые непарсимые строки), `parseInt("abc")` вернёт
`NaN`. Тогда `skip = NaN`, `take = NaN`. Prisma при `take: NaN` интерпретирует значение как
отсутствующее и возвращает **все совпадающие записи без пагинации**. Сравните с `controllers/news/getNews.ts:7-8`,
где fallback `|| 1` / `|| 20` корректно защищает от NaN.

### Воспроизведение

`GET /api/lessons?page=abc&limit=xyz` — ответ содержит все уроки текущего пользователя без ограничения.

### Последствия

Утечка производительности: один запрос может вернуть несколько мегабайт данных и нагрузить БД полным
сканом. Также — некорректный JSON-ответ: `pagination.totalPages = Math.ceil(N / NaN) = NaN`.

### Предлагаемое исправление

Защитить fallback'ом и явным radix:

```ts
// before
const pageNum = parseInt(page as string);
const limitNum = parseInt(limit as string);

// after
const pageNum = Math.max(1, parseInt(page as string, 10) || 1);
const limitNum = Math.min(100, Math.max(1, parseInt(limit as string, 10) || 10));
```

### Почему это не false positive

Прочитан `getLessons.ts:7-150`. Fallback `"1"`/`"10"` срабатывает только при отсутствии параметра, не
при невалидном значении. `getNews.ts` в том же проекте делает корректно. Тест-кейса на NaN-входы нет.

## 9. lesson-cancellation: фильтр очистки `$cancellingLesson` не проверяет ID урока

- **Severity:** High
- **Файл:** `frontend/src/features/lessons/models/lesson-cancellation.model.ts:90-98`
- **Категория:** Frontend Effector

### Описание

```ts
sample({
  clock: lessonModel.updateLessonFx.doneData,
  source: $cancellingLesson,
  filter: (cancellingLesson, lesson) => {
    return Boolean(cancellingLesson && lesson.status === "CANCELLED");
  },
  fn: () => null,
  target: [$cancellingLesson, $cancellationInfo],
});
```

`updateLessonFx` — глобальный эффект `lessonModel`. Он вызывается не только при подтверждении
отмены текущего урока, но и в WebSocket-обработчике (`web-socket.model.ts`, строки 112-122) при
`lesson_status_updated` от cron-задачи. Фильтр не проверяет `lesson.id === cancellingLesson.id` —
любой урок, перешедший в `CANCELLED`, обнуляет `$cancellingLesson`.

### Воспроизведение

1. Открыть диалог подтверждения отмены урока A.
2. В этот момент cron на сервере (или другой пользователь — нет, проект one-user-per-tutor, но
   возможно через другую вкладку) переводит **другой** урок B в `CANCELLED`. Сервер шлёт
   WebSocket-событие → фронт вызывает `lessonModel.updateLesson` для B → `updateLessonFx.doneData`
   проходит фильтр (cancellingLesson=A, lesson=B со статусом CANCELLED).
3. `$cancellingLesson` обнуляется в `null`.
4. Пользователь нажимает "Подтвердить" → `lessonCancellationConfirmed` → в sample на строке 76
   `filter: Boolean` ($cancellingLesson=null) возвращает false → API-запрос отмены не уходит.

### Последствия

Молчаливая потеря пользовательского действия: диалог закрывается (через `confirmDialogClosed`), но
урок A не отменён. Никаких ошибок в UI.

### Предлагаемое исправление

```ts
// before
filter: (cancellingLesson, lesson) =>
  Boolean(cancellingLesson && lesson.status === "CANCELLED"),

// after
filter: (cancellingLesson, lesson) =>
  Boolean(
    cancellingLesson &&
    cancellingLesson.id === lesson.id &&
    lesson.status === "CANCELLED"
  ),
```

### Почему это не false positive

Прочитан `lesson-cancellation.model.ts:90-98` и `web-socket.model.ts` — `updateLesson` действительно
вызывается из WS-обработчика для произвольного урока, не только для текущего. Тест
`lesson-cancellation.model.test.ts` сценарий с одновременным открытым диалогом и WS-событием не
покрывает.

## 10. LessonCell рендерит "0" в DOM при `lesson.price === 0`

- **Severity:** High
- **Файл:** `frontend/src/pages/lessons/components/LessonCell/LessonCell.tsx:62`
- **Категория:** Frontend React/UI

### Описание

```tsx
{lesson.price && (
  <Box display="flex" justifyContent="space-between" alignItems="center" mt="auto">
    <Typography variant="caption" fontWeight="bold">{lesson.price}₽</Typography>
    ...
  </Box>
)}
```

Тип `Lesson.price` — `number | undefined` (`shared/types`). Если значение равно `0` (бесплатный урок,
например, пробный или для родственника), выражение `0 && <Box />` возвращает `0`, и React рендерит
текстовый узел `0` непосредственно в карточку урока. Та же проблема есть в `compact`-режиме строки 25
(`{lesson.price ? ... : ""}`) — она корректна, но строка 62 — нет. Аналогичный паттерн с
`student.hourlyRate && ...` также встречается в `StudentInfo.tsx:21`, `StudentCard.tsx:46`,
`StudentSelector.tsx:54`, но там severity ниже.

### Воспроизведение

Создать урок с `price: 0` (или урок для ученика с `hourlyRate=0`). В представлении расписания — в
ячейке появляется "сирота" `0` в нижней части карточки.

### Последствия

Визуальный артефакт: непонятное число "0" в карточке расписания. Для тутора — выглядит как баг
интерфейса, ставит под сомнение корректность отображения других данных.

### Предлагаемое исправление

```tsx
// before
{lesson.price && (
  <Box ...>...</Box>
)}

// after
{lesson.price != null && lesson.price > 0 && (
  <Box ...>...</Box>
)}
```

(Аналогично — `student.hourlyRate != null && student.hourlyRate > 0` в трёх упомянутых местах.)

### Почему это не false positive

Прочитан `LessonCell.tsx` целиком. Строка 62 действительно использует усечённое `&&` без явной
проверки. Тип `Lesson.price?: number` допускает `0`. Тест-кейса на `price=0` ни в `LessonCell.test.tsx`,
ни в соседних компонентах нет.
