## Находки

### 1. Регистрация ученика возвращает 500, но при этом аккаунт уже создан и ссылка погашена

- **Категория:** 🐛 Bug
- **Severity:** Critical
- **Сценарий:** P1.2 / Acceptance #3
- **Файл/место:** `backend/src/services/studentAuth/studentAuth.ts:81-167` (атомарная транзакция → fire-and-forget email → `generateStudentToken` (line 137))
- **Однозначность исправления:** да

#### Шаги
1. В `backend/.env` отсутствует `STUDENT_JWT_SECRET` (или указан, но процесс не перезагружен)
2. Tutor создаёт ссылку → student открывает её → заполняет валидную форму → "Зарегистрироваться"
3. На POST `/api/student-auth/register` сервер возвращает 500 "Внутренняя ошибка сервера"
4. UI остаётся на форме регистрации, ученик думает, что регистрация не удалась

#### Ожидание
Либо ошибка обнаруживается на старте сервера (fail-fast) и регистрация недоступна вообще, либо JWT генерируется ДО ТОГО как `StudentUser` создаётся и invitation помечается USED — чтобы транзакция роллбэкнулась.

#### Реальность
- `StudentUser` создан с валидным паролем
- `StudentInvitation.status = USED`
- `generateStudentToken` бросает `Error("STUDENT_JWT_SECRET is not set")`
- Контроллер ловит исключение → 500
- Ученик не получает токен и не понимает, что он уже зарегистрирован (может попробовать перейти по ссылке ещё раз → "Ссылка недействительна")

#### Скриншот
![5xx after registration](./2026-05-23-029-student-cabinet/screenshots/05-student-registration-form.png)

#### Network / DB
```
POST /api/student-auth/register → 500 {"error":"Внутренняя ошибка сервера"}
SELECT * FROM student_users → 1 row (с verificationCode, hashed password)
SELECT * FROM student_invitations → status=USED, usedAt=now()
```

#### Предлагаемое исправление
1. В `backend/src/index.ts` на boot валидировать наличие `STUDENT_JWT_SECRET` (как для других секретов) — process.exit(1) если не задан.
2. В `registerStudentByInvite` (`services/studentAuth/studentAuth.ts:81-99`) сначала вычислять JWT-пэйлоад (можно даже сгенерировать токен и сразу проверить, что подпись прошла), и только потом запускать `prisma.$transaction` создания `StudentUser`. Альтернатива — обернуть `generateStudentToken` в той же транзакции, но т.к. она не модифицирует БД, проще сделать вызов ДО транзакции.
3. Регрессионный тест: env без `STUDENT_JWT_SECRET` → registerByInvite не должен оставлять "зомби"-аккаунт.

### 2. WebSocket `/ws/student` handshake падает 400 — realtime полностью неработоспособен

- **Категория:** 🐛 Bug
- **Severity:** Critical
- **Сценарий:** P2.4 / FR-031a / SC-010
- **Файл/место:** `backend/src/lib/websocket/WebSocketManager.ts:19-34`
- **Однозначность исправления:** нет (нужно архитектурное решение, как разводить WSS)

#### Шаги
1. Залогиниться как ученик → попасть в кабинет
2. Открыть DevTools → Console: множественные ошибки `WebSocket connection to 'ws://localhost:3001/ws/student?token=...' failed: Error during WebSocket handshake: Unexpected response code: 400`
3. В другой вкладке tutor создаёт урок для ученика
4. Карточка в расписании ученика **не появляется** до ручного клика "Сегодня"

#### Ожидание (FR-031a, SC-010, quickstart 2.4)
Урок появляется в кабинете ученика в течение 5 секунд без перезагрузки.

#### Реальность
- `new WebSocketServer({ server, path: '/ws' })` и `new WebSocketServer({ server, path: '/ws/student' })` оба регистрируют upgrade-listener на одном HTTP-сервере.
- Согласно [ws docs](https://github.com/websockets/ws#multiple-servers-sharing-a-single-https-server), при таком подходе первый WSS при path mismatch вызывает `socket.destroy()` → второй WSS не успевает обработать.
- В консоли также видны ошибки для tutor-WS: `Invalid frame header @ ws://localhost:3001/ws` — то же явление в другую сторону.
- `curl -i -H "Upgrade: websocket"` на `/ws/student` отдаёт `HTTP/1.1 400 Bad Request`.

#### Console
```
WebSocket connection to 'ws://localhost:3001/ws/student?token=...' failed: Error during WebSocket handshake: Unexpected response code: 400
Student WS error: Event
… (повторяется при каждом backoff-реконнекте)
```

#### Предлагаемое исправление
Использовать `noServer: true` для обоих `WebSocketServer` и руками подписаться на единственный `server.on('upgrade', ...)`-listener, направляющий запрос в нужный WSS по `req.url`. Это документированный паттерн самой `ws`. Регрессионный тест: открыть параллельно `/ws` + `/ws/student` с валидными токенами — оба должны коннектиться. Дополнительно: проверить, что существующие `student-broadcast.test.ts` идут не в полную дорожку, а в обходные моки (если так — добавить честный integration test).

### 3. Раздел "Расписание" не делает initial fetch на mount — отображает "уроков нет" даже если они есть

- **Категория:** 🐛 Bug
- **Severity:** High
- **Сценарий:** P2.1 / quickstart 2.1
- **Файл/место:** `frontend/src/features/studentSchedule/models/student-schedule.model.ts:17,61`
- **Однозначность исправления:** да

#### Шаги
1. Залогиниться как ученик с уроками на текущей неделе
2. После авторизации редирект на `/student/cabinet/schedule`
3. Подождать 2 секунды

#### Ожидание
Сетка показывает уроки текущей недели. В сети — `GET /api/student-cabinet/lessons?weekStart=...`.

#### Реальность
- Никакого запроса к `/api/student-cabinet/lessons` не происходит
- Сетка показывает "На этой неделе уроков нет"
- После любого клика по "Сегодня", "Вперёд", "Назад" — запрос летит, уроки появляются

#### Корень
```ts
export const $weekStart = createStore<Date>(getWeekStart(new Date()));
// …
sample({ clock: $weekStart, target: loadLessonsFx });
```

`sample({ clock: store, target: fx })` фейерит на UPDATE стора, а не на initial value. При первом маунте `$weekStart` уже инициализирован и нет апдейта → fetch не происходит.

#### Скриншот
![empty schedule despite lessons](./2026-05-23-029-student-cabinet/screenshots/08-email-verified-empty-schedule.png) — student2 (нет уроков). У student1 с уроками тот же экран сразу после login — пустой, пока не кликнуть.

#### Предлагаемое исправление
Завести `StudentSchedulePageGate` (или использовать существующий, если есть) и добавить:
```ts
sample({
  clock: StudentSchedulePageGate.open,
  source: $weekStart,
  target: loadLessonsFx,
});
```
ИЛИ инициализировать `$weekStart` через `createStore<Date | null>(null)` и `sample` для установки значения на mount — тогда update произойдёт и текущий триггер сработает. Регрессионный тест: при маунте `StudentSchedulePage` — ровно один вызов `loadLessonsFx`.

### 8. localStorage студента и tutor токены сосуществуют — student tab "видит" tutor UI

- **Категория:** ⚠️ UX issue / security
- **Severity:** Medium
- **Сценарий:** Edge isolation
- **Файл/место:** `frontend/src/shared/auth/tokenStorage.ts`, `frontend/src/features/auth/...login model...`
- **Однозначность исправления:** нет (продуктовое решение)

#### Шаги
1. На устройстве сначала залогинился tutor (set `authToken`)
2. Без logout открыта другая вкладка → переключение тумблера на "Ученик" → вход ученика (set `studentToken`)
3. localStorage держит **оба** токена
4. В студентской вкладке открыть `/students` (URL tutor)
5. Загружается **tutor UI** с реальными данными — потому что `authToken` остался валиден

#### Ожидание
При логине ученика очищать `authToken` (и наоборот). Или явный гейт "у меня один активный сеанс на устройство".

#### Реальность
Сосуществование токенов даёт студенту техническую возможность вернуться в tutor-UI через прямой URL — на ноутбуке/телефоне, который ранее использовал преподаватель.

#### Скриншот / Воспроизведение
Воспроизведено через DevTools: localStorage содержит {authToken: …, studentToken: …}, а `GET /students` грузит tutor-список учеников.

#### Предлагаемое исправление
