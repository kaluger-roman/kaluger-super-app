# Делегирование задач

Сохраняем процессы с сабагентами из прежнего workflow. Основной агент — оркестратор:
задаёт область, запускает независимые проверки параллельно, объединяет результаты,
проверяет доказательства и отвечает за итог. Он не заменяет эти этапы собственным
последовательным чтением кода. Небольшие обычные правки вне этих сценариев не требуют
полного набора reviewer-агентов.

## Запуск и контекст

- Передавать checkout, base/ref и diff (включая staged/unstaged/untracked), узкую роль,
  применимые конвенции, ожидаемый результат и ограничения на изменения.
- Для анализа, research, реализации и review выбирать максимальный доступный
  reasoning effort через поддерживаемый параметр инструмента; модель Codex по
  умолчанию наследуется, привязки к Opus/Sonnet/Haiku нет. Если настройка недоступна,
  не заявлять, что effort был изменён. Browser QA и scoring не требуют max effort.
- Независимые задачи запускать одновременно в пределах доступных слотов. Остальные
  держать в очереди и запускать по мере завершения; лимит слотов не отменяет роли.
- Не раздавать всем полную историю чата: передавать минимальные исходные артефакты.
  Reviewer'ам не сообщать заранее выводы других reviewer'ов.
- На реализацию назначать явные границы файлов. Зависимые этапы выполнять после
  проверки результата предшественника. Review/research/scoring — без редактирования;
  browser QA владеет своими страницами и тестовыми данными. Один браузерный сценарий
  не запускать одновременно несколькими агентами в общей вкладке.
- Worker не запускает рекурсивно тот же orchestration skill. Вложенный research или
  review диспетчеризует основной агент: не занимать слот агентом, который только ждёт.
- Ответ worker: роль, статус, findings/артефакты, file/line, trigger/impact/evidence,
  выполненные проверки и непроверенное. Ошибка или недоступный worker — пробел
  покрытия, а не чистый результат. При отсутствии agent tools явно сообщить ограничение.

## Независимые углы code review

Сохраняются девять отдельных reviewer-задач; при малом числе слотов — волнами:

1. Соответствие `AGENTS.md` и конвенциям с точным правилом и его расположением.
2. Очевидные дефекты непосредственно в diff; без предположений о внешнем состоянии.
3. Глубокая логика и инварианты с чтением окружающего кода.
4. Безопасность, права доступа, секреты и утечки данных.
5. Типы, API/CLI/env/JSON-контракты, схемы и миграции.
6. Удалённое поведение: где восстановлен инвариант каждой удалённой защиты/ветки.
7. Вызывающий и вызываемый код: разрывы контрактов между файлами.
8. Wrapper/proxy: реальное делегирование, передача параметров и потерянные операции.
9. Обходные решения и тесты, которые проходят без проверки нужного поведения.

Неприменимая роль возвращает пустой результат с причиной. Основной агент объединяет
кандидатов по первопричине. Каждый кандидат получает независимую scorer-проверку
другим агентом: исходный diff, контекст, воспроизводимость, оценка и обоснование.
Scorer'ы работают параллельными ограниченными пачками; автор находки не подтверждает
её сам. Основной агент перепроверяет спорные выводы, порог и результаты проверок.
В отчёте сохраняются статусы reviewer/scorer задач и реальные пробелы покрытия.

## Другие сценарии

- `bug-hunt`: 7 областей — Effector/model, React/UI, backend, auth/security,
  realtime/cron, данные/Prisma/миграции, обходные решения и ложноположительные тесты.
- `improve-hunt`: 9 областей — UX, design, security, backend performance,
  frontend performance, a11y, DX/code quality, maintainability/observability, workarounds.
- `e2e-hunt`: 8 областей — auth, students, lessons, profile/finance, reports, admin,
  dashboard/news, PWA/realtime. Для запроса одной области — только её worker.
- В hunt-запросах с ограниченной областью исключать неприменимые направления явно;
  bug/improve worker возвращает до пяти обоснованных кандидатов, E2E — до шести journeys.
  Итог: до 10 bug/improvement находок, до 25 E2E journeys. Дедупликация, проверка
  и разрешённая публикация остаются у основного агента.
- `score-issues`: независимые scorer'ы получают пачки по 8 issues и рубрику,
  возвращают JSON с четырьмя баллами и объяснением; основной агент валидирует каждый
  номер/диапазон и пишет через существующий скрипт. Не обрезать значимые доказательства.
- `auto-feature`: отдельные workers для спецификации, mockups, clarify/plan/tasks,
  реализации и browser QA; review — девять ролей выше. Оркестратор проверяет результаты,
  ведёт прогресс, принимает решения и исправляет подтверждённые review/QA находки.
- `auto-bug-fix`: отдельные workers для диагностики, исправления с регрессионным
  тестом и browser QA; review — девять ролей. Review/QA исправления у оркестратора.
- `speckit-plan`: параллельные research workers для независимых неизвестных,
  технологий и интеграций; основной агент собирает решения в согласованный план.

Делегирование не расширяет разрешения на GitHub, Git, деплой или данные. Применяются
режимы draft/report, границы текущей задачи и инструкции соответствующего навыка.
