# E2E Testing Conventions

Stack: Playwright (Chromium). Конфиг: `frontend/playwright.config.ts`. Тесты: `frontend/e2e/**`.

> Краткая шпаргалка с примерами кода — `frontend/e2e/README.md`. Этот документ — правила и обоснования.

## Зачем e2e

E2e — на вершине test pyramid. Они **дорогие** (медленные, flaky, сложно поддерживать), поэтому фокус — на том, что **дешевле никак не поймать**:

- Интеграция всех слоёв (UI ↔ API ↔ DB ↔ обратно) на критичных user journeys.
- Регрессии, которые проходят сквозь несколько модулей и не ловятся unit/integration.
- Smoke: «приложение вообще загружается, логин работает, основной flow проходит».

E2e **не для**:

- Валидации форм, форматирования, расчётов — unit-тесты.
- Бизнес-логики сервисов — backend integration.
- Стилей, цветов, отступов — visual regression (отдельная стратегия с тегом `@visual`).
- Каждой комбинации фильтров/сортировок — один пример достаточно.

Простой фильтр перед написанием e2e: задать два вопроса. (1) «Если это сломается, кто-то заплатит деньгами/временем?» (2) «Можно ли поймать дешевле без браузера?» E2e оправдан, только если на (1) — да, на (2) — нет.

## Два режима

### Functional (основной)

Имитирует journey с функциональными assertion'ами о наблюдаемом состоянии (URL, видимые тексты, появление элемента). Лежат в папках по областям (`auth/`, `students/`, …). Тег `@regression` + area-тег.

E2e **не блокируют PR**. Прогоняются полным сьютом ночью в отдельном CI job — приоритет качество и широта покрытия, а не скорость. Если регрессия найдена утром — фиксится отдельным PR, а не откатывает мердж.

### Visual (`@visual`)

Скриншот-регрессии. Только `expect(page).toHaveScreenshot()`, без функциональных проверок. Лежат в `frontend/e2e/visual/`. Запускаются отдельно (`--grep @visual`). Не смешивать с functional в одном файле — разные стратегии падают и поддерживаются по-разному.

## Test pyramid для проекта

Целевые ориентиры (не строгие SLA):

- **Функциональные e2e** — все `@regression`, прогоняются ночным CI. Нет жёсткого верхнего предела по количеству или времени, но всё, что **дешевле поймать unit/integration-тестом, должно ловиться там**.
- Visual — по необходимости (минимум — главные экраны, дашборд, список уроков, профиль).

Если сюита начинает идти дольше нескольких десятков минут — это сигнал, что часть проверок логически принадлежит на нижний уровень пирамиды (unit/integration), а не что нужно резать e2e. Резать — последняя мера.

## Source of truth для покрытия

Покрытие e2e ведётся **в самих тестах**, не в отдельном `coverage.md`. Имя `test.describe` + теги — это и есть журнал journeys. Команды:

```bash
# Все функциональные journeys (ночной прогон)
npm run test:e2e -- --grep-invert "@draft|@visual"

# По области
npm run test:e2e -- --grep "@auth" --list
```

Что планируется покрыть — описывается в спеках фич (`specs/<NNN>-<feature>/spec.md`, секция «User journeys»). После реализации journeys превращаются в `test.describe(...)`. Параллельный долгоживущий чеклист **не вести** — он протухает.

Инвентаризация пробелов — командой `/e2e-hunt` (раз в спринт или по запросу), отчёты в `docs/e2e-coverage/`.

## Тэг-схема

Каждый `test.describe` обязан иметь:

1. **Один level-тег** — `@regression` | `@visual` | `@draft`
2. **Один area-тег** — `@auth` | `@students` | `@lessons` | `@profile` | `@reports` | `@admin` | `@dashboard` | `@news` | `@pwa`

Возможны несколько area-тегов, если journey пересекает области (редкий случай). `@draft` — временный тег для черновиков `/e2e-check`, исключается из прогонов; убирается после доработки.

## Имена и язык

- `test.describe` — на **русском**, как видит пользователь: `'Создание ученика'`, `'Восстановление пароля'`. Совпадает с journey-формулировкой из спеки.
- `test('...')` — на **русском**, в форме «учитель делает X и видит Y».
- Файл — kebab-case, без префиксов: `create-student.spec.ts`, `forgot-password.spec.ts`.

Это согласуется с общим правилом проекта: error messages и UI на русском, идентификаторы и код — на английском.

## Селекторы

Приоритет (сверху — предпочтительнее):

1. `getByRole('button', { name: 'Сохранить' })`
2. `getByLabel('Email')`
3. `getByText('Ученик создан')`
4. `getByPlaceholder('Введите email')`
5. `data-testid` — только если выше ничего не подходит

**Запрещены:** CSS-классы (`.MuiButton-root`), `nth-child`, XPath, селекторы по auto-сгенерированным классам стилей.

## Тестовые данные

- Стартовое состояние БД — через API (`POST /api/auth/login` + REST для setup), не через UI. UI используется **только** для журналирования journey, который тестируем.
- Изоляция: каждый тест либо создаёт уникальные данные (`student-${Date.now()}-${randomUUID()}`), либо использует Playwright fixture с автоочисткой.
- Авторизованный контекст — через `storageState` в `fixtures/`. Не логиниться через UI в каждом тесте, кроме самого `auth/`-area.
- Не использовать прод-данные. Тесты гоняются на dev-сервере (`npm run dev`) с тестовой БД.

## Page Objects

Применять **только когда** один и тот же экран встречается в 3+ тестах с дублирующейся настройкой. Преждевременная абстракция — главный источник flaky и неподдерживаемой иерархии.

Когда становятся нужны — `frontend/e2e/pages/<Area>Page.ts`, named export класса или функции `createStudentsPage(page)`. **Никаких `export default`** (общая конвенция проекта).

## Стабильность и flakiness

- Использовать `await expect(...).toBeVisible()` вместо `waitForSelector` — встроенный auto-retry умнее.
- Не ставить `waitForTimeout` (магические задержки). Если тест моргает — найти конкретное условие готовности (видимый toast, исчезнувший спиннер, обновлённый URL) и ждать его.
- Тест, упавший один раз и прошедший после ретрая, — это **не** «просто моргнул». Это сигнал, что либо неправильное условие готовности, либо реальная гонка в коде. Разобраться, не глушить.
- Если flaky тест нельзя починить за разумное время — пометить `test.skip` с TODO и issue, не оставлять «иногда падает».

## Линтинг и типы

- TypeScript строгий. Никаких `any` (общая конвенция).
- Названные импорты, никаких `default exports`.
- ESLint и Prettier применяются к `frontend/e2e/**` так же, как к остальному фронту.

## Связанные команды

- **`/e2e-check`** — перед PR анализирует diff vs main, флагует user-facing изменения без e2e и потенциально сломанные тесты, опционально создаёт `*.draft.spec.ts`. Отчёт в `docs/e2e-coverage/checks/`.
- **`/e2e-hunt`** — параллельный обход областей через subagent'ы, инвентаризация journeys, приоритизированный отчёт о пробелах в `docs/e2e-coverage/`.

## Что считать «готовым» для PR с фичей

E2e не блокируют merge — сюита прогоняется ночью. Но перед мерджем фичи (особенно с тегом «user-facing change») автор должен:

1. Если фича добавляет новый user journey — добавить соответствующий e2e с `@regression` + area-тег.
2. Если фича меняет существующий journey — обновить e2e, не добавлять дубликат.
3. Если фича удаляет functionality — удалить мёртвые e2e.
4. `/e2e-check` не сообщает о Critical/High пробелах в покрытии.

Не каждая фича = новый e2e. Косметические правки, рефакторинги, конфиги — не требуют e2e. Главный критерий — изменилось ли наблюдаемое user-facing поведение.
