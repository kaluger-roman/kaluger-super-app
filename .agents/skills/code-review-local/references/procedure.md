## Контекст

Перед выполнением прочитать корневой и применимые вложенные `AGENTS.md`,
`docs/subagents.md` и нужные конвенции. Проверить локальный checkout,
`git status --short --branch`, текущую дату и существующие артефакты этой процедуры.
Работа выполняется на этом Mac; Git — `git -C <checkout>`, окружение —
`docs/dev-stack.md` и `docs/qa-docker.md`.

## Задача

Прогнать code-review **локальных изменений ветки**: девять независимых Codex reviewers, recall-углы и проверка обходных решений, затем независимый scoring 0–100. Внешний code-review plugin не требуется. Контракт — [report.schema.json](report.schema.json); browser/git/state platform notes — [runtime.md](../../auto-feature/references/runtime.md).

1. **Источник diff:** локальный merge-base выбранного `base-ref` и HEAD, committed
   изменения и текущее рабочее дерево, включая релевантные новые файлы. Режим
   `committed | working-tree | mixed` фиксируется для отчёта; наличие коммитов не
   исключает незакоммиченные fixes. Никаких `gh pr diff` и мутаций индекса.
2. **Порог фильтрации настраиваемый:** по умолчанию **50** (а не 80, как в plugin'е). Меняется через `--threshold`.
3. **Вывод структурирован:** машинно-читаемый JSON в `docs/code-reviews/<report-slug>/iter-<N>.json` + краткий человекочитаемый stdout.

Команда предназначена для интеграции в оркестратор `$auto-feature` (в режиме `--silent`), но **полностью самостоятельна** и может вызываться вручную.

## Парсинг аргументов вызова

Аргументы вызова — пробел-разделённый список флагов:

- `--threshold N` — целое 0–100, минимальный score для попадания в финальный список. По умолчанию **50**.
- `--base-ref REF` — git-ref для базы сравнения. По умолчанию **`main`**.
- `--iter N` — номер итерации, используется в имени output-файла. По умолчанию **автоинкремент** (читать `docs/code-reviews/<report-slug>/` и взять `max+1`, или `1` если пусто).
- `--silent` — не печатать findings в stdout, только путь к JSON-файлу одной строкой (для оркестратора).
- `--feature SLUG` — переопределяет имя поддиректории для отчёта (по умолчанию — имя текущей ветки, нормализованное в безопасный slug).
- `--worktree PATH` — checkout, который ревьюить, в том виде, как его видит сессия (`.worktrees/<slug>`, `/Users/<user>/<repo>/.worktrees/<slug>`). По умолчанию — cwd сессии. С ним «Контекст» выше относится к cwd сессии, а не к checkout'у: ветку, diff stats и папки отчётов взять заново для `PATH`.

Примеры:
- `$code-review-local` — порог 50, base=main, авто-iter, человекочитаемый stdout
- `$code-review-local --threshold 70 --base-ref origin/main` — строже + другой base
- `$code-review-local --silent --iter 3 --feature 029-student-cabinet` — для оркестратора

### Checkout и git

`<checkout>` — проверенный локальный путь из `--worktree` или cwd. `<GIT>` —
`git -C <checkout>`; все Git-команды выполняются в нём, файлы читаются по
`<checkout>/<repo-relative path>`. Никакого SSH/sshfs/repo-git proxy.

Проверить threshold как integer 0–100, iter как positive integer. `--feature`
принимать только как безопасный single-segment slug без `..`, slash/backslash,
NUL; имя ветки по умолчанию нормализовать (например, `codex/foo` → `codex-foo`).
Сырой branch сохранить в JSON. Ref проверить как commit через `rev-parse --verify`;
не интерполировать аргументы пользователя в shell-код. `--iter` с существующим
файлом — ошибка с предложением свободного номера, не разрешение перезаписать историю.

## Этап 0. Предполётная проверка

1. Убедиться, что есть git и мы в репозитории: `<GIT> rev-parse --is-inside-work-tree`. Если нет — ошибка.
2. Убедиться, что `<base-ref>` существует: `<GIT> rev-parse --verify <base-ref>`. Если нет — ошибка с предложением: `--base-ref origin/main` или `--base-ref HEAD~10`.
3. **Определить режим и снять net diff, не меняя index:**
   - Вычислить `<merge-base>`: `<GIT> merge-base <base-ref> HEAD`.
   - Снять tracked patch: `<GIT> diff --no-ext-diff --binary <merge-base> --`.
     Он включает итоговые committed + staged + unstaged изменения. Для статуса режима
     отдельно сравнить `<merge-base>..HEAD` и `HEAD` с рабочим деревом.
   - Получить untracked через `<GIT> ls-files --others --exclude-standard -z`; проверить
     релевантные source/config/tests/docs файлы и приложить их в patch через read-only
     `git diff --no-index --no-ext-diff -- /dev/null <path>` (exit 1 означает diff).
     Не включать secrets, generated caches, собственные review reports и screenshots.
     Считать статистику по единому net набору, не дважды за commit и working tree.
   - Везде далее `<DIFF-CMD>` означает этот полный снимок (tracked + новые файлы),
     не команду, которую надо буквально вызвать. Для каждого агента один patch,
     список файлов и snapshot metadata (HEAD/base/working-tree state).
   - **Никогда не применять `git add -N` / `git reset`**: staged состояние пользователя
     не нужно менять ради чтения. Если файлы меняются во время review, пометить snapshot
     устаревшим и получить актуальный проход; не соединять разные состояния как одно.

4. Посчитать shortstat полного снимка. Если **0 изменений** — записать пустой JSON с реальными нулевыми counts; `--silent` возвращает только path, иначе `No diff vs <base-ref> — nothing to review.` Reviewer jobs для пустого diff не нужны.
5. Если diff > **2000 строк** (insertions+deletions) — при обычном выводе предупредить пользователя: `Warning: diff is large (XXXX lines) — review may take 3-5 minutes.` и продолжить.

## Этап 1. Сбор контекста

Прежде чем запускать reviewer'ов, собрать **shared context** один раз:

1. **Список изменённых файлов** — полный набор из Этапа 0, с признаком tracked/new.
2. **Полный diff** — сохранить единый снимок во временный уникальный файл, например
   `/tmp/code-review-local-<run-id>/diff.patch`. Использовать `mktemp`/эквивалент,
   а не общий фиксированный файл; записать pathname в prompts всем reviewer/scorer.
   Индекс пользователя остаётся неизменным; после завершения удалить лишь свой файл.

3. **Список релевантных AGENTS.md:**
   - Корневой `AGENTS.md` (если есть).
   - Для каждой изменённой папки — все `AGENTS.md` вверх по дереву (от файла до корня).
   - Конвенции: проверить наличие `docs/conventions/{frontend,backend,frontend-testing,backend-testing,e2e-testing}.md` и подмешать в shared context (как **«дополнительный AGENTS.md»** — нарушение конвенции = нарушение AGENTS.md).
4. **Последние коммиты ветки** для контекста намерения:
   ```bash
   <GIT> log <base-ref>..HEAD --oneline --no-decorate
   ```

Если diff пустой — см. Этап 0, шаг 3.

## Этап 2. Запуск 9 параллельных reviewer-агентов

**ВАЖНО (max effort):** `collaboration.spawn_agent`, модель наследовать из настроек Codex. Для reviewer и scorer запросить maximum supported reasoning effort; в каждом prompt явно указать:

> Operate at **maximum reasoning effort**. Think deeply before each conclusion. Do not skim — read every changed hunk carefully. Better to spend extra time than to miss a real bug.

Запланировать **все девять отдельных reviewer jobs**. Запускать независимые jobs параллельно в пределах доступных runtime-слотов, остальных — очередью, не объединять роли. Если вызывает auto-pipeline, его Main напрямую диспетчеризует jobs без waiting-wrapper. Каждому передать:
- путь к diff-файлу (`<temporary-diff-path>`),
- `<checkout>`: файлы из diff'а читать по путям `<checkout>/<путь>`,
- список изменённых файлов,
- список путей к релевантным AGENTS.md и docs/conventions/*,
- последние коммиты ветки (контекст намерения),
- **формат ответа — строго JSON** (см. ниже).

### Роли агентов (адаптированы под локальный diff, без PR-агентов)

**Agent #1 — AGENTS.md & conventions compliance**
- Проверяет соответствие изменений всем AGENTS.md в зоне действия (root + nested) и файлам `docs/conventions/*.md`, релевантным изменённым файлам (frontend/* → frontend.md и frontend-testing.md; backend/* → backend.md и backend-testing.md; e2e/* → e2e-testing.md).
- Для каждого finding'а — цитировать конкретное правило (с указанием файла и строки правила).

**Agent #2 — Shallow bug scan (только diff)**
- Читает **только** diff, без расширенного контекста. Ищет очевидные баги: null-разыменования, забытые `await`, off-by-one, неправильные условия, потерянные `return`, дубликаты в массивах, опасные default'ы, неверные типы, ошибки в SQL/Prisma where-условиях.
- **Не флагать** то, что зависит от внешнего состояния (без чтения других файлов).

**Agent #3 — Deep logic & context scan**
- Может **читать связанные файлы** (Read tool) для понимания контекста: вызывающий код, сигнатуры функций, схемы Prisma.
- Ищет логические баги, требующие межфайлового понимания: неправильный порядок параметров, использование удалённого API, нарушение инвариантов модели, race conditions в Effector/WebSocket-флоу.
- **Не дублировать** Agent #2 — фокус на том, что **нельзя** увидеть из одного diff'а.

**Agent #4 — Security & data leakage**
- SQL/NoSQL injection, SSRF, открытые SECRET'ы, JWT/токены в логах, утечка PII в response (например, в `select` Prisma забыли исключить `password`), CSRF, отсутствие auth-проверок на новых роутах, raw HTML в React (XSS), небезопасный `eval`/`Function`, незаэкранированные user inputs в shell-командах.
- Особое внимание: контроллеры в `backend/src/controllers/`, любые `res.json()`, `prisma.*.findMany`, новые middleware.

**Agent #5 — Type & contract safety**
- `any` / `as any` / `// @ts-ignore` в TS (если AGENTS.md/конвенции запрещают — это finding'и).
- Несогласованные сигнатуры между controller ↔ service ↔ Prisma-схемой.
- Изменения API-контрактов (response shape, query params) без соответствующей правки фронта.
- Изменения Prisma-схемы без миграции, или миграция без backfill для NOT NULL.
- Effector: события без типов, эффекты без error-handling, stores без явного типа.

> Агенты #6–#8 — recall-углы, перенесённые из протокола `/code-review` (max effort). Они ловят то, что shallow/deep-сканы пропускают: исчезнувшее поведение, поломку вызывающих и ошибки делегирования в обёртках.

**Agent #6 — Removed-behavior auditor (удалённое поведение)**
- Для **каждой строки, которую diff УДАЛЯЕТ или заменяет**, назвать инвариант/поведение, которое она обеспечивала, затем найти в новом коде место, где этот инвариант восстановлен.
- Если восстановления нет — это finding: убранный guard или проверка, потерянная ветка обработки ошибки, суженная валидация, удалённый тест, покрывавший реальный кейс.
- Категории: `bug` (убранная защита/валидация), `logic` (потерянная ветка), `convention` (удалён тест вопреки правилу «всё новое покрыто тестами»).
- **Не дублировать** Agent #2/#3 — фокус строго на том, что **исчезло** из кода, а не на том, что добавлено.

**Agent #7 — Cross-file tracer (call-sites и контракты)**
- Для каждой функции/метода, которые diff меняет, найти **вызывающих** (Grep по символу) и проверить, не ломает ли изменение их call-site: новое предусловие, изменённая форма возврата, новое исключение, новая зависимость по порядку/таймингу.
- Проверить и **вызываемых**: не делает ли параллельное изменение в этом же diff'е существующий вызов небезопасным.
- Может **читать связанные файлы** (Read/Grep): сигнатуры, типы, Prisma-схему, фронтовых потребителей API.
- `file`/`line_start` указывать на место, где нужен фикс (может быть **вне diff'а** — напр. файл-вызывающий); `snippet` тогда из этого файла.
- Категории: `bug`/`logic` (сломанный call-site), `type` (рассогласование контракта controller↔service↔front).
- **Не дублировать** Agent #3: тот ищет логические инварианты **внутри** изменённого кода; этот — **разрыв контракта между изменённым кодом и остальной кодовой базой**.

**Agent #8 — Wrapper/proxy correctness (обёртки и прокси)**
- Когда diff добавляет/меняет тип, **оборачивающий** другой (cache, proxy, decorator, adapter, repository поверх Prisma, Effector-обёртка над эффектом): проверить, что каждый метод ходит в **обёрнутый экземпляр**, а не обратно через registry/session/глобал.
  - Пример: кеширующий провайдер с полем `delegate`, который резолвит id через `session.get(...)` вместо `delegate.get(...)`, повторно войдёт в кеш или зарекурсится.
- Проверить, что обёртка **форвардит все методы**, которые реально используют вызывающие (нет «дыр» в делегировании).
- Может читать оба типа (обёртку и обёрнутый) через Read.
- Категории: `bug` (рекурсия / повторный вход / потерянный метод), `logic`.
- Если в diff'е **нет** оборачивающих типов — вернуть `{"agent": "wrapper-proxy", "findings": []}` и не выдумывать.

**Agent #9 — Hacks & workarounds (костыли)**
- Ищет не баги, а **костыли**: места, где проблема обойдена, а не решена. Может читать связанные файлы и сравнивать с тем, как ту же задачу решает остальная кодовая база (Grep по похожим модулям в `main`).
- Что флагать:
  - лечение симптома вместо причины, частный случай под конкретный сценарий там, где общая схема решила бы его сама; одинаковые guard'ы/фильтры, разбросанные по многим местам вместо одного механизма;
  - магические задержки, таймауты, ретраи, `setTimeout(0)`/микротаск-трюки, порядок, который держится на очерёдности эффектов Effector или колбэков, флаги, замазывающие гонку;
  - обход типов: `as`, `as unknown as`, non-null `!`, `@ts-ignore`/`@ts-expect-error`, `eslint-disable`, валидатор без type guard, после которого приходится кастовать;
  - тестовые швы в прод-коде: параметры/дефолты/экспорты, нужные только тестам (`__resetForTest`, инъекция зависимостей, которую в проде никто не передаёт, `if (NODE_ENV === "test")`), тестовые хелперы в публичном API модуля;
  - проглоченные ошибки: `catch` с одним логом на нижнем уровне, после которого вызывающий считает операцию успешной; фолбэк по умолчанию, скрывающий промах (`?? "tutor"`, `?? ""`, «если не нашли — берём первый»);
  - UI: борьба со специфичностью (`!important`, `& .Mui*-root`, `"& > *"`), магические пиксели, компенсирующие соседние элементы, эскалация `z-index`, `useEffect`/ref/счётчик-«пинок» для синхронизации состояния, которое должно жить в модели, чтение мутабельного глобала в render;
  - тесты: проходят вхолостую (ожидание совпадает с начальным значением, мок обходит проверяемый код, `not.toContainEqual` с объектом, который никогда не совпадёт), фиксированные sleep вместо ожидания условия, утечка моков между тестами (`mockClear` вместо `mockReset`), пиксели из styled-файлов вместо поведения, скопированный setup; в e2e — `waitForTimeout`, `force: true`, проверка, не отличающая успех от провала;
  - дублирование логики (две функции/эффекта с одинаковым телом, параллельные пути, делающие одно и то же чуть по-разному), мёртвый код, неиспользуемые экспорты/пропсы/поля, параллельные копии типов (например, ручные lowercase-копии Prisma-енумов);
  - переусложнение (слои, колбэки, опции и обобщения, которые никто не использует) и, наоборот, модульное мутабельное состояние или инверсия слоёв там, где в кодовой базе есть принятый паттерн.
- Каждый finding — с конкретным «почему это костыль» в `rationale` и правильным решением в `fix_hint` (не «добавить комментарий»). Категория — `hack` (или `convention`, если прямо нарушено правило из `docs/conventions/*`).
- **Не дублировать** Agent #2/#3: если место — просто баг, его ловят они; здесь — код, который сейчас работает, но держится на обходе.

### Совместимость имён и независимость

`claude-md` остаётся legacy v1 идентификатором role/category, но означает текущие
`AGENTS.md` и конвенции. Старый `CLAUDE.md` не требуется. Не менять старые JSON
отчёты ради переименования. Reviewer видит исходный snapshot, не чужие выводы.
Сохранить status каждого из девяти jobs (`completed | failed | unavailable`) и scope;
неприменимая роль возвращает пустой findings с объяснением, не исчезает из покрытия.

### Формат ответа агента (обязательный)

Каждый агент возвращает **только** JSON следующего вида (без markdown-обвязки, без префиксов):

```json
{
  "agent": "claude-md|shallow-bug|deep-logic|security|type-safety|removed-behavior|cross-file|wrapper-proxy|hacks",
  "findings": [
    {
      "title": "Краткое описание проблемы (одна строка, на русском)",
      "category": "bug|claude-md|convention|logic|security|type|hack",
      "file": "backend/src/controllers/auth.ts",
      "line_start": 42,
      "line_end": 45,
      "snippet": "≤5 строк кода из diff'а, точно как в файле",
      "rationale": "Почему это проблема (1-2 предложения). Цитировать AGENTS.md/convention правило если применимо.",
      "fix_hint": "Конкретное предложение исправления (1-2 предложения)."
    }
  ]
}
```

**Если findings нет** — вернуть `{"agent": "<role>", "findings": []}`.

## Этап 3. Независимый scoring Codex

Собрать **все findings** со всех 9 reviewer'ов в единый список. Для **каждого finding'а** создать отдельную независимую scorer-задачу (не автор находки), с моделью Codex из настроек и max effort. Исторический batch 10–15 кандидатов сохраняется как очередь; одновременно запущено не больше доступных слотов. Каждый кандидат получает индивидуальный score, не общую оценку пачки.

Каждому scorer-агенту Codex передать:
- title, file, line_start-line_end, snippet, rationale, fix_hint — всё из finding'а,
- diff (`<temporary-diff-path>`) — для верификации в контексте,
- список релевантных AGENTS.md/конвенций.

**Промпт scorer-агенту Codex:**

> Ты оцениваешь, насколько уверенно конкретный finding из code-review является **настоящей** проблемой (а не false positive). Прочитай diff и при необходимости связанные файлы. Верни одно число — score 0–100 — по этой рубрике:
>
> - **0** — Полностью false positive. Не выдерживает лёгкой проверки, или это pre-existing issue (не из этого diff'а).
> - **25** — Может быть проблемой, но не удалось убедиться. Если стилистическое — правило не было явно прописано в AGENTS.md/конвенциях для этого файла.
> - **50** — Подтверждённая проблема, но мелочь или редкий случай. На фоне остального PR — не очень важно.
> - **75** — Точно проблема, высокая вероятность срабатывания в проде. Прямо влияет на функциональность, или явно нарушает AGENTS.md.
> - **100** — Абсолютная уверенность. Точно сломает прод. Прямые доказательства из кода.
>
> Для категории `hack` (костыль от Agent #9): подтверждённый по коду костыль, который держит поведение на обходе (проглоченная ошибка, гонка, замазанная порядком, тест, проходящий вхолостую, тестовый шов в прод-API, мёртвый код) — не ниже **50**, даже если правило не прописано в конвенциях; чистая вкусовщина без конкретного вреда — **25**.
>
> Operate at maximum effort. Если сомневаешься между двумя значениями — выбирай нижнее (better safe than wrong).
>
> Верни **только JSON**: `{"score": NN, "verification_note": "одно предложение почему именно так"}`.

**Таймаут:** 30 секунд с фактического запуска scorer, не с постановки в очередь. Если ответа нет за 30 секунд — пометить score как `null` и `verification_note: "timeout"`. Такие findings сохраняются в `filtered_out` с reason=`timeout` и в metadata scorer coverage, но **не** в финальном фильтре. Это непроверенный кандидат, а не false positive; `coverage_complete=false`. Не выдавать пустой final findings при timeout за чистое ревью. Poll/wait ограничивать остатком deadline и освобождать слот завершившейся/прерванной задачи.

## Этап 4. Фильтрация и подготовка JSON

1. Объединить findings со scores. Финальный объект на одну находку:
   ```json
   {
     "id": "f1",
     "agent": "shallow-bug",
     "title": "...",
     "category": "bug",
     "file": "...",
     "line_start": 42,
     "line_end": 45,
     "snippet": "...",
     "rationale": "...",
     "fix_hint": "...",
     "score": 75,
     "verification_note": "..."
   }
   ```
   `id` — последовательный `f1`, `f2`, …; идентификаторы уникальны по отчёту, включая filtered_out, сохранять candidate origin для аудита.

2. **Дедупликация:** если два finding'а указывают на тот же `(file, line_start, title-substring)` — оставить один (с **максимальным** score), в `rationale` добавить `(also flagged by: <other-agent>)`. Дополнительно объединять одну доказанную первопричину при сдвинутых строках/разных заголовках, сохраняя весь список источников и лучший evidence; разные причины не сливать.

3. **Фильтр по threshold:** оставить только `score >= threshold` **и** `score != null`. Остальные сохранить отдельно как `filtered_out` (с теми же полями + причина: `"below threshold"` или `"timeout"`).

4. **Severity на основе score** (для удобства оркестратора):
   - `score == 100` → `"critical"`
   - `75 <= score < 100` → `"high"`
   - `50 <= score < 75` → `"medium"`
   - `0 <= score < 50` → `"low"` (если пользователь снизил threshold).
   Это историческая severity-шкала уверенности review, не GitHub criticality; не применять её к issue scoring.

5. **Финальный объект отчёта:**
   ```json
   {
     "schema_version": 1,
     "branch": "029-student-cabinet",
     "base_ref": "main",
     "threshold": 50,
     "iteration": 1,
     "timestamp": "2026-05-24T12:34:56Z",
     "diff_stats": { "files_changed": 47, "insertions": 1234, "deletions": 567 },
     "summary": {
       "raw_findings": 42,
       "after_dedup": 35,
       "after_score_filter": 8,
       "by_severity": { "critical": 0, "high": 3, "medium": 5 },
       "by_category": { "bug": 4, "claude-md": 2, "security": 1, "type": 1 }
     },
     "findings": [ /* отфильтрованные, отсортированные по score DESC, потом по file ASC */ ],
     "filtered_out": [ /* всё что отсеяно — для прозрачности и debug */ ]
   }
   ```

## Ограничения

- **Не редактировать прод-код.** Команда строго read-only по отношению к исходникам. Фиксы — задача вызывающей стороны (оркестратора или человека).
- **Не делать git-операций, меняющих историю/ветки/рабочие файлы.** Read-only `diff`/`log`/`rev-parse`/`rev-list` через `<GIT>` — всегда ОК. Индекс также read-only; `add -N`/`reset` запрещены. Никаких `commit`/`push`/`checkout`/`branch`/`stash`.
- **Не запускать тесты, линтеры, билды.** Это отдельные шаги (CI / pre-commit). Reviewer'ы должны явно игнорировать "issues a linter would catch".
- **Не работать с GitHub** (`gh`-командами). Это локальная команда, никаких комментариев в PR не делать.
- **Findings строго в JSON-схеме.** Если reviewer вернул не-JSON или нарушил схему — пытаться извлечь JSON по `{...}` блоку; если не получилось — пометить `agent` как `failed` и продолжить без его findings (в `summary` записать `agents_failed: ["<role>"]`).
- **Дедупликация обязательна** — иначе оркестратор будет фиксить одно и то же 5 раз.
- **Все sub-agents (reviewer'ы и scorer'ы) — с моделью Codex из текущих настроек**, оба с явным "max effort" в промпте.
- **Описания на русском** (как и весь output для пользователя). JSON-ключи — английские, как принято.

## Проверка контракта перед выдачей

Сохранить в JSON аддитивный `coverage`: `{complete, reviewers, scorers}`. Reviewer entry
содержит role/status/note; scorer entry — finding_id/status/score/verification_note.
`summary.agents_failed` перечисляет сбои, `summary.scorers_failed` — непроверенные IDs.
`summary.raw_findings`, `after_dedup`, `after_score_filter` и все category/severity counts
должны соответствовать данным. Сортировать final по score DESC, затем file ASC.
`score:null` не проходит даже threshold=0. Не-JSON reviewer сначала попытаться извлечь
из единственного JSON-объекта; не удалось — failed, без выдуманного пустого результата.
При ошибке scorer schema — score=null, reason=`unverified`; серьезный неподтверждённый
кандидат остаётся видимым в filtered_out/coverage. Верифицировать relative file и
актуальные line_start/end по сохранённому snapshot; cross-file findings могут быть вне diff.
