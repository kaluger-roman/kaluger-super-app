## Контекст

Перед выполнением прочитать корневой и применимые вложенные `AGENTS.md`,
`docs/subagents.md` и нужные конвенции. Проверить локальный checkout,
`git status --short --branch`, текущую дату и существующие артефакты этой процедуры.
Работа выполняется на этом Mac; Git — `git -C <checkout>`, окружение —
`docs/dev-stack.md` и `docs/qa-docker.md`.

Browser/rollback adapter: [runtime.md](../../auto-feature/references/runtime.md).
Контракты: [findings.schema.json](findings.schema.json), [round-context.schema.json](round-context.schema.json).

## Задача

Прогнать фичу текущей ветки руками **через доступный браузерный инструмент** с позиции пользователя / QA / product owner: пройти все ключевые сценарии из спецификации, сделать скриншоты ключевых экранов и проблем, сверить наблюдаемое поведение с Acceptance Scenarios и quickstart-чеклистом, оценить общее качество фичи и записать развёрнутый MD-отчёт в `docs/manual-qa-reports/`.

аргументы вызова парсятся так:

- содержит `--fix` → **режим автофикса**: после написания отчёта чини все находки, помеченные как «однозначные» (см. Этап 6). Архитектурные/спорные изменения — не трогать.
- содержит идентификатор фичи (формат `NNN-something`) → использовать как override для спеки (`specs/<id>/`), а не текущую ветку.
- содержит URL (`http://...`) → использовать как base URL напрямую (Docker-стек не поднимать).
- содержит `--host` → не поднимать Docker; тестировать уже запущенные dev-серверы на `webUrl` из `bash scripts/dev-stack.sh ports` текущего checkout.
- содержит `--teardown` → после отчёта снести QA-стек (`bash scripts/qa-stack.sh down`). По умолчанию стек остаётся поднятым для ручной до-проверки.
- содержит `--context <path>` → **повторный круг для оркестратора** (`$auto-feature`, `$auto-bug-fix`): JSON с тем, что уже проверено и что перепроверить (см. «Контекст круга» ниже). Влияет на Этап 3 и на `findings.json`.
- иначе → дефолт: спека = ветка, base URL = **изолированный Docker-стек checkout** (поднимается на Этапе 2), без автофикса.

Примеры:
- `$manual-qa` — поднять изолированный стек ветки и прогнать фичу, без автофикса.
- `$manual-qa --fix` — прогон + автофикс однозначных багов.
- `$manual-qa 028-forgot-password` — прогон фичи `028-forgot-password` (даже если ты на другой ветке).
- `$manual-qa --host` — прогон по уже запущенным dev-серверам текущего checkout (URL из dev-stack ports), без Docker.
- `$manual-qa --fix --teardown` — прогон с автофиксом, в конце снести стек.

## Этап 1. Сбор спецификации фичи

1. Определить feature id из аргументов или текущей ветки. Точно сопоставить `specs/<id>/`, отделив `codex/` от имени ветки. При повторяющихся числовых префиксах использовать полный slug, не первую папку. Если спеки нет — fallback на diff ниже; не завершать раньше него.
2. Прочитать (в этом порядке приоритета):
   - `specs/<id>/spec.md` — **источник правды** для User Stories и Acceptance Scenarios.
   - `specs/<id>/quickstart.md` — **готовый пошаговый чеклист** ручного прогона, если есть; следовать ему как основному сценарию.
   - `specs/<id>/tasks.md` — понять, что фактически реализовано (по статусам задач) и что могло остаться TODO.
   - `specs/<id>/contracts/` — API-контракты, чтобы знать ожидаемые форматы запросов/ответов при анализе network-логов.
   - `specs/<id>/data-model.md` — какие сущности нужны в БД для воспроизведения сценариев.
   - `specs/<id>/checklists/` — дополнительные проверочные списки, если есть.
Для имени отчёта нормализовать ветку в безопасный `report-slug` (slash → hyphen), сохранив реальную ветку отдельно в JSON.
3. Прочитать `CHANGELOG.md` (топ-30 строк), последние коммиты ветки (`git log main..HEAD --oneline`) и незакоммиченные изменения (`git status --short`) — увидеть, что фактически в diff'е. Оркестраторы не коммитят до конца работы, поэтому фиксы под проверку обычно лежат в рабочем дереве.
4. Из всех материалов составить **единый список сценариев для прогона** — Priority P1 обязательно, P2 — если время позволяет, edge cases из секции «Edge Cases» спеки — обязательно.

Если спеки нет вовсе — построить план тестирования из tracked diff от merge-base main/HEAD до рабочего дерева плюс релевантные untracked файлы (без мутаций index) — коммиты ветки вместе с незакоммиченными изменениями (новые роуты, новые формы, новые эндпоинты) и сообщить в отчёте, что прогон шёл «без спеки», только по diff'у.

## Этап 2. Подготовка окружения

1. **Поднять изолированный QA-стек ветки.** (Пропустить при `--host` — тогда base URL = `webUrl` из `bash scripts/dev-stack.sh ports`; или при URL-override в аргументах вызова.)

   ```bash
   bash scripts/qa-stack.sh up
   ```

   Собирает и поднимает отдельный Docker-стек (web + backend + postgres) с именем `qa-<checkout>-<hash пути>` на **эфемерном порту** и печатает JSON: `{"url":"http://localhost:<port>","adminEmail":"admin@qa.local","adminPassword":"QaAdmin!2026",...}`. Распарсить `url` — это **base URL** всего прогона. Стек изолирован (своя свежая БД, отдельный порт), поэтому manual-qa и qa-roam можно гонять параллельно на разных ветках. Первая сборка — 2–4 мин, дальше из кэша.

   Если вернулся `{"error":...}` или Docker не запущен — сообщить пользователю «Запусти Docker Desktop и повтори $manual-qa» и завершить. Детали и тимдаун — `docs/qa-docker.md`.

2. **Подготовить тестовые данные.** БД стека **свежая и пустая** (накатаны только миграции) — данные надо создать. Все обращения к БД идут **внутрь контейнера** через `exec-backend` (на хосте `npx tsx` смотрел бы в личную БД разработчика, не в стек). Поскольку БД изолированная, `npm run db:seed` здесь **безопасен** (можно поднять базовый набор одной командой):

   ```bash
   bash scripts/qa-stack.sh exec-backend 'npm run db:seed'
   ```

   Команда печатает JSON с логинами и паролями созданных аккаунтов; состав набора — `backend/src/services/devSeed`. Повторный запуск пересоздаёт только этот набор.

   Пример read-запроса (Prisma-клиент уже сгенерирован в контейнере, CommonJS):
   ```bash
   bash scripts/qa-stack.sh exec-backend 'node -e "const {PrismaClient}=require(\"@prisma/client\"); const p=new PrismaClient(); p.user.findMany({take:3,select:{id:true,email:true,name:true}}).then(r=>console.log(JSON.stringify(r,null,2))).finally(()=>p.\$disconnect())"'
   ```
   Быстрый SQL-просмотр — `bash scripts/qa-stack.sh psql "select email from users limit 5;"`. Админ-логин для стека: `admin@qa.local` / `QaAdmin!2026` (печатается в выводе `up`).

3. **Создание недостающих сущностей** — через `db:seed` или точечные `exec-backend`-вставки. Правила:
   - Для точечных сущностей — маркер `[mqa <YYYY-MM-DD-HHMM>]` в именах/email, чтобы отличать в отчёте.
   - Чистить за собой не нужно: весь стек (вместе с БД-томом) сносится одной командой `bash scripts/qa-stack.sh down`. Зафиксировать использованные аккаунты в секции «Артефакты прогона».

4. **Открыть Playwright** через `browser_navigate` на base URL. Проверить, что страница реально отрисовалась (`browser_snapshot`). Если фронт упал в рантайме — это уже находка `Severity: Critical`.

## Этап 3. Построение тест-плана прогона

Из материалов Этапа 1 составить упорядоченный список «шаг → ожидаемый результат → актуальный результат». Этот план — будущая секция «Покрытие сценариев» в отчёте.

Пример строки плана:
```
[P1.1] Преподаватель создаёт ссылку-приглашение в карточке ученика
  Шаги: /login → toggle "преподаватель" → email/пароль → /students → открыть карточку → "Создать ссылку-приглашение"
  Ожидание (Acceptance Scenarios #1): отображается URL /student-invite/<token>, кнопка "Скопировать", индикатор "ожидает регистрации"
  Скриншоты: 01-login.png, 02-students.png, 03-invite-created.png
```

Одна строка плана — один сценарий со своими шагами, как `[P1.1]` выше; лимиты ниже считают строки, а не отдельные действия в браузере. Число шагов внутри сценария не ограничено: столько, сколько нужно, чтобы дойти до проверки и сверить результат.

Сценарии не дублируют друг друга: каждая строка проверяет то, чего не проверяет ни одна другая. Строки с одной и той же проверкой (один Acceptance Scenario из спеки и quickstart, тот же edge case с другими данными без нового поведения) свести в одну. Общая подготовка (логин, переход на экран) — шаги внутри сценария, а не отдельная строка.

Включить в план **обязательно**:
- Все P1 User Stories и их Acceptance Scenarios.
- Все пункты из секции «Edge Cases» спеки.
- Negative paths: невалидные данные, дубликаты, истёкшие токены, неавторизованный доступ к защищённым роутам.
- Realtime/WebSocket-сценарии, если есть (открыть две вкладки/контекста через `browser_tabs`, проверить пуш-обновления).
- Smoke по неизменённым областям: если фича вводит общий компонент (например, тумблер на /login), проверить, что старая роль логинится по-прежнему.

Если план получается > 40 строк — урезать P2 и не-критичные edge cases, но **никогда** не урезать P1. Перепроверки и обязательные сценарии из `--context` (`recheck`, `must_check`) в лимит не входят. Урезанные сценарии записать в `coverage.untested` (`findings.json`): следующий круг оркестратора возьмёт их.

### Контекст круга (`--context <path>`)

Файл пишет оркестратор:

```json
{
  "iteration": 2,
  "must_check": [ { "title": "Повтор бага: ...", "steps": ["..."], "expected": "..." } ],
  "recheck": [ { "finding_title": "...", "scenario_id": "P1.2", "steps": ["..."], "expected": "..." } ],
  "covered_scenarios": [ { "id": "P1.1", "title": "..." } ],
  "known_open_findings": [ { "title": "...", "scenario_id": "P1.3", "status": "open|rejected" } ]
}
```

Все поля необязательны. План строится в таком порядке:

1. `recheck` — находки, исправленные после прошлого круга: пройти точно по их шагам и записать результат в `recheck_results`.
2. `must_check` — обязательные сценарии (например, шаги воспроизведения бага), как обычные строки плана.
3. Сценарии из полного списка Этапа 1, которых нет в `covered_scenarios` (сверка по `id`, при расхождении id — по смыслу `title`). Уже пройденные не повторять, кроме шагов, без которых не дойти до нужного экрана.

`known_open_findings` уже известны оркестратору: не репортить их повторно, даже если снова видны. Если после вычитания `covered_scenarios` новых сценариев нет, а `recheck` и `must_check` пусты — прогнать ничего не нужно: записать `findings: []`, пустой `coverage.scenarios` и завершить.

## Этап 4. Прогон через доступный браузерный инструмент

До первого screenshot выбрать единый свободный `run_stem = YYYY-MM-DD-report-slug[-N]`:
не должны существовать ни `<run_stem>.md`, ни `<run_stem>.findings.json`, ни каталог
`<run_stem>/screenshots`. Использовать этот stem во всех артефактах текущего круга.
При resume сохранять существующие кадры и брать следующий свободный NN; никогда
не перезаписывать доказательства прошлого круга или отчёта.

Идти по плану шаг за шагом. На каждом шаге:

1. **Действие** — `browser_navigate` / `browser_click` / `browser_fill_form` / `browser_type` / `browser_press_key`.
2. **Снимок DOM** — `browser_snapshot` (структурированный snapshot, не путать со скриншотом). Используется для сверки и для подбора `ref` для следующих кликов.
3. **Скриншот** — `browser_take_screenshot` сохраняет PNG в указанный путь. Сохранять в `docs/manual-qa-reports/<run_stem>/screenshots/NN-<slug>.png`, где `NN` — двузначный порядковый номер, `slug` — kebab-case описание (`01-login-form`, `02-invite-link-created`).
4. **Проверки**:
   - Соответствует ли увиденное Acceptance Scenarios? (текст, поля, статусы, redirects)
   - `browser_console_messages` — есть ли error/warning в консоли?
   - `browser_network_requests` — есть ли 4xx/5xx, неожиданные эндпоинты, утечка чувствительных полей в ответе (на критичных шагах вытащить тело ответа и сверить с `contracts/`)?
5. **Запись результата** — в локальном буфере держать структуру по каждому шагу:
   ```
   { step, expected, actual, screenshots, console, network, status: 'pass'|'fail'|'warn' }
   ```

**Эргономика прогона:**
- Перед каждой формой делать `browser_snapshot` и подбирать `ref` — это надёжнее, чем угадывать селекторы.
- Для realtime — `browser_tabs` (новая вкладка под учеником), действие на первой вкладке, `browser_wait_for` на второй с ожиданием изменения текста / появления карточки.
- При обнаружении модалок и подтверждений — `browser_handle_dialog`.
- Респонсив: на 1–2 ключевых экранах сделать `browser_resize` (например, 375×812) и скриншот — отметить очевидные ломки.
- Не пытаться обходить email-верификацию через UI (реальный код не уходит — RESEND в стеке заглушён): вытащить код напрямую из БД через `bash scripts/qa-stack.sh exec-backend '...'` (поле `verificationCode` в нужной таблице).

**Что писать в `Bash`-вставках:**
- Чтение данных и подготовка тестовых сущностей — `bash scripts/qa-stack.sh exec-backend '...'` (внутри контейнера, против БД стека). Только короткие однострочники. Никаких массовых апдейтов.
- Чистить артефакты не обязательно — стек сносится целиком на Этапе 7 (`down`) при `--teardown`.

## Этап 5. Категоризация находок

Каждое отклонение — отдельная находка. Поля:

- **Заголовок** (одна строка, начинается с глагола: «Пустой стейт на странице расписания не отображается»).
- **Категория**:
  - ❌ **Spec mismatch** — наблюдаемое поведение прямо противоречит Acceptance Scenario / spec.md.
  - 🐛 **Bug** — что-то сломано (ошибка, исключение, неработающая кнопка, неконсистентный стейт, утечка данных в API).
  - ⚠️ **UX issue** — работает, но плохо с точки зрения пользователя (нет фидбэка после действия, мисс-эппинг ошибки, неудобный flow, неработающий keyboard nav).
  - 💡 **Improvement** — можно сделать лучше (a11y, копирайт, дизайн-консистентность, перфоманс восприятия).
- **Severity**:
  - **Critical** — фича не работает / ломает другую функциональность / утечка чувствительных данных / возможна потеря пользовательских данных.
  - **High** — критичный P1-сценарий невозможен или нарушен; пользователь не может завершить главный flow.
  - **Medium** — edge case сломан / P2 нарушен / заметная UX-проблема.
  - **Low** — мелкое улучшение, текст, иконка, мелкий visual glitch.
- **Шаги воспроизведения** — кратко, по плану из Этапа 3.
- **Ожидание vs Реальность** — две короткие строки.
- **Скриншоты** — ссылки на сохранённые PNG (`./<branch>/screenshots/NN-...png`).
- **Файл/строка** (если очевидно из снапшота/исходника) — Read нужного файла, чтобы подтвердить место.
- **Console/Network outliers** — копировать только релевантные строки (не весь лог).
- **Однозначность исправления** — `да` / `нет`. «Да» означает: причина в коде однозначна, исправление не требует архитектурного решения и не задевает других областей. Этот флаг используется автофиксом на Этапе 6.

Дубликаты сводить в один пункт. Не репортить субъективные предпочтения, отсутствие тестов как таковое (для этого есть `$e2e-check`), общие архитектурные замечания (для этого `$improve-hunt`).

Перед изменениями сохранить initial MD+JSON (Этап 7), затем дописать autofix outcomes; первоначальное observed expected/actual не переписывать как будто бага не было.

## Этап 6. Автофикс (только если аргументы вызова содержат `--fix`)

Чинить **в отдельном проходе после написания отчёта**, чтобы отчёт зафиксировал состояние «до».

**Что чинить (любая Severity, но категория конкретная):**
- ❌ **Spec mismatch** с однозначной причиной — например, отображается «Сохранить» вместо «Зарегистрироваться» из спеки.
- 🐛 **Bug** с однозначной причиной — `null`-разыменование, забытый `await`, неправильное условие, потерянный handler, не передан prop, неправильный путь в `navigate`.
- ⚠️ **UX issue** с однозначным решением — отсутствует `aria-label` на icon-only кнопке, не закрывается модалка по Esc, autofocus не на первом поле формы, кнопка submit активна при пустых полях, отсутствует loading state там, где запрос длится > 300мс.
- 💡 **Improvement** с однозначным решением — захардкоженный цвет вместо `theme.palette.*` (если рядом уже используется тема), отсутствующий `alt`, дублирующиеся литералы, выносимые в константу.

**Что НЕ чинить (даже с `--fix`):**
- Любые изменения схемы БД и миграции.
- Изменения публичных API-контрактов (роуты, response shape).
- Архитектурные перестановки (перенос файлов между слоями FSD, переименование экспортов).
- Глобальные стилевые/типографические решения, не локализованные одним компонентом.
- Любая находка, отмеченная «Однозначность исправления: нет».
- Любая находка, требующая решения от продукт-овнера (тексты копирайта, новые поля, изменения flow).

**Процедура для каждого однозначного фикса:**
1. Перечитать соответствующий файл (Read) — без перечтения не редактировать.
2. **Перед редактированием прочитать** `docs/conventions/frontend.md` (если фронт) или `docs/conventions/backend.md` (если бек), а для тестов — соответствующий `*-testing.md`. Не нарушать конвенций: no `any`, no `export default`, no `useEffect` для fetching, no `<form>` теги, named exports, `type` вместо `interface`, error-messages на русском.
3. Сделать минимальную правку (Edit) — не делать «попутный рефакторинг».
4. **Добавить регрессионный тест** — обязательно для категорий 🐛 Bug и ❌ Spec mismatch. Юнит-тест на сервис/модель если фикс в логике; компонент-тест если фикс в UI-поведении. Для UX/Improvement тест не обязателен.
5. Прогнать релевантные тесты: frontend — `npm --prefix frontend test -- <path>`; backend — `bash scripts/dev-stack.sh test-backend --testPathPatterns=<path>` против отдельной тестовой БД.
6. Если фикс фронтовый — `npm --prefix frontend run lint` (или поддержанная targeted-команда из package.json).
7. Если фикс бэковый и затрагивает типы — `npm --prefix backend run build` (быстрая проверка типов).
8. Повторить исходный браузерный сценарий на сборке с фиксом; в QA Docker пересобрать `qa-stack.sh up`, данные сохраняются. Если что-то падает после фикса — **откатить правку** (Edit обратно только свой patch или восстановить снимок перед попыткой; не `git checkout -- <file>`) и пометить находку в отчёте как «попытка автофикса не удалась, нужен ручной разбор».

В конце прохода добавить в отчёт секцию «Автофикс»:
- список исправленных находок (со ссылкой на пункт выше),
- список изменённых файлов (`git diff --name-only`),
- список добавленных тестов,
- список находок, которые пропущены автофиксом (с причиной).

**Не делать `git commit`/`push`** — пользователь сам решит, как объединять автофиксы с основной работой. При большом наборе автофиксов в финальном сообщении напомнить: «после ревью diff'а — commit отдельным коммитом с префиксом `fix(qa): ...`».

**Правила заполнения:**

- `steps` — обязательный массив точных шагов воспроизведения каждой новой находки; оркестратор переносит его в `recheck`. Для legacy JSON без `steps` прочитать шаги из MD, не выдумывать и не объявлять повтор непроведённого сценария.
- `category` — одно из `spec-mismatch | bug | ux | improvement` (соответствие иконкам ❌🐛⚠️💡 в MD).
- `severity` — одно из `critical | high | medium | low`.
- `readiness` — одно из `green | yellow | red` (по той же логике что в MD).
- `unambiguous_fix` — boolean, дублирует поле «Однозначность исправления» из MD.
- `autofix_status` — обязательное поле, значения:
  - `fixed` — автофикс применён успешно и тесты прошли,
  - `failed` — попытка автофикса не удалась (откат),
  - `skipped` — не подходит под критерии автофикса (`unambiguous_fix=false` или категория исключена),
  - `disabled` — запуск был без `--fix`.
- `screenshots` — массив **путей от корня репозитория** (с префиксом `docs/...`), не относительных. Чтобы оркестратор мог их прочитать без знания cwd.
- `file` / `line_hint` — лучшая догадка по результатам Read, может быть `null`.
- `coverage.untested` — сценарии полного списка Этапа 1, которые в этом прогоне не проходились (урезаны лимитом, не хватило данных и т.п.), с причиной; уже пройденные в прошлых кругах (`covered_scenarios`) сюда не входят. Пусто — всё покрыто.
- `recheck_results` — только при `--context` с непустым `recheck`, иначе `[]`. Повторно воспроизведённая находка идёт сюда со статусом `still_reproduces`, а не в `findings`.
- Поля `expected`/`actual` — короткие, для контекста; полное описание остаётся в MD.

**Если автофикс выключен** (`--fix` не передан):
- `autofix_enabled: false`,
- у всех находок `autofix_status: "disabled"`, остальные autofix-поля — `null`.

**Если фича без спеки** (Этап 1 fallback): `spec_path: null`, `feature_id` = имя ветки.

## Ограничения

- **Поднимать изолированный Docker-стек** через `bash scripts/qa-stack.sh up` (кроме `--host`/URL-override). Не трогать личные dev-серверы и личную БД пользователя — стек полностью отдельный. Если Docker не запущен — попросить запустить Docker Desktop и завершить.
- **БД стека изолированная** — `db:seed` и точечные `exec-backend`-вставки безопасны. Личную БД не сидить (она не используется). По умолчанию стек **остаётся поднятым** после прогона; снести — `bash scripts/qa-stack.sh down` (или флаг `--teardown`).
- **Git только read-only** для revision/diff/status. Не делать `commit`, `push`, `branch`, не менять index. Автофикс остаётся в working tree — пользователь сам решит, что коммитить.
- **Не править прод-код без `--fix`.** Без флага команда строго read-only по отношению к исходникам.
- **Не менять `package.json`, `prisma/schema.prisma`, миграции.** Никогда — даже с `--fix`.
- **Не репортить отсутствие тестов** как находку (для этого есть `$e2e-check` и `$e2e-hunt`).
- **Не дублировать `$bug-hunt` и `$improve-hunt`** — те идут по статическому анализу всей кодовой базы. Эта команда — только то, что наблюдается при реальном прохождении сценариев фичи.
- **Описания на русском.** Имена файлов скриншотов / slug'и — kebab-case latin (`01-login-form`).
- **Скриншот обязателен** для каждой находки, кроме чисто текстовых (опечатки в копирайте) — там достаточно цитаты + строки.
- **Нет жёсткого лимита на число находок** — фиксируй столько отдельных пунктов, сколько необходимо, чтобы добросовестно описать наблюдаемое состояние фичи. Дубликаты по-прежнему сводить в один пункт; не репортить субъективные предпочтения. Если находок объективно много (например, ≥ 20) — сгруппируй визуальные/копирайт-мелочи в один пункт-сводку, чтобы отчёт оставался читаемым, но не отбрасывай реальные баги ради лимита.
- **Не сообщать stack trace из консоли целиком** — только релевантные строки (имя ошибки + место).
- **В финальном тексте пользователю** — путь к MD-отчёту, путь к JSON, оценка готовности, главное действие на одну строку.
- **`findings.json` обязателен** — пишется всегда (даже при отсутствии находок: тогда `findings: []`, а `coverage.total` равно числу сценариев в `coverage.scenarios` текущего круга, без отдельных recheck; recheck-only круг имеет total=0 и непустой `recheck_results`). Это публичный контракт для оркестраторов.

## Дополнительные инварианты отчёта

- `coverage.total = scenarios.length = passed + failed + warned`; не прибавлять
  recheck как новую строку coverage и не выдавать покрытые в прошлых кругах за текущие.
- `summary.total_findings = findings.length`; severity/category totals и IDs
  согласованы с MD. Recheck still_reproduces находится только в recheck_results,
  известные open/rejected не дублируются в новых findings.
- `readiness=green` только при реальном прохождении обязательного scope без
  блокирующих находок/пробелов; yellow — доработки/неполное покрытие, red — сломанный
  главный flow/critical. Это оценка QA, не разрешение на merge.
- URL override и --host не дают разрешение сидить/сбрасывать чужую БД. Seed, прямые
  записи и teardown применяются только к изолированному disposable стеку этого запуска.
- `--teardown` выполняется после записи артефактов; при URL/host override без созданного
  QA-стека ничего не сносить. В final указать, оставлен ли стек, и его фактический URL.
