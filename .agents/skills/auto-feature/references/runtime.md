# Runtime Codex для полного pipeline

Эта инструкция заменяет только платформенные механизмы прежних команд. Число
фаз, пользовательские checkpoints, контракты, лимиты и условия выхода сохраняются.

## Локальный checkout и изоляция

1. До правок прочитать `git status --short --branch`, `git rev-parse --show-toplevel`,
   `git worktree list --porcelain`, `git rev-parse --git-common-dir`. Различать корневой
   checkout и уже назначенный linked/Codex-managed worktree, включая detached HEAD.
2. При новом запуске из основного checkout создавать отдельный task worktree в
   ignored `<repo>/.worktrees/<safe-slug>` через локальный `git worktree add -b
   codex/<safe-slug> <path> <base-ref>`. Выбрать проверенную базу по текущей задаче;
   не переносить чужие незакоммиченные изменения. Если новый запрос явно продолжает
   эту же задачу, использовать её worktree/state вместо второго экземпляра.
3. В уже назначенном worktree работать в нём; **не вкладывать новый worktree**.
   Detached HEAD допустим во время работы, но перед стартовым PR создать локальную
   ветку `codex/<safe-slug>`. При существующей ветке задачи сохранить её, когда она
   относится к этому запросу. `feature_slug` (`NNN-name`) и Git `branch` (`codex/NNN-name`)
   — разные поля. В specs и report paths использовать безопасный slug, не сырое имя ветки.
4. Существующий worktree не удалять, не сбрасывать и не создавать заново. Resume
   выполняется в `state.worktree_path`: каждый shell-вызов получает этот workdir,
   git — `-C <path>`. Нет инструмента EnterWorktree и переключения процесса «по имени».
   Отсутствующий/stale путь нельзя автоматически заменять текущим checkout: сверить
   Git worktree inventory/ветку/артефакты и согласовать нужный экземпляр.
5. Зависимости и Prisma client **локальные для каждого worktree**. Запускать
   `bash scripts/setup-local.sh`; не делать симлинки `node_modules`. Серверы и БД —
   `scripts/dev-stack.sh`, production-build QA — `scripts/qa-stack.sh`. Не SSH/sshfs,
   не `home`, не прежний VPS, не реальные production-данные.

## State, журнал и импорт legacy

- Feature state: `.codex/workflow/auto-feature/<slug>/state.json`.
  Bug state: `.codex/workflow/auto-bug-fix/<slug>/state.json`.
  Эти каталоги локальные и ignored; runtime state не включать в коммит.
- Перед стартом/пустым вызовом искать state и в этих каталогах, и в legacy
  `.claude/auto-feature/*/state.json`, `.claude/auto-bug-fix/*/state.json` текущего
  checkout и обнаруженного worktree задачи. Legacy — источник истории для импорта,
  **не** место новых записей. Ничего не удалять из legacy.
- Если выбран legacy-запуск и новой директории ещё нет: целиком скопировать его
  каталог (state, все qa-context, журналы и вспомогательные файлы) в соответствующий
  `.codex/workflow/.../<slug>/`; сохранить точную исходную копию state как
  `legacy-state.json`. Сохранить неизвестные поля и все массивы итераций. Проверить
  количество файлов/хеши копий, затем обновить лишь runtime-ссылки на перенесённые
  `.claude/auto-*` артефакты. Добавить `legacy_import: {source_path, imported_at}`.
  `branch`, `worktree_path`, approvals, timestamps и результаты не выдумывать и не
  переписывать до проверки реального checkout. Старые screenshots/reports не перемещать.
- Совместимость schema v1: старый `remaining_qa_findings` мог содержать вместе с
  open/rejected находками непроверенные сценарии `{id,title,priority,reason}` без
  `status`. Схема принимает оба варианта. После сохранения `legacy-state.json`
  перенести именно такие записи в `remaining_qa_untested`, сохранив все исходные
  поля; дедуплицировать лишь полностью одинаковые записи. В findings оставить
  open/rejected и неизвестные записи без потери данных. Отразить нормализацию
  в `legacy_import`; не выдумывать status/доказательства для непройденного сценария.
  Проверить сумму записей до/после и итоговую схему. При неоднозначной форме —
  остановить импорт для разбора, не отбрасывать элементы ради валидатора.
- Если новый и legacy state уже существуют: не перезаписывать, сравнить slug,
  worktree, timestamps, историю фаз/итераций. Явный `--resume` выбирает новый state
  только при однозначной непрерывной истории; расходящиеся истории показать для
  выбора/сведения с сохранением обеих. Пустой вызов предлагает все активные запуски,
  «начать новый» и «только посмотреть state»; не выбирать молча самый свежий.
- Оркестратор — единственный писатель state. Перед записью перечитать актуальный
  JSON, сохранить прежнюю версию в `state-history/<timestamp>-<counter>.json`, затем
  записать новый целый JSON атомарно через соседний временный файл и rename. Не
  append JSON и не затирать историю итераций. `updated_at` обновлять каждой записью.
  Импортная копия и history сохраняются даже после completed/cancelled.
- `phases` — **массив**, записи выбирать по `name`; обозначение `phases.spec` в
  процедуре означает запись `phases.find(p => p.name === "spec")`, не новый JSON-объект.
  Статусы: `pending | in_progress | awaiting_approval | completed | blocked |
  cancelled | skipped`. На старте фазы создать запись с `started_at`; после реального
  завершения — `completed_at`, artifacts, notes. Ошибка сохраняет шаг, причину и хвост
  лога. Warning/convergence/cap не превращать в clean.
- Схемы: [feature state](state.schema.json) и
  [bug state](../../auto-bug-fix/references/state.schema.json). `schema_version: 1`
  и прежние имена полей сохраняются; новые поля аддитивны. Проверять факты по файлам,
  Git и результатам команд; прежнее `completed` само по себе не доказательство.

## Делегирование и прогресс

`collaboration.spawn_agent` — реальный механизм workers. Каждый worker получает
checkout, фазу, цель, разрешённые файлы, релевантные конвенции, актуальные входные
артефакты и точный JSON-контракт. Модель наследуется из настроек Codex; не задавать
Claude ID. Для анализа/кода/review/scoring — maximum supported reasoning effort,
явно в инструкции. Если runtime требует отдельный override effort, использовать
поддерживаемое значение с тем же настроенным model; не выдумывать скрытые параметры.
Browser QA использует ту же настроенную модель, без старого обязательного downgrade.

Зависимые фазы идут последовательно. Независимые review/research jobs — параллельно
до реального лимита слотов, остальные в очереди. Девять review roles и независимые
scorers диспетчеризует главный оркестратор напрямую: пустая wrapper-задача не занимает
слот, пока ждёт дочерних. Исполнитель не вызывает рекурсивно auto-feature/auto-bug-fix.
Workers не коммитят/публикуют. Main проверяет артефакты и сам чинит review/QA findings.
Неуспешные/недоступные workers фиксируются как пробел покрытия, не как чистая проверка.

Сохранить карту 7 feature / 5 bug фаз. Если доступен инструмент плана/progress —
использовать его; иначе `progress_tasks` в state (id, title, status) и краткие
комментарии при переходах. Не выдумывать TaskCreate/TaskUpdate API и не создавать
отдельные чаты пользователя ради этих внутренних задач.

## Обязательные checkpoints

Feature: **после готовой spec и после готовых mockups**. Bug: **после диагноза и
плана фикса**. Параметр `--checkpoints` принимается для совместимости с промежуточной
миграцией, но checkpoints обязательны и без него. Уже данное конкретное утверждение
того же артефакта учитывается; общее поручение «сделать фичу» его не заменяет.

Перед вопросом подготовить проверяемый артефакт и краткий итог. Записать
`status: awaiting_approval` и `pending_checkpoint` с phase, artifact paths и опциями.
Задать вопрос в финальном сообщении и ждать ответа; инструмент запроса пользователя
использовать только если его доступная схема разрешает такой checkpoint. Не ставить
approval-вопрос в промежуточный commentary. Назвать и связать точный SKILL.md,
процитировать требование, объяснить, почему требуется ответ. Варианты: approve,
правки, отмена; для mockups также откатить/пропустить после отдельного подтверждения
удаления. Истечение времени и отсутствие ответа не являются approve.

Правки сохраняются в `user_revisions`; доработанный артефакт снова предъявляется.
Approve сохраняет `user_approved: true`, время и основание; cancel сохраняет state.
Если фаза неприменима (например, нет UI), сначала показать обоснование отсутствия
mockups на её checkpoint и записать согласованный skip; не молча убирать checkpoint.

Resume явно заданного slug не требует повторного выбора запуска. `in_progress`
требует согласования повторного выполнения фазы, `blocked` — retry/skip/stop с причиной,
`awaiting_approval` — показать тот же ожидающий checkpoint. Skip не может объявить
упавшие обязательные проверки успешными или снять блокер исходного бага. Все фазы
completed → повторить финальный отчёт, ничего не запускать заново автоматически.

## Browser adapter

Названия `browser_navigate`, `browser_snapshot`, `browser_resize`, `browser_tabs`,
`browser_console_messages` и т. п. в процедуре — семантика операций, **не обещание**
доступных tool names. Сначала discover tools, прочитать документацию реально доступного
браузера (например, `mcp__cua_repl`) или использовать локальный Playwright проекта.
Не выдумывать MCP API. Для CUA соблюдать его ограничения на evaluate, наблюдение DOM,
снимки и доступ к сети; если нет console/network capabilities — указать пробел, не
объявлять проверку пройденной. Независимые роли/видеозвонки — отдельные контексты/страницы,
fake media только в тестовом браузере. При отсутствии пригодного инструмента остановить
браузерную фазу с понятным blocked; не подменять реальный UI прогон чтением кода.

Серверы запускать с PTY/session или поддержанным background API, записывать handles;
ждать readiness до 120 секунд короткими polls (каждый ≤60 s). Останавливать только
свои процессы по handle/PID, не все процессы порта. Скриншоты — local ignored,
приложить реальные пути и не утверждать, что кадр снят, пока это не наблюдалось.

## Git-поставка и безопасный rollback

Явный вызов полного auto-pipeline включает прежний default: изолированная ветка,
стартовый draft PR через `node scripts/start-task-pr.mjs`, финальные commit/push и CI.
Пользовательский `local-only`/ограничение текущего запроса приоритетнее и записывается
в state. Стартовый скрипт — единственное исключение из запрета межфазных коммитов;
он может создать пустой стартовый коммит. Если сеть/токен недоступны — warning и
локальное продолжение, затем честно отметить непоставленную часть.

`--closes N` передавать только для issue, полностью входящего в scope; перед финальной
поставкой проверить полноту решения, иначе заменить на `Refs #N`. Сохранить существующую
секцию «Сессии Codex» и ссылки; приватные пути/содержимое транскриптов не публиковать.
`$news`, PR ready, merge и deploy — отдельная явная команда пользователя. Не запускать
`$e2e-check` автоматически и не удалять worktree после работы. Посторонние подтверждённые находки — отдельные deduplicated issues через `$create-issue`
и `$score-issues` по восстановленному default AGENTS.md; явный local-only/report scope
оставляет warning/open локально. Не расширять текущую реализацию.

Перед каждой попыткой review/QA fix сохранить patch/снимок затрагиваемого состояния.
После неудачи откатывать **только свою попытку**, сохраняя всё до неё (в том числе
ранние фиксы и пользовательские изменения). Не использовать `git checkout -- file`,
`reset --hard`, глобальный stash/reset ради локального отката. После проверки каждой
попытки отражать результат/откат в state, включая failed_fixes и тестовые доказательства.
