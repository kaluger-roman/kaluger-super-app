# Research: Смена пароля и email

**Feature Branch**: `023-change-password-email`
**Date**: 2026-02-24

## Research Questions & Decisions

### RQ-001: Хранение pendingEmail во время верификации

**Decision**: Добавить поле `pendingEmail` в модель User. Переиспользовать существующие поля `verificationCode` и `verificationCodeExpiry` для хранения кода подтверждения нового email.

**Rationale**: Пользователь уже верифицирован на момент смены email (он авторизован, а авторизация требует `isEmailVerified: true`). Поэтому поля `verificationCode` и `verificationCodeExpiry` свободны и могут быть переиспользованы. Нужно только одно новое поле `pendingEmail` для хранения нового адреса до подтверждения.

**Alternatives considered**:
- Отдельные поля `pendingEmailCode` + `pendingEmailCodeExpiry`: избыточно, дублирует существующие поля
- Отдельная таблица EmailChangeRequest: over-engineering для текущих требований
- Хранение в JWT/сессии: ненадёжно, теряется при перезагрузке

### RQ-002: Нужна ли Prisma-миграция для смены пароля?

**Decision**: Нет. Смена пароля обновляет существующее поле `password` в модели User. Миграция не требуется.

**Rationale**: Поле `password` уже существует в схеме. Смена пароля — это просто `prisma.user.update({ data: { password: newHash } })`.

### RQ-003: Должна ли смена пароля инвалидировать JWT-токен?

**Decision**: Нет. Текущая сессия остаётся валидной после смены пароля.

**Rationale**: JWT-токен содержит `{ userId, email }` — пароль не входит в payload. Токен валиден 7 дней и не зависит от пароля. Инвалидация потребовала бы token blacklist (Redis/БД), что выходит за рамки текущей задачи. Все другие устройства продолжат работать до истечения токена.

**Alternatives considered**:
- Инвалидация всех токенов: требует инфраструктуру blacklist, не оправдано для MVP
- Смена JWT_SECRET: инвалидирует ВСЕ сессии ВСЕХ пользователей

### RQ-004: Должна ли смена email генерировать новый JWT-токен?

**Decision**: Да. После успешной смены email система выдаёт новый JWT-токен с обновлённым email в payload.

**Rationale**: JWT содержит `{ userId, email }`. Если email сменился, текущий токен содержит устаревший email. Нужно обновить токен и сохранить его в localStorage на фронтенде.

### RQ-005: Где разместить UI смены пароля и email?

**Decision**: На существующей странице профиля (`/profile`), как отдельные секции под текущими полями (имя, ставка налога).

**Rationale**: Смена пароля и email — это действия управления аккаунтом, логически связанные с профилем. Отдельная страница не оправдана для двух форм. Текущая страница профиля уже содержит данные пользователя.

**Alternatives considered**:
- Отдельная страница `/settings`: over-engineering, нет других настроек для неё
- Модальные окна: менее удобны для форм с несколькими полями

### RQ-006: Структура фронтенд-кода по FSD

**Decision**: Создать feature `changePassword` и `changeEmail` в `frontend/src/features/`. Каждая feature содержит модель (Effector) и UI-компоненты. Страница профиля импортирует и рендерит их.

**Rationale**: Соответствует FSD-архитектуре проекта. Features — уровень для use-case модулей. Профильная страница (pages) компонует features.

### RQ-007: Переиспользование компонента ввода кода верификации

**Decision**: Компонент ввода 6-значного кода из `features/emailVerification/` НЕ переиспользуется напрямую. Создаётся новый экземпляр UI для смены email в рамках feature `changeEmail`, но логика ввода кода (6 полей, авто-переход, paste) будет вынесена в shared-компонент при необходимости.

**Rationale**: Текущий `EmailVerificationForm` тесно связан с моделью верификации при регистрации (есть кнопка logout, специфичная навигация). Для смены email нужна другая обёртка, но базовая механика ввода кода идентична. Если код дублируется значительно — вынести `CodeInput` в `shared/ui/`.

**Alternatives considered**:
- Полное переиспользование `EmailVerificationForm`: компонент слишком специфичен для регистрации
- Создание абстрактного `VerificationFlow`: over-engineering по принципу VII (Simplicity)
