# Phase 0 — Research & Decisions: Личный кабинет ученика (MVP)

**Feature**: 029-student-cabinet
**Date**: 2026-05-10

Этот документ собирает решения по неоднозначным точкам, выявленным на этапе планирования. Каждая запись:
- **Decision** — что выбрано
- **Rationale** — почему
- **Alternatives considered** — что отвергнуто и почему

Все решения уважают спецификацию ([spec.md](./spec.md)) и Constitution v1.0.0.

---

## R-01. Изоляция таблицы `StudentUser` vs роль в `User`

**Decision**: Отдельная таблица `StudentUser`. Аутентификация — отдельный JWT-секрет (`STUDENT_JWT_SECRET`), отдельный middleware (`authenticateStudent`), отдельный набор API-эндпоинтов (`/api/student-auth/*`, `/api/student-cabinet/*`).

**Rationale**:
- Зафиксировано пользователем в Clarifications спеки: явный выбор изоляции
- Минимизирует риск утечки репетиторских прав (контроллер с tutor-аутентификацией физически не может получить student-токен и наоборот — секреты разные, payload-ы разные)
- Существующий `adminAuth` уже использует тот же паттерн (отдельный секрет `ADMIN_JWT_SECRET`, отдельный middleware), новая роль идеологически встраивается рядом
- Существующая `User` (модель преподавателя) **не модифицируется** → нулевой риск регрессий в auth-сценариях преподавателя

**Alternatives considered**:
- *Поле `role` в `User`* — отклонено: требует модификации существующих эндпоинтов и middleware, большие тестовые поверхности регрессий, и явно отвергнуто пользователем
- *RBAC (отдельные таблицы Role/Permission)* — отвергнуто: overkill для двух ролей, нет UI для управления правами

## R-02. Логин: общая страница `/login` с тумблером

**Decision**: Единая страница `/login`, на ней — тумблер (Material UI `ToggleButtonGroup` или `Tabs`) с двумя положениями "Войти как: преподаватель / ученик". Положение тумблера определяет, какой axios-клиент и какой эндпоинт использовать (`/api/auth/login` или `/api/student-auth/login`). По умолчанию — "преподаватель" (сохраняем привычное поведение). `localStorage`-запоминание положения тумблера в MVP **не реализуется** (Simplicity), включается отдельной задачей если запросят.

**Rationale**:
- Зафиксировано пользователем
- ToggleButtonGroup с Material UI хорошо ложится на существующий стиль auth-форм
- Дефолт "преподаватель" — старое поведение для существующих пользователей не меняется ни визуально (тумблер только добавляется), ни функционально
- Никакого "автопоиска по обеим таблицам" — пользователь сам выбирает подсистему, никаких неоднозначностей по email-коллизиям

**Alternatives considered**:
- *Отдельные страницы `/login` и `/student/login`* — отвергнуто пользователем
- *Единый эндпоинт + определение роли по email* — отвергнуто: при том, что email уникален только в пределах своей таблицы, бэкенд не сможет однозначно решить, в какую подсистему стучаться, без хака с приоритетом таблиц

**Widget choice**: предпочесть `ToggleButtonGroup` (более очевидно "переключатель/тумблер" семантически), а не `Tabs` (которые обычно ассоциируются со страницами). Финальный выбор — на этапе реализации, по дизайну существующих auth-экранов.

## R-03. Хранение токенов и переключение сессий на одном устройстве

**Decision**: Два разных ключа в `localStorage`:
- `token` — существующий, для tutor-сессии (не трогаем)
- `studentToken` — новый, для student-сессии

Активным считается тот, чей контекст роута. Глобально оба токена могут лежать одновременно (если человек — и преподаватель, и ученик у кого-то), но в одной вкладке axios-клиент использует только один — выбираемый по контексту. На уровне UI: переключение между ролями = повторный логин (или редирект на `/login` с тумблером).

**Rationale**:
- Сохраняет старое поведение преподавательской сессии полностью
- Позволяет реалистичный кейс "преподаватель сам берёт уроки у другого преподавателя" — два аккаунта на одном устройстве, не мешают друг другу
- Не требует общей абстракции "current account" — каждая подсистема своими гардами на роутах проверяет свой токен

**Alternatives considered**:
- *Один ключ `token` для обеих подсистем* — отвергнуто: при переходе из tutor-кабинета в student-кабинет (например, в новой вкладке по student-invite) пришлось бы перетирать tutor-сессию, что злит пользователя
- *Cookie вместо `localStorage`* — отвергнуто: текущая система использует `localStorage` для tutor JWT, переход на cookies — отдельная фича безопасности, выходит за рамки

## R-04. Email-верификация для StudentUser — переиспользование, а не дублирование

**Decision**: Создать **отдельный сервис** `services/studentEmailVerification.ts`, который использует те же helpers (`utils/verification.ts`: `generateVerificationCode`, `getVerificationCodeExpiry`, `isResendCooldownActive`, константы `MAX_VERIFICATION_ATTEMPTS`, `RESEND_COOLDOWN_SECONDS`) и тот же `services/email.ts` для рассылки. Шаблон письма — тот же визуальный, но отдельная вызывающая функция (например, `sendStudentVerificationEmail`), чтобы при необходимости менять текст для ученика без риска для преподавателей.

**Rationale**:
- Constitution VII (Simplicity) — не вводим общий "verifiable account" интерфейс ради двух потребителей
- helpers в `utils/verification.ts` уже pure — переиспользуются без рефакторинга
- Бизнес-логика (счётчик попыток, cooldown, expiry) — в новом сервисе, чтобы не путать с tutor-кодом и не ловить регрессии

**Alternatives considered**:
- *Полное дублирование (copy/paste services/emailVerification + services/email-templates)* — отвергнуто: лишний код без выгоды
- *Generic `EmailVerification<T>` сервис с дженериком таблицы* — отвергнуто: преждевременная абстракция, текущие 2 потребителя не оправдывают сложности

**Поведение MVP до подтверждения email**: единообразно с tutor — ученик попадает в кабинет, видит баннер "Подтвердите email" с возможностью повторной отправки (cooldown 60 с) и ввода кода. Доступ к разделам кабинета **не блокируется** в MVP (баннер достаточен — повторяет существующий UX преподавателя).

## R-05. Жизненный цикл `StudentInvitation` и удаление карточки `Student`

**Decision**:
- `StudentInvitation.studentId` → `Student.id` с `onDelete: Cascade` — при удалении карточки её приглашения исчезают
- `Student.studentUserId` → `StudentUser.id` через **обратную связь** в `StudentUser` (см. R-06)
- Активная (`pending`) запись в `student_invitations` — максимум одна на `studentId`, гарантируется логикой сервиса (отзыв старой при выдаче новой) + проверкой при чтении (если по какой-то причине их две — берём самую свежую)
- Технический максимум жизни токена — **365 дней** через `expiresAt`. Поле выставляется при создании. Истёкшие токены чистятся cron-job'ом раз в сутки или просто отклоняются на стороне валидации (lazy cleanup). MVP — lazy cleanup; cron — позже при росте таблицы

**Rationale**:
- 365 дней — баланс между "не сгорает по таймеру" (как требовал пользователь) и защитой от вечно валидных токенов в БД
- Cascade на удалении `Student` упрощает консистентность — ни один потерянный invitation не валяется в таблице
- Lazy cleanup без cron-задачи (Simplicity для MVP)

**Alternatives considered**:
- *Без верхней границы* — отвергнуто: безопасность (вечный токен в БД — потенциальный вектор)
- *Срок 30/90 дней* — отвергнуто: пользователь явно сказал "долго"
- *Cron каждый день* — отложено за пределы MVP; добавим, когда таблица превысит ~10k записей

## R-06. Связь `Student ↔ StudentUser`

**Decision**: FK живёт на стороне `StudentUser`:
- `StudentUser.studentId` — `String?` (nullable), `@unique`, `@@index`, `onDelete: SetNull`
- При удалении/архивации `Student` → ссылка из `StudentUser` обнуляется, но сам `StudentUser` остаётся (ученик может войти, увидеть пустое расписание и текст "связь с преподавателем прекращена" в "Настройках")

Со стороны `Student` дополнительное поле `studentUserId` **не нужно** — обратная связь читается через `StudentUser` по уникальному `studentId` (и Prisma сделает обратную виртуальную связь сам).

**Rationale**:
- FK на "ребёнке" — стандартная практика для one-to-one в Prisma
- `SetNull` сохраняет аккаунт ученика при удалении карточки (требование пользователя)
- Меньше полей в `Student` (там и так много)

**Alternatives considered**:
- *FK на стороне `Student` (`studentUserId`)* — отвергнуто: семантически неверно, `Student` создаётся раньше; и пришлось бы добавлять поле в существующую часто-используемую таблицу
- *Связь many-to-many* — отвергнуто: 1:1 однозначно по спеке

## R-07. Уникальность email и cross-table коллизии

**Decision**: `StudentUser.email` имеет `@unique` (только в пределах своей таблицы). Никаких cross-table проверок нет. Один и тот же email может одновременно существовать как в `users` (tutor), так и в `student_users` (student) — это разные подсистемы со своими маршрутами входа.

**Rationale**:
- Зафиксировано пользователем (см. Clarifications спеки)
- Технически — простейшее решение: `unique` на колонке таблицы
- Поведенчески — реалистичный кейс: преподаватель сам учится у другого преподавателя, использует тот же email

**Alternatives considered**:
- *Уникальность системно (UNIQUE между таблицами)* — отвергнуто пользователем
- *DB-уровневый VIEW для cross-uniqueness* — overkill

**Edge case**: при попытке регистрации с email, уже занятым другим **`StudentUser`** — стандартная ошибка валидации формы (как при регистрации преподавателя сегодня). Cross-table коллизий не показываем — пользователю их видеть не нужно.

## R-08. Правила пароля для StudentUser

**Decision**: Полностью переиспользуем существующие правила из `services/changePassword.ts` / валидаторов tutor-регистрации (минимум 8 символов, заглавные и строчные буквы, цифра). Helper-функция извлекается в `utils/passwordPolicy.ts` (новый, общий) и используется обоими сервисами.

**Rationale**:
- Constitution V (Code Consistency) — единые правила для всей системы
- Уменьшает поверхность для расхождений в будущем

**Alternatives considered**:
- *Дублирование правил в `services/studentAuth.ts`* — отвергнуто: лишнее дублирование, риск рассинхронизации

## R-09. WebSocket / realtime для расписания ученика

**Decision**: Подключаем ученика к существующей WebSocket-инфраструктуре, но через **отдельный путь** `/ws/student?token=<studentToken>` рядом с существующим `/ws?token=<tutorToken>`. Используется один и тот же `WebSocketManager` с двумя независимыми пулами клиентов (`tutorClients: Map<userId, ws>`, `studentClients: Map<studentUserId, ws>`) и двумя путями аутентификации (`authenticateWebSocket` для tutor JWT и новый `authenticateStudentWebSocket` для student JWT). При изменении урока (`broadcastLessonStatusUpdate`, события создания/обновления/удаления/переноса) сервер шлёт уведомление **обоим** заинтересованным сторонам — преподавателю по `tutorId` (как сейчас) и ученику по `studentUserId`, если у урока `lesson.student.studentUser` существует и он подключён.

Фронт:
- В `features/studentSchedule/api/student-ws.ts` — open WS с `?token=<studentToken>` при монтировании страницы "Расписание", close при размонтировании или логауте
- На событиях `lesson_created`/`lesson_updated`/`lesson_deleted`/`lesson_status_updated` — Effector-эффект перезагружает текущую неделю расписания (или применяет точечный апдейт стора, если payload содержит достаточно полей)
- Авто-reconnect с экспоненциальным backoff'ом — единообразно с существующим tutor-клиентом

**Rationale**:
- Пользователь явно запросил realtime-обновления для ученика
- Изоляция сохраняется: разные пути, разные пулы клиентов, разные функции аутентификации, токены физически не смешиваются (tutor-token не подойдёт под `verifyStudentToken` и наоборот — секреты разные)
- Один экземпляр `WebSocketManager` (вместо двух) — меньше дублирования, общий метод `broadcastLessonStatusUpdate` принимает уже известные `tutorId` и опциональный `studentUserId` (получаемый из `lesson.student.studentUser` при вызывающем сервисе) и шлёт в оба пула
- Тесты разделения (cross-role secured): tutor token, открытый по `/ws/student`, должен быть отвергнут — и наоборот

**Alternatives considered**:
- *Не подключать (отложить за MVP)* — отвергнуто пользователем
- *Полностью отдельный `StudentWebSocketManager`* — отвергнуто: дублирует код роутинга и обработки соединений; единый менеджер с двумя пулами и двумя auth-стратегиями достаточно изолирован
- *Один общий путь `/ws` с `?role=tutor|student` в query* — отвергнуто: путь `/ws/student` явнее (видно по логам и сетевым инструментам), и не требует дискриминатора в auth-логике
- *Использовать SSE вместо WebSocket* — отвергнуто: проект уже на WS, плодить транспорты ради одной фичи нет смысла

**Что в payload уведомления** (минимальный набор для ученика, без чувствительных полей):
```ts
type StudentLessonWsEvent =
  | { type: "lesson_created";  lesson: StudentVisibleLesson }
  | { type: "lesson_updated";  lesson: StudentVisibleLesson }
  | { type: "lesson_deleted";  lessonId: string }
  | { type: "lesson_status_updated"; lessonId: string; status: LessonStatus };
```

Никаких полей `price`, `isPaid`, `notes`, `homework` в WS-сообщениях, отправляемых ученику (то же сужение, что и в `GET /api/student-cabinet/lessons`).

**Edge case**: если `Student` удалён/архивирован → сервер при следующей попытке вычислить `studentUserId` для `Lesson` каскадно их не найдёт (`Lesson` тоже удалятся каскадом). Если каким-то образом event дошёл, но `studentUserId` не определён — событие просто не отправляется в `studentClients`.

## R-10. Часовой пояс / форматирование времени уроков для ученика

**Decision**: Используем существующий механизм работы со временем (поле `User.timezone` у преподавателя — оно зафиксировано на уроках через `startTime`/`endTime`, ученик отображает их в **своём браузерном часовом поясе** по умолчанию). В MVP отдельного поля `timezone` для `StudentUser` не вводим.

**Rationale**:
- Constitution VII (Simplicity) — для MVP достаточно браузерного TZ
- Уроки сейчас хранятся в UTC через Prisma `DateTime`; преподаватель и ученик в одном городе, как правило, видят одно время — расхождений в подавляющем большинстве кейсов нет

**Alternatives considered**:
- *Поле `timezone` в `StudentUser`* — отложено за MVP
- *Принудительно отображать в TZ преподавателя* — отвергнуто: ученик может быть в другом регионе, и его собственный TZ для него понятнее

## R-11. UI расписания ученика — повторное использование, какого уровня?

**Decision**:
- **Не переиспользовать** компоненты из `features/lessons/ui/LessonsList/components/WeeklyView/*` (страховка от утечки тутор-функций — добавить урок, отметить оплаченным и т. п.)
- Создать `features/studentSchedule/ui/StudentWeeklyView` и `features/studentSchedule/ui/StudentLessonCard` как **новые** компоненты, копирующие визуальную идею (сетка дней, цветовое кодирование статусов)
- **Можно** переиспользовать примитивы из `@shared/ui` (например, базовые `<Box>`-обёртки, утилитарные хуки `useWeekRange`)
- Стили — `*.styled.ts` через styled-components, как везде в проекте

**Rationale**:
- Зафиксировано в спеке (FR-027) — пользователь явно потребовал отдельные компоненты
- "Утечка" функций репетитора (например, кнопка "+ Урок") — реальный риск, если случайно импортировать общий компонент
- `@shared/ui` примитивы безопасны: они не содержат бизнес-логики

**Alternatives considered**:
- *Полностью переиспользовать `WeeklyView` с пропсом `readonly`* — отвергнуто: подкрадывается риск пропустить пропс в одном месте, и tutor-кнопка появится у ученика
- *Дублировать всё, включая утилиты вычисления недели* — отвергнуто: ненужная разводка идентичной чистой логики

## R-12. Тумблер на `/login`: что делать при попытке входа неподходящим типом аккаунта

**Decision**: Бэкенд-эндпоинты `/api/auth/login` и `/api/student-auth/login` возвращают одинаково обтекаемое "Неверный email или пароль" при неуспешном входе (без раскрытия, существует ли email в другой подсистеме). Фронтенд тоже не подсказывает "попробуйте переключить тумблер".

**Rationale**:
- Безопасность — не даём злоумышленнику энумерировать почты в одной подсистеме через ответы другой
- Constitution VII — простой UX, не разводим спецсообщения

**Alternatives considered**:
- *"Этот email зарегистрирован как ученик — переключите тумблер"* — отвергнуто: раскрытие наличия аккаунта в другой подсистеме. Возможно вернёмся к этому позже как UX-улучшение, если оно окажется проблемой.

## R-13. Расширение `routes/students.ts` vs новый `routes/studentInvitations.ts` для tutor-эндпоинтов

**Decision**:
- Эндпоинты, где **репетитор** управляет приглашением своего ученика (`POST/GET/DELETE /api/students/:id/invitations`), живут в **существующем** `routes/students.ts` + `controllers/students/invitations.ts` (новая под-папка) — концептуально это "ещё одна операция над карточкой ученика", и таб "Ученики" репетитора уже имеет такие операции
- Эндпоинт **публичной валидации** токена (`GET /api/student-invitations/validate/:token`) живёт в **новом** `routes/studentInvitations.ts` — он не требует авторизации и не относится к области репетитора

**Rationale**:
- Авторизационные требования у этих эндпоинтов разные (требуют tutor JWT vs публичные) — разделение по файлам делает middleware-стек и тесты понятнее
- Существующий `routes/students.ts` уже содержит mutations над карточкой ученика — invitations логично присоединяются туда
- Публичная валидация — отдельный, узкий поверхности эндпоинт с собственным rate-limit'ом

**Alternatives considered**:
- *Все invitation-эндпоинты в `routes/studentInvitations.ts`* — отвергнуто: публичные и tutor-эндпоинты со страшно разной авторизацией в одном файле — путаница в middleware-цепочке

## R-14. Разрешение/ограничение генерации ссылки для архивированного `Student`

**Decision**: Если `Student.archived === true` — генерация новой ссылки **запрещена**. UI показывает соответствующее пояснение (например, "Архивированному ученику нельзя выдать приглашение — снимите архивацию"). Существующие `pending`-приглашения архивированного ученика **продолжают** работать (если ученик зайдёт по такой ссылке до архивации — ничего не сломается, но тогда edge-case "карточка архивирована, ученик регистрируется" обрабатывается как обычная регистрация и далее продолжает существовать с `studentId === null` после деактивации связи).

**Rationale**:
- Архивация = "ученик неактивен" — выдавать ему приглашение нелогично
- Не ломаем уже выданные ссылки — иначе пользователю придётся помнить, не архивировал ли он перед отправкой ссылки

**Alternatives considered**:
- *Запретить и активные ссылки сразу при архивации* — отвергнуто: излишняя сложность, и противоречит принципу "ссылка живёт долго и сгорает только при использовании"
- *Разрешить генерацию для архивированного* — отвергнуто: семантически странно

## R-16. Хранение и повторный показ raw invitation-URL преподавателю

**Decision**: Raw-токен показывается преподавателю **один раз** — в ответе на `POST /api/students/:id/invitations` (момент создания). После этого на сервере остаётся только SHA-256 хеш (FR-015), и повторно сформировать URL для копирования сервер не может. Если преподаватель закрыл/обновил карточку, не скопировав ссылку — он видит "Ссылка создана, ожидает регистрации (создана X дней назад)" и кнопки "Создать новую ссылку" (отзывает старую и выдаёт новую) и "Отозвать". UX чуть жёстче, чем "показать сохранённый URL", но это плата за безопасность.

**Rationale**:
- Соответствует общепринятой практике для one-time tokens (GitHub PAT, Slack invite links, и т. д. — показывают raw только при создании)
- Уменьшает риск утечки raw-токенов через доступ к БД или backup'ам
- Для tutor-UX это нечасто (создал → сразу скопировал → отправил), и кнопка "Создать новую" покрывает случай "не скопировал"

**Alternatives considered**:
- *Хранить raw-токен на сервере* — отвергнуто: размывает смысл хеширования
- *Шифровать raw-токен ключом сервера и расшифровывать при чтении* — отвергнуто: усложняет инфраструктуру (key management) ради удобства, которое решается одной кнопкой "Создать новую"
- *Сохранять последний URL в `localStorage` преподавателя* — отвергнуто: не работает между устройствами; преподаватель открыл карточку с телефона — URL не виден

**Frontend-следствие**: компонент `features/tutorStudentInvitation/InvitationManager` хранит только-что-выпущенный URL в локальном Effector-сторе на время сессии. При смене карточки или перезагрузке страницы — URL теряется, и UI переключается в режим "ссылка есть, но скопировать нельзя — пере-выпустить?".

## R-15. Логаут ученика

**Decision**: Стандартный фронтенд-логаут — удаление `studentToken` из `localStorage` + редирект на `/login`. Бэкенд логаут-эндпоинт `POST /api/student-auth/logout` опционально (для будущих server-side blacklists), но в MVP ничего не делает кроме 204 No Content (тот же паттерн, что у tutor-логаута).

**Rationale**:
- Симметрия с существующим tutor-логаутом
- JWT — stateless, серверного блок-листа нет, удаление токена на клиенте достаточно

**Alternatives considered**:
- *Сложный механизм инвалидации (сервисная таблица revoked tokens)* — отвергнуто: вне рамок MVP, существующий tutor-логаут такой же
