# Feature Specification: Real-Time Data Synchronization

**Feature Branch**: `023-realtime-data-sync`
**Created**: 2026-02-25
**Status**: Draft
**Input**: User description: "Если с другого устройства поменять данные в 'мои данные', они не обновятся на другом открытом устройстве. Все обновления в системе должны быть синхронизированы."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Синхронизация профиля репетитора между устройствами (Priority: P1)

Репетитор открыл приложение на ноутбуке и на телефоне. На телефоне он обновил своё имя и налоговую ставку в разделе "Мои данные". На ноутбуке данные профиля автоматически обновились без перезагрузки страницы.

**Why this priority**: Это основной сценарий, описанный пользователем. Профиль — наиболее критичная для пользователя информация, которая должна быть консистентной на всех устройствах.

**Independent Test**: Можно протестировать, открыв два браузера с авторизованным пользователем, изменив профиль в одном и проверив обновление в другом.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован на двух устройствах, **When** он изменяет имя на одном устройстве, **Then** имя обновляется на втором устройстве в течение 3 секунд без перезагрузки
2. **Given** пользователь авторизован на двух устройствах, **When** он изменяет налоговую ставку на одном устройстве, **Then** ставка обновляется на втором устройстве в течение 3 секунд
3. **Given** пользователь авторизован, но WebSocket-соединение временно разорвано, **When** соединение восстанавливается, **Then** система получает актуальные данные профиля

---

### User Story 2 - Синхронизация списка учеников между устройствами (Priority: P1)

Репетитор добавил нового ученика, отредактировал данные существующего или архивировал ученика на одном устройстве. На другом открытом устройстве список учеников автоматически обновился.

**Why this priority**: Ученики — ключевая сущность приложения. Несинхронизированные данные учеников приводят к ошибкам при создании уроков и расчёте статистики.

**Independent Test**: Открыть два браузера, создать/изменить/архивировать ученика в одном, проверить обновление в другом.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован на двух устройствах и список учеников открыт, **When** он создаёт нового ученика на одном устройстве, **Then** ученик появляется в списке на втором устройстве без перезагрузки
2. **Given** пользователь авторизован на двух устройствах, **When** он изменяет данные ученика на одном устройстве, **Then** данные обновляются на втором устройстве
3. **Given** пользователь авторизован на двух устройствах, **When** он архивирует ученика на одном устройстве, **Then** ученик перемещается в архив на втором устройстве
4. **Given** пользователь авторизован на двух устройствах, **When** он разархивирует ученика на одном устройстве, **Then** ученик возвращается в активный список на втором устройстве
5. **Given** пользователь авторизован на двух устройствах, **When** он удаляет ученика на одном устройстве, **Then** ученик исчезает из списка на втором устройстве

---

### User Story 3 - Полная синхронизация данных уроков между устройствами (Priority: P1)

Сейчас между устройствами синхронизируется только статус урока. Все остальные данные урока (время, цена, домашнее задание, оценки, заметки) должны также синхронизироваться при создании, изменении и удалении уроков.

**Why this priority**: Уроки — центральная сущность приложения. Неполная синхронизация (только статус) создаёт ложное впечатление актуальности данных, хотя другие поля могут быть устаревшими.

**Independent Test**: Открыть два браузера, создать/изменить/удалить урок в одном, проверить полное обновление данных в другом.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован на двух устройствах, **When** он создаёт новый урок на одном устройстве, **Then** урок появляется на втором устройстве без перезагрузки
2. **Given** пользователь авторизован на двух устройствах, **When** он изменяет детали урока (время, цену, домашнее задание, оценку, заметки) на одном устройстве, **Then** все изменённые поля обновляются на втором устройстве
3. **Given** пользователь авторизован на двух устройствах, **When** он удаляет урок на одном устройстве, **Then** урок исчезает на втором устройстве
4. **Given** пользователь авторизован на двух устройствах, **When** cron-задача обновляет статус урока, **Then** статус обновляется на обоих устройствах (сохранение текущего поведения)

---

### User Story 4 - Синхронизация новостей между устройствами (Priority: P2)

Когда пользователь отмечает новость как прочитанную на одном устройстве, статус прочтения должен синхронизироваться на другие устройства, чтобы индикатор непрочитанных новостей был актуален.

**Why this priority**: Новости — менее критичная функциональность по сравнению с профилем, учениками и уроками, но несинхронизированный индикатор непрочитанных новостей раздражает пользователя.

**Independent Test**: Открыть два браузера, отметить новость прочитанной в одном, проверить что индикатор обновился в другом.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован на двух устройствах и имеет непрочитанные новости, **When** он отмечает новость как прочитанную на одном устройстве, **Then** счётчик непрочитанных новостей обновляется на втором устройстве
2. **Given** пользователь авторизован на двух устройствах, **When** появляется новая новость, **Then** индикатор непрочитанных новостей обновляется на обоих устройствах

---

### Edge Cases

- Что происходит при одновременном редактировании одних и тех же данных на двух устройствах? — Применяется стратегия "последний пишет побеждает" (last-write-wins): последнее сохранённое изменение перезаписывает предыдущее на обоих устройствах
- Что происходит если WebSocket-соединение разорвано в момент изменения данных? — При восстановлении соединения клиент запрашивает актуальные данные с сервера
- Что происходит при медленном соединении? — Данные на инициирующем устройстве обновляются сразу через HTTP-ответ, на других устройствах обновляются при получении WebSocket-сообщения
- Что происходит если пользователь находится на странице, не связанной с изменёнными данными? — Данные обновляются в фоновых хранилищах; при переходе на соответствующую страницу пользователь видит актуальные данные

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST синхронизировать изменения профиля пользователя (имя, налоговая ставка) на все подключённые устройства этого пользователя в реальном времени
- **FR-002**: Система MUST синхронизировать все операции с учениками (создание, редактирование, архивирование, разархивирование, удаление) на все подключённые устройства пользователя
- **FR-003**: Система MUST синхронизировать полные данные урока (не только статус) при создании, редактировании и удалении на все подключённые устройства пользователя
- **FR-004**: Система MUST синхронизировать статус прочтения новостей и появление новых новостей на все подключённые устройства пользователя
- **FR-005**: Система MUST отправлять синхронизационные события только тому пользователю, который владеет данными (не всем подключённым пользователям)
- **FR-006**: Система MUST обеспечивать получение актуальных данных после восстановления разорванного WebSocket-соединения
- **FR-007**: Система MUST сохранять обратную совместимость с существующей синхронизацией статусов уроков
- **FR-008**: Система MUST удалять удалённый урок из всех хранилищ на стороне клиента при получении события удаления

### Key Entities

- **Профиль пользователя**: Имя, налоговая ставка. Принадлежит одному пользователю. Редактируется только владельцем.
- **Ученик**: Имя, контактные данные, статус (активный/архивный). Принадлежит одному репетитору. Может быть создан, отредактирован, архивирован, разархивирован, удалён.
- **Урок**: Дата/время, длительность, цена, домашнее задание, оценка, заметки, статус. Связан с учеником и репетитором.
- **Новость**: Заголовок, содержание, версия. Статус прочтения привязан к пользователю.

## Assumptions

- Приложение — однопользовательское (каждый репетитор видит только свои данные), поэтому конфликтные ситуации между разными пользователями невозможны
- Конфликты между устройствами одного пользователя решаются стратегией "последний пишет побеждает" — это приемлемо, так как один человек вряд ли будет редактировать одни и те же данные одновременно на двух устройствах
- Существующая инфраструктура WebSocket (подключение, аутентификация, переподключение) используется повторно без существенных изменений
- При восстановлении соединения клиент перезапрашивает данные через существующие HTTP-эндпоинты, а не через специальный механизм "дельта-синхронизации"

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Изменения данных на одном устройстве отображаются на другом подключённом устройстве в течение 3 секунд
- **SC-002**: 100% мутаций данных (профиль, ученики, уроки, новости) вызывают синхронизацию на подключённые устройства
- **SC-003**: После восстановления разорванного соединения все данные на клиенте актуальны в течение 5 секунд
- **SC-004**: Пользователь не теряет данные при одновременном редактировании с двух устройств — одно из изменений всегда применяется
- **SC-005**: Существующая функциональность синхронизации статусов уроков продолжает работать без регрессий
