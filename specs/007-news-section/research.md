# Research: Раздел «Новости»

**Branch**: `007-news-section` | **Date**: 2026-02-22

## R-001: Механизм создания новостей из changelog

**Decision**: Backend CLI-скрипт `npm run news:generate`, который парсит CHANGELOG.md, фильтрует пользовательски значимые изменения и создаёт запись в БД через Prisma.

**Rationale**:
- Процесс контролируется разработчиком (запускается вручную)
- Прямой доступ к БД через Prisma — не нужен API-эндпоинт для создания
- Скрипт может запускаться как локально, так и на сервере при деплое
- Интеграция с существующим workflow: `/changelog` → `npm run news:generate` → deploy

**Alternatives considered**:
- API-эндпоинт `POST /api/news` — требует аутентификацию, нет админ-роли в системе, избыточно для одного разработчика
- Claude Code skill `/news` — слишком связан с конкретным AI-инструментом, не переносим
- Prisma seed при деплое — усложняет процесс деплоя, seed предназначен для начальных данных

## R-002: Хранение статуса прочтения новостей

**Decision**: Таблица `news_read_status` с полями `userId` и `lastReadAt`. Одна запись на пользователя.

**Rationale**:
- Простейший подход: сравниваем `lastReadAt` пользователя с `publishedAt` самой свежей новости
- Одна запись на пользователя, а не на каждую новость — минимум данных
- Достаточно для бейджа «есть непрочитанные» без необходимости отслеживать каждую отдельную новость

**Alternatives considered**:
- Таблица «прочтений» для каждой новости (many-to-many) — избыточно, нет необходимости знать, какие именно новости прочитаны
- Хранение lastReadAt в модели User — загрязняет существующую модель нерелевантным полем
- LocalStorage на фронтенде — не синхронизируется между устройствами

## R-003: Пагинация новостей

**Decision**: Cursor-based пагинация (cursor + take). Cursor — ID последней загруженной новости.

**Rationale**:
- Стандартный подход для хронологических лент
- Нет проблем со сдвигом данных при добавлении новых записей
- Простая реализация через Prisma `cursor` + `take` + `skip: 1`

**Alternatives considered**:
- Offset-based (page + limit) — проблемы со сдвигом при добавлении записей, но допустимо при малом объёме данных. Решено использовать offset-based для простоты, т.к. новостей будет мало.

**Updated Decision**: Offset-based пагинация (page + limit) — проще в реализации, объём данных минимальный (десятки записей, не тысячи).

## R-004: Фильтрация пользовательски значимых изменений

**Decision**: Включаются секции changelog: Added, Changed, Fixed, Removed, Security. Исключаются: Infrastructure, DevOps, рефакторинг, тесты.

**Rationale**:
- Совпадает с форматом Keep a Changelog, используемым в проекте
- Infrastructure-секция уже выделена в changelog — легко отфильтровать
- Пользователю важны: новые функции, изменения поведения, исправления багов, удалённые возможности, исправления безопасности

## R-005: Где расположить раздел «Новости» в навигации

**Decision**: Новый пункт в сайдбаре после основных разделов, перед профилем. Отдельная страница `/news`.

**Rationale**:
- Соответствует паттерну навигации в приложении (sidebar + page)
- Не требует изменений в существующих страницах
- Бейдж на пункте сайдбара — стандартный UX-паттерн

## R-006: Формат данных новости

**Decision**: Поля: `id`, `title` (заголовок), `content` (Markdown-текст), `version` (опциональная ссылка на версию), `publishedAt` (дата публикации), `createdAt`.

**Rationale**:
- `title` — краткое описание обновления для списка
- `content` — Markdown для структурированного описания (списки изменений)
- `version` — опциональная привязка к версии changelog
- `publishedAt` — может отличаться от `createdAt` (контент готовят заранее)
- Не привязано к конкретному пользователю (новости глобальные)
