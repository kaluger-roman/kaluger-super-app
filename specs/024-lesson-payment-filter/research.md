# Research: Фильтрация уроков по дате оплаты

## Decision 1: Подход к фильтрации на бэкенде

**Decision**: Добавить два новых query-параметра `paymentDateFrom` и `paymentDateTo` в существующий endpoint `GET /api/lessons`. Фильтрация по `paymentDate` поле Lesson модели с использованием Prisma `gte`/`lte`.

**Rationale**: Поле `paymentDate` (DateTime?) уже существует в модели Lesson. Существующий endpoint уже поддерживает множество фильтров — добавление двух новых параметров следует устоявшемуся паттерну. Не требуется миграция БД.

**Alternatives considered**:
- Отдельный endpoint `/api/lessons/by-payment-date` — отклонён, т.к. дублирует функциональность и нарушает текущий паттерн единого endpoint с фильтрами.
- Фильтрация на клиенте — отклонена, т.к. данные пагинированы и не все уроки загружены.

## Decision 2: Взаимодействие фильтров «неоплаченные» и «дата оплаты»

**Decision**: При включении `onlyUnpaid` автоматически сбрасывать `paymentDateFrom`/`paymentDateTo` на фронте. На бэкенде: если `onlyUnpaid=true`, игнорировать `paymentDateFrom`/`paymentDateTo`.

**Rationale**: Неоплаченные уроки по определению не имеют `paymentDate`. Применение обоих фильтров одновременно вернёт пустой результат — это запутает пользователя.

**Alternatives considered**:
- Показать предупреждение без автоматического сброса — отклонено, т.к. добавляет лишний шаг и не решает проблему.
- Запретить включение `onlyUnpaid` при активном фильтре дат — отклонено, т.к. менее интуитивно.

## Decision 3: UI-компонент для фильтра по дате

**Decision**: Два MUI `DatePicker` (дата начала, дата окончания) + набор MUI `Chip` для предустановленных периодов. Размещение внутри существующего компонента `LessonsFilters`.

**Rationale**: В проекте уже используется `@mui/x-date-pickers/DatePicker` (в `ReportsPage/DateRangeFilter`). Chip-компоненты MUI — стандартный способ для preset-кнопок. Размещение в существующем фильтре сохраняет консистентность.

**Alternatives considered**:
- Отдельная панель/карточка для фильтра дат — отклонена, занимает больше места и отделена от связанных фильтров.
- Select/dropdown с предустановленными периодами — отклонён, т.к. Chip'ы дают более быстрый доступ и визуально понятнее.

## Decision 4: Хранение состояния фильтра

**Decision**: Новые Effector-сторы `$paymentDateFrom`, `$paymentDateTo`, `$paymentDatePreset` в существующем файле `lessons-filters.model.ts`. Тип preset: `"currentMonth" | "lastMonth" | "currentWeek" | null`.

**Rationale**: Следует паттерну существующих фильтров (`$onlyUnpaid`, `$onlyWithoutHomework`). Стор preset позволяет подсветить активный чип.

**Alternatives considered**:
- Отдельный файл модели `lessons-payment-filter.model.ts` — отклонён, т.к. фильтры логически связаны и существующий файл мал (17 строк).

## Decision 5: Передача дат в API

**Decision**: Параметры `paymentDateFrom` и `paymentDateTo` передаются как ISO-строки. На бэкенде конвертируются: `paymentDateFrom` — начало дня (00:00:00), `paymentDateTo` — конец дня (23:59:59.999).

**Rationale**: Пользователь выбирает даты (без времени). Включение полного дня для обеих границ обеспечивает интуитивное поведение — если выбран 15 марта как конечная дата, все оплаты 15 марта попадут в результат.

**Alternatives considered**:
- Передавать точные ISO-timestamp — отклонено, т.к. DatePicker возвращает дату без времени, и нужна нормализация.
