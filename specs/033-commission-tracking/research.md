# Research: Учёт комиссий по ученикам (033-commission-tracking)

**Feature**: `033-commission-tracking` | **Phase**: 0 | **Spec**: [spec.md](./spec.md)

Спека утверждена и не содержит маркеров `[NEEDS CLARIFICATION]`. Ниже —
технические решения, которые спека сознательно оставляет реализации,
и обоснование каждого. Все решения проверены по коду в этом worktree.

---

## R1. Хранение: новое поле `Student.commissionAmount`

**Decision**: `commissionAmount Decimal @db.Decimal(10, 2) @default(0)`
(NOT NULL) в модели `Student` (`backend/prisma/schema.prisma`).
Миграция — `ALTER TABLE "students" ADD COLUMN "commissionAmount"
DECIMAL(10,2) NOT NULL DEFAULT 0;`.

**Rationale**: `Decimal(10,2)` — ровно тот тип, которым в схеме уже описаны
все денежные величины (`Student.hourlyRate`, `Lesson.price`,
`TaxRatePeriod.rate`), значит точность до копеек (FR-001, edge case
«комиссия задана с копейками») получается бесплатно и согласованно.
`NOT NULL DEFAULT 0` даёт бэкфилл существующих строк одним DDL —
PostgreSQL проставит 0 всем уже заведённым ученикам в момент применения
миграции, отдельный `UPDATE` не нужен (FR-003, SC-002). Nullable-поле
потребовало бы `?? 0` в каждом месте чтения и допускало бы состояние
«комиссия не задана», которого в спеке нет.

**Alternatives considered**:

- `Int` в копейках — быстрее и без плавающей точки, но ломает единообразие
  со всеми остальными деньгами в схеме и требует конвертации на каждой
  границе. Отклонено.
- Отдельная таблица `student_commissions` — спека прямо фиксирует
  «одна сумма на ученика, нескольких комиссий не бывает» и «отдельный
  журнал выплат не ведётся» (Assumptions). Таблица была бы
  over-engineering (конституция, принцип VII). Отклонено.
- Хранение рассчитанного зачёта на уроке (`Lesson.commissionCredit`) —
  см. R2. Отклонено.

## R2. Зачёт комиссии — производная величина, не хранимая

**Decision**: ни сумма зачёта по уроку, ни «погашено»/«осталось» по ученику
в БД не хранятся. Всё вычисляется на лету из
(`student.commissionAmount`, полный хронологический список уроков ученика)
чистой функцией при каждом ответе API.

**Rationale**: спека требует полного ретроактивного пересчёта при
изменении суммы комиссии, цены урока, статуса, отметки об оплате,
переносе, отмене, удалении и добавлении урока (FR-013, FR-021, Edge Cases).
Любое хранимое значение пришлось бы инвалидировать во всех этих точках —
это денормализация с семью источниками рассинхрона ради величины,
которая считается одним линейным проходом по урокам одного ученика.
Инвариантов SC-003 / SC-010 («отклонение 0 ₽ при любых изменениях»)
производный расчёт достигает по построению, хранимый — только при
безошибочной инвалидации.

**Alternatives considered**:

- Материализованное поле на `Lesson` + пересчёт в хуках сервисов
  создания/обновления/удаления урока и обновления ученика. Отклонено:
  7 точек инвалидации, риск рассинхрона, нарушает принцип VII.
- Кэш агрегатов на `Student` (`commissionRepaid`). Отклонено по той же
  причине; выигрыш только в статистике, где всё равно нужен полный
  список уроков для атрибуции по дате оплаты (R5).

## R3. Точность денег: считаем в копейках целыми числами

**Decision**: чистый аллокатор работает в целых копейках
(`Math.round(rub * 100)`), наружу отдаёт рубли (`kop / 100`).

**Rationale**: SC-003 и SC-010 требуют отклонения ровно 0 ₽. Цепочка
`min(remaining, price)` с вычитанием на `number` в рублях накапливает
ошибку двоичной дроби (классическое `0.1 + 0.2`), и «погашено + осталось»
перестаёт точно равняться комиссии. Целые копейки делают инвариант
арифметически точным. Исходные значения приходят из
`Prisma.Decimal(10,2)` — то есть уже ограничены двумя знаками, округление
при входе безопасно и не теряет данных.

**Alternatives considered**:

- Арифметика на `Prisma.Decimal` внутри аллокатора. Корректно, но тянет
  Prisma-тип в чистую утилиту (`backend/src/utils/`), которая по
  конституции (принцип II) должна быть свободна от инфраструктуры,
  и усложняет юнит-тесты. Отклонено.
- Округление результата до 2 знаков на выходе каждой операции.
  Маскирует проблему, но не гарантирует точного равенства суммы.
  Отклонено.

## R4. Алгоритм распределения: два прохода, факт по дате оплаты

**Decision**: один чистый аллокатор, два последовательных прохода
по списку уроков ученика, каждый со своей сортировкой.

1. **Сортировка**: факт — по эффективной дате оплаты
   (`paymentDate ?? startTime`) возрастающе; прогноз — по `startTime`
   возрастающе. В обоих случаях tie-break по `id` лексикографически, что
   даёт детерминированный порядок при совпадающих датах (Edge case «два
   урока с одинаковой датой и временем»). Факт идёт по дате оплаты, чтобы
   порядок зачёта совпадал с базой дат показателя списаний (FR-010):
   иначе оплата раннего урока задним числом переписывала бы цифру
   за уже закрытый период. У неоплаченных уроков порядка оплат нет,
   поэтому прогноз остаётся хронологическим по дате урока.
2. **Проход 1 — факт**: `remaining = commissionAmount`. Урок участвует,
   если `price > 0 && status === "COMPLETED" && isPaid === true`
   (FR-006 — ровно набор уроков показателя «Заработок»).
   `credit = min(remaining, price)`, `remaining -= credit`. Урок с
   `credit > 0` получает пометку `{ amount, state: "FACT" }`.
3. **Проход 2 — прогноз**: стартует от `remaining`, оставшегося после
   прохода 1 (Assumptions спеки: «прогноз считается в два прохода»).
   Урок участвует, если `price > 0` и он ещё может погасить комиссию:
   `status ∈ {SCHEDULED, RESCHEDULED, IN_PROGRESS}` **или**
   (`status === "COMPLETED" && !isPaid`). `forecast = min(remaining, price)`,
   `remaining -= forecast`. Урок получает `{ amount, state: "FORECAST" }`.

**Rationale**: два прохода — прямое требование Assumptions: иначе ранний
неоплаченный урок «съел» бы часть остатка и сдвинул бы фактические зачёты,
а прогноз по определению не должен влиять ни на одну денежную цифру
(FR-020, SC-009). Один урок по построению получает максимум одну пометку:
множества «факт» и «прогноз» не пересекаются (FR-007 — «у одного урока
одновременно MUST NOT быть двух пометок»).

**Статусы**: в схеме нет статуса `MISSED` — «пропущенные» уроки спеки
в этой кодовой базе представлены `CANCELLED`. `RESCHEDULED` — это активный
статус предстоящего урока (уже используется так в
`backend/src/services/statistics/statistics.constants.ts:ACTIVE_STATUSES`
и в `lessonStatusUpdater`), поэтому он прогноз-годен. Итог: из обоих
проходов исключён только `CANCELLED`.

**Уроки без ученика**: пробные уроки с `studentId === null` в аллокатор
не попадают вовсе — комиссия привязана к ученику (FR-016).

**Alternatives considered**:

- Один проход с «резервированием» остатка под неоплаченные уроки.
  Отклонено: прогноз начал бы влиять на факт, нарушая SC-009.
- Сортировка по `createdAt` или по `id`. Отклонено: FR-005 явно
  требует хронологию по дате урока.
- Tie-break по `createdAt`. Работает, но `id` (cuid) уже уникален
  и монотонен по времени создания — отдельное поле в выборке не нужно.

## R5. Период списания — по дате оплаты, с существующим fallback

**Decision**: фактический зачёт относится к периоду по
`paymentDate ?? startTime`, и диапазон совпадает с тем, что уже
используется для «Поступления за период» и налога.

**Rationale**: FR-010 требует относить списание по дате оплаты — «той же
базе дат, что у показателя „Поступления за период“ и у расчёта налога».
В коде эта база — `paidInRangeWhere` в
`backend/src/services/statistics/statistics.helpers.ts`, которая уже
обрабатывает legacy-уроки без `paymentDate`:
`OR: [{ paymentDate: range }, { paymentDate: null, startTime: range }]`,
и `computeTaxSummary` передаёт в разбивку `lesson.paymentDate ?? lesson.startTime`.
Повторяем ровно это правило, чтобы «списано в счёт комиссий» и
«поступления за период» никогда не расходились по набору уроков.
Отдельного решения спека тут не требует — конвенция уже есть в коде.

**Alternatives considered**:

- Игнорировать уроки без `paymentDate`. Отклонено: показатель списаний
  разошёлся бы с «Поступлениями за период» на legacy-данных.

## R6. Где вычисляется зачёт: общий сервис `commission` + чистая утилита

**Decision**:

- `backend/src/utils/commission.ts` — чистая функция-аллокатор
  (`allocateCommission`), без Prisma, без побочных эффектов.
- `backend/src/services/commission/` — оркестрация с Prisma:
  батч-загрузка уроков нужных учеников, раскладка результатов
  по `lessonId` / `studentId`, агрегаты для статистики.
  Состав папки по `docs/conventions/backend.md`: `commission.ts` +
  `commission.types.ts` + `commission.helpers.ts` + `index.ts`.

**Rationale**: конституция, принцип II — «Utils are pure functions with
no side effects or state», вся бизнес-логика с БД живёт в `services/`.
Аллокатор — самая нагруженная тестами часть фичи (весь список edge cases
спеки проверяется на нём юнит-тестами без БД), поэтому он обязан быть
чистым.

**Важное следствие из состояния кода**: у учеников **нет сервисного слоя** —
`backend/src/controllers/students/*` ходят в Prisma напрямую и отдают
**сырую модель Prisma** (`res.json({ students })`), без какого-либо
`toStudentDto`. Аналогично `backend/src/services/lessonsQuery/lessonsQuery.ts`
(`fetchLessonsPage`) возвращает сырые строки с `include: { student: true }`.
Значит:

- `commissionAmount` начнёт отдаваться клиенту **автоматически**, как только
  появится колонка: `backend/src/lib/prisma.ts` патчит
  `Prisma.Decimal.prototype.toJSON` в `toNumber()`, поэтому новый
  `Decimal`-столбец сериализуется числом без единой правки маппера;
- производные `commissionRepaid` / `commissionRemaining` и
  `lesson.commissionCredit`, наоборот, **негде** появиться сами —
  для них нужно явное обогащение ответа. Поэтому сервис комиссий
  экспонирует две функции обогащения (`attachCommissionToStudents`,
  `attachCommissionToLessons`), которые вызываются в
  `getStudents` / `getStudent` / `createStudent` / `updateStudent`
  и в `fetchLessonsPage`. В `fetchLessonsPage` это первый маппер поверх
  сырых строк — его появление и есть вся структурная правка слоя уроков.

**Принятое допущение**: `GET /api/lessons` вкладывает в каждый урок
полную строку ученика (`include: { student: true }`), поэтому
`commissionAmount` поедет и там. Это тьютор-онли роут (за
`authenticateToken`), фронтовый тип `Lesson.student` — `Pick<…>` без полей
комиссии, лишнее поле просто игнорируется. Сужать `include` до `select`
ради этого не будем: правка затронула бы весь слой уроков ради
косметики (принцип VII). В кабинет ученика эти данные не попадают —
см. R11.

## R7. Батч-загрузка: не N+1

**Decision**: во всех трёх потребителях (список уроков, список учеников,
статистика) уроки учеников с `commissionAmount > 0` грузятся **одним**
`prisma.lesson.findMany({ where: { studentId: { in: ids } }, select: {…} })`
и группируются в памяти по `studentId`.

**Rationale**: зачёт по уроку зависит от **всех** уроков ученика с самого
первого, а не только от попавших в текущую страницу выдачи — значит
страничной выборки недостаточно и нужен отдельный запрос. Один запрос
на весь набор учеников страницы вместо запроса на ученика снимает N+1.
`select` — минимальный: `id, studentId, startTime, price, status, isPaid,
paymentDate`.

**Guard (важно для FR-003)**: если у репетитора нет ни одного ученика
с `commissionAmount > 0`, дополнительный запрос **не выполняется вовсе**,
а в DTO не добавляется ни одного поля комиссии. Это и гарантия
«ничего не изменилось» для репетиторов без комиссий, и отсутствие
регрессии по производительности для большинства пользователей.

**Alternatives considered**:

- Считать зачёт на фронте. Отклонено: фронт видит только страницу уроков
  и не может знать более ранние уроки ученика; плюс расчёт нужен
  и в статистике (FR-010), где фронта с уроками нет.
- Один SQL-запрос с оконной функцией (`SUM(...) OVER (PARTITION BY ...)`).
  Отклонено: сырой SQL в обход Prisma, два прохода на окнах выражаются
  громоздко, тестируется хуже чистой функции (принцип VII).

## R8. Контракт API — зафиксирован на этапе макетов

**Decision**: типы, уже объявленные в `frontend/src/shared/types/`
на этапе макетов, и есть финальный контракт; бэкенд реализуется под них.

- `Lesson.commissionCredit?: { amount: number; state: "FACT" | "FORECAST" } | null`
  (`frontend/src/shared/types/lesson.ts`) — одна пометка на урок;
  `null`/отсутствие = пометки нет (FR-008).
- `Student.commissionAmount / commissionRepaid / commissionRemaining`
  (`frontend/src/shared/types/student.ts`) — первое хранимое,
  два последних производные.
- `Statistics.hasCommissionStudents / commissionWrittenOffSum /
  commissionRemainingTotal` (`frontend/src/shared/types/statistics.ts`).

**Rationale**: макеты уже собраны на реальных компонентах против этих
типов и утверждены пользователем. Менять форму контракта сейчас значит
переписывать утверждённый UI. Зеркальные типы добавляются в
`backend/src/types/` (`student.ts`, `lesson.ts`, статистика), как того
требует конвенция «Shared types split by domain».

**`hasCommissionStudents`** считается по **всем** ученикам репетитора,
включая архивных: у архивного ученика прошлые фактические списания
остаются и должны показываться в прошлых периодах (FR-017 + edge case
«ученик архивирован»). А вот `commissionRemainingTotal` суммирует остаток
**только по неархивированным** (FR-025).

## R9. Форматирование денег с копейками

**Decision**: `formatCurrency` из `@shared` получает необязательный
параметр опций, включающий показ копеек; поведение по умолчанию
не меняется. Пометки о комиссии, блок прогресса и показатели статистики
комиссий вызывают его с этим флагом.

**Rationale**: текущая реализация округляет до целых рублей, а edge case
спеки «комиссия задана с копейками, остаток меньше рубля» требует
показать дробный остаток корректно. Менять поведение `formatCurrency`
глобально нельзя: FR-003 требует, чтобы численные значения всех
существовавших до фичи показателей остались прежними, а у функции
десятки call-site'ов. Опциональный параметр со старым значением
по умолчанию даёт нулевое влияние на существующий UI.

**Alternatives considered**:

- Автоматически показывать копейки, когда дробная часть ненулевая.
  Соблазнительно, но это глобальное изменение поведения всех
  существующих денежных надписей — выходит за рамки спеки и нарушает
  FR-003. Отклонено.
- Отдельная функция `formatCurrencyPrecise`. Рабочий вариант, но
  дублирует локаль/символ валюты; параметр проще (принцип VII).
  Оставлено как запасной вариант, если сигнатура с опциями окажется
  хуже читаемой на call-site'ах.

## R10. Актуальность данных без перезагрузки (FR-013, SC-006)

**Проблема**, найденная в коде: `frontend/src/app/model/webSocket.model.ts`
обрабатывает единственное сообщение `lesson_status_updated` и точечно
патчит один урок через `lessonModel.updateLesson`;
`frontend/src/entities/lesson/models/stores.model.ts` на
`updateLessonFx.doneData` тоже заменяет **только изменённый** урок
в сторах. Между тем отметка урока оплаченным меняет пометки **соседних**
уроков того же ученика (прогноз сдвигается — US2 сценарий 11), его блок
прогресса и показатели статистики.

**Decision**: после мутаций урока (создание, обновление, удаление)
и после сохранения ученика перезагружать активные списки уроков /
учеников, а не патчить один элемент — но **только когда у репетитора
есть ученики с ненулевой комиссией**. Флаг берётся из уже загруженных
данных (`$statistics.hasCommissionStudents` / наличие ученика
с `commissionAmount > 0` в сторе учеников). Страница статистики
перезагружается по своему `ReportsPageGate.open` /
`statisticsLoadRequested` — это уже реализовано и отдельной работы
не требует.

**Rationale**: гарантирует корректность пометок и прогресса в рамках
сеанса без ручного обновления страницы (FR-013, SC-006, US4 сценарий 7),
и при этом для репетиторов без комиссий поведение приложения не меняется
ни на один сетевой запрос (FR-003).

**Alternatives considered**:

- Возвращать в ответе мутации урока пересчитанные зачёты по всем урокам
  ученика и патчить их точечно. Меньше трафика, но нестандартная форма
  ответа и заметное усложнение моделей. Отклонено (принцип VII).
- Новое WebSocket-событие «комиссия пересчитана». Отклонено:
  существующий WS-канал рассчитан на статусы уроков, добавление домена
  туда — расширение инфраструктуры ради одной фичи.

## R11. Изоляция от кабинета ученика (FR-015)

**Decision**: DTO кабинета ученика (`backend/src/services/studentCabinet/`,
`backend/src/types/studentCabinet.ts`) не расширяется ни одним полем
комиссии; сервис комиссий в этот путь не подключается. Покрывается
интеграционным тестом, который явно проверяет отсутствие полей
`commission*` в ответах кабинета.

**Rationale**: кабинет собирает ответ по собственным типам с явным
`select`, а не переиспользует DTO репетитора, — значит утечки по умолчанию
нет. Но FR-015 — требование безопасности, а не стиля, поэтому его нужно
закрепить тестом, а не только отсутствием кода.

## R13. Валидация комиссии: и в UI, и в модели, и на сервере

**Состояние кода**: на фронте у формы ученика **нет стора ошибок полей** —
единственная проверка живёт guard'ом в
`frontend/src/features/students/models/studentForm.model.ts` и показывает
**тост** (`notificationsModel.showErrorEvent`), а не ошибку под полем.
Компонент `CommissionField` уже умеет рисовать ошибку, но его
`isCommissionInvalid` вычисляется локально на рендере и **никак не блокирует
`formSubmitted`**. На бэке валидация ручная, в
`backend/src/controllers/students/validators.ts`, и существующая проверка
ставки написана как `if (data.hourlyRate && data.hourlyRate < 0)` —
truthiness-паттерн, который пропускает `NaN` и не различает «поле
не прислано» и «прислан 0».

**Decision**: три уровня, каждый обязателен.

1. **UI** — `CommissionField` продолжает показывать
   `COMMISSION_ERROR_TEXT` («Комиссия не может быть отрицательной»)
   под полем; это уже утверждённый макет.
2. **Модель** — в `studentForm.model.ts` добавляется guard по образцу
   проверки имени: `formSubmitted` с невалидной комиссией уходит в
   `showErrorEvent` и **не** доходит до `validatedSubmit`, значит
   сохранения не происходит (FR-004). Без этого guard'а форма
   сохранила бы отрицательное значение, несмотря на красное поле.
3. **Сервер** — `validateCreateStudentDto` / `validateUpdateStudentDto`
   отвергают отрицательное и нечисловое значение явной проверкой
   (`typeof !== "number" || Number.isNaN || < 0`), а не truthiness;
   пустое/`null`/`undefined` нормализуется в `0` в `prepareUpdateData`,
   потому что колонка `NOT NULL DEFAULT 0` (FR-004: «пустое поле
   трактуется как 0»).

**Rationale**: FR-004 требует, чтобы сохранение **не происходило** —
красной подсветки поля для этого недостаточно. Серверная проверка нужна
независимо от клиента (API открыт для любого авторизованного клиента).
Повторять здесь truthiness-баг соседнего поля нельзя: `0` — совершенно
легальное значение комиссии, и `if (value && value < 0)` на нуле
ведёт себя случайно.
