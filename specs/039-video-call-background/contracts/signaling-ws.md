# Contract: сигналинг звонка — дополнения 039

Расширяет `specs/030-webrtc-video-calls/contracts/signaling-ws.md`. Протокол единый для любого клиента (браузер, PWA, нативная оболочка PR #95): состояния — доменные (FR-030), без браузерных событий. Транспорт — существующие `/ws` (преподаватель) и `/ws/student` (ученик). Все новые типы добавляются в `CALL_SIGNAL_TYPES` (бэкенд) и в парсеры обеих сторон; неверно сформированные сообщения отбрасываются молча, как сейчас.

## Общие типы

```ts
type PresenceState = "on_screen" | "background";
type PeerPresence = PresenceState | "disconnected";

type CallSnapshot = {
  callId: string;
  status: "ringing" | "accepted" | "connected";
  direction: "incoming" | "outgoing";          // с точки зрения получателя снимка
  peerName: string;
  lesson: CallLessonSummary | null;
  iceServers: IceServer[];                      // свежие TURN-учётки для получателя
  peerPresence: { presence: PeerPresence; audioSuspended: boolean; videoSuspended: boolean };
  connectedAt: string | null;                   // ISO, для счётчика длительности
};
```

## Клиент → сервер

### `presence_update`

```json
{ "type": "presence_update", "presence": "on_screen", "audioSuspended": false, "videoSuspended": false }
```

- Без `callId`: присутствие участника, а не звонка. Шлётся после `connection_ready` и при каждой смене видимости/состояния медиа.
- Валидация: `presence ∈ {on_screen, background}`, флаги — boolean; иначе отброс.
- Сервер: сохраняет в реестре присутствия; если участник в звонке — `call_peer_presence` собеседнику (только при изменении); если адресат `ringing`-звонка ушёл в `background` и push ещё не отправлялся — отправляет push (R3).
- Ответа нет (ни на `on_screen`, ни на `background`): снимок звонка запрашивается отдельно — `call_sync`.

### `call_sync`

```json
{ "type": "call_sync" }
```

- Без полей: запрос «что сейчас с моим звонком». Ответ — `call_state` (ниже) отправителю.
- Клиент шлёт его по каждому сокету с транспортом при возврате страницы на экран, по сокету, ставшему готовым (`connection_ready`), если страница на экране или у неё есть звонок этой роли (скрытая страница без звонка не спрашивает: звонок, которого у неё нет, восстанавливается, когда на экран смотрят), и при открытии уведомления о звонке.
- Ответ заодно подтверждает живость сокета: нет `call_state` за `CALL_STATE_REPLY_TIMEOUT_MS` (3 с) при звонке этой роли → сокет переоткрывается (R7).

### `call_resume`

```json
{ "type": "call_resume", "callId": "…", "sessionRestart": true }
```

- `sessionRestart: true` — у клиента новое `RTCPeerConnection`, о котором собеседник ещё не знает (звонок восстановлен из снимка: холодный старт, другое окно). Флаг держится до подтверждения сервера `call_restart_announced`: запись в сокет ещё не значит, что сервер её получил (сокет мог умереть сразу после неё). Пока `call_resume` с `true` ждёт подтверждения на живом сокете, следующие `call_resume` несут `false` (собеседник не пересобирает соединение второй раз); пропал этот сокет (закрылся или не ответил на `call_sync`) до подтверждения → следующий `call_resume` этого звонка снова несёт `true`.
- Клиент шлёт `call_resume` и сразу после восстановления звонка в `ringing` (звонящий, отмеченный сервером как отключённый, иначе остался бы таким до конца ожидания).
- Сервер:
  1. звонка нет или отправитель не участник → ответ `call_state { call: null }`;
  2. повторная авторизация пары (как в `call_invite`) не прошла или не удалась (сбой БД: ошибка логируется, `call_error` не отправляется) → звонок завершается (`call_ended { reason: "hangup" }` собеседнику, запись по `resolveHangupStatus`), ответ `call_state { call: null }`;
  3. сокет, по которому пришёл `call_resume`, уже не зарегистрирован (закрылся или его заменил другой сокет участника, пока шла авторизация) → ничего не меняется и ответа нет: участник по-прежнему отключён, таймер ожидания идёт. Страница, чей сокет теперь зарегистрирован, пришлёт свой `call_resume` (вернувшаяся страница — после `call_state` по новому сокету): иначе вернувшийся телефон, вытеснивший вкладку, пущенную по `4004`, получил бы засчитанным её `call_resume { sessionRestart: true }`, а собеседник пересобрал бы соединение под `RTCPeerConnection`, которого нет (уточнение после code review, итерация 3);
  4. иначе: снять `disconnectedAt`/таймер отправителя; собеседнику `call_peer_resumed` (если участник был отключён или `sessionRestart`), затем `call_peer_presence` с актуальным присутствием отправителя; при `sessionRestart` после этого отправителю `call_restart_announced`;
  5. пересборка для собеседника из п. 4 запоминается до подтверждения доставки (`LiveCall.pendingPeerRestart`: сокет, в который она записана, или `null`). Собеседнику без соединения (отключён — есть `disconnectedAt` — или сокета нет) она не шлётся (`null`). Запись в сокет, который сервер ещё считает живым (сокет-зомби после сна iOS), пропадает бесследно, поэтому доставку подтверждает только любой сигнал собеседника по тому же сокету. Если собеседник присылает свой `call_resume` по другому сокету (или пересборка не отправлялась), сервер шлёт ему `call_peer_resumed { sessionRestart: true }` в ответ, после п. 4 для него, один раз; `call_resume` по тому же сокету только снимает ожидание. Вернувшийся сам с `sessionRestart: true` пересборку не получает: её делает другая сторона по его `call_peer_resumed { sessionRestart: true }`.
- Идемпотентно: повтор без отключения и без `sessionRestart` собеседнику ничего не шлёт (отправителю — только пропущенную пересборку из п. 5).

### `call_accept` / `call_reject` — новое необязательное поле `pushEndpoint`

```json
{ "type": "call_accept", "callId": "…", "pushEndpoint": "https://…" }
```

- `pushEndpoint` — endpoint push-подписки устройства, которое ответило или отклонило вызов (`registration.pushManager.getSubscription()`). Клиент читает его заранее, пока вызов звонит (`call_incoming`, восстановление звонка, регистрация service worker во время звонка), и не ждёт его при ответе: не успел прочитать, нет подписки или service worker — поле не отправляется. Повторный `call_accept` при восстановлении (`call_state` со звонящим вызовом, ниже) несёт его так же.
- Валидация: непустая строка не длиннее `PUSH_ENDPOINT_MAX_LENGTH` (2048); иначе отбрасывается только поле, сигнал обрабатывается как без него.
- Сервер запоминает его в `LiveCall.answeringEndpoint` и не шлёт этому устройству закрывающий `call_closed` (contracts/call-notification-push.md). Endpoint сужает только подписки самого адресата: чужой или неизвестный ничего не исключает.
- Своё уведомление о вызове (тег `call-<callId>`) ответившая страница закрывает сама (`registration.getNotifications`), там где платформа это позволяет.

Существующий `call_hangup` при выходе из аккаунта отправляется клиентом до закрытия сокета (FR-003: выход завершает звонок сразу).

## Сервер → клиент

### `call_state`

```json
{ "type": "call_state", "call": null }
{ "type": "call_state", "call": { "callId": "…", "status": "connected", "direction": "outgoing", "peerName": "…", "lesson": null, "iceServers": [ … ], "peerPresence": { "presence": "on_screen", "audioSuspended": false, "videoSuspended": false }, "connectedAt": "2026-10-27T10:00:00.000Z" } }
```

Ответ на `call_sync` и на неудачный `call_resume`. Реакция клиента — research R5, а также:

- снимок звонка, который эта страница сама завершила (`call_hangup`/`call_reject`/`call_cancel` ушли раньше, чем сервер их обработал), звонок не восстанавливает и ничего не завершает; клиент повторяет свой завершающий сигнал (сервер игнорирует его для уже снятого звонка);
- звонящий в `outgoing`, а снимок `accepted`/`connected` (`call_accepted` потерялся вместе с сокетом) → как `call_accepted`: камера/микрофон и offer, плюс `call_resume`;
- адресат уже ответил (`connecting`), а снимок `ringing` (`call_accept` не дошёл, пока сокета не было) → `call_accept` повторяется;
- приглашение ушло по сокету, который закрылся до `call_ringing`: снимок на новом сокете решает его судьбу — звонок есть → восстанавливается из снимка, `null` → завершается локально («Звонок завершён»). Пока сокет не терялся, снимок до `call_ringing` по-прежнему игнорируется. Если пользователь отменил такое приглашение до снимка (`callId` неизвестен, `call_cancel` отправить было некуда), первый снимок этой роли с исходящим звонком его не восстанавливает: клиент отправляет `call_cancel` с `callId` из снимка (сервер снимает звонящий вызов или, если адресат успел ответить, кладёт трубку). Новое приглашение до снимка отменяет это ожидание: сервер сам заменяет им ещё звонящий прежний вызов;
- после `call_resume` звонка с медиа клиент повторяет `call_media_state` (изменение, сделанное без сокета, до собеседника не дошло);
- снимок того же звонка (`resume`) применяет `peerPresence`: `call_peer_presence`, отправленный, пока сокета не было, потерян (уточнение после code review, итерация 4).

`call_accepted` звонка, которого у клиента нет, клиент не завершает `call_hangup`: он шлёт `call_sync` по сокету этой роли (если уже не ждёт ответа на него; скрытая страница без звонка этой роли — когда на неё посмотрят), и `call_state` восстанавливает звонок или повторяет завершающий сигнал страницы (уточнение после code review, итерация 4).

### `call_peer_presence`

```json
{ "type": "call_peer_presence", "callId": "…", "presence": "background", "audioSuspended": true, "videoSuspended": true }
```

- `disconnected` сервер ставит сам при `participantDisconnected`.
- Также отправляется каждой стороне при переходе `ringing → accepted`, если присутствие собеседника не `on_screen`.

### `call_peer_resumed`

```json
{ "type": "call_peer_resumed", "callId": "…", "sessionRestart": false }
```

`sessionRestart: true` → получатель пересобирает `RTCPeerConnection` с теми же локальными треками и шлёт offer (R6). Если пересобирать нечего — адресат ответил, но offer ещё не получал, — он строит соединение сам (камера/микрофон, video m-line) и шлёт offer как вежливая сторона.

`{ sessionRestart: true }` приходит и в ответ на собственный `call_resume` получателя, если собеседник пересобрал соединение, пока у получателя соединения не было, или получатель вернулся по другому сокету, а по прежнему после просьбы о пересборке ничего не прислал (`call_resume`, п. 5).

### `call_restart_announced`

```json
{ "type": "call_restart_announced", "callId": "…" }
```

Подтверждение отправителю `call_resume { sessionRestart: true }`: сервер принял его и передал собеседнику `call_peer_resumed { sessionRestart: true }`, а собеседнику без соединения или с сокетом, по которому доставка не подтвердилась, передаст на его `call_resume` (п. 5). Клиент перестаёт просить пересборку для этого звонка. Приходит раньше offer пересобравшегося собеседника (тот же сокет, сервер шлёт его первым).

### `call_ended` — новая причина

`reason: "peer_not_returned"` — у собеседника истёк период ожидания (FR-005). Фронт: тост ошибки «Собеседник не вернулся в звонок».

### `call_incoming` — идемпотентность

Повторный `call_incoming` с `callId`, равным текущему, игнорируется (раньше уходил `call_reject` как «занят»).

## Поведение сервера при транспорте

| Событие транспорта | Было | Стало |
|--------------------|------|-------|
| `close`/`error` зарегистрированного сокета | `terminateActiveCallForParticipant` | `participantDisconnected` (ожидание 3 мин; для адресата `ringing` без устройств — как раньше; с устройствами вызов продолжается, push уходит, если ещё не уходил, а если этот push (отправленный сейчас или раньше, пока адресат был в фоне) не доставлен ни на одно устройство и адресат не вернулся — `call_unavailable` звонящему, `MISSED`; повторно push не отправляется) + ожидающие сокеты закрываются `4004`, если звонок удерживается (в том числе продолжающийся вызов адресата) |
| замена сокета той же вкладки | `terminateActiveCallForParticipant` | звонок не трогается; присутствие остаётся тем, что знает собеседник, пока новая страница не пришлёт своё `presence_update` (смена пересылается собеседнику) |
| регистрация сокета | — | сервису звонков не сообщается; участник без присутствия считается `on_screen` |
| сокет другой вкладки/устройства, пока у участника звонок | ждать конца звонка | `wait`: ждать + проба живости держателя (`ping`, `terminate` через 5 с без `pong`). Исключения: (1) входящий вызов, ещё не принятый (`ringing`, участник — адресат): его не держит ни одно окно, поэтому новое подключение без `resume=1` (страница, открытая по уведомлению) забирает соединение (старый сокет закрывается `4000`), а `resume=1` получает отказ `4000`, как без звонка; (2) звонок ждёт возврата участника (`disconnectedAt` участника, `call_resume` после потери ещё не было): зарегистрированное соединение (например, скрытая вкладка, пущенная по `4004`) звонок не подхватило и не держит, поэтому новое подключение без `resume=1` и `resume=1` страницы, чьё соединение держало звонок при потере (`tab` = `LiveCall.disconnectedTabId`; без `tab` у той страницы — любой `resume=1`), забирают соединение (старый сокет закрывается `4000`); `resume=1` других вкладок (например, второй вкладки, отпущенной тем же `4004`) получает отказ `4000`. После `call_resume` звонок снова держит соединение, которое его прислало |
| отзыв токена (`disconnectUser`) | завершить звонок | `participantRevoked`: звонок завершается сразу, в том числе когда сокета уже нет и звонок ждёт возврата участника |
