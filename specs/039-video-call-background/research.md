# Research: 039 — видеозвонок переживает сворачивание приложения

Все неизвестные из Technical Context закрыты здесь. Формат: Decision / Rationale / Alternatives. Факты о коде проверены по ветке `039-video-call-background` (после merge `main`).

## R1. Что сейчас обрывает звонок (база для изменений)

Проверено в коде:

- `backend/src/lib/websocket/webSocketManager.ts`: `release()` в `close`/`error` зарегистрированного сокета вызывает `terminateActiveCallForParticipant` → звонок завершается сразу. То же при замене сокета той же вкладки (`previous && previous !== ws` → `terminateActiveCallForParticipant`).
- Heartbeat 30 с (`HEARTBEAT_INTERVAL_MS`): сокет без pong завершается `terminate()` → `close` → звонок завершён. Свёрнутая страница iOS перестаёт отвечать через 30–60 с.
- `callFlow.ringCallee`: нет `connectionOf(callee)` → запись `MISSED` + `call_unavailable`.
- Фронт: `socketConnection.model` → `detachTransportFx` → `callModel.transportDisconnected` → `callSignals.model` → `callConnectionLost` → звонок завершается локально с «Связь с сервером потеряна, звонок завершён».
- Фронт: `peerConnection.model` `connectionState === "failed"` → `callFailed` в любой фазе.
- Звук собеседника играет через `<video>` (`CallVideo`, `muted` только у своей плитки); iOS ставит `<video>` на паузу в фоне → звук умирает. Компонент `RemoteAudio` удалён на этапе макетов, вместо двух плашек одна `ContinueCallOverlay`.

## R2. Удержание звонка при потере соединения (FR-003…FR-006, FR-027)

**Decision**: транспорт сообщает сервису звонков только доменные факты потери связи: `participantDisconnected(participant)` (и `participantRevoked` при отзыве токена). Регистрацию сокета сервис не получает (уточнение после code review, итерация 2: прежний `participantConnected` сбрасывал присутствие в `on_screen` при замене сокета той же вкладки молча, и собеседник оставался на «свернул приложение»; теперь присутствие держится до `presence_update` новой страницы). Сервис (`services/callSignaling/callReconnect.ts`) держит в `LiveCall` по участнику `disconnectedAt` и таймер ожидания `CALL_RECONNECT_GRACE_MS = 180_000`. Потеря соединения не завершает звонок; таймер завершает его через 3 минуты (`call_ended` с причиной `peer_not_returned` ожидающему, запись по `resolveDropOutcome`, `endedAt = disconnectedAt`). Замена сокета той же вкладки и регистрация нового сокета звонок не трогают. Немедленное завершение остаётся только для отзыва токена (`disconnectUser`) и явного `call_hangup`.

**Rationale**: WebSocketManager — лишь один из транспортов; нативная оболочка (PR #95) будет говорить по тому же протоколу и вызовет те же функции (FR-027). Таймер в памяти процесса достаточен: звонки и так живут в памяти (`liveCalls`), рестарт сервера обрывает их и сейчас.

**Alternatives**: держать grace-логику в `WebSocketManager` (отвергнуто: привязка к браузерному транспорту, FR-027); хранить состояние звонка в БД (отвергнуто: избыточно для 1 процесса, YAGNI).

## R3. Особые случаи до ответа (уточнение 2026-10-27)

**Decision**:
- Звонящий потерял связь во время `ringing` → вызов продолжается до ответа/таймаута 40 с (таймер ожидания тоже запущен, но таймаут вызова наступает раньше). Ответ адресата при недоступном звонящем переводит звонок в `accepted`; `call_accepted` звонящий узнаёт при возврате из `call_state` (status `accepted`).
- Адресат потерял связь во время `ringing`: есть устройства для уведомлений о звонках → вызов продолжается, ожидающие вкладки адресата освобождаются (`4004`), push отправляется, если ещё не отправлялся; если этот push (или отправленный раньше, пока адресат был в фоне: `LiveCall` хранит исход доставки) не доставлен ни на одно устройство, а адресат не вернулся — как в `ringCallee`: `call_unavailable` звонящему, `MISSED`; нет устройств → прежнее поведение (`call_unavailable`, `MISSED`).
- Входящий вызов, ещё не принятый, не держит соединение: новое подключение адресата без `resume=1` (страница, открытая по уведомлению на другом устройстве, пока вызов показывает фоновая вкладка) забирает соединение, а не ждёт (уточнение после code review, итерация 2). Принятый звонок держит соединение, как раньше (R7). Вкладка, у которой так забрали соединение (или которой сервер отказал в `resume=1` с `4000`), пока у неё звенит этот вызов той же роли, завершает его локально без сигналов (вызов теперь звенит там), а не держит экран входящего с «Восстанавливаем связь…» до `LOCAL_GRACE_TIMEOUT_MS`. Отказ `4000` в `resume=1` при любом другом звонке этой роли (`outgoing`/`connecting`/`active`) означает, что звонка на сервере уже нет (держимый звонок дал бы `wait`, ждущий возврата — регистрацию страницы, которая его держала): страница сразу завершает его локально с тостом «Звонок завершён» (уточнение после code review, итерация 3). Если же заменён зарегистрированный сокет страницы со звонком (другая страница забрала звонок, ждавший возврата участника), звонок завершается без тоста. Нажатие на уведомление в уже открытом приложении (`call_notification_opened`) — явное действие, как «Использовать здесь»: сокет без зарегистрированного соединения (нет сокета, переподключение с `resume=1` после возврата на страницу, `elsewhere = "tab"`) открывается заново без `resume=1`; ждущий сокет (`elsewhere = "call"`) и зарегистрированный не трогаются. Зарегистрированный сокет может оказаться мёртвым (iOS после сна): пока ждём снимок для нажатого уведомления, `call_sync` проверяется на живость по всем сокетам, куда ушёл (а не только по сокету звонка страницы), и мёртвый сокет переоткрывается без `resume=1` — иначе другое устройство, держащее соединение, отказало бы `4000` и вместо входящего показалось бы «Использовать здесь» (issue #135).
- Пока свой сокет потерян, звонок в фазе вызова (`outgoing`/`incoming`) ждёт локально не дольше `RINGING_GRACE_TIMEOUT_MS = 45_000` (таймаут вызова 40 с + запас), а не `LOCAL_GRACE_TIMEOUT_MS`: сервер снимает непринятый вызов по таймауту независимо от сокета, и рингтон/гудки не должны звучать по уже снятому вызову. Вызов, принятый адресатом, пока звонящий был без сокета, вернётся из снимка при возврате сокета (уточнение после code review, итерация 3).
- Присутствие адресата «в фоне» во время `ringing` (свернул на экране входящего) → push, если ещё не отправлялся.

**Rationale**: соответствует Edge Cases спеки и не ломает FR-014.

## R4. Присутствие и состояние медиа (FR-002, FR-011, FR-030, FR-033)

**Decision**: клиент шлёт `presence_update { presence: "on_screen" | "background", audioSuspended, videoSuspended }` при каждой готовности сокета и при каждой смене видимости (`visibilitychange`, `pagehide`). Сервер хранит последнее значение на участника (реестр присутствия, сбрасывается при отключении) и, если участник в звонке, пересылает собеседнику `call_peer_presence { callId, presence, audioSuspended, videoSuspended }`; при потере соединения сервер сам шлёт `presence: "disconnected"`. При переходе звонка в `accepted` каждой стороне отправляется текущее присутствие собеседника, если оно не «на экране».

Флаги медиа — фактическое состояние, а не факт фона: `audioSuspended = !capability.backgroundAudio || micTrack.muted` (при уходе в фон), `videoSuspended = !capability.backgroundVideo || cameraTrack.muted`. На экране флаги берутся из `muted` треков (события `mute`/`unmute`). `capability` — чистый хелпер по платформе: iOS/iPadOS (WebKit, `isIos()`) — нет фонового микрофона и камеры; Android — микрофон есть, камеры нет; десктоп — есть оба. Нативная оболочка позже сообщит `audioSuspended: false`, и подписи пропадут без правок логики (FR-033).

Решение владельца после ручного QA (итерация 1, находка #2): янтарная плашка «Микрофон … приостановлен — … свернул приложение» (FR-011/FR-032) заменяет красный значок выключенного микрофона и тогда, когда участник выключил микрофон сам до сворачивания; так и оставлено, как в макете.

**Rationale**: доменные состояния без браузерных терминов (FR-030); подписи у собеседника определяются фактом медиа (FR-033); статус приходит за ≤5 с — сигнал уходит синхронно в `visibilitychange`, у iOS на это есть несколько секунд.

**Alternatives**: определять фон на сервере по heartbeat (отвергнуто: 30–60 с задержки, нет данных о медиа); слать присутствие внутри `call_media_state` (отвергнуто: присутствие нужно и вне звонка — для решения «отправлять ли push», FR-013/FR-018).

## R5. Восстановление звонка: `call_state` и `call_resume` (FR-004, FR-005, FR-008, FR-017)

**Decision**: на запрос `call_sync` (возврат на экран, готовый сокет, открытие уведомления; уточнение после code review: раньше ответом служил `presence_update(on_screen)`, из-за чего снимок с TURN-учётками уходил и на каждое mute/unmute трека) сервер отвечает снимком `call_state { call: CallSnapshot | null }` — звонок, в котором участник состоит (любой статус), или `null`. `presence_update` ответа не имеет. Клиент, получив снимок:
- локально звонка нет, снимок есть → восстанавливает: `ringing` + `incoming` → экран входящего; `ringing` + `outgoing` → экран вызова; `accepted`/`connected` → получает камеру/микрофон, строит новое `RTCPeerConnection`, шлёт `call_resume { callId, sessionRestart: true }`;
- локальный звонок совпадает со снимком → `call_resume { callId, sessionRestart: false }` (`true`, пока сервер не подтвердил `call_restart_announced`, что собеседнику передана пересборка для нового `RTCPeerConnection` восстановленного звонка); недостающие шаги догоняются (`call_accepted`, потерянный звонящим; неотправленный `call_accept`; `call_media_state`) — см. contracts/signaling-ws.md; присутствие собеседника берётся из снимка (`peerPresence`): `call_peer_presence`, ушедший в мёртвый сокет, иначе потерян, и плашка «свернул приложение»/«Восстанавливаем связь…» висела бы поверх живого видео (уточнение после code review, итерация 4);
- локальный звонок есть (фаза `incoming`/`connecting`/`active`), а снимок `null` или про другой звонок → звонок завершается локально без сигналов, тост «Звонок завершён» (FR-005/FR-006); снимок про другой звонок (у участника на сервере один звонок, значит, локальный кончился, а пришёл новый — например, входящий в сокет-зомби) затем восстанавливается, как при отсутствии локального звонка (решение `replace`, уточнение после code review, итерация 3); восстановление нового запрашивается по `callTerminated` заменяемого, а не параллельно с его завершением, чтобы сброс старого звонка не стёр новый (итерация 4);
- `call_accepted` звонка, которого у страницы нет, трубку не кладёт: страница шлёт `call_sync` по сокету этой роли (если ответа на прежний ещё ждёт — ждёт его), и снимок решает: звонок восстанавливается (например, у перезагрузившегося звонящего) или, если страница сама его завершила, повторяется её завершающий сигнал (`endedHere`). Скрытая страница без звонка этой роли не спрашивает (как `toReadySync`): звонок с камерой и звуком не включается там, куда никто не смотрит, а снимок придёт, когда на неё посмотрят. Раньше такая страница (вкладка, впущенная по `4004`) клала трубку в момент ответа (уточнение после code review, итерация 4);
- есть ожидающий `callId` из уведомления → снимок с этим `callId` снимает ожидание, а тост «Звонок уже завершён» (FR-017) показывается, только когда без него ответили все роли, куда ушёл `call_sync` (`$syncPendingRoles` пуст): во вкладке с сессиями преподавателя и ученика снимок `null` одной роли ещё ничего не решает (уточнение после code review, итерация 3).

Сервер на `call_resume`: участник не состоит в звонке / звонка нет → ответ `call_state { call: null }`; повторная авторизация пары (как при `call_invite`: `resolvePairForStudent` / принадлежность ученика) не прошла → звонок завершается (`call_ended` собеседнику), ответ `call_state null`; иначе снимает `disconnectedAt` и таймер, шлёт собеседнику `call_peer_resumed { callId, sessionRestart }` и текущее присутствие. Повторный `call_resume` без изменений идемпотентен (собеседнику ничего не шлётся, кроме случая `sessionRestart`).

Порядок сообщений на одном сокете гарантирует согласованность: снимок `null`, вычисленный до `call_ringing`, придёт раньше него и застанет `$callId === null` (no-op).

**Rationale**: один путь для тёплого возврата, холодного старта, перехода звонка в другое окно, «вернулся — а звонок кончился» и устаревшего уведомления. Ответ на `call_sync` заодно проверяет живость сокета (R7).

**Alternatives**: сервер сам шлёт снимок при регистрации сокета (отвергнуто: клиенту и так нужно сообщить присутствие, а явный запрос даёт и проверку живости после возврата); отдельное сообщение `call_resume_failed` (отвергнуто: `call_state null` выражает то же).

## R6. Медиа после возврата: ICE restart и пересборка сессии (FR-004, FR-007, FR-008a)

**Decision**:
- Ответственный за перезапуск ICE — всегда невежливая сторона (звонящий, `polite: false`); вежливая только отвечает. Так нет «glare» из двух restart-offer'ов.
- Звонящий запускает ICE restart (`pc.restartIce()` + `sendOfferFx`), когда: после своего `call_resume` (или получения `call_peer_resumed { sessionRestart: false }`) соединение не `connected`; `iceConnectionState` держится `disconnected` дольше `ICE_DISCONNECTED_RESTART_MS = 3000` или стало `failed`. Перед этим, если `signalingState !== "stable"` (offer потерялся у отключённого собеседника) — rollback. `failed` засчитывается один раз, по `connectionState` (сбой ICE переводит в `failed` и его), иначе два события дали бы два restart и два offer'а; `sendOfferFx`, вызванный, пока предыдущий offer ещё создаётся (`makingOffer`), откладывается до ответа на него (уточнение после code review, итерация 4).
- `failed` в фазе `connecting` (соединение ни разу не установилось) → прежнее `callFailed` (FR-008a). В фазе `active` → восстановление; если медиа не вернулось за `MEDIA_RECOVERY_TIMEOUT_MS = 180_000` → `callFailed(CONNECTION_FAILED_TEXT)`.
- Холодный старт (`sessionRestart: true`): восстанавливающая сторона строит новое `RTCPeerConnection`; собеседник по `call_peer_resumed { sessionRestart: true }` закрывает своё `RTCPeerConnection`, **не останавливая** свои треки, строит новое с теми же треками и новым удалённым `MediaStream` (`$remoteStream` обновляется). Offer шлёт сторона, получившая `call_peer_resumed { sessionRestart: true }`, после пересборки; если пересобирать нечего (адресат ответил, но offer ещё не получал) — она строит соединение и шлёт offer сама (уточнение после code review).
- Пересборка важнее ICE restart: restart и offer привязаны к `RTCPeerConnection`, на котором начались. Если пока они шли (rollback старого offer'а, `setLocalDescription`) соединение пересобрали по `call_peer_resumed { sessionRestart: true }` (вернувшийся звонящий получает пропущенную пересборку сразу после своего `call_resume`), restart не трогает новое соединение, offer закрытого не уходит, а флаги нового не сбрасываются: offer шлёт только пересборка (уточнение после code review, итерация 3).
- Длительность у восстановившегося после холодного старта считается от `connectedAt` из снимка.
- FR-007: при возврате (и на событие `ended` трека не по нашей инициативе) треки с `readyState === "ended"` получаются заново (`getUserMedia` того же вида) и ставятся через `replaceTrack`; `enabled` берётся из `$selfMediaState` (ручное выключение сохраняется). `NotReadableError` → тост «Микрофон занят другим приложением», повтор при следующем возврате или переключении микрофона, звонок не завершается.
- Демонстрация экрана, остановленная системой в фоне, считается завершённой (существующий `screenShare.model` обрабатывает `ended` трека).
- `navigator.audioSession.type = "play-and-record"` при начале звонка и `"auto"` по завершении, если API есть (Safari 16.4+), best-effort.

**Rationale**: perfect negotiation уже реализован (`peerConnection.model`); фиксированная роль инициатора restart убирает гонки. Пересборка нужна, потому что новое `RTCPeerConnection` имеет другой DTLS-отпечаток и не может «продолжить» старую сессию собеседника.

**Alternatives**: ICE restart с обеих сторон (отвергнуто: glare); завершать звонок на `failed` (отвергнуто уточнением 2026-10-27).

## R7. Сокет после возврата и переход звонка в другое окно (FR-004, FR-008)

**Decision**:
- Клиент: при возврате на экран (`resumed`) включённый, но не подключённый сокет подключается сразу (сейчас — только при `elsewhere === "tab"`, иначе ждёт 5 с `WS_RECONNECT_DELAY_MS`). То же на событие `online`.
- Проверка живости: после `call_sync` в звонке клиент ждёт `call_state` `CALL_STATE_REPLY_TIMEOUT_MS = 3000`; нет ответа → сокет считается мёртвым (iOS часто оставляет «открытый» сокет после сна) и переоткрывается с `resume=1` (та же `tabId` → сервер заменяет свой старый сокет, звонок не трогается). Таймер на patronum `delay` со счётчиком поколения.
- Пока свой транспорт потерян в звонке: звонок не завершается (убрать путь `transportDisconnected → callConnectionLost` для звонка, текст `TRANSPORT_LOST_TEXT` уходит), на экране звонка баннер `CallStatusBanner` «Восстанавливаем связь…». Локальный предел: если за `CALL_RECONNECT_GRACE_MS` + 10 с звонок не восстановлен — локальное завершение с «Звонок завершён».
- Сервер: решение `wait` (в звонке занята другая вкладка) запускает немедленную проверку живости держателя: `ping` и `terminate()`, если pong не пришёл за `HOLDER_PROBE_TIMEOUT_MS = 5000`. Когда держатель отключился, а звонок удерживается (grace), ожидающие сокеты закрываются кодом `HOLDER_GONE_CLOSE_CODE = 4004`; клиент обрабатывает его как `4003` — переподключается сразу, получает регистрацию, по `call_state` восстанавливает звонок (уточнение 2026-10-27). Скрытая вкладка по `4004` переподключается только когда на неё посмотрят: иначе, успев первой, она отнимала соединение у видимой, и та получала `4000` и «Использовать здесь» вместо звонка (уточнение после code review, итерация 4).
- Сокет, получивший `connection_waiting`, пока в этой вкладке есть живой звонок (звонок забрало другое окно) → локальный звонок завершается без сигналов (сигналы другой вкладки не трогаем).
- Звонок, ждущий возврата участника (после потери соединения `call_resume` ещё не было), соединение не держит: вкладку, пущенную по `4004`, но звонок не подхватившую (скрытая вкладка `call_sync` о чужом звонке не шлёт), вернувшаяся страница со звонком вытесняет даже с `resume=1`, а не получает `wait` и не гасит живой звонок (уточнение после code review, итерация 3: иначе звонок теряли обе стороны). Вытеснять с `resume=1` может только страница, чьё соединение держало звонок при потере (её `tabId` сервер запоминает в `LiveCall.disconnectedTabId`; страница без `tabId` — любая, как раньше): другие вкладки, отпущенные тем же `4004`, получают отказ `4000`, как без звонка, и не вытесняют друг друга. Иначе скрытая вкладка, переподключившаяся последней, вытесняла видимую, которая уже восстанавливала звонок, и звонок не восстанавливался нигде (уточнение после code review, итерация 4). Отказанная вкладка показывает «Использовать здесь» и при возврате на неё снова просит соединение: пока звонок не подхвачен, явное «Использовать здесь» (без `resume=1`) забирает соединение. Скрытая вкладка звонок не забирает намеренно: пользователь на другом устройстве, а камера и звук не должны включаться во вкладке, на которую никто не смотрит; если на неё посмотрят, `call_sync` восстановит звонок там.

**Rationale**: без пробы холодный старт PWA после выгрузки ждал бы до 60 с, а ожидающие вкладки не освобождались бы до конца звонка (сейчас их освобождает только `removeCall`).

**Alternatives**: всегда переоткрывать сокет после фона дольше N секунд (отвергнуто: лишние переподключения на десктопе; проверка через `call_state` дешевле и точнее).

## R8. Звук собеседника отдельно от видео (FR-009, US2-4)

**Decision**: новый компонент `PeerAudio` (`features/videoCall/ui/PeerAudio`), один на экран звонка, вне плиток: `<audio autoplay playsinline>` со `srcObject` = `MediaStream` из аудиотреков `$remoteStream`. Видео собеседника всегда `muted`. Элемент передаётся модели через ref (`peerAudioElementChanged` → стор `$peerAudioElement`); `srcObject` и `play()` ставит один эффект модели `resumePeerAudioFx` (`attach` к `$peerAudioElement` и `$peerAudioStream`), поэтому `continueCallClicked` вызывает `play()` синхронно внутри жеста (sample → эффект выполняется в том же тике). Модель ведёт `$peerAudioBlocked` (`peerAudioBlocked` / `peerAudioPlaying`); системная пауза элемента (`pause`: медиа-клавиши, отключённые наушники) → `peerAudioPaused` → снова `play()`. `ContinueCallOverlay` один: показывается по правилу `isContinueCallShown` (видео заблокировано или звук заблокирован; над заглушкой прерванного собеседника — только при заблокированном звуке), одно нажатие возобновляет видео (хук плитки) и звук (модель). При `visibilitychange → visible` звук пробует `play()` сам.

**Rationale**: iOS приостанавливает `<video>` в фоне, но `<audio>` с `MediaStream` продолжает играть там, где система позволяет; в худшем случае одно нажатие возвращает всё.

## R9. Push о входящем звонке и канал доставки (FR-013…FR-020, FR-028, FR-029)

**Decision**:
- `services/callNotification/`: тип `CallNotificationChannel = { channel: PushChannel; isConfigured(): boolean; deliver(device, message): Promise<DeliveryOutcome> }`, реестр каналов по `PushChannel` (сейчас только `WEB_PUSH`). Функции сервиса: `hasCallNotificationDevices(recipient)`, `notifyIncomingCall(recipient, call)`, `notifyCallClosed(recipient, call, outcome)`. Логика звонка вызывает только их (FR-028); APNs VoIP/FCM добавятся новым каналом.
- Низкоуровневая отправка web-push выносится в `lib/webPush.ts` (VAPID, `sendNotification` с опциями, удаление подписок на 404/410) и используется и напоминаниями (`pushNotification.ts`), и каналом звонков.
- Получатели: преподаватель — его `push_subscriptions` при `reminder_settings.callNotificationsEnabled !== false` (нет строки настроек = включено); ученик — подписки `studentUserId`. Канал без настроенных ключей (`VAPID_*`) — устройств нет (FR-025).
- Отправка входящего: `TTL = 40 с` (как `RING_TIMEOUT_MS`), `urgency: "high"`, `topic` = 32 символа base64url от SHA-256 `callId` (push-сервис заменяет недоставленное старое сообщение новым), тег уведомления `call-<callId>`. Пропущенный: тот же `topic`/тег, `TTL = 24 ч`, `urgency: "normal"`. Принят/отклонён на другом устройстве: тот же тег, `TTL = 60 с`, SW показывает нейтральное уведомление и сразу его закрывает.
- Решение в `ringCallee`: видимое окно = зарегистрированное соединение с присутствием `on_screen`. Есть соединение → `call_incoming` по сокету (как сейчас). Нет видимого окна и есть устройства → `notifyIncomingCall`, `LiveCall.pushNotified = true`. Нет соединения и нет устройств → прежнее `MISSED` + `call_unavailable`. Нет соединения, а доставка не удалась ни на одно устройство → звонок снимается: `call_unavailable` звонящему, `MISSED` (Edge Case «Подписка устарела»). Busy-проверка до push (push занятому не уходит).
- Закрывающий push только если `pushNotified`: отмена/таймаут → «Пропущенный звонок от <имя>»; ответ/отказ → нейтральное. Он уходит только после того, как завершилась отправка входящего (`LiveCall.incomingPush`): отправленный параллельно, он мог дойти до push-сервиса раньше входящего, и устройство «звонило» бы до ручного закрытия (уточнение после code review, итерация 4).

**Rationale**: iOS отзывает подписку, если push не показал уведомление, поэтому каждый push показывает уведомление; замена по тегу закрывает FR-016; `topic` + короткий TTL не дают устаревшему вызову прийти через минуту (Edge Case «уведомление с задержкой»), а клиентская проверка `call_state` закрывает остаток (FR-017).

**Alternatives**: отдельная таблица устройств для звонков (отвергнуто: та же модель подписки с типом канала — FR-029); кнопки «Принять/Отклонить» в уведомлении (вне рамок).

## R10. Service worker: показ и нажатие (FR-015, FR-016, FR-017)

**Decision**: `public/push-sw.js` различает `data.type`: `lesson_reminder` (как сейчас), `incoming_call` (`requireInteraction: true`, `renotify: true`, длинная вибрация, тег `call-<id>`), `missed_call` (тот же тег, `renotify: false`), `call_closed` (показать нейтральное «Вызов завершён» с тем же тегом и сразу закрыть все уведомления с этим тегом). На нажатие `incoming_call`: если есть окно приложения — `focus()` + `postMessage({ type: "call_notification_opened", callId })` без `navigate` (не перезагружать открытое приложение); иначе `openWindow(url)`, где `url` уже содержит `?call=<callId>`. `missed_call` — открыть/навести на историю звонков (как `navigate` сейчас). URL строит сервер по роли получателя: преподаватель `/dashboard?call=<id>`, история `/call/history`; ученик `/student/cabinet/schedule?call=<id>`, история `/student/cabinet/calls`.

Фронт: модель `callNotificationOpen.model` берёт `callId` из `?call=` при старте (и убирает параметр через `history.replaceState`) и из сообщения SW (слушатель `navigator.serviceWorker` в `App.tsx`, как остальные глобальные слушатели); ответ на него — `call_state` (R5).

Тесты SW: файл загружается в vitest через `node:vm` с поддельным `self`/`clients`/`registration`.

## R11. Подписка ученика и настройка преподавателя (FR-021…FR-025, US4, US5)

**Decision**:
- Схема: `PushSubscription.userId` становится необязательным, добавляются `studentUserId` (FK на `student_users`, `onDelete: Cascade`) и `channel PushChannel @default(WEB_PUSH)`; CHECK «ровно один владелец». `ReminderSettings.callNotificationsEnabled Boolean @default(true)`.
- Ученик: маршруты `/api/student-push/subscribe` (POST) и `/api/student-push/unsubscribe` (DELETE) под `authenticateStudent` (изолированная подсистема, backend.md). Эндпоинт, принадлежащий другому владельцу, → 403 «Подписка принадлежит другому пользователю» (как у преподавателя). Валидация подписки — общий `controllers/push/validators.ts`.
- Регистрация service worker и для ученика (после `getCurrentStudentFx.done`).
- Статус ученика (`CallNotificationsStatus`): ключи push на сервере не настроены или нет `PushManager` → `unsupported`; `isIos() && !isInStandaloneMode()` → `iosInstall` (раньше проверки поддержки); `Notification.permission === "denied"` → `denied`; разрешение есть и есть подписка браузера → `on` (при загрузке кабинета подписка повторно отправляется на сервер — upsert, привязывает устройство к текущему ученику); иначе `off`. Отказ в системном диалоге → `denied`, диалог повторно не вызывается.
- Закрытие карточки-приглашения и подсказки FR-012 запоминаются в `localStorage` (чтение в эффекте при старте модели, без patronum `reset` — см. memory gotcha).
- Преподаватель (уточнение 2026-10-27): `callNotificationsToggled` → `PUT /api/reminder-settings { callNotificationsEnabled }`; включение на неподписанном устройстве → `subscribePushFx` (свой `attach`-эффект); выключение напоминаний при включённых звонках не отписывает устройство; выключение последнего из двух — отписывает. Переключатель показывает, доходят ли звонки до этого устройства (`$isCallNotificationsOn` = настройка включена И устройство подписано; устройство, которое подписаться не может, показывает настройку), нажатие на неподписанном устройстве подписывает его, настройка остаётся включённой. Автоподписка при старте — только в сессии преподавателя и после загрузки его настроек: для напоминаний — как раньше (может спросить разрешение), для одних звонков — только если разрешение уже выдано (возврат подписки после выхода и входа, без новых системных запросов). Выход преподавателя сбрасывает его настройки и состояние подписки в сторах.
- FR-024: выход по кнопке идёт через оркестратор `sessionCleanup.model` (в `features/logoutConfirmation`): событие `logoutStarted(role)`, по которому `app/model/sessionLogout.model.ts` завершает текущий звонок (`callModel.hangUp` и др.; слой app, т.к. фича не может импортировать `features/videoCall`), удалить подписку устройства на сервере (токен ещё есть) и в браузере, с ограничением `LOGOUT_CLEANUP_TIMEOUT_MS = 3000`, затем прежний `userModel.logoutUser` / `studentUserModel.studentLoggedOut`. Вход ученика поверх сессии преподавателя (`userModel.tutorSessionCleared`) эту очистку не запускает: токен преподавателя сбрасывается в том же такте, а удаление подписки в браузере гонялось бы с `syncSubscriptionFx` кабинета ученика. Подписку браузера при входе перепривязывает к себе кабинет ученика (`contracts/push-api.md`, «Перепривязка подписки держателем браузера»), так что push преподавателя на это устройство больше не приходят; так же преподаватель забирает подписку, оставшуюся от ученика или другого преподавателя (`notificationsModel.syncSubscriptionFx`).

## R13. Картинка в картинке (US6, FR-026, P3)

**Decision**: делается последней, изолированной фазой как прогрессивное улучшение без UI: убрать `disablePictureInPicture` с видео собеседника, выставить `autoPictureInPicture = true` (WebKit; iOS 14+ Safari, где атрибут есть) и зарегистрировать `navigator.mediaSession.setActionHandler("enterpictureinpicture", …)` (Chromium, автоматическая PiP для видеозвонков) — всё за feature-detect, только при включённой камере собеседника. Подтверждение работы — ручной QA на устройствах; если QA не подтвердит пользы (PiP не появляется или ломает звук), фаза откатывается удалением одного хука, остальная фича от неё не зависит.

**Rationale**: в планировании нельзя проверить на реальных устройствах; поддержка PiP для `MediaStream`-видео в фоне PWA разная по версиям. Спека разрешает делать только при подтверждении.
