# Phase 0 — Research: гибкая ставка налога по периодам

Все «NEEDS CLARIFICATION» из Technical Context резолвятся ниже. Фоновых
неопределённостей нет — фича остаётся в рамках текущего стэка.

## Decision 1 — Хранение периодов: отдельная таблица `tax_rate_periods`

- **Decision**: завести отдельную Prisma-модель `TaxRatePeriod` с полями
  `id`, `userId`, `startDate (DateTime)`, `rate (Float)`, `createdAt`, `updatedAt`,
  с уникальным составным индексом `(userId, startDate)` и обычным индексом
  `(userId, startDate)` для быстрого диапазонного поиска.
- **Rationale**:
  - Реляционный подход даёт целостность через FK + onDelete: Cascade.
  - Уникальный составной индекс закрывает FR-013 на уровне БД (нельзя
    создать два периода с одинаковой датой начала у одного пользователя).
  - Поиск «период, действующий на дату X» сводится к
    `where userId AND startDate <= X order by startDate desc limit 1`,
    что эффективно при индексе по `(userId, startDate)`.
- **Alternatives rejected**:
  - **JSON-массив на User.periods**: проще выглядит, но ломается constraint
    уникальности на уровне БД и теряется индекс — придётся валидировать
    в коде, плюс невозможно эффективно агрегировать по диапазону.
  - **Отдельная таблица с `(startDate, endDate)` диапазонами**: даёт
    избыточную свободу (возможны пересечения и пробелы), требует ручной
    нормализации после каждой правки. Цепочка из start-only периодов проще.

## Decision 2 — Расчёт `taxAmount`: пер-уроком, в сервисе

- **Decision**: в `/api/statistics` заменить текущую формулу
  `Math.round(earnings * taxRate / 100)` на пер-уроковый расчёт через
  отдельный сервис `services/taxRate.ts`. Сервис принимает `(periods, lessons)`
  и возвращает `{ taxAmount, breakdown }`. Уроки берутся той же выборкой,
  что текущий `paymentsInRange` (фильтр по `paymentDate`, `isPaid: true`,
  `price > 0`), но с возвращением `select: { price: true, paymentDate: true }`
  (вместо `aggregate _sum`).
- **Rationale**:
  - Налог по смыслу — это «сколько денег, фактически поступивших,
    нужно отдать государству». Семантика «по дате оплаты» (FR-015,
    Story 2 acceptance #2) идентична существующему `paymentsInRange`.
  - `aggregate _sum` не подходит, потому что rate зависит от даты урока:
    одна агрегатная сумма не позволяет применить разные ставки.
  - Объём данных невелик (single-host, ~единицы тысяч уроков на пользователя
    в худшем случае); ОДИН `findMany` на оплаченные уроки в фильтре —
    приемлемо. Можно дополнительно ограничить `select` до двух полей.
- **Alternatives rejected**:
  - **Raw SQL с CASE-выражением**: даёт расчёт за один запрос, но
    усложняет тестирование (нет совместимости с in-memory mock'ами,
    нужно прокладывать через Prisma `$queryRaw`). Текущее правило
    «не мокаем Prisma, тесты на реальной БД» нивелирует выигрыш.
  - **Кэширование в БД готового taxAmount**: преждевременная оптимизация.
    Любой пересчёт вынужден инвалидировать кэш; добавляет сложность
    без необходимости (FR-018 — реактивность через next fetch).

## Decision 3 — Резолвер ставки: бинарный поиск по отсортированным периодам

- **Decision**: для расчёта берём все периоды пользователя одним запросом
  (отсортированные по `startDate ASC`), затем для каждого урока ищем
  применимый период линейно по уже отсортированному массиву (или
  бинарным поиском при `>5` периодах). Сервис экспортирует чистую функцию
  `resolveRate(paymentDate: Date, periods: TaxRatePeriod[]): number`,
  которая возвращает `0` если `paymentDate < periods[0].startDate`.
- **Rationale**:
  - Ожидаемое число периодов на пользователя — единицы; линейный поиск
    O(N×M) уроков×периодов всё равно укладывается в десятки миллисекунд.
  - Чистая функция тривиально юнит-тестируется без БД.
- **Alternatives rejected**:
  - **Запрос периода для каждого урока**: O(N) запросов в БД — недопустимо.
  - **Map paymentDate→rate**: периоды задаются как открытые диапазоны;
    Map-структура неудобна для запроса «последний period с startDate ≤ X».

## Decision 4 — Семантика «дата оплаты раньше самого раннего периода»: 0%

- **Decision**: если `paymentDate < earliestPeriod.startDate`, налог по этой
  оплате — `0₽`, и в breakdown выделяется отдельная строка с пометкой
  «вне настроенных периодов».
- **Rationale**: соответствует FR-016. Пользователь явно отказался от
  «расширения первой ставки в прошлое»; он лучше понимает, что часть
  доходов не покрыта настроенной историей, и может явно дозаконфигурить.
- **Alternatives rejected**: пер-уроком `null`/exception — ломает агрегат;
  расширение в прошлое — отвергнуто пользователем.

## Decision 5 — Структура breakdown для info-tooltip

- **Decision**: backend возвращает (наряду с `taxAmount`) поле
  `taxBreakdown: TaxBreakdownEntry[]`, где
  `TaxBreakdownEntry = { rate: number; earnings: number; tax: number; isOutsidePeriods?: boolean }`.
  Сортируется по `rate ASC`. В случае `taxEnabled=false` → `taxAmount=null`,
  `taxBreakdown=null` (фронт скрывает карточку целиком).
- **Rationale**: вычисление breakdown требует тех же данных, что и сумма;
  делать его на сервере дешевле, чем гонять список уроков на фронт.
  Признак `isOutsidePeriods` экономит фронту логику «как подписать строку
  с rate=0%, который не принадлежит ни одному периоду».
- **Alternatives rejected**:
  - Считать breakdown на фронте — потребует прокидывать список уроков
    в SPA и дублировать логику резолвера.
  - Не возвращать breakdown — нарушает FR-021.

## Decision 6 — Карточка налога: «Налоги (X%)» vs «Налоги»

- **Decision**: подпись формируется на фронте по длине `taxBreakdown`:
  - `length === 1` → подпись `"Налоги ({rate}%)"`, info-icon скрыт
  - `length > 1` → подпись `"Налоги"`, рядом `<InfoOutlined />`-иконка
    с MUI `<Tooltip>` с `arrow + click + hover` (управляемое раскрытие
    через `open`-state, чтобы корректно работало на мобильных).
- **Rationale**: соответствует FR-019, FR-020, FR-021. MUI Tooltip — уже
  используется в кодовой базе, не добавляем новых зависимостей.
- **Alternatives rejected**: Popover — оверкилл для строкового списка;
  всплывающие меню MUI Menu — семантически неправильны.

## Decision 7 — Модалка управления периодами: MUI Dialog

- **Decision**: используем `<Dialog>` из MUI с заголовком,
  скроллируемым контейнером для списка строк (`<TaxRatePeriodRow>` каждая
  строка: дата начала + ставка + кнопка удалить), кнопкой «Добавить период»
  внизу списка, и парой кнопок `Отмена / Сохранить` в `<DialogActions>`.
- **Rationale**: MUI Dialog уже используется (например, в страницах
  студентов и уроков); пользователь привыкнет к одинаковому паттерну.
  Атомарное сохранение по «Сохранить» / откат локальных правок по «Отмена»
  естественно ложится на эту структуру.
- **Alternatives rejected**:
  - Inline-редактирование на странице профиля — отвергнуто пользователем.
  - Drawer / отдельная страница — диспропорционально для 5–10 строк.

## Decision 8 — Модель состояния модалки: локальная Effector-копия

- **Decision**: при открытии модалки делаем снапшот серверного списка
  периодов в локальный стор `$draftPeriods` (массив, отсортированный
  по startDate). Все правки (add/edit/delete row) меняют только `$draftPeriods`.
  По «Сохранить» — отправляем дифф (или весь массив для простоты) на сервер
  и при успехе синкаем серверный стор `$periods`. По «Отмена» / закрытию —
  `$draftPeriods` сбрасывается. Эта схема избегает мерцания статистики
  во время правок (FR-014).
- **Rationale**: атомарность изменений + предсказуемость; не нужны
  оптимистические апдейты с rollback.
- **Alternatives rejected**:
  - Реальный CRUD пер-action: лишние вызовы; промежуточные состояния
    «попадают в статистику», нарушают FR-009.
  - Локальное хранение в React `useState` — нарушает Конституцию III.

## Decision 9 — Тумблер `taxEnabled` хранится на User

- **Decision**: добавляем поле `taxEnabled Boolean @default(false)` в модель
  `User`. Оно возвращается с `/api/profile`/`/api/auth/*` ответами как
  обычное поле и обновляется через расширенный `updateProfile`.
  Сервер валидирует: `taxEnabled=true` требует наличия как минимум одного
  периода у пользователя; в противном случае — 400 с сообщением
  «Чтобы включить учёт налога, добавьте хотя бы один период».
- **Rationale**: тумблер — атрибут пользователя, а не отдельная настройка;
  логично хранить рядом с `name`, `email`. Валидация на сервере покрывает
  FR-005.
- **Alternatives rejected**: отдельная таблица `tax_settings` —
  переусложнение для одной булевой настройки.

## Decision 10 — Миграция существующих пользователей

- **Decision**: однократная data-миграция в Prisma migration:
  ```sql
  -- Для пользователей с явно не-дефолтной ставкой: создать seed-период,
  -- включить тумблер
  INSERT INTO tax_rate_periods (id, user_id, start_date, rate, created_at, updated_at)
  SELECT cuid(), id, COALESCE(MIN(l.start_time), users.created_at) AS start_date,
         users.tax_rate, NOW(), NOW()
  FROM users
  LEFT JOIN lessons l ON l.tutor_id = users.id
  WHERE users.tax_rate <> 6.0
  GROUP BY users.id, users.tax_rate, users.created_at;

  UPDATE users SET tax_enabled = true WHERE tax_rate <> 6.0;
  -- Остальные остаются с tax_enabled = false (дефолт DB-уровня).
  ```
  (Реальная реализация — через Prisma `prisma migrate` + raw SQL в файле
  миграции, поскольку `cuid()` нужно генерировать средствами PostgreSQL
  или через временный JS-скрипт. См. quickstart.md.)
- **Rationale**:
  - Пользователи, явно настраивавшие ставку, не теряют расчёт.
  - Дефолтные «6%»-пользователи получают чистый старт по новой модели
    (соответствует пожеланию пользователя «не 6 процентов налога всегда»).
  - Дата начала seed-периода — самое раннее из «дата первого урока,
    дата создания аккаунта», чтобы все исторические оплаты попали
    под действующий период.
- **Alternatives rejected**:
  - Перенести всех с `taxEnabled=true` — сохраняет «6% всегда» по умолчанию,
    что противоречит пожеланию.

## Decision 11 — Удаление поля `User.taxRate`

- **Decision**: поле удаляется в той же Prisma-миграции, сразу после
  data-step переноса в `tax_rate_periods`. Schema, data-миграция и `DROP COLUMN`
  применяются одной транзакцией.
- **Rationale**: Конституция VII (Simplicity) явно запрещает
  speculative future-proofing и backwards-compat шины; держать мёртвое
  поле «на случай отката» — ровно это. Откат, если понадобится,
  выполняется обычным `prisma migrate` в обратную сторону по сохранённой
  истории миграций.
- **Alternatives rejected**:
  - Растянуть удаление на следующий релиз — нарушает Simplicity без
    реальной выгоды (приложение поле уже не читает).
  - Оставить поле deprecated навсегда — мусор в схеме.

## Decision 12 — WebSocket-инвалидация статистики

- **Decision**: текущий WebSocket-канал статистики (если есть) не используется
  для пуша по правкам периодов; фронт обновляет данные на следующем переходе
  на страницу статистики через обычный `loadStatisticsFx` (привязан к `Gate`).
  FR-018 «следующий запрос» — этого достаточно.
- **Rationale**: правки периодов — редкое событие (раз в год при смене
  налогового режима); пуш-обновления тут оверкилл.
- **Alternatives rejected**: WS-уведомление «periodsChanged» — ненужная
  сложность для одной вкладки одного пользователя.

## Decision 13 — Сценарий «taxEnabled=false»: API форма ответа

- **Decision**: backend по `/api/statistics` возвращает `taxAmount: null`
  и `taxBreakdown: null` если у пользователя `taxEnabled=false`.
  Карточка налога на фронте полностью скрывается, если оба поля `null`.
- **Rationale**: явный «нет данных» проще обрабатывать на фронте, чем
  «0 ₽», который семантически означает «есть данные, налог нулевой»
  (например, при ставке 0% или когда все оплаты до самого раннего периода).
- **Alternatives rejected**: всегда возвращать число и хранить отдельный
  булевый флаг — два source of truth, легко рассинхронизироваться.
