# Research: Восстановление пароля

**Feature Branch**: `028-forgot-password`
**Date**: 2026-05-09

## Research Questions & Decisions

### RQ-001: Формат токена сброса — 6-значный код vs URL-токен

**Decision**: URL-токен. 32 байта случайных данных (`crypto.randomBytes(32)`), кодированных в `base64url`. Передаётся в URL как query-параметр (`/reset-password?token=...`).

**Rationale**:
- Пользователь явно сослался на "ссылка/токен" в исходном описании.
- Индустриальный стандарт password reset (Auth0, AWS Cognito, GitHub, Google) — link-based, не code-based.
- Для смены email в проекте уже используется 6-значный код (FR-007 spec 023): сценарии разные. Email-верификация — ввод кода в UI (быстро, один экран), password reset — переход с другого устройства (где нет UI), поэтому ссылка удобнее.
- 32 байта = 256 бит энтропии — пространство `2^256`, перебор в реальном мире невозможен даже без rate-limit.
- `base64url` безопасен для URL без дополнительного percent-encoding.

**Alternatives considered**:
- 6-значный код: пользователь сам набирает; UX хуже (нужно копировать код, открывать форму вручную).
- JWT с истечением: подписывает state в токене, не нужно хранить — но не позволяет одноразовость без серверного state, а одноразовость требуется (FR-009). Также инвалидация старых токенов после нового запроса (FR-011) сложнее.
- UUID v4: 122 бита энтропии — достаточно, но 32 байта дают больший запас и единообразны с типичными crypto-токенами.

### RQ-002: Хранение токена — plain vs hashed

**Decision**: Хранить в БД **только хеш токена** (SHA-256). Сам токен (plain) пользователь видит в URL и больше нигде. При проверке: хешируем входной токен и ищем по `tokenHash` (unique index).

**Rationale**:
- FR-012: "компрометация на уровне БД не позволяла напрямую использовать токены".
- SHA-256 достаточно для коротких (минуты) одноразовых токенов — здесь не нужен медленный хеш bcrypt: токен и так высокоэнтропийный, защита от brute force не нужна, важна только защита от чтения дампа БД злоумышленником.
- Поиск по `WHERE tokenHash = ?` остаётся `O(log n)` благодаря unique-индексу.

**Alternatives considered**:
- Bcrypt: излишне дорогой (~100ms per check) для одноразовых токенов с высокой энтропией. Bcrypt оправдан для паролей, не для токенов.
- Plain-text: нарушает FR-012; при дампе БД любой токен в окне TTL немедленно эксплуатируем.

### RQ-003: Срок действия токена и cooldown повторных запросов

**Decision**:
- TTL токена сброса — **15 минут** (симметрично существующему `getVerificationCodeExpiry()`).
- Per-email cooldown между запросами восстановления — **60 секунд** (симметрично существующей константе `RESEND_COOLDOWN_SECONDS`).
- При новом запросе для одного и того же аккаунта старые **неиспользованные** токены этого пользователя помечаются использованными (`usedAt = now`), чтобы инвалидировать их (FR-011).

**Rationale**: 15 минут — индустриальный диапазон (10–60 мин); короче = меньше окно атаки, длиннее = удобнее для пользователя. Параметры симметричны существующим — единообразный UX.

### RQ-004: Защита от энумерации аккаунтов

**Decision**:
- Бекенд **всегда возвращает 200 + одно и то же сообщение** на `POST /forgot-password`, независимо от существования email.
- При несуществующем email письмо не отправляется, но эмулируется аналогичная задержка ответа (см. RQ-005).
- Сообщение: "Если адрес зарегистрирован, мы отправили на него письмо со ссылкой для сброса пароля."

**Rationale**: FR-004, FR-024. Стандартная практика OWASP Authentication Cheat Sheet.

**Alternatives considered**:
- Возвращать "email не найден": нарушает FR-004, позволяет злоумышленнику собирать список email-адресов в системе.
- Случайный 200/404: непредсказуемое UX; не помогает: атакующий измеряет время и распределение.

### RQ-005: Защита от тайминговой атаки на энумерацию

**Decision**: На уровне сервиса — после lookup пользователя выполнять "фиктивный" хеш-расчёт того же стиля, что и для существующего пользователя, чтобы среднее время ответа было сопоставимым. На практике — большая часть времени уходит на `prisma.passwordResetToken.create()` (не выполняется для несуществующего email), поэтому делаем не-блокирующую "no-op" задержку или фоновую запись в логи.

**Rationale**: Полное выравнивание тайминга — over-engineering для нашего масштаба. Средняя задержка существующих сервисов ~50-200ms, разброс из-за сети намного больше. **Достаточно**: одинаковый HTTP-ответ (RQ-004) + per-IP rate-limit (RQ-006), который делает массовый perpetual probing невозможным.

**Alternatives considered**:
- Полный хеш фейковый: усложняет код, выгода маргинальна.
- Игнорировать: даёт ~10-50ms разницу, эксплуатируема через тысячи запросов; но rate-limit это блокирует.

### RQ-006: Per-IP rate limiting

**Decision**: Использовать существующий `express-rate-limit` (уже в проекте, см. `middleware/rateLimit.ts`). Создать новый `passwordResetRateLimiter` с настройками: окно 15 минут, **5 запросов на IP**.

**Rationale**:
- Существующий `authRateLimiter` (20 req / 15 min) применяется к login/register/verify-email — слишком "щедрый" для password reset, где основной риск — DoS на email-провайдер.
- 5 req / 15 min достаточно для легитимных кейсов (пользователь забыл пароль, повторил 1-2 раза, попробовал alt-email — это покрывается); атакующий получает 5 шансов / 15 мин / IP.
- Параметры устанавливаются на уровне middleware и применяются к `/forgot-password`. На `/reset-password` (применение токена) лимит не нужен — токен достаточно длинный.

**Alternatives considered**:
- Переиспользовать `authRateLimiter`: проще, но 20 req за 15 мин — слишком много для отправки писем; может вызвать жалобы от Resend на abuse.
- Кастомный per-email key (не только IP): сложнее, требует кастомного key generator. Может быть добавлено позже, если захочется усилить.

### RQ-007: Структура URL для страницы установки пароля

**Decision**: Query-параметр: `/reset-password?token=<token>`.

**Rationale**:
- Token в URL — стандартный паттерн (Google, Facebook, GitHub).
- Query-param проще для роутинга (one route, no path params), удобнее для копирования в адресной строке email-клиентом.
- Frontend получает токен через `useSearchParams()` от react-router.

**Alternatives considered**:
- Path param `/reset-password/:token`: чуть короче URL, но сложнее с Suspense/preloading в react-router; никаких преимуществ для нашего кейса.
- Hash fragment `/reset-password#token=...`: преимущество — токен не уходит в логи бэкенда (фрагмент видит только клиент); но затрудняет SSR и копирование. Не используем.

### RQ-008: Должна ли страница установки пароля валидировать токен при загрузке?

**Decision**: Да. Страница вызывает `POST /api/auth/reset-password/verify` при mount, и если токен невалиден/истёк/использован — показывает понятную ошибку и кнопку "Запросить новую ссылку"; иначе показывает форму.

**Rationale**: FR-014 явно требует "проверять валидность при открытии". UX-выгода: пользователь не вводит новый пароль, чтобы потом узнать, что ссылка протухла.

**Alternatives considered**:
- Проверять только на submit: проще, но плохое UX (две лишние формы и шанс потерять введённый пароль).
- GET-эндпоинт `?token=...`: SEO-индексация и логирование URL могут утечь токен. POST с токеном в body безопаснее.

### RQ-009: Что делать с активными сессиями пользователя после успешного сброса?

**Decision**: Не инвалидировать. Существующие JWT остаются валидными (как и при "Смене пароля" — assumption из spec 023). Документировать как известное ограничение.

**Rationale**: Текущая архитектура auth не имеет server-side session blacklist (JWT — stateless). Реализация инвалидации потребует либо blacklist (Redis/БД-таблица), либо ротацию `JWT_SECRET` (выкинет всех). Это выходит за рамки текущей фичи и конституционного принципа VII (Simplicity). Большинство пользователей, забывших пароль, не имеют активной сессии в любом случае.

**Alternatives considered**:
- Blacklist токенов: добавляет инфраструктуру (новая таблица + middleware-проверка) ради edge-case. Отдельная фича, если станет нужна.
- Ротация `JWT_SECRET` пользователя: требует поле `tokenVersion` в User и проверку в middleware. Тоже отдельная фича.

### RQ-010: Что делать с `isEmailVerified` после успешного сброса?

**Decision**: Если у пользователя `isEmailVerified === false`, после успешного сброса пометить email как verified (`isEmailVerified = true`).

**Rationale**: Факт перехода по ссылке из письма доказывает контроль над почтовым ящиком — это и есть верификация. Альтернатива (оставить unverified) странна: пользователь только что доказал владение email, но статус не обновлён. Не вредит security, повышает удобство (пользователь не должен делать verification заново).

**Alternatives considered**:
- Оставить статус как есть: легче, но дублирует процесс верификации без причины.
- Инвалидировать существующие коды верификации (`verificationCode = null`): не нужно, потому что мы уже подтвердили email через ссылку.

### RQ-011: Где разместить ссылку "Забыли пароль?" на форме логина

**Decision**: Под полями ввода, перед кнопкой "Войти" (или непосредственно после поля пароля). Стиль — `Button variant="text"` (как существующая ссылка в `ChangePasswordDialog`).

**Rationale**:
- Самый частый паттерн (Material Design, большинство SPA): ссылка под полем пароля справа или по центру.
- Текстовая кнопка визуально соответствует ссылке "Нет аккаунта? Зарегистрироваться", уже присутствующей внизу формы.
- Использование `Button` (а не `Link`) единообразно с существующим паттерном диалога смены пароля и добавляет правильную keyboard-доступность.

**Alternatives considered**:
- В шапке/тулбаре: нелогично; пользователь ищет ссылку рядом с полем пароля.
- Как иконка/tooltip: непонятно, требует дополнительного hover, плохо на мобильных.

### RQ-012: Структура frontend кода — одна feature или две?

**Decision**: Две отдельные features: `forgotPassword` (запрос восстановления) и `resetPassword` (установка нового пароля по токену).

**Rationale**:
- У них разный state (`$email + $isSent` vs `$token + $newPassword + $confirmPassword + $tokenStatus`).
- Разные API-вызовы и разные UI.
- По FSD каждая feature соответствует одному use-case; смешать их = увеличить связность без выгоды.
- Конституционный принцип VII (Simplicity): "no premature abstractions" — общую часть (например, успех/ошибка) в abstract feature `passwordRecovery` выносим **только** если будет реальное переиспользование (его не будет).

**Alternatives considered**:
- Одна feature `passwordRecovery` со всеми моделями: больше зависимостей внутри, выше когнитивная нагрузка при чтении модели.
- Helpers/hooks в shared: не оправдано; кода не так много, чтобы выносить общее.

### RQ-013: Email-шаблон для письма со ссылкой

**Decision**: Создать `sendPasswordResetEmail(email, resetUrl)` рядом с существующими `sendVerificationEmail` и `sendEmailChangeVerification` в `services/email.ts`. HTML-шаблон в стиле существующих писем (заголовок + блок с кнопкой/ссылкой + предупреждение о ненужности).

**Rationale**:
- Минимальное изменение существующей инфраструктуры — добавляем функцию, не трогая остальные.
- Согласованность визуального стиля писем для пользователя.
- Включает не только кнопку "Сбросить пароль", но и текстовую копию ссылки на случай, если CTA-кнопка не отрисуется в почтовом клиенте.

**Alternatives considered**:
- Шаблонизатор (Handlebars, MJML): сейчас в проекте просто template literals — добавление зависимости не оправдано.
- Plain-text fallback: Resend отправляет HTML, который большинство клиентов рендерит. Plain-text не критичен.

### RQ-014: Где брать base URL для ссылки в письме

**Decision**: Бэкенд читает `FRONTEND_URL` из `.env` (env-переменная, **уже подразумевается** для dev/prod). Если не задана — упасть с понятной ошибкой при старте сервиса (fail-fast).

**Rationale**: На разных окружениях разные домены (`localhost:3000` в dev, `tutor.kaluger.ru` в prod). Хардкодить нельзя, переменная окружения — стандарт.

**Alternatives considered**:
- Запрос `Origin` header из запроса: ненадёжно (заголовок устанавливается клиентом, можно спуфить и заставить сервер генерировать ссылку на чужой домен в письме — фишинг).
- Дефолтное значение `localhost`: ломает prod, плохо.

### RQ-015: Как тестировать защиту от энумерации и rate-limit

**Decision**:
- В Jest-интеграционных тестах bypass rate-limiter включён (см. `isTestEnv` в `middleware/rateLimit.ts`).
- Для теста rate-limit-поведения — отдельный test-suite с временным включением лимита (через переопределение `process.env.NODE_ENV`) или мок middleware на конкретный test.
- Защита от энумерации проверяется так: один и тот же ответ (`200`, тот же body) для существующего и несуществующего email; mock на `sendPasswordResetEmail` показывает, был ли вызван.

**Rationale**: Существующая инфраструктура проекта уже оборачивает rate-limit в `skip` для тестов; мы соблюдаем эту конвенцию. Защита от энумерации — observable contract тестируется без необходимости тестировать тайминг.
