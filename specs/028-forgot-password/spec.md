# Feature Specification: Восстановление пароля ("Забыли пароль")

**Feature Branch**: `028-forgot-password`
**Created**: 2026-05-09
**Status**: Draft
**Input**: User description: "Реализовать функцию 'Забыли пароль'. Сейчас уже есть страница-заглушка и ссылка из окна смены пароля. Нужно: 1) реализовать полноценный flow восстановления пароля по email с использованием стандартных подходов (отправка письма со ссылкой/токеном, страница установки нового пароля, защита от перебора и злоупотреблений); 2) добавить ссылку 'Забыли пароль?' на экран логина. Использовать существующую инфраструктуру email-верификации (есть рабочий механизм отправки писем через шаблоны)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Восстановление доступа по email-ссылке (Priority: P1)

Пользователь забыл пароль и не может войти в систему. Он открывает страницу "Забыли пароль", вводит email, на который зарегистрирован аккаунт, и получает письмо с уникальной ссылкой для сброса пароля. Перейдя по ссылке, он попадает на страницу установки нового пароля, вводит новый пароль дважды и сохраняет изменения. После этого он входит в систему с новым паролем.

**Why this priority**: Это основной end-to-end сценарий фичи. Без него пользователь, потерявший доступ, не может восстановить аккаунт без обращения в поддержку. P1 — потому что это единственная цель фичи; всё остальное лишь повышает удобство и безопасность.

**Independent Test**: Можно полностью протестировать так: с любого устройства открыть `/forgot-password`, ввести email существующего аккаунта, получить письмо со ссылкой, перейти по ней, установить новый пароль и убедиться, что вход работает только с новым паролем.

**Acceptance Scenarios**:

1. **Given** пользователь не авторизован и находится на странице восстановления пароля, **When** он вводит email существующего аккаунта и нажимает "Отправить", **Then** на этот email уходит письмо со ссылкой для сброса, и пользователю показывается нейтральное сообщение об отправке (без подтверждения существования email)
2. **Given** пользователь получил письмо со ссылкой, **When** он переходит по ссылке в течение срока действия токена, **Then** открывается страница установки нового пароля
3. **Given** пользователь на странице установки пароля, **When** он вводит валидный новый пароль и его подтверждение и нажимает "Сохранить", **Then** пароль обновляется, токен сброса погашается, и пользователь видит сообщение об успехе с возможностью перейти к экрану входа
4. **Given** пользователь успешно сменил пароль через flow восстановления, **When** он вводит новые учётные данные на экране входа, **Then** вход успешен; вход со старым паролем больше невозможен
5. **Given** пользователь вводит email несуществующего аккаунта, **When** он отправляет форму, **Then** показывается то же нейтральное сообщение об отправке, но письмо не отправляется (защита от энумерации)
6. **Given** пользователь вводит новые пароли, не совпадающие между собой, **When** он нажимает "Сохранить", **Then** показывается ошибка "Пароли не совпадают", и пароль не меняется

---

### User Story 2 - Точка входа "Забыли пароль?" с экрана логина (Priority: P2)

Пользователь, который не помнит пароль, открывает страницу входа. Под полями логина и пароля он видит ссылку "Забыли пароль?", по которой переходит к форме запроса восстановления.

**Why this priority**: Без этой ссылки flow восстановления пароля недоступен пользователю, который не залогинен (а это ровно та аудитория, которой он нужен). P2, а не P1, потому что технически P1-сценарий уже работает по прямому URL — но без видимой точки входа фича бесполезна для большинства пользователей.

**Independent Test**: Можно протестировать визуально и кликом: открыть страницу входа, найти ссылку "Забыли пароль?", кликнуть, оказаться на странице запроса восстановления.

**Acceptance Scenarios**:

1. **Given** пользователь открыл страницу входа в систему, **When** он смотрит на форму, **Then** под полями email и пароля (или рядом с кнопкой "Войти") видна ссылка "Забыли пароль?"
2. **Given** пользователь на странице входа, **When** он кликает по ссылке "Забыли пароль?", **Then** он переходит на страницу восстановления пароля
3. **Given** пользователь видит ссылку "Забыли пароль?" в диалоге смены пароля (существующая точка входа), **When** он кликает по ней, **Then** он переходит на ту же страницу восстановления, что и из формы логина

---

### User Story 3 - Защита от перебора и злоупотреблений (Priority: P3)

Злоумышленник или скрипт многократно отправляет запросы на восстановление пароля для разных или одного и того же email-адреса, пытаясь перебрать токены сброса либо завалить пользователя письмами. Система ограничивает частоту запросов, не раскрывает наличие email-адреса в базе и инвалидирует устаревшие/использованные токены.

**Why this priority**: Без этих ограничений фича становится вектором атаки (DoS на email, энумерация аккаунтов, перебор токенов). P3 — потому что MVP-flow (P1) и точка входа (P2) могут работать без полной защиты в development-окружении, но **на production эти меры обязательны**.

**Independent Test**: Можно протестировать симулируя атаку: отправить несколько подряд запросов на восстановление с одного источника или для одного email и убедиться, что лишние запросы отклоняются с понятной ошибкой; перейти по уже использованной/просроченной ссылке и убедиться, что доступ к форме сброса не выдаётся.

**Acceptance Scenarios**:

1. **Given** пользователь только что отправил запрос на восстановление пароля, **When** он повторно нажимает "Отправить" в течение периода ожидания (cooldown), **Then** показывается ошибка с указанием, через сколько секунд можно повторить запрос
2. **Given** одно и то же или разные email-адреса используются для частых запросов с одного источника (IP/устройства), **When** превышен порог частоты запросов, **Then** дальнейшие запросы временно отклоняются
3. **Given** ссылка для сброса пароля уже была использована, **When** пользователь снова переходит по ней, **Then** страница сообщает, что ссылка недействительна, и предлагает запросить новую
4. **Given** срок действия ссылки истёк (15 минут), **When** пользователь по ней переходит, **Then** страница сообщает, что ссылка истекла, и предлагает запросить новую
5. **Given** пользователь несколько раз запросил восстановление подряд (в пределах разрешённого), **When** он использует токен из самого свежего письма, **Then** сброс проходит успешно; токены из более ранних писем должны быть недействительны
6. **Given** в письме приходит ссылка с длинным криптостойким токеном, **When** злоумышленник пытается перебирать токены, **Then** вероятность угадать токен пренебрежимо мала и попытки попадают под общие ограничения частоты

---

### Edge Cases

- Пользователь запрашивает восстановление для аккаунта с **неподтверждённым email**: сценарий допустим — flow проходит как обычно, потому что email уже использовался при регистрации; после установки нового пароля email можно считать косвенно подтверждённым (опционально — отметить как verified)
- Пользователь устанавливает **новый пароль, совпадающий с текущим**: запрос отклоняется с тем же сообщением, что и в существующей "Смене пароля" ("Новый пароль должен отличаться от текущего")
- Пользователь устанавливает пароль, **не проходящий валидацию** (короткий, без цифры и т.д.): запрос отклоняется с тем же сообщением о требованиях, что и в "Смене пароля"
- Пользователь **переходит по ссылке, имея активную сессию** другого аккаунта: страница сброса всё равно работает; пароль меняется именно для аккаунта, чей email указан в токене (а не для текущей сессии); после сброса рекомендуется выйти из текущей сессии или обновить её
- Пользователь **закрыл страницу установки пароля, не сохранив**: токен остаётся валидным до истечения срока или повторного запроса; пользователь может вернуться по той же ссылке
- Email-сервис **не доставил письмо** (сбой Resend): пользователю показывается нейтральное сообщение (как и при успехе) во избежание энумерации; пользователь может повторить запрос после cooldown — неуспешные отправки логируются для мониторинга
- Пользователь вводит **email с другим регистром или пробелами**: email нормализуется (как и в существующей верификации) перед поиском
- Аккаунт был **удалён** между отправкой письма и переходом по ссылке: ссылка считается недействительной, сценарий идентичен "уже использованной/просроченной"
- Пользователь использует ссылку для аккаунта **админа/особой роли**: flow работает идентично — никакой дискриминации по ролям не предусмотрено; защита та же

## Requirements *(mandatory)*

### Functional Requirements

#### Запрос восстановления

- **FR-001**: Система ДОЛЖНА предоставлять публичную (доступную без авторизации) страницу для запроса восстановления пароля по адресу `/forgot-password` (заменяет существующую страницу-заглушку)
- **FR-002**: Система ДОЛЖНА позволять пользователю ввести email-адрес и инициировать запрос на восстановление пароля одним действием
- **FR-003**: Система ДОЛЖНА отправлять на указанный email письмо с уникальной ссылкой для сброса пароля, если такой email зарегистрирован в системе
- **FR-004**: Система ДОЛЖНА показывать одно и то же нейтральное сообщение об успехе **независимо от существования email** в базе (защита от энумерации аккаунтов)
- **FR-005**: Система ДОЛЖНА нормализовать email (lowercase, trim) перед поиском пользователя — единообразно с существующей логикой верификации
- **FR-006**: Письмо ДОЛЖНО отправляться через ту же инфраструктуру отправки писем и быть в том же формате (HTML), что и существующие письма верификации — единообразный отправитель, оформление и узнаваемость для пользователя
- **FR-007**: Письмо ДОЛЖНО содержать понятный пользователю текст на русском с пояснением цели письма, прямой ссылкой на страницу сброса и предупреждением "если вы не запрашивали — проигнорируйте"

#### Токен сброса

- **FR-008**: Токен сброса ДОЛЖЕН быть длинной (минимум 32 байта энтропии) криптостойкой случайной строкой, безопасной для использования в URL
- **FR-009**: Токен сброса ДОЛЖЕН быть **одноразовым** — после успешной установки нового пароля токен погашается и повторно использован быть не может
- **FR-010**: Токен сброса ДОЛЖЕН иметь ограниченный срок действия (15 минут с момента отправки письма)
- **FR-011**: При запросе нового токена для того же аккаунта Система ДОЛЖНА инвалидировать ранее выпущенные неиспользованные токены этого аккаунта (актуальным остаётся только последний токен)
- **FR-012**: Токены ДОЛЖНЫ храниться в базе таким образом, чтобы их компрометация на уровне БД не позволяла напрямую использовать их (хеширование токена при хранении — стандартная практика)

#### Установка нового пароля

- **FR-013**: Система ДОЛЖНА предоставлять страницу установки нового пароля (доступную по ссылке из письма), которая принимает токен сброса из URL
- **FR-014**: Страница установки пароля ДОЛЖНА проверять валидность токена при открытии и показывать понятное сообщение, если токен недействителен/истёк/использован, со ссылкой на повторный запрос
- **FR-015**: Форма установки пароля ДОЛЖНА требовать ввод нового пароля и его подтверждения (двойной ввод)
- **FR-016**: Система ДОЛЖНА валидировать новый пароль по существующим правилам (минимум 8 символов, заглавные и строчные буквы, цифра — единообразно со "Сменой пароля")
- **FR-017**: Система ДОЛЖНА отклонять новый пароль, если он совпадает с текущим паролем аккаунта
- **FR-018**: После успешного сброса пароля Система ДОЛЖНА показать сообщение об успехе и предложить пользователю перейти к экрану входа (или автоматически перенаправить туда)

#### Точки входа в UI

- **FR-019**: На экране логина ДОЛЖНА присутствовать видимая ссылка/кнопка "Забыли пароль?", ведущая на страницу `/forgot-password`
- **FR-020**: Существующая ссылка "Забыли пароль?" в диалоге смены пароля ДОЛЖНА продолжать работать и вести на ту же страницу
- **FR-021**: Все надписи и сообщения, видимые пользователю, ДОЛЖНЫ быть на русском языке

#### Защита от перебора и злоупотреблений

- **FR-022**: Система ДОЛЖНА ограничивать частоту запросов на восстановление пароля для одного email-адреса (cooldown между запросами — не короче 60 секунд, единообразно с существующим cooldown повторной отправки кода верификации)
- **FR-023**: Система ДОЛЖНА ограничивать общую частоту запросов на восстановление пароля с одного источника (IP/устройства), чтобы предотвратить массовую энумерацию и DoS на email-провайдер
- **FR-024**: Превышение лимитов частоты ДОЛЖНО приводить к временному отказу с понятным сообщением, а не к раскрытию того, существует ли email в базе
- **FR-025**: Сбои отправки письма (например, ошибка email-сервиса) ДОЛЖНЫ логироваться, но пользователю ДОЛЖНО показываться то же нейтральное сообщение, что и при успехе

### Key Entities

- **User**: Существующая сущность. Используются поля `email` (поиск пользователя), `password` (обновление). Дополнительные поля для процесса сброса (например, хеш токена и срок действия) — добавляются как отдельная сущность связанная с User, чтобы не пересекаться с уже существующими полями процесса email-верификации (`verificationCode`, `verificationCodeExpiry`, `verificationCodeSentAt`, `verificationAttempts` — они зарезервированы под подтверждение email и смену email).
- **PasswordResetToken** (новая сущность): представляет одноразовый токен сброса пароля. Ключевые атрибуты — связь с пользователем, хеш токена, время выпуска, время истечения, признак использования. Может потребоваться счётчик/лог для антифрод-метрик.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь, забывший пароль, может полностью восстановить доступ за **не более 3 минут** (от открытия страницы "Забыли пароль" до успешного входа с новым паролем) — без обращения в поддержку
- **SC-002**: **100%** запросов на восстановление с валидным существующим email приводят к доставке письма (при условии работающего email-провайдера)
- **SC-003**: **0%** ответов системы позволяют отличить существующий email от несуществующего (в неудачных и успешных сценариях сообщение и время ответа — одинаковые в пределах нормального разброса)
- **SC-004**: **100%** ссылок для сброса перестают работать после **первого** успешного использования или по истечении **15 минут**
- **SC-005**: При тестировании на превышение частоты запросов (например, 10 запросов за минуту с одного источника) **минимум 80%** избыточных запросов отклоняются с rate-limit-сообщением до отправки письма
- **SC-006**: Все ошибки и сообщения отображаются на русском языке (соответствие локали проекта — 100%)
- **SC-007**: Снижение количества обращений в поддержку с темой "забыл пароль / не могу войти" минимум на **70%** в течение первого месяца после запуска фичи

## Assumptions

- "Стандартный подход" интерпретируется как **link-based reset** (ссылка с одноразовым непредсказуемым токеном в URL), а не 6-значный код, так как пользователь явно упомянул "ссылка/токен" и это индустриальный стандарт для password reset (в отличие от email-верификации, где для регистрации используется 6-значный код)
- Срок действия токена сброса — **15 минут**, симметрично существующему сроку для verification code (`getVerificationCodeExpiry`)
- Cooldown повторных запросов восстановления для одного email — **60 секунд**, симметрично существующей константе `RESEND_COOLDOWN_SECONDS`
- Дополнительный per-IP rate limit реализуется на уровне API/middleware с разумным дефолтом (например, не более 5 запросов на восстановление в минуту с одного IP)
- Существующая инфраструктура отправки писем (Resend + HTML-шаблон) переиспользуется для письма со ссылкой сброса
- Правила валидации нового пароля (минимум 8 символов, заглавные и строчные буквы, цифра) — те же, что и в существующей "Смене пароля"
- Сброс пароля **не завершает существующие активные сессии** другого устройства автоматически — единообразно с поведением "Смены пароля" (текущий проектный JWT не имеет server-side blacklist; такая инвалидация — задача отдельной фичи). Если пользователь подозревает компрометацию, он может отдельно запросить выход на всех устройствах в будущем (вне рамок этой фичи)
- Аккаунт с **неподтверждённым email** также может пройти flow восстановления; успешный сброс может опционально пометить email как подтверждённый (т.к. факт получения письма доказывает контроль над ящиком) — окончательное решение — на этапе планирования
- Дизайн страницы "Забыли пароль" и страницы установки пароля следует существующему стилю auth-форм (Material UI, тот же `AuthLayout` контейнер)
- Ссылка "Забыли пароль?" на экране логина размещается **под полями ввода рядом с кнопкой "Войти"** или непосредственно под полем пароля — по аналогии с привычным расположением в большинстве веб-приложений
