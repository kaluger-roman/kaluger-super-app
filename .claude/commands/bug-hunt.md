## Контекст

- Сегодня: !`date +%Y-%m-%d`
- Существующие отчёты: !`ls -t docs/bug-reports/ 2>/dev/null | head -5 || echo "(папка ещё не создана)"`

## Задача

Найти потенциальные баги в кодовой базе, валидировать каждого кандидата и записать подробный отчёт в `docs/bug-reports/YYYY-MM-DD-bug-hunt.md` (если файл с этой датой уже существует — добавить суффикс `-2`, `-3`, …).

**Не более 10 багов в одном отчёте.** До отчёта код не трогать; после отчёта — исправить то, что выберет пользователь, и прогнать круги ревью и QA (Этапы 4–6).

## Этап 0. Worktree и draft PR

Отчёт — артефакт задачи, поэтому команда работает в своём worktree и сразу открывает draft PR (правило CLAUDE.md «Draft PR at Task Start»):

1. `EnterWorktree` (deferred tool — если его schema не загружена, сначала `ToolSearch` с `select:EnterWorktree`) с `name: "bug-hunt-YYYY-MM-DD"` (дата — сегодняшняя; если такой worktree уже есть — суффикс `-2`, `-3`, …). Если сессия уже внутри worktree этой задачи — не создавать новый.
2. `node scripts/start-task-pr.mjs --title "Bug hunt YYYY-MM-DD" --summary "Отчёт о потенциальных багах по всей кодовой базе."`. Если скрипт упал (нет сети/токена) — предупредить одной строкой и продолжить.
3. Все пути ниже (`docs/bug-reports/…`) — относительно этого worktree.

## Этап 1. Параллельное исследование

Запустить **в ОДНОМ сообщении** несколько subagent'ов `feature-dev:code-reviewer` параллельно — по одному Agent-вызову на область, каждый с `model: "opus"`. В начало каждого промпта добавить: «Operate at **maximum reasoning effort**. Read the code you cite in full before concluding; better to return fewer candidates than a false positive.» Каждому subagent дать узкий фокус и попросить вернуть до 5 высокоуверенных кандидатов с `файл:строка`, severity и обоснованием.

**Обязательные области:**

1. **Frontend Effector** (`frontend/src/**/model/**`):
   - `patronum reset` со store, чьё начальное значение читается из localStorage (известный gotcha: `reset` возвращает к initial из `createStore(...)`, а не к текущему localStorage)
   - Гонки в эффектах, неотменяемые запросы при unmount
   - `sample` с неправильно подобранным `clock`/`source`/`filter`
   - Подписки store без gate/scope (утечки)

2. **Frontend React/UI** (`frontend/src/**/*.tsx`):
   - `useEffect` для data fetching (запрещён по конвенции)
   - `<form>` теги (запрещены)
   - `any` (запрещён, должно быть `unknown`)
   - `export default` (запрещён)
   - Утечки подписок (отсутствует cleanup)
   - setState после unmount, race conditions

3. **Backend services/controllers** (`backend/src/{services,controllers,routes}/**/*.ts`):
   - Связанные операции без `prisma.$transaction`
   - Утечка stack trace / Prisma errors в API ответы
   - Забытые `await`, unhandled promise rejection
   - Race conditions при create без upsert
   - Отсутствие валидации входных данных на границе

4. **Auth/Security** (`backend/src/middleware`, route definitions):
   - Роуты без `requireAuth` middleware
   - Отсутствие проверки ownership ресурса (доступ к чужим данным по id)
   - Утечка чувствительных полей в API ответах (вся `User` модель вместо select)
   - Сырые SQL/raw queries с интерполяцией
   - JWT_SECRET / другие критические env не проверяются на старте

5. **Real-time / Cron** (`backend/src/lib/websocket*`, cron jobs):
   - Двойная отправка при reconnect
   - Cron дублирует записи при рестарте сервера во время тика
   - Отсутствие идемпотентности у scheduled-операций
   - Утечки соединений (не закрывается при auth fail)
   - Timezone-баги (UTC vs локальное время)

6. **Data integrity / Prisma** (`backend/prisma/schema.prisma`, миграции, использование Prisma):
   - Отсутствие unique/index на полях, которые этого требуют
   - Конфликты soft-delete + cascade
   - Off-by-one в pagination (limit/skip/cursor)
   - Использование результата `findUnique` без проверки на `null`
   - Опасные миграции (rename без шага копирования, drop column в одном шаге)

7. **Костыли, которые прячут баги** (вся кодовая база, включая тесты):
   - Проглоченные ошибки: `catch` с одним логом на нижнем уровне, после которого вызывающий считает операцию успешной
   - Фолбэки, скрывающие промах (`?? ""`, `?? "tutor"`, «не нашли — берём первый»), из-за которых неверная ветка срабатывает молча
   - Порядок, который держится на очерёдности эффектов/колбэков или на магической задержке, вместо явной зависимости
   - Тесты, проходящие вхолостую (ожидание совпадает с начальным значением, мок обходит проверяемый код) — баг, который они «покрывают», на деле не покрыт

**Промпт для subagent (подставить в `prompt` Agent-вызова, адаптировать под область):**

> Тебе нужно найти до 5 **высокоуверенных** потенциальных багов в области `<область — конкретный путь>` проекта. Только реальные баги — не стиль, не форматирование, не отсутствие комментариев.
>
> Для каждого кандидата:
> 1. Прочитай связанный код, проследи путь вызова, проверь edge cases.
> 2. Если бага не воспроизводится в реалистичном сценарии или сомневаешься — отбрось. Лучше меньше, но точнее.
> 3. Проверь, не покрыт ли сценарий тестом (если покрыт — это не баг).
>
> Верни список в строгом формате:
>
> ```
> N. **[Severity: Critical|High|Medium|Low]** Краткий заголовок
>    Файл: path/to/file.ts:42
>    Описание: что не так
>    Сценарий: как воспроизвести
>    Последствия: что произойдёт у пользователя / в данных
>    Исправление: конкретное предложение (можно с before/after снippетом)
>    Валидация: что я проверил, чтобы исключить false positive
> ```
>
> **Контекст проекта.** Tutor app для RU рынка. Frontend — FSD + Effector + MUI. Backend — Express + Prisma + PostgreSQL. Конвенции: no `any`, no `export default`, no `useEffect` для data fetching, no `<form>` теги, `const fn = () =>` вместо `function fn()`, named exports, `type` вместо `interface`, error messages на русском. Известный gotcha проекта — `patronum reset` сбрасывает store к initial-значению из `createStore(...)`, а не к "логическому дефолту"; если initial читается из localStorage — `reset` вернёт значение на момент создания стора.

## Этап 2. Финальная валидация

Собрать всех кандидатов от subagent'ов. Для каждого:

1. Прочитать упомянутый файл (Read).
2. При необходимости — `grep`/`Glob` для проверки usage и защит выше по стеку.
3. Убедиться, что баг достижим в реалистичном сценарии.
4. Отбросить **дубликаты** (один баг от нескольких агентов — оставить с лучшим описанием).
5. Отбросить случаи, **покрытые тестами**.
6. Отбросить всё, в чём остаются сомнения.

**Если в сумме больше 10 — отобрать самые важные** в приоритете Critical → High → Medium → Low.

## Этап 3. Отчёт

1. Если папки `docs/bug-reports/` нет — создать через `mkdir -p docs/bug-reports`.
2. Сформировать имя файла `docs/bug-reports/YYYY-MM-DD-bug-hunt.md` (если такой уже есть — `-2`, `-3`, …).
3. Записать отчёт по структуре ниже (Write tool).
4. Закоммитить и запушить отчёт в ветку worktree: `git add docs/bug-reports/<файл>`, `git commit -m "docs(bug-hunt): report YYYY-MM-DD"`, `git push`. PR остаётся draft — что из отчёта брать в работу, решает пользователь.

## Этап 4. Исправление выбранного (✋ checkpoint)

После отчёта — один вопрос пользователю через `AskUserQuestion` (multiSelect): какие багов из отчёта исправить в этом worktree (варианты — пункты отчёта, Quick Wins первыми; плюс «Ничего, только отчёт»). Если выбрано «Ничего» — команда на этом заканчивается.

Выбранное Main исправляет **сам, в основном потоке** (не в sub-agent), по тем же правилам, что Фаза 3/5 `/auto-bug-fix`:

1. Перед правкой — перечитать релевантный `docs/conventions/*.md`.
2. На каждое исправление — регрессионный тест (frontend → vitest, backend → jest), кроме чисто визуальных правок без логики.
3. После правок — тесты затронутых файлов, `npm run lint` (frontend/backend), `npm run build` (backend), `npx tsc --noEmit -p .` (frontend).
4. **Без коммитов:** правки остаются в рабочем дереве, коммит/push/`/changelog`/`/news`/`gh pr ready` — только по команде пользователя (как в `/auto-feature`).

## Этап 5. Code-review loop

Тот же цикл, что Фаза 5 `/auto-feature`: sub-agent (`model: "opus"`, max effort) запускает `/code-review-local --silent --threshold 50 --iter <N> --feature bug-hunt-YYYY-MM-DD`, Main читает JSON и фиксит findings в основном потоке (с регрессионными тестами), затем следующая итерация.

- **До 5 итераций.** Выход раньше, если результат сошёлся: findings нет; ≥80% сигнатур (`<category>:<file>:<line_start>:<title-first-30-chars>`) совпадают с прошлой итерацией (convergence); или все оставшиеся findings — score 50 без конкретного вреда (мелочи, которые не стоят ещё одного круга).
- Не удавшийся после двух попыток фикс — откатить и записать в отчёт как оставшийся.

## Этап 6. Manual QA loop

Только если исправления затронули то, что видит пользователь (UI, API-ответы, тексты). Иначе — пропустить и написать почему.

- Sub-agent (`model: "opus"`, max effort) запускает `/manual-qa --fix` (промпт и ожидаемый JSON — как в Фазе 6 `/auto-feature`; отчёты `-run2`, `-run3`, … не перезаписывают прошлые).
- После каждого прогона Main исправляет оставшиеся однозначные находки сам (с регрессионным тестом); находки, где нужно продуктовое или дизайнерское решение, — спросить пользователя одним `AskUserQuestion`.
- **До 5 прогонов.** Выход раньше, если результат сошёлся: readiness `green` и нет находок выше `low`; ≥80% находок повторяют прошлый прогон; или новый прогон не нашёл ничего ценного (только `low` без конкретного вреда).

## Этап 7. Итог

Одно сообщение пользователю: путь к отчёту, ссылка на draft PR, что исправлено, сколько кругов ревью и QA прошло и почему остановились (чисто / сошлось / cap), что осталось. Предложить следующий шаг: коммит и подготовка PR (`/changelog`, `/news`, `gh pr edit`, `gh pr ready`) — только после ответа пользователя.

## Ограничения

- **До checkpoint Этапа 4 — только чтение и запись отчёта.** Прод-код правится только после выбора пользователя в Этапе 4. Из git-операций — worktree и draft PR (Этап 0), коммит отчёта (Этап 3) и `git checkout -- <file>` для отката неудавшегося фикса; никаких `stash`/`reset`, `gh pr ready` — только по команде пользователя.
- **Максимум 10 багов** на отчёт.
- **Не репортить:** typos, форматирование, отсутствие комментариев, чисто стилистические замечания.
- **Описания багов на русском.** Code-сниппеты — как в исходнике.
- **Файл и строка обязательны** для каждого бага.
- В финальном текстовом сообщении пользователю — указать путь к созданному отчёту, ссылку на draft PR и одну строку со сводкой (`N багов: Critical X, High Y, Medium Z, Low W`).
