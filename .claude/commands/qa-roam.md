## Задача

Сыграть роль реального QA / пользователя / product owner'а: походить по живому приложению через Playwright MCP, потыкать в случайные сценарии (каждый запуск — разный набор), фиксировать на скриншотах что показалось странным/неудобным/неработающим, и записать **не более 5** самых ценных предложений по улучшению в `docs/qa-roam-reports/YYYY-MM-DD-qa-roam.md` (если файл с этой датой уже есть — суффикс `-2`, `-3`, …).

**Ограничения по сути:**

- Это **не bug-hunt** (тот ищет баги в коде) и **не improve-hunt** (тот читает код). Здесь — только то, что **видно/чувствуется при использовании** приложения как реальный пользователь.
- **Код НЕ менять**, тесты НЕ запускать, git-операций НЕ делать. Только отчёт + скриншоты.
- Каждый запуск должен давать **разный** результат: рандомизация выбора сценариев — обязательна (см. Этап 2).

`$ARGUMENTS`:
- пусто → случайно выбрать 2–3 роута из autodiscovered списка
- `<path>` (например `/students` или `/lessons`) → роуминг только по этому роуту и тому, что с него достижимо

### Что считается «находкой»

| ✅ Репортить | ❌ Не репортить |
|---|---|
| Кнопка «Сохранить» висит disabled без объяснения, что не так с формой | Цвет primary чуть бледный (вкус) |
| После создания ученика список не обновляется до F5 | Заголовок страницы можно было бы написать иначе |
| 500-ка в network на странице расписания, у пользователя пустой экран | Не нравится анимация перехода |
| Удаление урока без подтверждения — кликнул мимо, данные пропали | Кнопка «Создать» могла бы быть FAB вместо обычной |
| Поле «Email» позволяет ввести «aaa» и сабмитить, ошибка только после ответа сервера | В консоли warning от React (не влияет на пользователя) |
| Скриншот: текст ошибки на английском («Internal Server Error») в RU-интерфейсе | Лишний `useEffect` в коде (это для improve-hunt) |
| На мобильном (resize 375px) сайдбар перекрывает контент | TypeScript-типы можно улучшить (это для improve-hunt) |

Ключевой тест: «Заметил бы это **реальный учитель**, использующий приложение?» Если да и это ухудшает опыт — репортить. Если это видно только при чтении кода — не сюда.

## Этап 1. Discovery роутов и случайный план обхода

**Никакого хардкод-списка областей в этой команде нет** — это сознательное решение, чтобы команду не приходилось обновлять при появлении новых страниц.

### 1.1. Получить актуальный список роутов

Источник правды — `frontend/src/app/components/AppRoutes/AppRoutes.tsx`. Распарсить все `path="..."` через `grep`:

```bash
grep -oE 'path="[^"]+"' frontend/src/app/components/AppRoutes/AppRoutes.tsx \
  | sed -E 's/path="(.+)"/\1/' \
  | grep -vE '^/$|/\*|^/login$|^/register$|^/verify-email|^/forgot-password|^/reset-password' \
  > /tmp/qa-roam-routes.txt
```

Фильтр `grep -vE` отбрасывает: служебный `/`, wildcards, чистый auth-flow (он покрывается на Этапе 0 при логине). Остаются «внутренние» роуты приложения.

**Если файл AppRoutes.tsx не нашёлся** (роутинг переехал) — fallback: взять имена директорий из `frontend/src/pages/` и попробовать угадать роут (`Reports` → `/reports`). Если и это не сработало — сказать пользователю и остановиться.

### 1.2. Случайно выбрать 2–3 роута из списка

Использовать сид из Контекста (`date +%s`), чтобы **разные запуски давали разный набор**:

```bash
SEED=$(date +%s)
N=$(( (SEED % 2) + 2 ))   # 2 или 3 роута
awk -v seed=$SEED 'BEGIN{srand(seed)} {print rand()"\t"$0}' /tmp/qa-roam-routes.txt \
  | sort | head -$N | cut -f2
```

Если `$ARGUMENTS` непустой — взять только указанный путь, без рандомизации количества.

### 1.3. Сценарии — генерировать на лету, не хардкодить

Для каждого выбранного роута сценарий **не предопределён**. На Этапе 2 ты:

1. Переходишь на роут.
2. Делаешь `browser_snapshot` (accessibility tree) — это покажет **актуально существующие** кнопки, формы, ссылки, списки.
3. Сам решаешь, что попробовать, исходя из увиденного и роли «реальный пользователь, который видит этот экран впервые». Без оглядки на старые версии экрана.

Примеры мыслительного процесса (ориентир, не чеклист):
- Видишь кнопку «Добавить ученика» → попробуй добавить.
- Видишь список → проверь пустое состояние (через фильтр без результатов или удаление всех записей), проверь длинный список (если есть скролл).
- Видишь форму → попробуй сабмит без обязательных полей, с edge-case значениями, нажми Enter.
- Видишь таблицу с действиями (редактировать/удалить) → попробуй удалить и отмени, проверь подтверждение.
- Видишь переключатели/табы → переключись несколько раз, проверь сохранение состояния при F5.

### 1.4. Случайный модификатор (универсальный, не зависит от фичи)

Выбрать **минимум один** модификатор для всего прохода — он применяется ко всем сценариям. Тоже через сид:

```bash
MODS="mobile-375 tablet-768 desktop edge-input-long edge-input-emoji edge-input-xss double-click keyboard-only"
SEED=$(date +%s)
echo $MODS | tr ' ' '\n' \
  | awk -v seed=$SEED 'BEGIN{srand(seed+1)} {print rand()"\t"$0}' \
  | sort | head -2 | cut -f2
```

Расшифровка:
- `mobile-375` / `tablet-768` / `desktop` — `mcp__playwright__browser_resize` на старте.
- `edge-input-long` — везде, где есть текстовый input, попробовать 500–1000 символов.
- `edge-input-emoji` — везде вставлять эмодзи (👨‍👩‍👧, проверка surrogate pairs).
- `edge-input-xss` — `<script>alert(1)</script>` в имена/описания (должно экранироваться).
- `double-click` — кнопки «Сохранить»/«Создать» кликать дважды подряд (защита от double-submit).
- `keyboard-only` — все формы заполнять и сабмитить **только** Tab + Enter, без мыши (проверяет focus order и Enter-submit).

Одной строкой **перед** началом обхода:

## Этап 2. Активный обход через Playwright MCP

Для каждого выбранного роута сделать 1–2 «пробы» (одна полноценная попытка пройти осмысленный путь — например создание сущности от и до). Для **каждой пробы**:

1. **Старт:** `browser_navigate` на стартовый URL области. Сделать `browser_snapshot` (accessibility tree) — это даст структуру страницы для умных кликов.
2. **Скриншот «до»:** `browser_take_screenshot` с понятным именем (например, `students-list-before.png`).
3. **Действия:** последовательность из 3–8 шагов (click/type/select), **наблюдая** результат каждого:
   - После каждого значимого действия — `browser_snapshot` или `browser_take_screenshot`.
   - Параллельно собирать `browser_console_messages` (искать `error`, `warning` уровня error) и `browser_network_requests` (искать `status >= 400`, очень долгие запросы, дубли).
4. **Проверки** (всё, что применимо):
   - **Видимый фидбэк:** после save — есть ли toast/snackbar/сообщение об успехе? Если нет — кандидат в находки.
   - **Loading state:** при долгом запросе — есть ли спиннер/скелетон? Если нет — кандидат.
   - **Empty state:** на странице со списком при отсутствии данных — что показано? Если просто пустота без объяснения — кандидат.
   - **Ошибки:** при сценарии с заведомо неверными данными — текст ошибки на русском? Понятный? Не «Internal Server Error»?
   - **Сохранение состояния:** после refresh — данные на месте? Фильтры? Авторизация?
   - **Навигация:** кнопка «назад» в браузере работает корректно? URL отражает состояние?
   - **a11y-минимум:** есть ли видимый focus при Tab? Можно ли отправить форму с Enter?
   - **Согласованность:** одинаково ли выглядят похожие элементы (кнопки, диалоги, иконки)?
5. **Скриншот «после»:** финальное состояние.
6. **Логирование наблюдений:** записать в рабочий список **всё, что показалось странным** — даже мелочи. Фильтрация будет на Этапе 3.

**Скриншоты** сохранять в `docs/qa-roam-reports/screenshots/YYYY-MM-DD-NNN-<имя>.png` (NNN — порядковый номер). Эти файлы потом упомянуты в отчёте.

### Бюджет

Жёсткой отсечки «10 действий на пробу» нет — это убило бы любой нетривиальный journey (recurring-серия, forgot-password-цикл, отчёт-с-фильтрами легко требуют 15–25 шагов). Вместо этого:

- **На пробу:** идти до естественного конца journey (сохранил / убедился, что не получилось / упёрся в баг). Если в районе **25 действий** ещё не видно края — это сигнал «застрял», свернуть пробу и записать наблюдение «journey слишком длинный/непонятный для нового пользователя» (это сама по себе находка).
- **На всю команду:** общий потолок ~60 действий браузера и ~25 скриншотов на запуск. Если упёрся — отчитаться по тому, что успел.
- **Скриншоты** — снимать щедро, не экономить: каждое «не так» снимать сразу (потом не вернуться к тому же состоянию), плюс кадр «до» и «после» для каждой пробы. Это дешёвый эвиденс — лучше иметь лишний, чем потерять.

### Шаблон промпта для себя (внутренний)

Перед каждой пробой проговорить вслух (в сообщении пользователю, одной строкой):

> Проба на `/students` (мод. mobile-375 + emoji): попробую добавить ученика с именем «Иван 👨‍👩‍👧 Петров» и посмотрю, как он отрисуется в списке.

После пробы — короткая (1–2 строки) сводка:

> Готово (12 действий). Наблюдения: (1) нет фидбэка после save; (2) эмодзи в списке заменился на «?».

Собрать все наблюдения с Этапа 2. Применить фильтры:

## Ограничения

- **Не более 5 пунктов** в отчёте. Меньше — нормально, если меньше и нашёл качественно.
- **Каждый пункт — со скриншотом**, путь относительно репозитория. Скриншоты лежат рядом в `screenshots/`.
- **Без кода**. Это отчёт о пользовательском опыте, а не PR.
- **Только то, что видел сам в этом запуске.** Не репортить «по памяти» из других проходов.
- **Описания на русском**, как говорил бы реальный пользователь («не понятно, что делать», «думал, что сломалось»).
- **Не редактировать прод-код, не запускать тесты, не делать git-операций.**
- **Уважать тестовые данные.** Префикс `qa-roam-` для всего создаваемого. Не удалять то, что создано не этим процессом.
- В финальном сообщении пользователю — путь к отчёту, seed, выбранные области, и одна строка-сводка: `N улучшений: High X, Medium Y; Quick Wins: <короткие заголовки>`.
