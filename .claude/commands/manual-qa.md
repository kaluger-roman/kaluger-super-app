## Контекст

- Сегодня: !`date +%Y-%m-%d`
- Текущая ветка: !`git branch --show-current`
- Спека ветки: !`BR=$(git branch --show-current); ls specs/$BR/ 2>/dev/null | head -10 || echo "(specs/$BR/ не найден — попытайся подобрать по префиксу)"`
- Frontend (3000): !`curl -s -o /dev/null -w "%{http_code}" http://localhost:3000 || echo "down"`
- Backend (3001): !`curl -s -o /dev/null -w "%{http_code}" http://localhost:3001/api 2>/dev/null || echo "down"`
- Существующие отчёты: !`ls -t docs/manual-qa-reports/ 2>/dev/null | head -5 || echo "(папка ещё не создана)"`

## Задача

Прогнать фичу текущей ветки руками **через Playwright MCP** с позиции пользователя / QA / product owner: пройти все ключевые сценарии из спецификации, сделать скриншоты ключевых экранов и проблем, сверить наблюдаемое поведение с Acceptance Scenarios и quickstart-чеклистом, оценить общее качество фичи и записать развёрнутый MD-отчёт в `docs/manual-qa-reports/`.

`$ARGUMENTS` парсятся так:

- содержит `--fix` → **режим автофикса**: после написания отчёта чини все находки, помеченные как «однозначные» (см. Этап 6). Архитектурные/спорные изменения — не трогать.
- содержит идентификатор фичи (формат `NNN-something`) → использовать как override для спеки (`specs/<id>/`), а не текущую ветку.
- содержит URL (`http://...`) → использовать как base URL вместо `http://localhost:3000`.
- иначе → дефолт: спека = ветка, base URL = `http://localhost:3000`, без автофикса.

Примеры:
- `/manual-qa` — прогон фичи текущей ветки, без автофикса.
- `/manual-qa --fix` — прогон + автофикс однозначных багов.
- `/manual-qa 028-forgot-password` — прогон фичи `028-forgot-password` (даже если ты на другой ветке).
- `/manual-qa --fix http://localhost:3002` — прогон с автофиксом на нестандартном порту.

## Этап 1. Сбор спецификации фичи

1. Определить feature id из аргументов или текущей ветки. Если в `specs/<id>/` нет файлов — попробовать `ls specs/ | grep <prefix>`; если ничего — сообщить пользователю и завершить.
2. Прочитать (в этом порядке приоритета):
   - `specs/<id>/spec.md` — **источник правды** для User Stories и Acceptance Scenarios.
   - `specs/<id>/quickstart.md` — **готовый пошаговый чеклист** ручного прогона, если есть; следовать ему как основному сценарию.
   - `specs/<id>/tasks.md` — понять, что фактически реализовано (по статусам задач) и что могло остаться TODO.
   - `specs/<id>/contracts/` — API-контракты, чтобы знать ожидаемые форматы запросов/ответов при анализе network-логов.
   - `specs/<id>/data-model.md` — какие сущности нужны в БД для воспроизведения сценариев.
   - `specs/<id>/checklists/` — дополнительные проверочные списки, если есть.
3. Прочитать `CHANGELOG.md` (топ-30 строк) и последние коммиты ветки (`git log main..HEAD --oneline`) — увидеть, что фактически в diff'е.
4. Из всех материалов составить **единый список сценариев для прогона** — Priority P1 обязательно, P2 — если время позволяет, edge cases из секции «Edge Cases» спеки — обязательно.

Если спеки нет вовсе — построить план тестирования из `git diff main...HEAD` (новые роуты, новые формы, новые эндпоинты) и сообщить в отчёте, что прогон шёл «без спеки», только по diff'у.

## Этап 2. Подготовка окружения

1. **Проверить, что dev-серверы подняты.** Если frontend (3000) или backend (3001) недоступен — НЕ запускать самостоятельно через background-Bash (риск конфликта с уже запущенными сессиями пользователя), а вывести инструкцию пользователю:

   ```
   Dev-серверы не подняты. Запусти в двух отдельных терминалах:
     ! cd backend && npm run dev
     ! cd frontend && npm start
   и снова вызови /manual-qa.
   ```

   и завершить выполнение. Префикс `!` в Claude Code выполнит команду интерактивно в текущей сессии.

2. **Проверить тестовые данные** (читая БД через `npx tsx` со скриптом-однострочником, **без** изменений на этом шаге). Если для прогона нужны сущности, которых нет (например, преподаватель с не подтверждённым email, ученик без зарегистрированного аккаунта, уроки на текущей неделе) — на этапе прогона их можно создать **напрямую через Prisma** (см. ниже). Не использовать `db:seed` — он перезаписывает локальные данные пользователя.

   Пример короткого read-запроса:
   ```bash
   cd backend && npx tsx -e "
   import { PrismaClient } from '@prisma/client';
   const p = new PrismaClient();
   console.log(JSON.stringify(await p.user.findMany({ take: 3, select: { id: true, email: true, name: true } }), null, 2));
   await p.\$disconnect();
   "
   ```

3. **Создание недостающих тестовых сущностей разрешено через прямые Prisma-вставки** для ускорения. Правила:
   - Все имена/email содержат маркер `[mqa <YYYY-MM-DD-HHMM>]`, чтобы потом легко найти.
   - Минимально необходимый набор — никаких массовых сидов.
   - Если возможно, в конце прогона удалить созданные сущности тем же способом (для тех, что в полной мере поддерживают удаление). Если удаление рискованно — оставить и зафиксировать список в отчёте в секции «Артефакты прогона».

4. **Открыть Playwright** через `mcp__playwright__browser_navigate` на base URL. Проверить, что страница реально отрисовалась (`browser_snapshot`). Если фронт упал в рантайме — это уже находка `Severity: Critical`.

## Этап 3. Построение тест-плана прогона

Из материалов Этапа 1 составить упорядоченный список «шаг → ожидаемый результат → актуальный результат». Этот план — будущая секция «Покрытие сценариев» в отчёте.

Пример строки плана:
```
[P1.1] Преподаватель создаёт ссылку-приглашение в карточке ученика
  Шаги: /login → toggle "преподаватель" → email/пароль → /students → открыть карточку → "Создать ссылку-приглашение"
  Ожидание (Acceptance Scenarios #1): отображается URL /student-invite/<token>, кнопка "Скопировать", индикатор "ожидает регистрации"
  Скриншоты: 01-login.png, 02-students.png, 03-invite-created.png
```

Включить в план **обязательно**:
- Все P1 User Stories и их Acceptance Scenarios.
- Все пункты из секции «Edge Cases» спеки.
- Negative paths: невалидные данные, дубликаты, истёкшие токены, неавторизованный доступ к защищённым роутам.
- Realtime/WebSocket-сценарии, если есть (открыть две вкладки/контекста через `browser_tabs`, проверить пуш-обновления).
- Smoke по неизменённым областям: если фича вводит общий компонент (например, тумблер на /login), проверить, что старая роль логинится по-прежнему.

Если план получается > 20 шагов — урезать P2 и не-критичные edge cases, но **никогда** не урезать P1.

## Этап 4. Прогон через Playwright MCP

Идти по плану шаг за шагом. На каждом шаге:

1. **Действие** — `browser_navigate` / `browser_click` / `browser_fill_form` / `browser_type` / `browser_press_key`.
2. **Снимок DOM** — `browser_snapshot` (структурированный snapshot, не путать со скриншотом). Используется для сверки и для подбора `ref` для следующих кликов.
3. **Скриншот** — `browser_take_screenshot` сохраняет PNG в указанный путь. Сохранять в `docs/manual-qa-reports/<YYYY-MM-DD-branch>/screenshots/NN-<slug>.png`, где `NN` — двузначный порядковый номер, `slug` — kebab-case описание (`01-login-form`, `02-invite-link-created`).
4. **Проверки**:
   - Соответствует ли увиденное Acceptance Scenarios? (текст, поля, статусы, redirects)
   - `browser_console_messages` — есть ли error/warning в консоли?
   - `browser_network_requests` — есть ли 4xx/5xx, неожиданные эндпоинты, утечка чувствительных полей в ответе (на критичных шагах вытащить тело ответа и сверить с `contracts/`)?
5. **Запись результата** — в локальном буфере держать структуру по каждому шагу:
   ```
   { step, expected, actual, screenshots, console, network, status: 'pass'|'fail'|'warn' }
   ```

**Эргономика прогона:**
- Перед каждой формой делать `browser_snapshot` и подбирать `ref` — это надёжнее, чем угадывать селекторы.
- Для realtime — `browser_tabs` (новая вкладка под учеником), действие на первой вкладке, `browser_wait_for` на второй с ожиданием изменения текста / появления карточки.
- При обнаружении модалок и подтверждений — `browser_handle_dialog`.
- Респонсив: на 1–2 ключевых экранах сделать `browser_resize` (например, 375×812) и скриншот — отметить очевидные ломки.
- Не пытаться обходить email-верификацию через UI (там ходит реальный код): для тестового аккаунта проще вытащить код напрямую из БД через `npx tsx` (поле `verificationCode` в нужной таблице).

**Что писать в `Bash`-вставках:**
- Чтение данных и подготовка тестовых сущностей — `cd backend && npx tsx -e "..."`. Только короткие однострочники / однофайловые скрипты. Никаких массовых апдейтов.
- Очистка артефактов в конце прогона — там же.

## Этап 5. Категоризация находок

Каждое отклонение — отдельная находка. Поля:

- **Заголовок** (одна строка, начинается с глагола: «Пустой стейт на странице расписания не отображается»).
- **Категория**:
  - ❌ **Spec mismatch** — наблюдаемое поведение прямо противоречит Acceptance Scenario / spec.md.
  - 🐛 **Bug** — что-то сломано (ошибка, исключение, неработающая кнопка, неконсистентный стейт, утечка данных в API).
  - ⚠️ **UX issue** — работает, но плохо с точки зрения пользователя (нет фидбэка после действия, мисс-эппинг ошибки, неудобный flow, неработающий keyboard nav).
  - 💡 **Improvement** — можно сделать лучше (a11y, копирайт, дизайн-консистентность, перфоманс восприятия).
- **Severity**:
  - **Critical** — фича не работает / ломает другую функциональность / утечка чувствительных данных / возможна потеря пользовательских данных.
  - **High** — критичный P1-сценарий невозможен или нарушен; пользователь не может завершить главный flow.
  - **Medium** — edge case сломан / P2 нарушен / заметная UX-проблема.
  - **Low** — мелкое улучшение, текст, иконка, мелкий visual glitch.
- **Шаги воспроизведения** — кратко, по плану из Этапа 3.
- **Ожидание vs Реальность** — две короткие строки.
- **Скриншоты** — ссылки на сохранённые PNG (`./<branch>/screenshots/NN-...png`).
- **Файл/строка** (если очевидно из снапшота/исходника) — Read нужного файла, чтобы подтвердить место.
- **Console/Network outliers** — копировать только релевантные строки (не весь лог).
- **Однозначность исправления** — `да` / `нет`. «Да» означает: причина в коде однозначна, исправление не требует архитектурного решения и не задевает других областей. Этот флаг используется автофиксом на Этапе 6.

Дубликаты сводить в один пункт. Не репортить субъективные предпочтения, отсутствие тестов как таковое (для этого есть `/e2e-check`), общие архитектурные замечания (для этого `/improve-hunt`).

## Этап 6. Автофикс (только если `$ARGUMENTS` содержит `--fix`)

Чинить **в отдельном проходе после написания отчёта**, чтобы отчёт зафиксировал состояние «до».

**Что чинить (любая Severity, но категория конкретная):**
- ❌ **Spec mismatch** с однозначной причиной — например, отображается «Сохранить» вместо «Зарегистрироваться» из спеки.
- 🐛 **Bug** с однозначной причиной — `null`-разыменование, забытый `await`, неправильное условие, потерянный handler, не передан prop, неправильный путь в `navigate`.
- ⚠️ **UX issue** с однозначным решением — отсутствует `aria-label` на icon-only кнопке, не закрывается модалка по Esc, autofocus не на первом поле формы, кнопка submit активна при пустых полях, отсутствует loading state там, где запрос длится > 300мс.
- 💡 **Improvement** с однозначным решением — захардкоженный цвет вместо `theme.palette.*` (если рядом уже используется тема), отсутствующий `alt`, дублирующиеся литералы, выносимые в константу.

**Что НЕ чинить (даже с `--fix`):**
- Любые изменения схемы БД и миграции.
- Изменения публичных API-контрактов (роуты, response shape).
- Архитектурные перестановки (перенос файлов между слоями FSD, переименование экспортов).
- Глобальные стилевые/типографические решения, не локализованные одним компонентом.
- Любая находка, отмеченная «Однозначность исправления: нет».
- Любая находка, требующая решения от продукт-овнера (тексты копирайта, новые поля, изменения flow).

**Процедура для каждого однозначного фикса:**
1. Перечитать соответствующий файл (Read) — без перечтения не редактировать.
2. **Перед редактированием прочитать** `docs/conventions/frontend.md` (если фронт) или `docs/conventions/backend.md` (если бек), а для тестов — соответствующий `*-testing.md`. Не нарушать конвенций: no `any`, no `export default`, no `useEffect` для fetching, no `<form>` теги, named exports, `type` вместо `interface`, error-messages на русском.
3. Сделать минимальную правку (Edit) — не делать «попутный рефакторинг».
4. **Добавить регрессионный тест** — обязательно для категорий 🐛 Bug и ❌ Spec mismatch. Юнит-тест на сервис/модель если фикс в логике; компонент-тест если фикс в UI-поведении. Для UX/Improvement тест не обязателен.
5. Прогнать релевантные тесты: `npm test -- <path>` (фронт vitest или бек jest — см. memory).
6. Если фикс фронтовый — `cd frontend && npm run lint` на затронутом файле.
7. Если фикс бэковый и затрагивает типы — `cd backend && npm run build` (быстрая проверка типов).
8. Если что-то падает после фикса — **откатить правку** (Edit обратно или `git checkout -- <file>`) и пометить находку в отчёте как «попытка автофикса не удалась, нужен ручной разбор».

В конце прохода добавить в отчёт секцию «Автофикс»:
- список исправленных находок (со ссылкой на пункт выше),
- список изменённых файлов (`git diff --name-only`),
- список добавленных тестов,
- список находок, которые пропущены автофиксом (с причиной).

**Не делать `git commit`/`push`** — пользователь сам решит, как объединять автофиксы с основной работой. При большом наборе автофиксов в финальном сообщении напомнить: «после ревью diff'а — commit отдельным коммитом с префиксом `fix(qa): ...`».

## Ограничения

- **Не запускать dev-серверы самостоятельно.** Если они не подняты — попросить пользователя через подсказку `! cd ... && npm run ...` и завершить.
- **Не использовать `db:seed`.** Подготовка данных — только точечные Prisma-вставки с маркером `[mqa <YYYY-MM-DD-HHMM>]`.
- **Никаких git-операций.** Не делать `commit`, `push`, `branch`. Автофикс остаётся в working tree — пользователь сам решит, что коммитить.
- **Не править прод-код без `--fix`.** Без флага команда строго read-only по отношению к исходникам.
- **Не менять `package.json`, `prisma/schema.prisma`, миграции.** Никогда — даже с `--fix`.
- **Не репортить отсутствие тестов** как находку (для этого есть `/e2e-check` и `/e2e-hunt`).
- **Не дублировать `/bug-hunt` и `/improve-hunt`** — те идут по статическому анализу всей кодовой базы. Эта команда — только то, что наблюдается при реальном прохождении сценариев фичи.
- **Описания на русском.** Имена файлов скриншотов / slug'и — kebab-case latin (`01-login-form`).
- **Скриншот обязателен** для каждой находки, кроме чисто текстовых (опечатки в копирайте) — там достаточно цитаты + строки.
- **Не больше 15 находок** на отчёт; если больше — приоритизировать по severity (Critical → High → Medium → Low) и сослаться на пропущенные одной строкой.
- **Не сообщать stack trace из консоли целиком** — только релевантные строки (имя ошибки + место).
- **В финальном тексте пользователю** — путь к отчёту, оценка готовности, главное действие на одну строку.
